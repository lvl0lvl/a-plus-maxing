# Recipe: Zip-Aware Healthkit Adapter — `read_readings` Accepts an Apple Health Zip (Mirrors `dna.land`)

This task produces CODE: the extension of `scripts/ingest/adapters/healthkit.py` so its
`read_readings(self, export_file)` accepts an Apple Health export `.zip` — it detects a zip
(`zipfile.is_zipfile`), extracts the single `*/export.xml` member to a staged path (MIRRORING
`dna.land`'s zip-member extraction: `zipfile.is_zipfile` branch → locate the one member of
interest → `zf.open(member)` streamed copy), then runs its EXISTING streamed `iterparse` read
over the extracted xml. A pre-extracted raw `export.xml` reads exactly as today; a non-zip
non-xml fails loud. The extraction lives in the ADAPTER, NOT a serve-layer module and NOT the
shared routine — matching the accepted ADRs (ADR-0013's `complements ADR-0012` edge: "the
zip-member extraction lives in the ingest/adapter layer per that amendment, so this server still
adds no extraction logic"; ADR-0012's amendment: "the adapter accepting a zip"). ADR-0003-T2's
0-shared-routine-edit invariant protects `ingest.py`/`adapter.py`/`scheduler.py` (the SHARED
routine), NOT the adapters — so editing `healthkit.py` is allowed and does NOT violate it. Because
the adapter accepts the zip, an Apple Health zip is ingestable from BOTH `python -m scripts.ingest`
AND (later, `ADR-0013-T4`) the web upload — a serve-layer extraction would leave the CLI needing a
manual unzip. The TDD Steps follow the standard RED/GREEN/REFACTOR/REGRESSION cycle.

## Interface Contracts

This task EXTENDS the frozen ADR-0003-T1 adapter contract's `read_readings` input handling, consumed by `ADR-0013-T4` (the route passes the uploaded zip to this adapter) and by the existing CLI.

- **Method:** `HealthKitAdapter.read_readings(self, export_file)` in `scripts/ingest/adapters/healthkit.py` — **EXTENDED CONTRACT (this task):** `export_file` may now be an Apple Health export `.zip` OR a raw `export.xml`. A zip is detected (`zipfile.is_zipfile`), its single `*/export.xml` member extracted (streamed), and the existing `iterparse` read runs over it; a raw xml reads as today; a zip with no `*/export.xml` (or a non-zip non-xml) raises. The yielded reading shape (`item`/`timepoint`/`source`/`value`) and the daily-aggregation / metric-map are UNCHANGED. **Invariant (load-bearing for criterion 5):** the zip-awareness lives ONLY in the adapter; `ingest.py` / `adapter.py` / `scheduler.py` are byte-unchanged (`dna.py` too). **Breaks if:** the zip-awareness is pushed into `ingest.run` / `adapter.py` / `scheduler.py` — then criterion 5 (0-shared-routine-edit) and the ADR-0003-T2 invariant / the ADR-0013 "server adds no extraction logic to the ingest layer" coherence fail.
- **Dependent task:** `ADR-0013-T4` (the route passes the staged upload — zip or xml — to `ingest.run` via this adapter, adding NO extraction of its own). **Change control:** `ADR-0013-T4` MUST NOT add extraction logic; the adapter owns it.
