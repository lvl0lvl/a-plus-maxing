# Recipe: Lab-Loop / Watch-Out / Physician-Feedback Store Schemas

> **This task DEFINES the store-state contract that ADR-0007-T2's render views read
> 1:1.** Four states — **pending** (a recommended-but-undrawn panel), **not-yet-answered**
> (an unanswered watch-out check-in), **no-prior** (a biomarker with one stored timepoint),
> **answered-over-time** (a stored watch-out answer / physician-feedback entry carried into
> the NEXT generation) — are the data-in store schema this task fixes. Two no-fabrication
> behaviors are asserted ADVERSARIALLY (failing-capable): a pending panel re-read on a later
> generation is STILL pending, never a fabricated result (crit 1); a single-timepoint biomarker
> reads **no-prior**, never a fabricated trend (crit 2). Two carry-forward behaviors are asserted
> as DROP-FAILS-THE-TEST: a watch-out answer stored this cycle is read on the next generation
> (crit 3), a physician-feedback entry is carried forward (crit 4) — a dropped answer/entry turns
> the test RED. The schema performs **0 automated signal detection** — it only stores operator-entered
> answers; the watch-out question SET is DERIVED from the operator's active protocols/compounds, never
> evaluated against a threshold (crit 5, NG-6, failing-capable: a planted threshold-evaluation step →
> FAIL). The schemas append THROUGH the cross-spec store API (`scripts/store/store.py`) — they do NOT
> reimplement append/read/keying — and store local-only with 0 model-bound send (crit 6, egress guard
> over a store/read cycle observes 0 outbound + SEC-03 failing-capable injection).

## TDD Steps

**Four cycles.** Rationale (per `tdd-planning.md` "When to Split"): 7 ACs exceed the 3-AC split threshold, and there is a natural dependency order — the store-state definitions (pending / not-yet-answered / no-prior, crit 1-2) and the question-derivation + 0-automation floor (crit 5) must exist before the carry-forward reads (crit 3-4) can be asserted over them, and the egress boundary (crit 6) wraps the assembled store/read cycle. **Cycle 1** fixes the store-state schema (pending, not-yet-answered, no-prior — crit 1, 2) plus question-derivation + the NG-6 0-automation floor (crit 5). **Cycle 2** adds the watch-out-answer carry-to-next-generation (crit 3). **Cycle 3** adds the physician-feedback carry-forward (crit 4). **Cycle 4** wraps a real store/read cycle under the egress guard + the SEC-03 fail-injection (crit 6). Total = 16 steps. Per `tdd-planning.md` "Size Guardrail" this exceeds the 3-cycle boundary — see the Deviations note (DEV-1, non-blocking advisory; no upstream defect); the four cycles are an internal ordering of ONE single-file schema (1 source + 1 test, within the manifest), NOT a task split, and the dependency chain (state-definitions → carry-forward → egress-over-assembled-cycle) makes a 3-cycle compression fragment the no-fabrication-vs-carry-forward separation; the four-cycle shape is the accepted form for a 7-AC single-file store schema. (crit 7 is the test gate, satisfied by the Cycle 4 REGRESSION run of `pytest tests/store/test_loop_schema.py`.)

## Interface Contracts

This task **PUBLISHES** the **store-state contract** consumed by `ADR-0007-T2` (the biomarker-matrix + projection render-time views read these store states and map them 1:1 to their rendered states — `ADR-0007-T2` criterion 4 is the cross-boundary integration check, spec line 300 + 324). The contract is load-bearing — `ADR-0007-T2` plans against these exact states, and a state the store records but the view misreads is a 2-decision defect (the ADR-0007 Negative risk). This is a real outgoing edge in the spec dependency map (`ADR-0007-T1 → ADR-0007-T2`, spec line 324), so the section is required (not a phantom, TP-10).

- **Module:** `scripts/store/loop_schema.py` — the data-in loop / watch-out / physician-feedback store schemas, writing THROUGH `scripts/store/store.py` (`store.append` / `store.read`) and the `keying.py` Line Field Set; it defines NO new key and reimplements NO store I/O.

- **Published store-state contract (the four states `ADR-0007-T2` reads 1:1):**
  - **`pending`** — a panel recommended by the assembled plan (`ADR-0006-T2`'s recommended-panel surface) but not yet drawn. Stored as "pending"; PERSISTS across generation cycles until a result is appended; a read returns "pending" verbatim, NEVER a fabricated result. (`ADR-0007-T2` renders this as "pending", never as a result — its crit 4.)
  - **`not-yet-answered`** — a watch-out check-in with no stored operator answer. A read returns "not-yet-answered", NEVER "clear" and NEVER an absent result. (`ADR-0007-T2` renders this as "not yet answered" — its crit 4.)
  - **`no-prior`** — a biomarker item with exactly one stored timepoint. A read returns the single timepoint plus a "no-prior" marker, NEVER a fabricated trend/delta/projection over one point. (For ≥2 timepoints the schema returns the stored timepoints as-is; the trend/projection is `ADR-0007-T2`'s render-view concern, not this store schema's.)
  - **`answered-over-time`** — a watch-out answer or physician-feedback entry stored in one generation and carried forward as a next-generation input on the NEXT plan/report generation read (the accepted one-generation loop latency). A stored answer/entry is NOT dropped, expired, or overwritten on the next read.

- **Behavioral contract:** the loop schemas store ONLY operator-entered answers + plan-recommended panels + physician-feedback entries; they perform 0 automated signal detection (no threshold evaluation, no signal/alert emission — NG-6). The watch-out question SET is DERIVED at generation from the operator's active protocols/compounds (the questions to ASK), not evaluated against any cutoff. All persistence is local file I/O through `store.append` / `store.read`; 0 model-bound send.

- **Dependent task (consumes this contract):** **`ADR-0007-T2` (biomarker-matrix + projection render-time views)** — its render views read the pending / not-yet-answered / no-prior / answered-over-time store states and map them 1:1 to their rendered states (`ADR-0007-T2` crit 4, the cross-boundary integration check). The edge `ADR-0007-T1 → ADR-0007-T2` is spec line 324.

- **Change control:** `ADR-0007-T2` MUST NOT change the store-state contract (the four state markers or their no-fabrication / carry-forward semantics) without Architect review — a divergence breaks the 1:1 state mapping the render views stand on (the 2-decision defect surface). `ADR-0007-T1` likewise MUST NOT change the `ADR-0002-T1` `store.append` / `store.read` / `keying.py` interface (it consumes them) without Architect review.
