# Recipe: No-Train Router + Summary Derivation Implementation

> **This is the V1 plan-reasoning PII enforcement — the no-train router.**
> It implements the contract the `ADR-0006-T0` spike fixed: derive the
> plan-reasoning summary from store-read state over the spike's closed Summary
> Field-Set, route the dispatch to the no-train lane, and — the load-bearing
> security behavior — **fail (raise) a dispatch whose payload carries ANY field
> outside the closed Summary Field-Set** (a WHITELIST: allow only field-set
> tokens, raise on every field in the field-set's complement — known-excluded
> raw-PII OR a novel/unanticipated field absent from the set, not only a
> named-excluded subset). That raise is a PAYLOAD-FIELD-LEVEL check the spike
> designed: it inspects the dispatch payload's fields against the field-set and
> rejects any out-of-field-set field BEFORE the send. **Fail-closed:** if
> `summarize` raises or returns a malformed/partial summary, `dispatch` raises
> rather than send a partial/empty payload; any field whose field-set membership
> cannot be affirmatively established is treated as OUT-of-set and raises
> (decided by whitelist inclusion, mirroring `ADR-0001-T1`'s default-deny
> posture). It is NOT a bare wrap in `egress_guard.run` — the egress guard
> inspects call-occurrence-carrying-store-content, which is ORTHOGONAL to
> payload field-set membership (a field-set token and an out-of-field-set token
> are both store-derived content reaching the model, so the guard cannot
> distinguish them; conversely a clean summary dispatch may not trip it). The
> egress guard is retained as a COMPLEMENT (catches accidental store-content
> egress on non-model paths). The Wave 4 → Wave 5 boundary gates this router
> GREEN — specifically the no-train routing (crit 2) and the whitelist raise
> (crit 4) — BEFORE Wave 5 lets `ADR-0006-T2` reason over operator state
> (enforcement-first, build plan §5b).

## Risk Pre-Check

The spec task block carries two risk mitigations; both gate this task's GREEN before any implementation, and both are first-class RED targets — not optional add-ons. A router that routes to the no-train lane but cannot RAISE on an injected raw-PII field would silently re-open the exact risk it exists to close (it would send raw PII to the model).

- **Risk ADR-0006 Negative (plan reasoning is the one PII-touching dispatch; cannot reason over raw PII; bounded by the store read model).** This risk is implemented by crit 1, 3, 4. Gate: before GREEN, the RED phase MUST include tests that assert (a) `router.summarize(store_read)` returns a summary whose field set EQUALS the `ADR-0006-T0` Summary Field-Set and a named raw-PII field EXCLUDED by the spike is ABSENT (crit 1 — the field-set-only summary), (b) `router.dispatch` over a `summarize`-built summary carries 0 raw-PII to the model, verified by asserting the captured model-bound payload's field set is a SUBSET of the Summary Field-Set, with the cross-spec `egress_guard.run` complement observing 0 store-content egress on the non-model path (crit 3 — the whitelist assertion), and (c) — the load-bearing WHITELIST gate — `router.dispatch` RAISES when handed a payload containing ANY field outside the closed Summary Field-Set, and the test attributes the raise to THAT FIELD'S PRESENCE (its absence from the field-set) in the payload (crit 4 — the payload-field-level whitelist check). The crit-4 RED phase MUST plant TWO out-of-set fields and assert a raise for each: (i) a NAMED-EXCLUDED raw-PII field, and (ii) — the falsifying whitelist target — a field OUTSIDE the Summary Field-Set AND ABSENT from the named-excluded raw-PII list (a novel/unanticipated field), proving the check is "allow only field-set tokens" (whitelist), not "block known-bad fields" (blacklist). A whitelist implementation passes both; a blacklist implementation that only blocks named-excluded fields PASSES (i) but FAILS (ii). A test that asserts only the no-train-lane routing without the whitelist raise, OR a test that asserts the raise by wrapping the dispatch in `egress_guard.run` (whose call-occurrence signal is orthogonal to payload field-set membership — it cannot distinguish a field-set token from an out-of-field-set token, both being store-derived content reaching the model), FAILS this gate. A placeholder test (`assert True`) fails this gate.

- **Constraint D1→ADR-0006 (no-train summaries).** This constraint is implemented by crit 2, 3, 4. Gate: before GREEN, the RED phase MUST include a test asserting `router.dispatch(summary)` routes to the NO-TRAIN lane (not the default/train-eligible lane) — the dispatch's lane attribute is the no-train lane (crit 2) — AND the crit-3 whitelist-subset assertion AND the crit-4 whitelist raise assertion (both out-of-set fields, named-excluded and novel) above. The 0-raw-PII falsifiable check (crit 3) is the basis of this constraint the downstream `ADR-0006-T2` carries; it must be exercised over a REAL `summarize`→`dispatch` path, not a no-op.

- **Fail-closed / default-deny (Security MEDIUM-1).** This mirrors `ADR-0001-T1`'s explicit fail-closed posture (`run` returns FAIL when capture cannot be established — never pass). Gate: before GREEN, the RED phase MUST include a test asserting that when `router.summarize` raises or returns a malformed/partial summary (derivation fails), `router.dispatch` RAISES and the model sink is NEVER reached (never sends a partial/empty payload). Any field whose field-set membership cannot be affirmatively established is treated as OUT-of-set and raises (the whitelist decides inclusion; ambiguity defaults to deny). A `dispatch` that sends a partial/empty payload on a failed-derivation summary, or that defaults an unestablishable field to in-set, FAILS this gate.

- **Egress-occurrence vs payload-PII-content discrimination (crit 4 — the load-bearing distinction the egress guard does NOT itself supply).** The `ADR-0001-T1` egress guard's `run(callable)` observes whether an OUTBOUND CALL CARRYING STORE CONTENT OCCURRED across the whole invocation — a call-occurrence signal that is ORTHOGONAL to payload field-set membership. A field-set token and an out-of-field-set token are BOTH store-derived content reaching the model, so the guard cannot distinguish them; conversely a clean summary dispatch may not trip it. The guard is therefore not the router's raw-PII discriminator. Gate: the crit-4 RED test MUST assert the raise comes from a PAYLOAD-FIELD-LEVEL WHITELIST check — it plants a field outside the Summary Field-Set (both a named-excluded raw-PII field AND a novel field absent from the named-excluded list) INTO the dispatch payload and asserts `router.dispatch` RAISES BECAUSE that field is outside the field-set (not on the named-excluded list specifically, and not because a network call occurred). A test that proves the raise only via `egress_guard.run` failing fails this gate, because that signal is orthogonal to field-set membership and cannot tell a field-set token from an out-of-field-set one.
