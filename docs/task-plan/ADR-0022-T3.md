# Recipe: Dispatch-Count Instrumentation + Fail-Closed Cap

This task INSTRUMENTS the orchestrator's per-plan AGGREGATE dispatch count (N plan-domain
specialists + each gate dispatch + each revise iteration) and adds a CONFIGURABLE fail-closed
cap: when a run's dispatch tally would exceed the cap, the orchestrator HALTS to the honest /
partial no-plan state and SURFACES the count; under the cap, the run completes normally and the
count is reported. The cap is a build-plan PARAMETER, not a hard-coded constant — proven by
running two configs over the same fixture (a low cap that trips, a high cap that does not),
yielding different outcomes (ADR-0022 OQ-4, disposition #4 instrument + cap). The ceiling NUMBER
is an operator/billing fact confirmed at the operator-present live-run checkpoint downstream; this
task builds the MECHANISM only.

**Build-plan wave attestation (v1-build):** this is build-plan Wave 3
(`docs/build-plan/build-plan-plan-gen-engine.md` §Wave 3). The prior wave's checkpoint Go/No-Go
(Wave 2 → Wave 3: orchestrator core records ≥1 plan unattended; inner-safety-gate-bypass probe =
0; de-id-IN no-train-lane-only + outage-halt green; OUT re-insertion 0-tracked-PII green) must
have passed before this task builds. The orchestrator this task wires the counter into
(`scripts/plan/plan_orchestrator.py`) is ADR-0022-T1's merged output (present, 10959 bytes,
`run_orchestrated` confirmed).

**What the orchestrator's dispatch path looks like TODAY (grounded against the live tree).** In
`run_orchestrated` ([plan_orchestrator.py:101-185](../../scripts/plan/plan_orchestrator.py#L101)),
three dispatch classes accrue the aggregate count this task instruments:
- **N specialist dispatches** — the `for domain in domains:` loop
  ([plan_orchestrator.py:174-177](../../scripts/plan/plan_orchestrator.py#L174)) calls
  `dispatch(domain, prompt, summary)` once per requested domain (1-4).
- **Each GATE dispatch** — the injectable `gate_dispatch=` seam
  ([plan_orchestrator.py:133-138, 155](../../scripts/plan/plan_orchestrator.py#L133)), whose
  ADR-0022-T1 default is the inert `_noop_gate_dispatch` (0 dispatches on a normal run); the
  Wave-3 judge (ADR-0023-T1) and safety review (ADR-0024-T1) wire real gate dispatches here.
- **Each REVISE iteration** — the `reauthor` / `adjudicator` hooks forwarded to
  `pipeline.run_generation` ([plan_orchestrator.py:182-185](../../scripts/plan/plan_orchestrator.py#L182));
  the bounded revise loop (ADR-0022-T2, Wave 4) drives N re-author passes.

The counter is a SEAM the orchestrator increments at each of these dispatch classes; the cap is
checked before the dispatch is issued (fail-closed BEFORE the over-budget call, never after). The
counter module (`scripts/plan/dispatch_budget.py`) is the standalone accrual + cap mechanism; the
orchestrator imports it and wires the increment + the cap check into the dispatch path. The
N=3 revise cap (ADR-0022-T2) is FIXED at build-plan time; THIS dispatch cap stays runtime-
configurable because its ceiling is an operator/billing fact (spec §ADR-0022-T2 Note (cap N)).

**INTRA-WAVE / INTRA-FILE SHARED-FILE COORDINATION (load-bearing — see UPSTREAM FLAG).**
`scripts/plan/plan_orchestrator.py` is modified by THREE dependency-ordered tasks across three
waves: ADR-0022-T1 (W2, Create) → **ADR-0022-T3 (W3, Modify — THIS task)** → ADR-0022-T2 (W4,
Modify). T3 and T2 never co-occupy a wave, so this is sequencing, NOT a parallel-edit collision
(build plan §Cross-Spec Coordination, BP-07 clear). The `/execute-plan` driver MUST sequence T3
before T2 on the shared file; T2 (the revise loop) builds ON TOP of T3's instrumented dispatch
path (each revise iteration the loop adds is a counted dispatch class this task already
instruments). T1's seam contract — the `run_generation` hook signature + the `record_plan` call
set — is the stable interface T3 extends; T3 adds the counter wiring WITHOUT changing that
contract. Flagged below (non-blocking) so the driver sequences, not parallel-edits, the file.

## Risk Pre-Check

Risk (ADR-0022 OQ-4 / Consequence — the autonomous loop's aggregate dispatch volume vs the
subscription rate/usage ceiling): an unbounded generate→judge→safety-review→revise loop, re-run
as data arrives, can exceed the subscription ceiling the cost case rests on, with no fail-closed
stop.

- **Gate condition:** Before proceeding to GREEN, a RED test must exist that asserts (a) the
  count ACCRUES across every dispatch class (specialist + gate + revise) and equals the dispatch
  tally over a synthetic run [AC-1]; (b) a cap set BELOW the tally HALTS to honest/partial no-plan
  with **0 plans recorded past the cap** and the count surfaced [AC-2]; (c) the cap is
  CONFIGURABLE — two configs (one allowing, one blocking) over the SAME fixture yield DIFFERENT
  outcomes, proving the cap is a parameter not a hard-coded constant [AC-3].
- The fail-closed-on-exceed assertion (AC-2) and the configurability assertion (AC-3) are the
  load-bearing falsification probes — a test that asserts only "the count is reported" (AC-4) but
  not the 0-plans-past-cap halt is INSUFFICIENT; the RED phase MUST include the halt probe AND the
  two-config probe.
- A placeholder test (`assert True`) fails this gate. AC-3's two-config probe is non-tautological
  ONLY if the SAME fixture run under config-A (cap above tally) records a plan AND under config-B
  (cap below tally) records 0 plans — a test running one config proves nothing about
  hard-coding.

## Interface Contracts

This task adds a downstream-consumed parameter and a counted dispatch path. The contract:

- **`scripts/plan/dispatch_budget.py`** — the per-plan dispatch-budget object: constructor takes a
  configurable integer cap (keyword, defaulting to a named module-level sane-default constant); an
  increment-and-check method called BEFORE each dispatch (increments the count, signals the
  fail-closed halt when the post-increment count exceeds the cap, carrying the count reached); a
  read accessor surfacing the current count. **Behavioral contract:** the cap check is fail-closed
  (the over-budget dispatch is never issued); the count is surfaced on both the normal and the
  halt paths; the cap is a parameter, never a hard-coded literal at the increment site.
- **`run_orchestrated`'s new cap parameter** (in `scripts/plan/plan_orchestrator.py`) — a
  keyword-only parameter defaulting to the `dispatch_budget` module's sane default. **This is the
  shared file ADR-0022-T2 (Wave 4) also modifies.** ADR-0022-T2 adds the bounded revise loop,
  whose N re-author passes are a counted dispatch class this task ALREADY instruments — T2 builds
  on this instrumented dispatch path. **Dependent tasks (ADR-0022-T2) MUST NOT change the
  `run_orchestrated` cap-parameter contract or the `dispatch_count` result key without Architect
  review** (the build plan's seam-contract notice, Core Rule 10). The intra-file sequencing (T1 →
  T3 → T2) is the build plan's §Cross-Spec Coordination row for `plan_orchestrator.py`.
