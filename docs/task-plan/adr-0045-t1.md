# Recipe: The Monitoring Compiler — Rule Grammar for Tier-1-Safe vs Must-Escalate

> Wave-3 Tier-3 entry task (Dependencies: ADR-0041-T1, ADR-0044-T1 — both MERGED). It creates
> `scripts/plan/monitoring_compiler.py` — `compile_config(domain_programs) -> monitoring_config`,
> which compiles each program's specialist-authored `monitoring_signals` + `adjustment_rules`
> (ADR-0041 fields 3-4) into a DETERMINISTIC config that classifies every `adjustment_rule` as
> **Tier-1-auto-apply-safe** (bounded numeric range, in the rule's own domain, monotone direction —
> safe for the daily loop to auto-apply with 0 model calls) vs **must-escalate** (material,
> cross-domain, or safety-threshold — routed to a human/specialist tier). An out-of-domain-bounds
> or safety-crossing rule is REJECTED at compile time, fail-closed. This is a GREENFIELD module —
> it makes NO frozen-spine edit; the frozen four (`store.py` / `keying.py` / `pipeline.py` /
> `adjudicate.py`) stay byte-frozen (an entry-state `numstat=0` check only). The compiled config
> LIVES in the ADR-0044 comprehensive plan model (`scripts/store/plan_model.py`) as its
> `monitoring_config` element — the value rides `plan_model.record_plan_version` → the frozen
> `store.append` unchanged (disposition #14), no `plan_model` edit. The load-bearing property is
> FAIL-CLOSED classification: a rule the compiler cannot positively certify bounded-in-domain-
> monotone NEVER lands Tier-1-auto-apply — an ambiguous/out-of-bounds/non-monotone rule escalates
> or is rejected. A rule that could auto-apply an unsafe adjustment un-modelled is the exact live
> risk this compiler prevents (ADR-0045 Consequences-Negative-2). The single consumer is
> ADR-0045-T2's four-tier executor, which runs the compiled config; this task's obligation is the
> classification grammar + its RED tests + the round-trip, verified against synthetic fixtures.

## Risk Pre-Check

**BLOCKING GATE — the fail-closed classification is this task's safety deliverable.** Do not proceed to GREEN until a real (non-`assert True`) test exists for every risk below. A placeholder test fails this gate. This is NOT a store-surface task (the compiler writes nothing to `scripts/store/`; its output RIDES `plan_model`'s already-adversarially-tested record path) — the store-adversarial battery (bead `pka`) does NOT apply here; it was discharged by ADR-0044-T1 on the model this config rides.

- **Risk (ADR-0045 Consequences-Negative-2 — a mis-compiled rule auto-applying un-modelled is a live safety risk):** if `compile_config` marked an out-of-bounds / cross-domain / safety-threshold / non-monotone rule Tier-1-auto-apply-safe, the ADR-0045-T2/T3 daily deterministic loop would auto-apply an unsafe adjustment with 0 model calls and 0 human review.
  - Gate condition (fail-closed classification, over synthetic fixtures): RED must include AC-2 (a material-in-domain rule, a cross-domain rule, a safety-threshold rule, AND a non-monotone rule each compile to a **must-escalate** entry, NEVER Tier-1) AND AC-3 (an out-of-domain-bounds rule AND a safety-crossing rule are **REJECTED at compile** — `compile_config` raises `MonitoringCompileError`, fail-closed, never returning a config that marks them Tier-1). A test that lets any of these classify Tier-1-auto-apply-safe, or a `compile_config` that returns a config admitting an out-of-bounds rule instead of raising, FAILS this gate. `compile_config` is the fail-fast classification boundary: the unsafe rule escalates or the compile raises, it never silently auto-applies.
  - Gate condition (the auto-apply set is a POSITIVE certification, not a default): the Tier-1 classification fires ONLY when the compiler can positively certify all three of {bounded, in-domain, monotone}; the absence/ambiguity of any one → must-escalate. A "default-to-Tier-1-unless-proven-unsafe" implementation is the inverted, fail-OPEN posture this gate forbids — asserted via the mixed-config invariant below AND the explicit ambiguous/under-specified-rule case (AC-2 (v), QA-W3-06): a rule MISSING a certification axis (no declared direction / no declared bound) must compile `MUST_ESCALATE`, never Tier-1 — closing the fail-open hole where a compiler certifies the explicit escalate triggers yet defaults a missing-axis rule to Tier-1.
  - Gate condition (offense-naming is STRUCTURAL, not substring): the AC-3 rejection tests assert the raised `MonitoringCompileError` names the offense through a STRUCTURED accessor (`.offending_rule`), NOT `assert <name> in str(exc.value)` — a generic kitchen-sink message satisfies a substring check vacuously (a raise-for-the-wrong-reason would pass).
  - Gate condition (mixed-config invariant, RED-capable): one `compile_config` call over a program carrying ALL of {a Tier-1-safe rule, a material rule, a cross-domain rule, a safety-threshold rule, a non-monotone rule, **an ambiguous/under-specified rule (QA-W3-06)**} asserts EXACTLY the one bounded-in-domain-monotone rule carries the Tier-1 token and **0** of the other five do — a single-count assertion that turns RED if any escalate-class rule leaks into Tier-1.
  - Gate condition (RED-capability proven, not assumed): before GREEN, each classification/rejection test (AC-2's FIVE escalate cases incl. the ambiguous/under-specified case + the mixed-config invariant + AC-3's two rejection cases) is observed RED against a wrong-but-present **classify-everything-Tier-1** `compile_config` stub (returns a config marking every rule Tier-1-auto-apply-safe, never raising), then the stub is reverted (Step 1 continued, RED-capability falsification). Module-absent ImportError proves only absence; this proves each assertion turns red when `compile_config` is present-but-fail-open. This is the PF-S130-01 non-tautology guarantee: a mutation that mis-classifies a must-escalate rule as Tier-1 REDs the classification test.
- **Risk (constraint-propagation, ADR-0044 — the compiled config MUST live in the model, not a side stream):** if the config did not round-trip through `plan_model`, a downstream executor reading the stored model would not find the config, and the monitoring loop would silently no-op.
  - Gate condition (AC-4, PRODUCTION-PATH round-trip, RED-capable): the compiled config is stored via the REAL `plan_model.record_plan_version` and read back via the REAL `plan_model.read_plan_version` (NOT a hand-built dict compare), asserting the read-back `monitoring_config` equals the compiled config intact. A non-`dict` or empty config would be rejected by `validate_plan_version` at the writer boundary, so a passing round-trip also proves the config satisfies the model's non-empty-dict `MONITORING_CONFIG` contract. RED-capable: a revert to the thin `plan_schema` spine, or a compiler that emits a non-JSON-serializable config, drives it RED.

It iterates each domain's `adjustment_rules`, classifies each rule, and returns a NON-EMPTY, JSON-serializable `monitoring_config` dict that (a) groups per domain the compiled rule entries each tagged with its classification token from `{TIER1_AUTO_APPLY_SAFE, MUST_ESCALATE}`, and (b) bundles that domain's `monitoring_signals` as the observables the daily loop evaluates rules against. The config is composed of plain dict/list/str/number/bool ONLY (no `set`/`tuple`/`frozenset`) so it round-trips through `plan_model` → the frozen `store.append`'s JSON serialization intact (AC-4). The exact config key spellings + per-entry payload are executor discretion; the STRUCTURE is pinned in Interface Contracts.
  - **The classification grammar** (the axes are the spec's named ones; the concrete numeric encoding of a rule's declared change is executor discretion — pin the axes + their bucket mapping, not the arithmetic):
    - An `adjustment_rule` entry declares: a TARGET signal reference + a domain (the in-domain vs cross-domain axis), a BOUNDED numeric range/delta it drives with a DIRECTION (the bounded + monotone axes), and optionally a MATERIALITY magnitude and a SAFETY marker (referencing the program's `refusal_escalation`). A `monitoring_signal` (whose per-entry sub-structure beyond the tier ADR-0041-T1 assigns to THIS task) declares the target signal's operating BOUNDS + materiality THRESHOLD — the envelope boundedness/materiality/out-of-bounds are evaluated against.
    - **Tier-1-auto-apply-safe** ⟸ the rule POSITIVELY certifies ALL THREE of {bounded (driven change ⊆ the target signal's declared bounds), in-domain (target domain == the program's own domain), monotone (single direction)}. This is a positive certification, NEVER a default.
    - **must-escalate** ⟸ the rule is in-domain-and-in-bounds but trips a NON-FATAL escalate trigger: MATERIAL (magnitude ≥ the signal's materiality threshold, < the bound), CROSS-DOMAIN (target/`cross_domain_seams` reaches another domain), SAFETY-THRESHOLD (gated by a `refusal_escalation` marker), NON-MONOTONE (bidirectional), or AMBIGUOUS/UNDER-SPECIFIED (a required certification axis — direction / bound — is MISSING, so `{bounded, in-domain, monotone}` cannot be POSITIVELY certified; QA-W3-06). ## Interface Contracts

This task CREATES `scripts/plan/monitoring_compiler.py` — the compiled-config contract ADR-0045-T2's four-tier executor reads. The contract is the shared seam:

- `monitoring_compiler.compile_config(domain_programs: Mapping) -> dict` — `domain_programs` is the `{domain_name: seven-field DOMAIN PROGRAM}` mapping (the `plan_model` `DOMAIN_PROGRAMS` shape; `domain_program.validate`-conformant on arrival). Returns a NON-EMPTY, JSON-serializable `monitoring_config` dict classifying every `adjustment_rule` as Tier-1-auto-apply-safe vs must-escalate and bundling the per-domain `monitoring_signals` observables. Raises `monitoring_compiler.MonitoringCompileError` (fail-closed) on an out-of-domain-bounds or safety-crossing rule; never returns a config that admits such a rule.
- **The classification vocabulary** — `monitoring_compiler.TIER1_AUTO_APPLY_SAFE` and `monitoring_compiler.MUST_ESCALATE`, module-level `str` constants forming the closed two-member set every compiled rule entry is tagged with (the twin of `domain_program.DOMAIN_KINDS`). ADR-0045-T2's tier predicate reads a rule's tag: `TIER1_AUTO_APPLY_SAFE` → the Tier-1 auto-apply path (0 model calls); `MUST_ESCALATE` → the Tier-2/3/4 escalation paths.
- `monitoring_compiler.MonitoringCompileError` — the single typed rejection channel. Carries a STRUCTURED offense accessor `.offending_rule` (the offending `adjustment_rule` entry — the rule mapping or a stable reference). A caller identifies the offense STRUCTURALLY, not by substring-scanning the message.
- **The `monitoring_config` shape (T1-pinned STRUCTURE)** — a non-empty mapping that, per domain, carries (i) the compiled `adjustment_rule` entries each tagged with a classification token, and (ii) the domain's `monitoring_signals` observables. JSON-serializable throughout (plain dict/list/str/number/bool — no `set`/`tuple`) so it rides `plan_model.record_plan_version` → the frozen `store.append` unchanged. The concrete key spellings + per-entry payload are executor discretion; the STRUCTURE is pinned here (0 pre-existing tree definition — grep = 0 hits) so ADR-0045-T2 plans against a stable config.
- **The classification tag-access seam (ARCH-W3-04, T1-pinned)** — the module exports a `monitoring_compiler.classification_of(entry) -> str` accessor returning the entry's classification token (`TIER1_AUTO_APPLY_SAFE` | `MUST_ESCALATE`); ADR-0045-T2's tier predicate reads a compiled entry's tag THROUGH this accessor, NOT by hardcoding a discretionary per-entry config key. This keeps the per-entry tag KEY spelling internal to the compiler (executor discretion) while the READ seam 0045-T2 depends on is self-describing + stable — removing the latent coupling of 0045-T2 hardcoding the tag key against an interface-DEFINING config. - **The `adjustment_rule` entry grammar (T1-pinned STRUCTURE — the ADR-0041-T1-assigned ownership)** — a rule declares a target signal + domain (in-domain vs cross-domain), a bounded numeric range/delta + a direction (bounded + monotone), and optionally a materiality magnitude + a `refusal_escalation` safety marker. ADR-0041-T1's Interface Contracts explicitly assigns this grammar to ADR-0045-T1: "`adjustment_rules` — T1 pins presence + non-empty-for-compound; the rule grammar (bounded / in-domain / monotone Tier-1-safe vs must-escalate) is OWNED by ADR-0045-T1." The compiler does NOT modify `domain_program.py`; it reads these fields and defines their classification-relevant sub-structure.
- **Where the config LIVES (round-trip contract, ADR-0044):** the compiled config is stored as the `monitoring_config` element of the ADR-0044 comprehensive plan version (`plan_model.MONITORING_CONFIG`), which `plan_model.validate_plan_version` requires to be a non-empty dict.
