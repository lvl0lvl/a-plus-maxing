# Recipe: Shared Ingestion Routine, Adapter Interface, Dedupe + Manual-Entry Fallback

This task produces CODE: the common adapter-interface module (`scripts/ingest/adapter.py`),
the shared ingestion routine (`scripts/ingest/ingest.py` — `run` / `manual_entry` /
`import_csv`), and their tests. It PUBLISHES the adapter interface + shared routine consumed
by `ADR-0003-T2` (adapters implement the interface; the 0-shared-routine-edit proof diffs
`ingest.py`/`adapter.py`) and `ADR-0003-T3` (the scheduler invokes `ingest.run`). The TDD
Steps follow the standard RED/GREEN/REFACTOR/REGRESSION cycle from `tdd-planning.md`: RED
calls `/write-tests` with AC IDs (expect FAIL), GREEN describes changes (no literal code),
REFACTOR names review targets, REGRESSION runs the full `pytest` suite. The dedupe key is
IMPORTED from `scripts/store/keying.py` — there is NO second key definition anywhere in
`scripts/ingest/` (criterion 3). The routine writes ONLY to `vault/store/` and invokes NO
model step, verified by two independent mechanisms (criterion 5).

## Risk Pre-Check

This task carries risk mitigations in the spec → Risk Pre-Check is active. Each gate maps to a concrete `pytest` test (or a `rg`/guard assertion run inside a test) that must exist in the RED phase and fails if the mitigation is absent. A placeholder (`assert True`) fails each gate.

- **Risk ADR-0003 N3** (the dedupe key cannot be finalized independently of D2 keying; a later D2-keying change re-opens the dedupe design). Mitigation: criterion 3 enforces a SINGLE shared key module so the ingestion dedupe key fits the store's (item, timepoint, source tag) keying (constraint D2→D3). **Gate (single-shared-key, falsifiable):** a RED test must assert BOTH (a) `rg "def .*key" scripts/ingest/` returns 0 matches (no independent key function is defined anywhere under `scripts/ingest/`), AND (b) the routine's dedupe identity is derived by CALLING `keying.py`'s key function — exercised by asserting that two readings the SHARED `keying.py` key maps to the SAME identity dedupe to one stored line through `ingest.run` (so the routine's dedupe behavior is bound to the imported key, not a private copy). A test that only greps for the string fails the gate if it does not also prove the routine dedupes VIA the imported key. This gate is satisfied in Cycle 2 RED (the `ingest.run` import cycle). **Falsifiable RED:** the `rg`-0 assertion turns RED if a second key function is introduced under `scripts/ingest/`; the dedupe-via-imported-key assertion turns RED if the routine derives identity by any path other than the shared key. **Negative-control failing-capability proof (the `rg "def .*key"`=0 static assertion passes vacuously before any code exists, so its falsifiability is exercised, not merely asserted in prose):** the Cycle 2 RED includes a documented one-time negative-control step that introduces a transient probe — a throwaway `def _probe_key` under `scripts/ingest/` (e.g. a scratch file) — re-runs the `rg "def .*key" scripts/ingest/`=0 assertion and confirms it FAILS with the probe present, then removes the probe and confirms the assertion returns to 0. This parallels the build plan's SEC-01(b) monkeypatch flip that proves the hook's scanner is load-bearing: it proves the static gate is failing-capable, not a constant-true assertion.
- **Constraint D1→D3** (no raw reading through a model step; the routine writes ONLY to the local store). Mitigation: criterion 5, carried by TWO independent mechanical halves. **Gate (dual-mechanism, both falsifiable):**
  - **Half A — dynamic egress (0 outbound calls):** a RED test must wrap a REAL `ingest.run(adapter, export_file)` invocation in ONE zero-arg closure and pass it to `egress_guard.run`, asserting the result is truthy (0 outbound network calls observed across the whole `ingest.run` invocation). A test that asserts 0 egress over a no-op (rather than over a real `ingest.run`) fails this gate — it must exercise the production ingestion path. **Falsifiable RED:** this assertion turns RED if `ingest.run` makes (or spawns a child that makes) any outbound call — the guard is failing-capable by construction (`ADR-0001-T1`).
  - **Half B — static no-model-step (`rg` 0 model/API calls):** a RED test must assert `rg` over `scripts/ingest/` finds 0 model/API-client call references (the static no-model-step scan). **Falsifiable RED:** this assertion turns RED if any model/API-client call is introduced under `scripts/ingest/`. The model/API-client token set scanned must match the no-raw-reading-to-model rule's token set read from the `ADR-0001-T0` spike's "No-Raw-Reading-To-Model Rule" section (loaded scoped in the Context Load List — do not invent a narrower set). **Negative-control failing-capability proof (this static assertion, like Half B, passes vacuously before any code exists):** the Cycle 3 RED includes a documented one-time negative-control step that introduces a transient probe — a throwaway model/API-client call reference (one token from the spike's token set) under `scripts/ingest/` (e.g. a scratch line) — re-runs the `rg`-over-`scripts/ingest/`=0 model/API-client assertion and confirms it FAILS with the probe present, then removes the probe and confirms the assertion returns to 0. This proves the static gate is failing-capable (same SEC-01(b)-style flip as the crit-3 negative control), not a constant-true assertion.

  BOTH halves are first-class RED targets in Cycle 3, not optional add-ons. A criterion-5 implementation that runs only Half A (egress) OR only Half B (static scan) fails this gate — the build plan Wave 3→4 boundary (line 91) requires criterion 5 to carry BOTH mechanical halves.
- **Risk ADR-0002 N2 inherited** (NDJSON enforces no schema; the no-schema discipline lives in ingestion). Mitigation: the dedupe/validation runs HERE against the shared field set. **Gate:** the dedupe-and-write path goes through `store.append` (which `ADR-0002-T1` made reject a reading missing any Line Field Set field) — so a malformed reading is rejected at the store boundary, not silently written by the routine. **Gate condition:** the criterion-1/criterion-2 import tests assert imported readings land via `store.append` (verified by `store.read` returning them), so the routine inherits the store's field-set rejection rather than bypassing it with a raw file write. A routine that writes NDJSON lines directly (bypassing `store.append`) fails this gate — it would re-open the N2 no-schema hole the store closed.

## Interface Contracts

This task PUBLISHES the adapter interface + the shared ingestion routine, both consumed by downstream Wave-3/Wave-4/Wave-5 tasks, so the contract is load-bearing.

- **Interface:** the common export contract in `scripts/ingest/adapter.py` — **NAMED CONTRACT (frozen at this task; `ADR-0003-T2`'s 0-shared-routine-edit proof requires this surface stable):**
  - **`source_tag` (source-identity accessor):** a no-argument accessor (attribute or zero-arg method, implementer discretion) returning the source tag string carried into each store reading per `keying.py`'s Line Field Set.
  - **`read_readings(export_file)` (readings-yielding method):** takes one argument (the export file / path) and returns an iterable of readings; each reading carries every `keying.py` Line Field Set field (item id, timepoint, source tag, value field(s)) in the store reading shape. The return is an iterable of readings — not a count, not a write side effect.
  - The names (`source_tag`, `read_readings`), the arity (zero-arg accessor; one-arg yield method), and the return shape (string source tag; iterable of Line-Field-Set readings) are the published contract every adapter conforms to. The contract does NOT dictate base-class-vs-Protocol — the implementer chooses the mechanism; only the names/arity/return-shape are frozen here.
  - The interface exposes ONLY the export-contract surface (source identity + yield-readings); it carries NO dedupe or store-write logic — those belong to the shared routine, so an adapter cannot fork the dedupe key.
  - **Invariant (load-bearing for the downstream 0-edit proof):** the adapter interface and `ingest.run` name NO per-source export field; all export-format specifics live inside each adapter's `read_readings` mapping. **Breaks if:** the interface or `ingest.run` references a source-specific export field — then `ADR-0003-T2` criterion 3 (Garmin 0-edit) and criterion 6 (format-rename 0-edit) fail, because a source-specific field in the shared surface forces a shared-routine edit when that source's format changes or a new source is added.
  - **Dependent task (implements this interface):** `ADR-0003-T2` (the HealthKit, Oura, Garmin, and Whoop adapters implement this interface; criterion 3's `git diff --numstat` 0-shared-routine-edit proof diffs `scripts/ingest/adapter.py` to assert adding an adapter changes 0 lines in the interface).

- **Function:** `run(adapter, export_file)` in `scripts/ingest/ingest.py`
  - Reads the export's readings via the `adapter.py` interface, derives each reading's dedupe identity by CALLING `keying.py`'s key function (the single shared key — no second key under `scripts/ingest/`), and writes each reading through `store.append`. Idempotent on the shared key: a re-run over already-stored readings appends 0 duplicate lines; an export mixing already-stored and new timepoints appends only the new-timepoint delta. Writes only to `vault/store/`; invokes no model step.
  - **Dependent tasks (consume `run`):** `ADR-0003-T2` (its adapters are run through this unchanged routine; criterion 3's diff of `scripts/ingest/ingest.py` asserts adding an adapter changes 0 lines), `ADR-0003-T3` (the scheduler's unattended entry point invokes `ingest.run` over the wired adapters; criterion 1).

- **Functions:** `manual_entry(item, reading)` and `import_csv(path)` in `scripts/ingest/ingest.py`
  - The manual-entry / CSV-import fallback: each writes a reading (or CSV of readings) into the SAME `vault/store/` files as adapter imports, through the same `store.append` path (same shared key, same field-set rejection). Labs / food / weight enter the store via this fallback (spec Dependency Map; the manual-entry path for sources without a wired adapter, e.g. Whoop until wired — `ADR-0003-T2` N2).
  - **Dependent task (relies on the fallback):** `ADR-0003-T2` (Whoop is the registered-but-unwired case that narrows to this manual-entry fallback until wired).

- **Change control:** Dependent tasks (`ADR-0003-T2`, `ADR-0003-T3`) MUST NOT change the adapter interface or the `run` / `manual_entry` / `import_csv` signatures without Architect review. `ADR-0003-T2`'s 0-shared-routine-edit proof depends on `adapter.py` + `ingest.py` being stable; `ADR-0003-T3`'s scheduler depends on `ingest.run` being the invariant entry point.
