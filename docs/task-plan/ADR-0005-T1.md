# Recipe: PII-Free-Trunk Gitignore Boundary + Pre-Commit Content-Scan Hook

> **This is the trunk content-scan trust boundary.** The hook this task builds —
> `block-pii-commit.sh` — is the substrate mechanism that stops a filled-scaffold
> value, a `vault/store/` file, or a tracked-file PII token from ever being
> committed. It **CONSUMES** ADR-0001-T1's `pii_scan.scan(tracked_files) -> int`
> (the SEC-01(a) reuse contract); it MUST NOT reimplement the token scan in bash.
> The SEC-01(b) adversarial check (build plan line 241) makes that reuse
> falsifiable: stub `scan` to return 0 and the hook must FAIL to block a planted
> token. A hook that still blocks while `scan` returns 0 has a private bash
> scanner — a reuse-contract violation and a no-go.
>
> **Hook mechanism (pinned).** `block-pii-commit.sh` is a **PreToolUse Bash-tool
> gate**, mirroring `.claude/hooks/block-commit-main.sh` and
> `block-ungated-vault-write.sh` exactly. It signals a **block by printing
> deny-JSON** (`{"hookSpecificOutput":{…,"permissionDecision":"deny",…}}`) to
> **stdout and exiting 0** — NOT by exiting non-zero. It signals an **allow by
> emitting empty/no-deny stdout and exiting 0**. Every block/allow assertion in
> this recipe (and the test harness, mirroring
> `test_block_commit_main.sh` / `test_block_ungated_vault_write.sh`) is keyed on
> the **observable deny-JSON output**, never on exit code. The spec ACs say
> "non-zero exit" — that wording is INVERTED for a PreToolUse hook; see the
> Upstream Flags. **Fail-closed:** any error in the scan path emits deny, never
> allow (Security HIGH-1). **Residual:** a PreToolUse Bash hook only gates
> AGENT-issued `git commit` Bash calls — human-terminal, IDE, and CI commit paths
> are NOT gated (see Deviations / residual; the follow-up is a server-side
> backstop).

## Risk Pre-Check

This task carries the ADR-0005 Negative consequences and constraint D2→ADR-0005 (store exclusion boundary) as risk mitigations (spec task block "Risk Mitigations"). The gate conditions below must hold as falsifiable RED-equiv targets BEFORE any GREEN-equiv work (a placeholder `assert true` / a test that only exercises the pass direction FAILS this gate). **All block/allow assertions are keyed on the observable deny-JSON output** (block = `"permissionDecision":"deny"` present on stdout; allow = empty/no-deny stdout) — NEVER on exit code, because this PreToolUse hook exits 0 on both block and allow (Fix 1 / Security HIGH-2).

- **Risk: discipline burden — no substrate mechanism stops staging a filled scaffold / store file** (ADR-0005 Negative; criteria 4, 6). Gate: the RED-equiv `bash` test MUST include (a) a case that stages a filled-scaffold value and asserts the hook **emits deny-JSON** AND names the offending file in the deny reason (crit 4), and (b) a case that stages a `vault/store/` file and asserts the hook **emits deny-JSON** (crit 6). Without the hook these fail (no deny-JSON emitted — the staged file is not blocked).

- **Risk: the content-scan guarantee needs an enforcement mechanism that does not yet exist** (ADR-0005 Negative; criteria 1, 2, 5). Gate: the RED-equiv test MUST include (a) a clean-staged-tree case asserting the hook **emits empty/no-deny stdout** (allow) — paired with the SEC-01(b) inverse so the clean-pass is only meaningful alongside proof `scan` was actually consulted (Fix 6: do NOT assert the hook "reports 0 hits"; its contract emits no such string — allow is observable as no-deny stdout), and (b) a planted-tracked-file-PII-token case asserting the hook **emits deny-JSON** via `scan`'s ≥1 (crit 5 fail-direction). The planted token MUST include at least one NON-CANONICAL-CASE token (e.g. a mixed-case email like `Op.User@Example.COM`) so an inherited `pii_scan` normalization gap surfaces at this boundary (Fix 7 / Security LOW-2).

- **Scoped-identity gate (ADR-0005 amended Decision 2026-06-06 / bead `qwj` option iii) — the identity check is path-scoped; the agnostic checks are trunk-wide.** The hook MUST NOT run the operator-IDENTITY (name) patterns over the full staged set — doing so blocks the project's own governance/session/design prose (the operator name is accepted provenance, not committed health data, per the amended ADR-0005 Decision). The hook partitions its staged set into (a) DATA-BEARING paths and (b) the rest, and runs the identity check ONLY over (a); the operator-AGNOSTIC checks (structural `{item,timepoint,value}` store-line patterns + the generic `@gmail.com` contact pattern) run over the FULL staged set. Gate (RED-equiv, falsifiable both directions): (i) stage a NON-data-bearing tracked file (e.g. a HANDOFF/design-style prose file) containing the operator name and assert the hook **emits empty/no-deny stdout** (allow — name in prose is provenance); (ii) stage a DATA-BEARING-path file containing the operator name and assert the hook **emits deny-JSON** (block — identity in a health-data path is a leak). A hook that blocks (i) has run the identity patterns trunk-wide (the broken behavior); a hook that allows (ii) has failed to scope the identity check to data-bearing paths.

- **Fail-closed / default-deny gate (Security HIGH-1).** The hook MUST FAIL CLOSED: any error in the scan path — `pii_scan` import fails, `scan` raises, the `python3 -c` scan invocation returns non-zero, or the `jq` / `git diff --cached` plumbing fails — MUST emit deny (block), NEVER allow. The existing mirrors use allow-on-error idioms (`2>/dev/null || echo ""`, `|| exit 0`) tolerable for a branch-name annoyance hook but a silent PII bypass at a distribution boundary; this hook does the opposite at the scan path. Gate: the RED-equiv test MUST include a case that makes the scan invocation error (e.g. point the scanner resolution at an unimportable module / force the `python3 -c` to return non-zero) with a planted token staged, and asserts the hook **emits deny-JSON** (blocks). A hook that allows on scan error FAILS this gate.

- **SEC-01(b) shared-scanner reuse gate (THE load-bearing gate; build plan line 241) — DETERMINISTIC stub seam (Fix 5 / QA-F2).** The hook MUST resolve `pii_scan` through a **deterministic env override** (the same `*_PROJECT_ROOT` / module-override pattern the existing hooks use for `PROJECT_ROOT`) — e.g. a `BLOCK_PII_COMMIT_PII_SCAN_ROOT`-style variable (never set in production) that points the hook's `python3 -c` import at the scanner. The RED-equiv test sets that override to a stub `pii_scan` whose `scan` **returns 0 AND writes a sentinel** (a marker file / line the test then reads), and asserts (i) the hook **emits empty/no-deny stdout** (does NOT block) for a staged planted token, AND (ii) **the sentinel was written** (the stub was actually exercised). The sentinel assertion closes the vacuous-pass hole: a `PYTHONPATH`-only shadow can silently fail to take effect (an absolute/`PROJECT_ROOT`-resolved import is not shadowed → the REAL scan runs → the test passes for the wrong reason). **Gate rule:** if the hook still blocks while the stubbed `scan` returns 0, OR the sentinel was not written (stub never ran ⇒ vacuous pass), the reuse contract is unproven and this is a NO-GO. A recipe whose hook greps for PII tokens in bash FAILS this gate by construction.

- **Negative-placement gate (crit 3; project mandate "assert placement, not just existence") — keyed on the SHARED path constant (Fix 4 / Security MED-1 + QA-F4).** The RED-equiv test MUST stage a filled-scaffold value and a `vault/store/` file and assert `git ls-files` lists **0** of them — the data is NOT in the tracked set. This is distinct from crit 1's `git check-ignore` (which asserts the path is ignored); crit 3 asserts the negative placement (the staged value does not reach the tracked set). The filled-scaffold-value path used here, the `.gitignore` exclusion pattern (AC-1), the hook's condition-1 path matcher, and the AC-4 forced-add block MUST all be driven by ONE path/glob constant — AC-3 (negative-placement) and AC-4 (forced-add block) assert against the SAME representative value (one identical path, not two independently-chosen), so the three restatements cannot drift into green-tests-but-broken-boundary.

## Interface Contracts

This task **CONSUMES** a published interface and does not create a new broadly-reused one.

- **Consumes (reuse contract, SEC-01(a)):** `scan(tracked_files) -> int` from `scripts/guard/pii_scan.py` (published by ADR-0001-T1). The hook passes its exact staged-file set as `tracked_files`; `scan` returns the integer operator-PII hit count and emits a `PII-HIT: <path>` line on **stderr** per offending file. **This offending-file channel is pinned by the ADR-0001-T1 RECIPE** (`docs/task-plan/ADR-0001-T1.md`, Interface Contracts "Offending-file channel" + the Cycle-2 Step-6 GREEN `pii_scan.py` step), the producing recipe's implementation contract — NOT by the spec, whose ADR-0001-T1 AC-3 says only "names the offending file" and does not fix the channel/format (4th Upstream Flag). The hook's filename-extraction reconciles against the recipe + the Entry-State as-built capture, not the spec. The hook blocks iff the return is ≥1 (for the token condition). The hook MUST NOT reimplement the token scan in bash — SEC-01(b) (build plan line 241) makes this falsifiable by stubbing `scan` to 0 and requiring the hook to NOT block. ADR-0005-T1 MUST NOT change this signature or channel without Architect review (ADR-0001-T1 RECIPE Interface Contracts, change control). **Scoped invocation (ADR-0005 amended Decision 2026-06-06, `qwj` option iii):** the hook makes TWO scoped calls to this same surface (no signature change) — an agnostic-trunk-wide call (full staged set, empty `identity_config`) and an identity-data-bearing-only call (data-bearing subset, `DEFAULT_IDENTITY_CONFIG`); both pass an explicit file list as `tracked_files`. No `pii_scan.py` change is required — the scoping is the caller's file-list + `identity_config` choice.

- **Exposes:** `.claude/hooks/block-pii-commit.sh` — a **PreToolUse Bash-tool** git-commit gate (mirroring `block-commit-main.sh` / `block-ungated-vault-write.sh`) that **signals a block by printing deny-JSON (`"permissionDecision":"deny"`) to stdout and exiting 0**, and an allow by emitting empty stdout and exiting 0 (NEVER exit non-zero). It denies a commit staging a filled-scaffold value, a `vault/store/` file, or a tracked-file PII token (the last routed through `pii_scan.scan` over the `git diff --cached` staged set), and is fail-closed (any scan-path error denies). **This task does not create a new shared interface beyond the hook** (the hook is a leaf consumer; ADR-0005-T2 depends on the `.gitignore` boundary this task extends, not on a code interface from the hook). **Residual (Fix 1 / Fix 7):** as a PreToolUse Bash hook it gates only AGENT-issued `git commit` Bash calls — human-terminal, IDE, and CI commit paths are NOT gated; this is LOCAL, AGENT-ONLY enforcement with no CI/pre-push backstop (see Deviations / Residual).

**UPSTREAM FLAG: SPEC — AC "non-zero exit" block wording is INVERTED for a PreToolUse hook (Fix 1 / Security HIGH-2)**
- Source: `docs/spec/adr-0004-adr-0007-spec.md` `### ADR-0005-T1` AC-4, AC-5, AC-6 (each says the hook "blocks (non-zero exit)").

**UPSTREAM FLAG: SPEC — AC-2 "`git ls-files`" names the wrong fileset for a pre-commit gate (Fix 3 / Security MED-2)**

- Blocking: No. The recipe scans the staged set; the gate is correct.
