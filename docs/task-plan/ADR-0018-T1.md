# Recipe: Demographic-Form Activation — The Four Orphan Tokens Get Real Inputs (Form Stays Objective-Only)

This task produces CODE: it activates the kept Step-1 "About you" demographic layer of the
intake form. Today the four demographic placeholders are DEAD `_field(..., True)` calls
([vault/design/templates/intake.py:258-266](../../vault/design/templates/intake.py#L258)) that
render a `box ph` static box and POST nothing — outside the `<form method=post action=/upload>`
`capture_form` ([intake.py:408-413](../../vault/design/templates/intake.py#L408)). As a result the
four demographic `SUMMARY_FIELD_SET` tokens `training-age-band` / `sex-for-dosing` /
`bodyweight-band` / `equipment-access-class` ([scripts/plan/router.py:18-23](../../scripts/plan/router.py#L18))
have NO working input — they are ORPHANS (a member of the closed field set with no producer).
This task turns Step-1 into working capture: each demographic input POSTs into `capture_form`,
`capture.persist_capture` routes it BY ITS DATA CLASS, and `summarize` derives each of the four
tokens from a real submitted value (0 orphans, against today's baseline of 4). It RECONCILES the
`equipment-access-class` DOUBLE-SOURCE collision (`_RAW_TO_FIELD["postal-address"] =
"equipment-access-class"` already maps via `_region_class`, [router.py:82,293-295,304](../../scripts/plan/router.py#L82),
AND ADR-0018 now wires the demographic equipment selection to the same token). The form stays
OBJECTIVE-ONLY: after activation `capture_form` carries demographics + content-upload affordances
and **0 rich-section fields** (goals/training/nutrition/supplement/peptide are CHAT-only, the
Wave-A `/chat` panel). This is a STORE-SURFACE task — the four demographic writes land in
`scripts/store/`, so `docs/checklists/store-adversarial-tests.md` is binding. The TDD Steps follow
the standard RED/GREEN/REFACTOR/REGRESSION cycle.

**Decision on `bodyweight-band` (no raw kg ever stored).** Capture the bodyweight as a de-identified BAND directly — either the form offers a band `<select>` (coarse weight bands) whose value IS the `bodyweight-band` token (pass-through), OR the form takes a raw value the CAPTURE seam coarsens to a band before any `store.append` (so no raw-kg store item is ever written). The recipe's GREEN step picks the band-select shape (simpler, and it keeps `bodyweight-band` a pass-through `WIRED_TOKENS` member with a `_BOUNDED_ENUMS` entry, mirroring `recovery-status-band`). Rationale: a raw-kg store item would be a named-excluded raw-PII surface needing its own derivation; the band-select avoids storing any raw weight, and the per-token output scan (criterion 2) proves the emitted token carries no raw value.

**Decision on the `equipment-access-class` reconciliation (AC 3).** Pin ONE source: the demographic equipment selection. The existing `postal-address → equipment-access-class` derivation ([router.py:82,293-295,304](../../scripts/plan/router.py#L82)) is REMOVED (the demographic selection is the authoritative, non-inferred source; the postal-address inference was a coarse proxy now superseded by a direct objective input) — OR kept ONLY as a documented distinct fallback under a DIFFERENT token if a fallback is genuinely needed (escalate if so; the recipe's GREEN removes it). Removing the `_RAW_TO_FIELD["postal-address"]` entry + the `_region_class` / `_FIELD_DERIVATION["equipment-access-class"]` derivation makes `equipment-access-class` a pass-through `WIRED_TOKENS` token fed only by the demographic selection. The disjointness tripwires stay green because `postal-address` remains in `EXCLUDED_RAW_PII` (it is still named-excluded raw PII, just no longer a derivation source). **If removing the postal derivation breaks an existing test, HALT and escalate** — do not silently delete a tested behavior; surface the reconciliation choice.
