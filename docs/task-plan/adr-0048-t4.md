# ADR-0048-T4 — Onboarding credential UI (SPA screen-wizard step 9 + My Info Connections & Keys)

## Goal

Extend the SERVED SPA (`vault/design/templates/app_view.html`, rendered by `app_shell.render`) with the two
credential-onboarding surfaces faithful to the operator-signed-off mockup
`prototype/credential-onboarding-mockup.html`: **Surface A** — extend the `screen-wizard` **step 9**
(currently "API key", `app_view.html:751-768`) into "Connect your data & keys"; **Surface B** — extend
`screen-profile` (`app_view.html:607-628`) with a "Connections & Keys" panel. Both are static render
shells whose "Connect"/PAT/OAuth affordances POST to the already-merged ADR-0048-T2 connect-start route +
ADR-0048-T3 per-source write/status handlers (this task RENDERS, does not re-implement). Skippable +
resumable, secret-free (no `client_id`/`client_secret` field), Garmin manual-path, inline-only, frozen-six
untouched.

## PF-S142-01 retarget — read this first (why the served SPA, not `intake.py`)

The spec was AMENDED S143 (PF-S142-01, bead `a-plus-maxing-2awb`): the prior Surface-A target `intake.py`
is an UNSERVED CLI-only 6-step artifact — `server.py` serves ONLY `generate.run('app')` (the SPA) at
`GET /` and 404s every other GET (`server.py:133/:139`); `generate.py` maps `'app'→app_shell` and
`'intake'→intake` as INDEPENDENT templates (`:27`); `app_shell.py` references `intake.py` nowhere. The
LIVE intake surface is the SPA's `screen-wizard` (`app_view.html:631`), which is ALREADY a 9-step flow
whose **step 9 is "API key"** (`app_view.html:649` stepper label, `:751` the `wstep`, header "Step 1 of
9" `:634`). So the mockup's "Step 9 of 9 — Connect your data & keys" maps DIRECTLY onto the existing
step 9 — **extend it, do NOT renumber or rebuild.** (The mockup's 9-step framing is ACCURATE for the
served surface; the prior recipe's "append to the 6-step stepper" reconciliation was grounded on the
wrong file.) A recipe premise "modify surface S" grounds against the SERVED path to S — which route
renders it — never S's mere file-existence (the PF-S142-01 guard).

## The served-render seam (grounding the two surfaces)

`app_shell.render(store_read=None, *, status=None, _today=None, _root=None)` (`app_shell.py:546`) reads
`app_view.html` (`_VIEW.read_text`, `:575`) and fills `<!--MARKER-->` placeholders (`.replace`) —
`<!--DOC_CARDS-->`, `<!--PLAN_ZONE-->`, `_prefill_form`, `_wizard_prefill_script`. The completeness gate
matters for WHICH surface renders:
- **Surface A (`screen-wizard` step 9)** is PRESERVED in every render — `_lock_to_create_profile`
  (`app_shell.py:407`) strips only the four `_PLATFORM_SCREENS` (`:80`), NOT `screen-wizard`/
  `screen-equipment` (`:79` comment). So step 9's markup is present in a standalone/incomplete render;
  the Surface-A test can render `app_shell.render([])`.
- **Surface B (`screen-profile`)** is one of the four PLATFORM screens — it is STRIPPED when the profile
  is INCOMPLETE (`_intake_complete([])` False → `_lock_to_create_profile` removes it, `:585/:407`). So
  the Surface-B test MUST render a COMPLETENESS-COMPLETE store (seed via the house helper
  `_seed_complete_profile`/`_complete_profile_readings`, `tests/serve/test_app_shell.py:1444/:1452`), or
  `screen-profile` is absent and the assertion falsely REDs (QA-M2).

**Connection render-state (Architect F3):** per-source "connected" is KEYCHAIN-derived, NOT
`store_read`-derived — `server.py:1009` `_tracker_status` computes it as
`{source: oauth_pull._read_oauth_credential(source) is not None for source in oauth_pull._MANIFESTS}`.
Surface B's per-source status renders from an INJECTED connection map (mirror the `status=` injection
seam, `app_shell.py:572`), defaulting to all-not-connected for a standalone render; the server supplies
the live map from `_tracker_status`. Do NOT derive "connected" from `store_read` / `_default_status` /
`_intake_complete` (those read readings, a category error).
