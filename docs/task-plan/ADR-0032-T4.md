# Recipe: Care-Assistant→DNA-Research-Agent Hookup (STUB) — De-Associated, Allele-Agnostic Per-Variant Query + the Fail-Closed De-Association Guard + the 0-Spend Stubbed Dispatch

A Wave-2 task building ONE NEW module `scripts/genetics/research_query.py` (`test ! -e
scripts/genetics/research_query.py` → ABSENT [VERIFIED]) — the care-assistant→DNA-research-agent
hookup wired UP TO the dispatch only. It is the CROWN-JEWEL egress surface of ADR-0032: the ONE new
named egress class (generic, operator-de-associated, ALLELE-AGNOSTIC genetic-variant literature
queries) that ADR-0032 adds to ADR-0001, and nothing else. T4 builds three functions:

1. **`build_variant_query(gene, rsid) -> str` — the generic, allele-agnostic per-variant query.** It
   carries the variant (gene + rsID) and asks about the implications of EACH genotype — a question
   anyone could ask about the variant (the ADR's example shape: "current 2026 evidence on ACTN3
   rs1815739 — the implications of each genotype for strength training"). The signature takes NO
   allele parameter: the operator's own allele call NEVER enters the query by construction. The exact
   wording is implementer discretion (NFR-6); the PINNED contract is the gene + rsID presence + the
   no-allele-param signature.
2. **`assert_query_de_associated(query, *, identity_config=...)` — the fail-closed de-association
   guard.** It RAISES (fail-closed) if the query carries an allele-call pattern (`\([ACGTDI]+;[ACGTDI]+\)`
   or a bare `genotype is <allele>` allele statement) OR an operator-identity token. The identity scan
   reuses `pii_scan.scan_text` — the SAME operator-PII scanner `router._rx_interaction_classes_token`
   raises on ([`router.py:202`](../../scripts/plan/router.py) [VERIFIED]) — with `identity_config`
   defaulting to `pii_scan.DEFAULT_IDENTITY_CONFIG` (mirroring `summarize` at
   [`router.py:540`](../../scripts/plan/router.py) [VERIFIED]). A `build_variant_query` output PASSES
   the guard (the positive control); an injected allele/identity REDS it (the raising negative control).
3. **`dispatch_variant_research(gene, rsid, *, dispatcher=None)` — the STUBBED dispatch.** It REFUSES
   an `EXCLUDED_VARIANTS` variant (APOE/DRD2/BDNF — never built, never dispatched); otherwise it builds
   the query, GUARDS it (fail-closed via `assert_query_de_associated`), and either (a) `dispatcher=None`
   → a 0-spend DRY-RUN returning the would-be de-associated query (the live `aplus-research` Agent
   dispatch is OQ-1), or (b) calls the injected recording `dispatcher` EXACTLY ONCE with the guarded
   query. T4 records the query / dispatches to the stub — it makes NO live `aplus-research` call.

The research engine `aplus-research` runs as a Claude Code agent dispatch on the SUBSCRIPTION/agent
research lane the project's existing library work already uses — NOT the no-train `ModelClient`
backend (`scripts/model/client.py`, the single site `_ClaudeNoTrainBackend` imports the model SDK,
[`client.py:6-8`](../../scripts/model/client.py) [VERIFIED]). T4 wires UP TO that subscription-lane
dispatch and STUBS it; the live, metered variant research is OQ-1 (0 live spend). T4 touches NO
`client.py`, NO `router.py`, NO engine file: it is a NEW `scripts/genetics/` module that imports only
T2's `scripts.genetics.variants` curated/excluded set + `scripts.guard.pii_scan` (the read-only PII
scanner) — no outbound HTTP client, no model SDK.

The build is MOCK/STUB-tested at 0 live spend: a recording `dispatcher` callable records the query it
receives; `assert_query_de_associated` runs `pii_scan.scan_text` over an in-memory string (no file,
no network); no live API, no key, no `aplus-research` dispatch, no network socket.
