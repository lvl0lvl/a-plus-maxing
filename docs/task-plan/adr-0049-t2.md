## Consumer-contract grounding (the seams this task wires onto — the PF-S141-02 guard)

**(C1) The trigger's target — `POST /plan-loop` EXISTS and is already CSRF-gated (no new spend route).**
`server.py:235` routes `/plan-loop` → `_do_plan_loop` (`:865`). Its contract, verbatim from the live
docstring: "Fire one automated plan-evolution loop tick through the full-composition front door; answer
JSON. The cadence/manual loop trigger (ADR-0036-T1). It drives `plan_loop.regenerate` with the instance
loop `dispatch` + `deid_client` seams … over `self.store_root` — binding the trigger to
`run_orchestrated` -> `plan_driver.drive` -> the composed `gate_dispatch` + the five `orchestrate`
cross-domain holds. It is DISTINCT from `_do_generate_plan` and does NOT call it: the loop path never
reaches the screened-only route (the anti-degradation guard). … **CSRF gate (mirrors `_save_key` /
`_do_generate_plan`): a non-`application/json` POST is refused 415 BEFORE any work** — a cross-site
CORS-simple `text/plain` POST cannot drive the highest-spend loop tick (every specialist + judge + lens
dispatch)… Seams-absent state (mirrors `_do_generate_plan`)…". So AC-5 is satisfied BY REUSE: the
Update-now button POSTs `/plan-loop` with `Content-Type: application/json` (client-side `fetch`,
mirroring the T4 `_trackerConnect` fetch shape). **Do NOT add a second spend route.**

**(C1a) `/plan-loop`'s RESPONSE SHAPE — it is NOT a `_save_key`-shaped `{ok}` route (Arch-F1, the
grounding I initially missed — the PF-S141-02 return-shape guard).** `_do_plan_loop` (`server.py:865`)
answers, per family: 415 `{"results": {}, "error": …}`; **200 degraded `{"results": {}, "degraded":
true, "reason": "loop-dispatch-unavailable"}`** (the ONLY reachable 200 today — C2, `loop_dispatch =
None`); 200 success a bare `result` from `plan_loop.regenerate` (unreachable until `23xr`); 200 exception
`{"results": {}, "degraded": true, "reason": …}`. **There is NO `ok` field on any path.** So the trigger
JS gates on `!d.degraded && !d.error` for success and treats `d.degraded === true` as the honest
not-yet-available state keyed on `d.reason` — do NOT write `if(d.ok)` (undefined → paints failure always)
and do NOT fall back to the HTTP `r.ok` (true on any 200 → paints success on the degraded body: the exact
T4-A1 failure). Since the loop is degraded today, the degraded state is the ONLY reachable click outcome
(AC-1b covers it).

**(C2) The loop is HONESTLY DEGRADED — the trigger issues 0 metered spend today.** `server.py:175`
`loop_dispatch = None`; `scripts/serve/__main__.py:58/91/95` document that `main()` passes no
`loop_dispatch` because the metered dispatch is specialist-only and cannot serve the loop's judge/lens
name-spaces (the ADR-0049-T1 Tier-3 REJECT; bead `a-plus-maxing-23xr` is the arming precondition). So a
click fires ONE loop tick that reaches `_do_plan_loop`'s seams-absent path and answers an honest
no-plan JSON — **0 metered spend, 0 dispatches**. AC-1's "exactly ONE re-gen per explicit request" is
testable in this state (assert the loop entry-point is invoked exactly once per request, 0 times with
no request). Do NOT arm `loop_dispatch` (that is `23xr`, explicitly out of scope) and do NOT assert
metered spend.

**(C3) The schedule SETTING records INTENT — it does NOT arm launchd.** `scripts/runner/schedule/activate.py`
(ADR-0039-T3) is the **operator-owned** activation surface for the weekly cadence runner
(`RUNNER_LABEL = "com.aplusmaxing.cadence-runner"` `:40`; `enable()` renders the launchd plist; ships
DISABLED BY DEFAULT; `active_entry_count()`/`status()` read the REAL scheduler state). Spec AC-3 says the
setting "records the weekly cadence **intent** read by the schedule surface" — so this task RECORDS the
intent (a store reading), it MUST NOT call `activate.enable()`. **AC-4's glzi gate is live and real:**
`activate.py:44-52` is LABEL-REGISTRATION ONLY for `DAILY_MONITOR_LABEL` — there is NO daily enable path,
and the comment warns an `enable(DAILY_MONITOR_LABEL)` "would arm the WEEKLY spending runner under a
daily label". So Daily renders inert/"coming soon" and arms nothing.

**(C4) The persistence sink (Arch-F6/F7 amended).** There is no existing non-secret setting route.
CONSTRUCT the reading IN `server.py` conformant to `keying.LINE_FIELDS = ("item","timepoint","source",
"value")` (`scripts/store/keying.py:35` checks field PRESENCE only — there is no item allowlist, so
`plan-update-cadence` needs no keying registration → no frozen-six collision, AC-6 safe). Do NOT import
the private `capture._reading` (a cross-module boundary violation) and do NOT redefine the line shape
(`keying.py` forbids a second key definition). **Use `source: "settings"`, NOT `"intake"`** — the source
tag names the PRODUCING surface (`intake`/`rx-bpmh`/`care-review`/…); a Profile settings write is not an
intake capture, and tagging it `intake` bakes a false origin into the dedupe identity. Append through the
UNCHANGED `store.append` sink (`server.py:626` — "no second sink/gate/key"). **The store is append-only**
(`store.py:134` never overrides; each pick is a fresh `_now()` = a new series point, an intended cadence
history): so "the current cadence" = the LAST reading by timepoint (`store.read('plan-update-cadence')`
sorted, take the last `value`); unbounded growth per click is INTENDED (ADR-0002 audit trail), not a
leak. The new `/settings/schedule` route mirrors `_save_key`'s route+gate shape (`server.py:944`)
INCLUDING its `application/json` 415 gate.
