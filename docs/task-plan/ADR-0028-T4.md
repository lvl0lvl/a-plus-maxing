# Recipe: `/generate-plan` SKILL Reconcile to `plan_step.py` + NEW Value-Scan Over GATE/ADJUDICATOR Yield Payloads

Reconcile the `/generate-plan` skill (`.claude/skills/generate-plan/SKILL.md`, Modify) to drive the
shared driver THROUGH the `plan_step.py` step-harness (T3's per-round drive) instead of holding a live
`plan_driver.drive` generator object directly (a generator cannot pause for the Agent tool). The skill
fulfils each yielded typed request (`AUTHOR` / `GATE` / `REAUTHOR` / `ADJUDICATOR`) via a SUBSCRIPTION
agent dispatch and re-calls the harness with the appended envelope — it NEVER re-hosts the loop,
re-composes the disposition, or re-derives the adjudication release (the no-fork-at-the-skill
constraint).

The NEW value-scan: a value-level `pii_scan.scan_text_full` over the GATE yield payload (the assembled
plan), the ADJUDICATOR yield payload (the safety finding), and the REAUTHOR yield payload (the
constraint) — the FIRST-EVER scan over these DERIVED artifacts. The AUTHOR seam is structurally clean
(the orchestrator only holds the de-identified summary), but the assembled plan / finding / constraint
are DERIVED from the engine and their PII-freeness is transitive-but-unverified. 0 raw-PII in any
yielded payload; fails closed (the payload does NOT leave the process) on a seeded planted leak. The
scan reuses `pii_scan.scan_text_full` — the SAME value-scan the de-id-IN boundary uses
([deid_in.py:102]), the precedent shape — applied at the HARNESS boundary where the yielded request
payload is serialized before it leaves the process.

**What IS vs ISN'T mock-testable (load-bearing):** the LIVE subscription dispatch over REAL agents (the
skill dispatching real specialist + lens agents per round) is the S94 operator-present attestation, NOT
a mock-test target. The recipe's TESTABLE cycles are (a) the thin Python value-scan glue at the harness
boundary (the scan over the GATE/ADJUDICATOR/REAUTHOR yield payloads, RED-capable on a planted leak) +
(b) the dispatch-protocol + S94-deferral DOC in the skill prose. The glue test drives a FIXTURE
`dispatch`, never a real agent.

**WHERE the value-scan lands (SE's call per the harness boundary — stated assumption):** the spec File
Manifest names `scripts/plan/plan_step.py` (created in T3) as the value-scan's home, with the harness
boundary as where "the yielded request payload is serialized before it leaves the process." This recipe
ASSUMES the scan lands in `scripts/plan/plan_step.py` (the harness boundary) — the same file the skill
drives through, so the scan covers every yielded payload on the harness drive path the skill uses. The
alternative (`plan_orchestrator.py`) was rejected: the orchestrator is the in-process reference consumer
(test/API mode), but the SKILL drives via the HARNESS, so a scan only in the orchestrator would NOT
cover the skill's drive path. The harness is the single boundary both consumers cross. (OQ-2-of-this-task,
resolved toward the harness per Ask-vs-Proceed step 3 — same interface, simpler placement; stated, proceed.)

**Build dependency vs runtime order (load-bearing):** the harness + the skill drive a FIXTURE consumer
in tests (a fixture `dispatch` + fixture GATE raw verdicts + fixture REAUTHOR/ADJUDICATOR envelopes),
never a live raw intake. At RUNTIME only the skill front-door feeds a real raw intake into the de-id
boundary, and only AFTER `deid_in` returns the de-identified summary. The SE/Security verifier confirms
at execute time that the build's drivers are fed ONLY fixtures (no live de-id-IN or live Agent-tool
dispatch introduced into the build path) — a watch-item, not a one-time check.

This task modifies `.claude/skills/generate-plan/SKILL.md` (prose) + `scripts/plan/plan_step.py` (the
value-scan code add) + `tests/plan/test_generate_plan_skill_glue.py` (the glue/value-scan test). It
touches NO inner-engine module (numstat = 0) and leaves `scripts/plan/deid_in.py` UNCHANGED (numstat =
0 — the NEW scan is a different surface, additive not a replacement). 0 live agent dispatch, 0 live spend.
