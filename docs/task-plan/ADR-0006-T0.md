## Risk Pre-Check

The spec task block carries two risk mitigations; both gate this spike's design content BEFORE the GREEN-equivalent describes the report. A spike that selects a mechanism which cannot fail on raw PII would silently re-open the exact risk it exists to close.

- **Risk ADR-0006 Negative (plan reasoning is the one PII-touching dispatch; constrained by the no-train summaries path + the store read model, narrowing the model's input).** Gate: the report's **Summary Field-Set** MUST enumerate a NAMED, closed field list AND explicitly name which raw-PII fields are EXCLUDED (criterion 2). Before the GREEN-equiv describes any other section, the RED-equiv (Step 1) MUST include a content assertion that the excluded-raw-PII list is non-empty and names concrete fields — a Summary Field-Set that says "relevant fields" or omits the exclusion list fails this gate (it would let the dispatch reason over un-narrowed input, the negative consequence).
- **Constraint D1→ADR-0006 (no-train summaries — the spike's Falsifiable Check is the basis of the 0-raw-PII criterion the downstream `ADR-0006-T1`/`ADR-0006-T2` tasks carry).** Gate: the report's **Falsifiable Check** MUST return a pass/fail result AND fail when an excluded raw-PII field appears in a model-bound dispatch (criterion 5). Before the GREEN-equiv describes the Recommendation, the RED-equiv MUST include a content assertion that the Falsifiable Check states (a) a pass/fail return and (b) a fail-direction on a planted excluded-raw-PII field — a check that only describes the pass direction, or that returns prose rather than pass/fail, fails this gate (it could not turn red, mirroring the no-op-guard failure ADR-0001-T1 exists to prevent).
- **Egress-occurrence vs payload-PII-content discrimination (criterion 4/5; the load-bearing distinction the egress guard does NOT itself supply).** The ADR-0001-T1 egress guard's `run(callable)` contract observes whether an OUTBOUND CALL CARRYING STORE CONTENT OCCURRED across the whole invocation — it is a call-occurrence signal, NOT a payload-field-set inspector. A legitimate no-train model dispatch IS itself an outbound call, so `egress_guard.run` wrapped around the dispatch would fail ANY model dispatch (raw-PII present or not) — making the bare guard non-discriminating as the router's raw-PII detector. Gate: the report's **Routing-Enforcement Mechanism** MUST specify HOW raw-PII-in-payload is discriminated DISTINCT from the egress guard's call-occurrence signal — it MUST name a payload-FIELD-LEVEL check (the dispatch payload is constructed ONLY from the Summary Field-Set tokens, plus a raise-on-injected-raw-PII check that rejects any payload field outside the field-set BEFORE the model-bound send), with the egress guard retained as a COMPLEMENT that catches accidental store-content egress on non-model paths, not as the raw-PII discriminator. Before the GREEN-equiv describes the Recommendation, the RED-equiv (the criterion-4 assertion) MUST require the report to RESOLVE this discrimination: a report that merely "names a fail-direction" without resolving the egress-vs-payload distinction (i.e. one that leans on `egress_guard.run` around the dispatch as the raw-PII detector) FAILS this gate, because that mechanism cannot distinguish a clean dispatch from a raw-PII-bearing one.

A placeholder report (the six section headers present but a section reading "TBD" / "relevant fields" / a Falsifiable Check with no fail-direction), OR a report whose Routing-Enforcement Mechanism leans on the egress guard's call-occurrence signal as the raw-PII detector (without a distinct payload-field-level check), FAILS this Risk Pre-Check. The field-set-excludes-named-raw-PII assertion, the falsifiable-check-fails-on-raw-PII assertion, and the egress-occurrence-vs-payload-PII discrimination assertion are first-class RED-equiv targets in Step 1, not optional add-ons.
