# Spec: Large-Change Hold-Until-Confirm via a Bounded Confirmation-Pointer (ADR-0040)

## Component Overview

This spec implements ADR-0040 — the TRUE large-change hold the ADR-0036 loop left open as OQ-4 (its T4 shipped only an ADVISORY that its own docstring calls "NOT a hold … the true hold-until-confirm is the deferred follow-on ADR-0036-T4b", [confirm.py:96-107](../../scripts/serve/confirm.py)). A materially-large automated re-gen (`_change_magnitude(...) >= LARGE_CHANGE_THRESHOLD_DOMAINS`, currently `3` of the closed 4-set `PLAN_DOMAINS`, [plan_loop.py:50](../../scripts/serve/plan_loop.py), [plan_schema.py:49](../../scripts/store/plan_schema.py)) is still RECORDED through the ADR-0032-frozen record path — the WRITE spine (`record_plan` → `store.append`) stays byte-frozen — but it does NOT become the standing plan and is NOT tailored/egressed until an explicit operator confirm. The hold is enforced at the STANDING-PLAN RESOLVER and the TAILORING SEAM, not the record write: (1) a bounded `(domain, plan_date) → decision` confirmation-pointer marks each held domain `pending`; (2) EVERY direct standing-plan reader applies a shared caller-side pre-filter that drops an unconfirmed `plan::<domain>` reading BEFORE the pure resolve, so a held re-gen resolves `NO_PLAN_TODAY` (plan `None`) — NOT a walk-back to the prior-dated plan — and 0 surfacing in the week/month horizon block; (3) the debounce (`_last_regen_date`) COUNTS the held re-gen (the ONE reader excluded from the skip) so no pending-over-pending storm fires; (4) `_post_promote_tailoring` is GATED so a held domain is neither tailored nor egressed; (5) an explicit operator CONFIRM flips the pointer, after which the reader stands the plan and the DEFERRED tailoring fires exactly once (idempotent per `(plan, date)`, ADR-0037). Decline / no-action leaves the held reading skipped (fail-closed: today stays `NO_PLAN_TODAY`, never the unconfirmed swap standing).

**OQ-1 realization (GROUNDED pick — a new bounded `plan-confirm::<domain>` store stream, NOT the ADR-0010 D2-extras flag).** Two homes were weighed against the live tree. Realization (b), a `pending_confirm` flag carried on the plan VALUE via the D2 open-on-extras seam, would avoid the ADR-0038 amendment — but it does NOT cleanly avoid coupling confirm-state into the immutable authored plan value, and it is not buildable under the freeze: the plan value is authored by the specialist and written by the ADR-0032-frozen record path INSIDE `run_orchestrated`; `regenerate` hands `run_orchestrated` the raw intake, never the plan dicts ([plan_loop.py:173-179](../../scripts/serve/plan_loop.py)), so the loop cannot inject the flag pre-promote without editing the frozen engine, and FLIPPING the flag on confirm would require a post-promote `correct_plan` re-record of the plan value — a write-path mutation that couples confirm-state into the authored plan document (the exact incoherence OQ-1 names). Realization (a), a new bounded `plan-confirm::<domain>` stream carrying exactly `(domain, plan_date) → decision`, keeps the record WRITE path byte-frozen (the marker is appended by the loop LAYER via the unchanged `store.append` sink under a DISTINCT item id — `record_plan` and the plan value are untouched) AND keeps confirm-state coherent (it lives in its own stream, single responsibility, never coupled into the plan value); its cost is the ADR-0038 no-new-store-stream relaxation. **The pick is (a).** Per AR-006, the `amends ADR-0038` edge (frontmatter + Related Decisions + DAG) therefore **STANDS** — it is NOT retracted, because a new bounded stream IS added; it is the opposite of the open `plan-arc::`-class content stream ADR-0038 rejected (it owns one fact no existing stream carries and that cannot be derived).

**EXTEND-NOT-REBUILD + fail-closed + 0-spend (hard constraints).** The frozen inner plan engine (`scripts/plan/{orchestrate,pipeline,assemble,generate_plan,adjudicate,adjust,track}.py`, `scripts/plan/plan_driver.py`, `scripts/plan/plan_orchestrator.py`) and the `record_plan`/`store.append`/`keying.py` WRITE path stay byte-frozen (`git diff --numstat origin/main` = empty for that glob). The hold is an ADDITIVE read-side pre-filter + a bounded confirmation-pointer + a tailoring-seam gate ONLY. `resolve_plan`'s pure date-equality body stays byte-unchanged (the pre-filter runs on the readings BEFORE the call); the ONE store-module read-function edit is `read_plan` (AR-007 — a read-side guard, not a write-path/engine line), which the frozen `track.py` and `maintained.py` inherit transitively without being edited. Everything is built + mock/fixture-tested at 0 live spend; the loop's live activation stays operator-gated (ADR-0039's disabled-by-default scheduled runner). The operator-present LIVE run (real key + real data + spend) is recorded in the Unresolved Concerns table as a Deferred downstream attestation, NOT a task.

How it fits: the hold sits on the ADR-0036 re-gen path (`regenerate` → the promoted-then-`>= threshold` branch, [plan_loop.py:194-206](../../scripts/serve/plan_loop.py)); it adds a confirm gate in front of standing + tailoring and does not re-host the loop, its debounce, or its safety composition. It CONSUMES the built S105 dynamic-loop surfaces (`plan_loop.py`, `horizons.py`, `tailoring.py`) and the confirm-curation serve precedent (`_do_confirm_extraction` / `_do_confirm_curation`, [server.py:197-202,542-591](../../scripts/serve/server.py)). Downstream it hands the confirm SURFACE/UX (OQ-5) to a later serve/front-end surface — out of scope here by construction.

Informing artifacts (load on demand): the source ADR (`docs/adr/ADR-0040-large-change-hold-until-confirm.md`), the loop set it depends on (`docs/adr/ADR-0036-automated-plan-evolution-loop.md`, `ADR-0037-care-agent-plan-tailoring.md`, `ADR-0038-plan-time-horizons.md`, `ADR-0039-scheduled-agent-runner.md`), the frozen-spine authority (`docs/adr/ADR-0032-dna-aware-planning.md`), the store-adversarial mandate (`docs/checklists/store-adversarial-tests.md`), and the format exemplar (`docs/spec/adr-0036-0038-dynamic-plan-loop-spec.md`).
