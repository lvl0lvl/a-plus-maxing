## ADR-0029: Adopt the Single-File Inline-Asset SPA (`app.html`) as the V1 Operator Front-End, Superseding the Intake Wizard Presentation

> **Y-Statement:** In the context of a V1 operator front-end that is today a fragmented multi-step `intake.py` wizard while an operator-approved single-file SPA (`app.html` — a four-screen left-nav shell) exists but carries off-file asset references the `render.emit` inline-only guard refuses (a lucide CDN load and a bare-path `images/body.png` image), facing the tension between the unified-navigation UX cohesion the S98 design phase required and the local-first / inline-asset / 0-external-request posture the serving guard enforces — alongside the obligation to preserve the ADR-0018 form/chat split and the crown-jewel PII boundary — we decided to adopt `app.html` with its off-file assets vendored inline as the front-end, served over the existing loopback server, superseding only the wizard PRESENTATION, to achieve one coherent self-contained front-end surface that passes the inline-asset guard and changes no backend contract, accepting that those off-file references must be inlined — lucide vendored, the bare-path image inlined as a `data:` URI or removed — before it can be served, that a single-file SPA is a larger maintenance surface than per-surface templates, and that ADR-0018-T1's wizard-targeted recipe must be retargeted.

### Context

The V1 operator front-end today is the multi-step `intake.py` wizard. The loopback server serves it as the GET `/` body — that body IS `generate.run('intake')`'s rendered HTML, and the server "adds a transport, not a new wizard" ([server.py L9-11, L70-81](../../scripts/serve/server.py) [VERIFIED]). Each operator surface (intake, dashboard, plan, specialist chat) is reached as its own template, not a single shell. During the S98 design phase the operator rejected that fragmentation, and a single-file SPA — `prototype/app.html` — was hand-built as the approved replacement: a persistent left-nav shell with four screens, `Dashboard` / `Upload Documents` / `Plan` / `Chat with Team` ([app.html L272-275](../../prototype/app.html) [VERIFIED]).

Several forces pull against each other across more than one perspective. From the operator's side, the four fragmented surfaces want to become one coherent navigation shell — the cohesion the S98 design phase set out to deliver. Pulling the other way, the serving path is a local-first, inline-only boundary that the SPA-as-built violates: `render.emit` assembles one self-contained local HTML file and, before writing, scans every asset reference at its syntactic position; if any resolves off-file — `_is_external` flags `http(s)://`, protocol-relative `//cdn`, AND bare paths, with only `data:` URIs and `#fragments` passing — it RAISES and writes nothing ([render.py L46-53, L113, L172-178](../../scripts/generate/render.py) [VERIFIED]; `_ASSET_ATTRS` at [render.py L37](../../scripts/generate/render.py) [VERIFIED]). The current intake template is served through that guard with 0 external asset references "(render.emit refuses otherwise)" ([intake.py L1-7](../../vault/design/templates/intake.py) [VERIFIED]) — but `app.html` carries TWO off-file references render.emit would refuse: the lucide CDN load `https://unpkg.com/lucide@latest/dist/umd/lucide.min.js` ([app.html L411](../../prototype/app.html) [VERIFIED]) AND a bare-path image `<img src="images/body.png">` whose bare `src` `_is_external` flags exactly as it flags the CDN URL ([app.html L292](../../prototype/app.html) [VERIFIED]; `_ASSET_ATTRS` includes `src`, [render.py L37](../../scripts/generate/render.py) [VERIFIED]). From the data-subject's side, the PII boundary must not move: ADR-0016 already relaxes egress only for the live `/chat` turn while persisted facts stay de-identified ([ADR-0016 Decision L24](ADR-0016-intake-conversation-egress-relaxation.md) [VERIFIED]), and a new front-end must introduce no new outbound class. From the maintainer's side, the backend contracts the SPA would consume are already accepted and unchanged — the loopback transport (ADR-0013), capture/persist routing (ADR-0014), `/chat` egress (ADR-0016), the conversation→store extractor (ADR-0017), and the planner's de-identified `SUMMARY_FIELD_SET` (ADR-0019) — and that front-end-shell decisions ARE recorded as ADRs here is precedent: the 7-zone dashboard shell (ADR-0009, accepted) and the unified-maintained-HTML output (ADR-0025, proposed) are both shell/output decisions ([ADR-0009 L3](ADR-0009-dashboard-visual-shell-seven-zones.md) [VERIFIED]; [ADR-0025 L8, L24](ADR-0025-unified-maintained-html-output.md) [VERIFIED]). The decision is therefore which front-end SHELL is served — not a backend, data-flow, or trust-boundary change.

### Decision

Adopt the single-file inline-asset SPA `app.html` — a persistent left-nav shell with four screens (`Dashboard`, `Upload Documents`, `Plan`, `Chat with Team`) — as the V1 operator front-end, served as the GET `/` body of the existing loopback server, with lucide (and every other asset) vendored INLINE so the served file carries 0 off-file references. This supersedes the multi-step `intake.py` wizard PRESENTATION only; the ADR-0018 form/chat split DECISION, the ADR-0001/0005/0016 PII boundary, and the ADR-0013 loopback transport are RETAINED. Intake (the `Upload Documents` screen, realizing the form/chat split) is the first surface wired; the other screens' live-data wiring is out of scope here.

### Rationale

The choice was evaluated against three alternatives — keep and activate the existing wizard (A), a multi-page app (B), and `app.html` as-is with the CDN lucide load (C) — across three binding criteria the context makes load-bearing: UX cohesion (one coherent navigation surface vs. fragmented surfaces), change cost, and local-first / inline-asset compliance (does the served HTML pass the render.emit guard with 0 off-file references). A fourth signal, alignment with ADR-0025's single self-contained-HTML output grain, is read as a COMPLEMENTARY directional alignment, not a binding criterion: ADR-0025 is `proposed` and governs the maintained PLAN output, not this front-end shell, so it is a shared direction the front-end moves WITH, not a constraint it must satisfy.

On **UX cohesion**, the SPA wins and the wizard cannot close the gap. Activating the existing wizard (A) is the smallest change — the recipe is approved and nothing new is served — but it leaves the four surfaces fragmented and re-delivers exactly the multi-step wizard UX the S98 design phase was convened to replace ([app.html L272-275](../../prototype/app.html) [VERIFIED] is the unified-nav shell A does not provide). A multi-page app (B) gives each surface its own page but duplicates nav state and per-page JavaScript and delivers no unified left-nav shell; it also runs counter to the single-self-contained-file DIRECTION ADR-0025 adopts for the maintained PLAN output ([ADR-0025 Decision L24](ADR-0025-unified-maintained-html-output.md) [VERIFIED]) — a complementary signal, not a binding front-end constraint, so B's rejection rests on the duplicated nav-state/JS and the missing unified shell. On **local-first / inline-asset compliance**, the as-built artifact fails and must be repaired: `app.html`'s unpkg lucide load is an off-file reference, so render.emit RAISES and writes nothing — the file is unservable over the existing transport until its off-file references are inlined — vendoring lucide AND inlining-or-removing the bare-path `images/body.png` image ([app.html L411, L292](../../prototype/app.html) [VERIFIED]; [render.py L46-53, L172-178](../../scripts/generate/render.py) [VERIFIED]). Adopting it as-is (C) is therefore rejected by constraint, not by preference: the served intake template already proves the boundary is real and enforced, carrying 0 external references because render.emit refuses otherwise ([intake.py L1-7](../../vault/design/templates/intake.py) [VERIFIED]). On **change cost**, A is cheapest and the chosen path is dearer — building the SPA and vendoring lucide — a cost accepted for the cohesion A cannot deliver. On **directional alignment with ADR-0025** (complementary, not binding — ADR-0025 is `proposed` and governs the maintained PLAN output, not the front-end shell), a single self-contained inline-asset file is the same philosophy ADR-0025 adopts for that output, so the SPA moves WITH an existing direction rather than against one — a tie-breaking signal, not the reason any alternative is rejected.

The chosen path is `app.html` with lucide vendored inline AND the bare-path `images/body.png` inlined (`data:` URI) or removed: it is the only option that delivers the unified-nav cohesion, passes the render.emit inline-asset guard (which requires BOTH off-file references resolved, not lucide alone), and aligns directionally with ADR-0025 — at a change cost higher than activating the wizard. Long-term, the single served file becomes the standing front-end surface: new operator surfaces are added as screens within it, and each must clear the same render.emit inline-asset guard before it can be served, so the inline-only discipline becomes a property of every future front-end addition rather than a one-time fix.

### Consequences

**Positive:**
- The four fragmented surfaces become one persistent left-nav shell (`Dashboard` / `Upload Documents` / `Plan` / `Chat with Team`), delivering the unified-navigation cohesion the S98 design phase set out to fix and which neither the wizard nor a multi-page app provides ([app.html L272-275](../../prototype/app.html) [VERIFIED]).
- The served front-end stays one self-contained offline file: it is served as the GET `/` body of the existing loopback transport, passes the render.emit guard with 0 external requests, and extends ADR-0025's single-self-contained-HTML posture rather than introducing a new output shape ([server.py L70-81](../../scripts/serve/server.py) [VERIFIED]; [render.py L172-178](../../scripts/generate/render.py) [VERIFIED]; [ADR-0025 Decision L24](ADR-0025-unified-maintained-html-output.md) [VERIFIED]).
- No backend churn: the SPA consumes the already-accepted contracts unchanged — loopback transport (ADR-0013), capture/persist routing (ADR-0014), `/chat` egress (ADR-0016), the extractor (ADR-0017), and the `SUMMARY_FIELD_SET` (ADR-0019) — introducing 0 new backend contract, data flow, or trust boundary, so the adoption is front-end-only.

**Negative:**
- Every off-file asset reference must be inlined before `app.html` can be served — vendoring lucide is necessary but NOT sufficient: today TWO references make render.emit RAISE and write nothing — the unpkg lucide CDN load ([app.html L411](../../prototype/app.html) [VERIFIED]) AND the bare-path `<img src="images/body.png">` image ([app.html L292](../../prototype/app.html) [VERIFIED]), since `_is_external` flags a bare path exactly as it flags an `http(s)://` URL ([render.py L46-53](../../scripts/generate/render.py) [VERIFIED]). Vendor lucide inline (the UMD bundle, or the used icons as inline SVG) AND inline `images/body.png` as a `data:` URI or remove it; until BOTH are resolved render.emit still refuses ([render.py L172-178](../../scripts/generate/render.py) [VERIFIED]) — a real conversion cost that blocks serving.
- The single-file SPA is a larger maintenance surface than per-surface server-rendered templates: all four screens, the nav state, and the vendored icon set live in one file, so a change to any screen edits the same artifact, and the file grows against ADR-0004's <500KB single-file budget — the real binding size constraint, owned by ADR-0004 (ADR-0025 echoes the same single-file direction for the maintained PLAN output [ADR-0025 Decision L24](ADR-0025-unified-maintained-html-output.md) [VERIFIED], but does not itself bind the front-end's size) — a constraint that tightens with every screen added over the next several releases.
- The supersession leaves ADR-0018-T1's recipe needing a retarget: that recipe targeted the `intake.py` wizard's Step-1 activation, and the wizard presentation is now superseded, so the demographics+uploads capture must be re-pointed at the SPA's `Upload Documents` screen or the recipe builds a surface that is being retired — a 1+ release dependency until the recipe is retargeted.

**Neutral:**
- As-built, the `Dashboard` and `Plan` screens ship a parallel hand-built layout of fabricated DEMO data — "Synced from WHOOP", an 84% RECOVERY ring, "SLEEP 7.8 HRS", an invented RHR/HRV/body-weight set ([app.html L290, L295-296](../../prototype/app.html) [VERIFIED]) — i.e. sample content, not the operator's data. This decision adopts only the SHELL and wires only the `Upload Documents` surface; the `Dashboard`/`Plan` screens stay visibly-placeholder until their own per-surface live-wiring replaces the fabricated rings/sample numbers with the real `dashboard.py` / plan output or ADR-0009 D2 awaiting-states (OQ-3, the ADR-0009 D1/D2 reconciliation named in the `tensions-with` Related-Decisions row) — they are NOT presented as the operator's data in this build.
- Serving the SPA re-points the GET `/` body SOURCE only: `server.py`'s `_render_intake` today returns `generate.run('intake')`'s rendered text as the GET `/` body ([server.py L70-81](../../scripts/serve/server.py) [VERIFIED]), and under this decision that body source becomes the SPA render. This is front-end serving glue — which rendered body the existing route returns — NOT a backend data-contract, route-table, or transport change; the route stays GET `/` on the same operator-started 127.0.0.1 loopback server (the Loopback validation criterion already expects this).
- `intake.py` is not deleted by this decision — its fate (delete vs. keep as a server-rendered fallback) is OQ-1; the supersession changes which front-end is SERVED, not which files exist on disk.
- The served front-end's transport, bind address, and egress posture are byte-unchanged: still the operator-started 127.0.0.1 GET `/` server making only the one ADR-0016 `/chat` turn — only the rendered body changes from the wizard to the SPA ([server.py L9-10](../../scripts/serve/server.py) [VERIFIED]; [ADR-0016 Decision L24](ADR-0016-intake-conversation-egress-relaxation.md) [VERIFIED]).

### Alternatives Considered

#### Alternative A: Keep and activate the existing `intake.py` wizard
Wire the dead steps into the existing multi-step server-rendered wizard (the ADR-0018-T1 path) and serve no SPA, keeping each surface its own template.
- **Supporting evidence:** Smallest possible change — the wizard is already the served GET `/` body, the recipe is approved, and the render.emit inline-asset guard already passes for it with 0 external references ([intake.py L1-7](../../vault/design/templates/intake.py) [VERIFIED]; [server.py L70-81](../../scripts/serve/server.py) [VERIFIED]). No SPA to build, no asset to vendor, no recipe retarget.
- **Trade-offs:** It does not deliver the load-bearing requirement. The S98 design phase was convened because the multi-step wizard's fragmented surfaces are the operator-rejected UX; activating it in place re-delivers exactly that fragmentation and provides no unified left-nav shell ([app.html L272-275](../../prototype/app.html) [VERIFIED] is the cohesion A cannot provide). Rejected because it fixes the wizard's wiring while leaving the fragmentation — the actual reason the design phase exists — untouched.
- **When this becomes the right choice:** If the operator's surfaces stayed few and self-contained enough that fragmented per-template pages were acceptable, activating the wizard in place would deliver a working front-end at far lower cost than standing up and maintaining a single-file SPA.

#### Alternative B: A multi-page app (one server-rendered HTML per surface, shared nav partial)
Render each surface as its own page with a shared navigation partial, rather than a single-file SPA.
- **Supporting evidence:** Each page is smaller and simpler in isolation, edits to one surface touch only that page, and each page is independently render.emit-able as its own self-contained file. A familiar server-rendered model with no client-side routing.
- **Trade-offs:** Navigation state and per-page JavaScript are duplicated across every page, and it delivers no unified left-nav shell — the cohesion the S98 design phase was convened to provide. It also runs counter to ADR-0025's single-self-contained-HTML DIRECTION for the maintained PLAN output ([ADR-0025 Decision L24](ADR-0025-unified-maintained-html-output.md) [VERIFIED]) — a complementary signal, not a binding constraint on the front-end. Rejected because it duplicates nav state/JS and delivers no unified shell, not because ADR-0025 forbids a page set.
- **When this becomes the right choice:** If client-side single-file size became the binding constraint (the SPA outgrows the <500KB budget) and per-page server rendering were cheaper than a growing single file, the multi-page split would relieve the size pressure a single SPA accumulates.

#### Alternative C: Adopt `app.html` as-is, including the CDN lucide load AND the bare-path image
Serve the approved artifact unchanged, keeping BOTH its off-file references — the `unpkg.com` lucide `<script>` AND the bare-path `<img src="images/body.png">` — rather than vendoring the icons inline and inlining-or-removing the image.
- **Supporting evidence:** Zero conversion cost — the operator-approved artifact ships exactly as designed, with the icon set delivered by a maintained CDN rather than a vendored copy that can drift from upstream.
- **Trade-offs:** render.emit refuses it: the unpkg load (and the bare-path `images/body.png` image alongside it) is an off-file reference, so the guard RAISES and writes nothing — the file cannot be served over the existing transport at all ([app.html L411, L292](../../prototype/app.html) [VERIFIED]; [render.py L46-53, L172-178](../../scripts/generate/render.py) [VERIFIED]) — and a CDN dependency (plus the bare-path image) violates the local-first / 0-external-request posture the whole render path enforces. Rejected by constraint #3, not by preference.
- **When this becomes the right choice:** If the local-first / inline-asset posture were ever relaxed to permit a vetted external asset host (a different trust model than V1's), serving the artifact as-is would remove the inline-vendoring cost — but that is a re-decision of the render.emit boundary, not of this front-end.

### Validation Approach

**Confirmation criteria:**
- **(Split preserved)** The served SPA contains BOTH an objective demographics+uploads form (the `Upload Documents` screen) AND a conversational rich-section surface (the `Chat with Team` screen) — verified by enumerating the served HTML's screens (expected: ≥1 objective-form surface AND ≥1 conversational surface; today both are present at [app.html L272-275](../../prototype/app.html) [VERIFIED]).
- **(PII boundary unchanged)** The served front-end's only outbound class is the ADR-0016 `/chat` one-turn egress, and every store write remains de-identified via ADR-0017 — verified by enumerating the outbound calls the served front-end makes (expected: exactly the ADR-0016 `/chat` turn, 0 additional classes).
- **(Inline-asset)** A render.emit run over the assembled `app.html` returns a written path rather than raising (expected: a written path, not a raise). This render.emit run is the AUTHORITATIVE inline-asset check: it scans every asset reference at its syntactic position, so a substring grep like `rg 'http|unpkg|cdn|//'` is NON-authoritative and cannot be substituted — it would not match a bare-path reference such as `images/body.png` that `_is_external` still flags ([render.py L46-53](../../scripts/generate/render.py) [VERIFIED]), so a 0 grep result can coexist with a render.emit raise.
- **(Loopback transport)** The SPA is served as the GET `/` body of `python -m scripts.serve` bound to 127.0.0.1, with 0 new serving process or port — verified by confirming the server's GET `/` body is the SPA render and the bind address is unchanged ([server.py L70-81](../../scripts/serve/server.py) [VERIFIED]).

**Falsification criteria:**
- If the served SPA lacks either the objective demographics+uploads form OR the conversational rich-section surface (0 of either), the ADR-0018 split is not preserved — block adoption until both surfaces are present.
- If the served front-end introduces ≥1 outbound class beyond the ADR-0016 `/chat` turn, OR ≥1 store write is not de-identified, the PII boundary is breached — block adoption.
- [AMENDED 2026-06-27, ADR-0030 §amends]: the "≥1 outbound class beyond the ADR-0016 `/chat` turn → block adoption" criterion immediately above is SCOPED to admit ONE additional authorized outbound class — the upload-extraction egress ADR-0030 introduces from the `Upload Documents` screen (the raw uploaded file → the no-train model → operator-confirmed readings → the store), on the SAME no-train lane and operator-confirmed before any reading lands. That second egress class does NOT block adoption; any OTHER outbound class still does, and the de-identified-store-write criterion above is unchanged.
- If the served HTML carries ≥1 off-file asset reference (today TWO: the unpkg lucide load at [app.html L411](../../prototype/app.html) [VERIFIED] AND the bare-path `<img src="images/body.png">` at [app.html L292](../../prototype/app.html) [VERIFIED], both flagged by `_is_external` at [render.py L46-53](../../scripts/generate/render.py) [VERIFIED]), render.emit RAISES and writes nothing — the file is unservable until BOTH are inlined (lucide vendored, the image inlined as a `data:` URI or removed); block serving on any non-zero off-file count.
- If a new server, port, or non-loopback bind is introduced to serve the SPA (≥1 new serving process or a bind other than 127.0.0.1), the ADR-0013 transport posture has changed — block adoption.
- Time horizon: run the split-present, off-file-reference, and transport checks at the first serve of the SPA and at every release thereafter; run the outbound-class check on every change to the SPA's network surface.

**Review triggers:**
- A new SPA screen or surface is added — re-confirm it introduces no new outbound class and no off-file asset reference before it ships.
- lucide (or any vendored asset) is updated — re-run the off-file-reference scan; an update that re-points at a CDN re-breaks render.emit.
- ADR-0016's egress carve-out or ADR-0017's extractor changes — re-confirm the `Chat with Team` surface still routes through the unchanged contracts.
- The North-Star transition is initiated — the loopback-served single-file SPA is superseded by the authenticated hosted front-end, at which point the inline-asset / loopback-transport posture is re-decided under that trust model.
