## ADR-0026: Select the V1 Subscription-Runtime Driver Model for the Programmatic Orchestrator

> **Y-Statement:** In the context of the S92 plan-generation engine, whose `run_orchestrated` drive layer invokes the agent `dispatch(domain, prompt, summary)` seam SYNCHRONOUSLY from INSIDE its inline revise loop ([plan_orchestrator.py:294, 369](../../scripts/plan/plan_orchestrator.py) [VERIFIED]) while a subscription specialist is a Claude Code Task AGENT that Python cannot synchronously spawn and pull output back from, facing the tension that the operator's binding constraint is "subscription for the specialists, judge, and safety lenses (not metered), API only for the PII de-id call" yet the safety-critical control flow (the bounded revise loop, `safety_passed is True` as the only surface path, scratch-and-promote, the de-id halt, the dispatch cap) must stay a SINGLE source of truth and must not be forked, we decided to adopt the SKILL-AS-ORCHESTRATOR, CONTROL-FLOW-INVERTED model (A′) — a `/generate-plan` skill session de-ids via the ADR-0027 API client (a Python call), then drives the revise loop through a single SHARED control-inversion driver: `run_orchestrated`'s inline gate→branch→re-dispatch loop is EXTRACTED (a behavior-preserving refactor of the S92-authored orchestrator wrapper, NOT the byte-frozen inner engine) into one driver that yields dispatch-requests and receives envelopes; the skill drives that driver by dispatching subscription agents per request, while `run_orchestrated` (API/test mode) drives the SAME driver with a programmatic `dispatch` — so the loop logic exists ONCE (no fork), the inner engine stays byte-frozen, and `run_orchestrated`'s public behavior is preserved by the full existing test suite staying green — to achieve subscription-mode autonomy without forking the fail-closed loop, accepting that the V1 live runtime is a Claude Code session (not a headless service), that the extract is a bounded reviewed refactor under test-suite protection that adds a new shared-driver seam to maintain, and that subscription dispatch is non-deterministic relative to the mock harness.

### Context

ADR-0022 fixed the V1 runtime as "a programmatic subscription orchestrator … mirroring the autonomous build pipeline" but explicitly deferred the DRIVE mechanism to build-planning: OQ-1 ("how does the autonomous orchestrator spawn the plan-domain specialist agents with their full role profiles inlined") and OQ-3 ("where does the orchestrator's drive layer live — a new `scripts/plan/` driver vs the skill harness") ([ADR-0022, OQ-1/OQ-3](ADR-0022-programmatic-subscription-orchestrator.md) [VERIFIED]). The S92 build then landed every engine piece but no production caller: `run_orchestrated` is the programmatic runtime surface, and `rg run_orchestrated scripts/` finds only its own definition, the `dispatch_budget` docstring, and tests — no front door composes it over real clients ([plan_orchestrator.py:136-305](../../scripts/plan/plan_orchestrator.py) [VERIFIED]).

Two forces pull against each other. The operator's binding constraint is subscription execution for everything except the PII de-id call: the specialists, the quality judge, the safety lenses, and the control flow run on a Claude Code subscription session dispatching AGENTS (not metered), while the one model call that ingests raw PII routes to the no-train API (ADR-0027). Against that constraint stands a structural impossibility in the built seam: `run_orchestrated`'s `dispatch` is SYNCHRONOUS and Python-shaped — `authors[domain] = dispatch(domain, prompt, summary)` ([plan_orchestrator.py:369](../../scripts/plan/plan_orchestrator.py) [VERIFIED]) — and expects a structured author envelope back in the call stack. Python cannot synchronously `Task`-dispatch a subscription agent and pull its reasoning back into a function return; the subscription agent is driven by the Claude Code session, not callable from inside a Python frame. So WHO drives the dispatches (a Python process vs the skill session) is genuinely undecided, and it fixes where the live runtime lives.

What is NOT undecided is the safety-critical half. `run_orchestrated` already owns the fail-closed control flow: the de-id sentinel halts to honest-no-plan with 0 dispatches ([plan_orchestrator.py:229-231](../../scripts/plan/plan_orchestrator.py) [VERIFIED]); the bounded revise loop treats `disposition.get("safety_passed") is True` as the ONLY surface path, routing `False`/`None`/absent/non-dict/raised to terminal `SAFETY_BLOCKED` ([plan_orchestrator.py:261-266](../../scripts/plan/plan_orchestrator.py) [VERIFIED]); scratch-and-promote keeps the real store clean on a block ([plan_orchestrator.py:252-276, 424-466](../../scripts/plan/plan_orchestrator.py) [VERIFIED]); the dispatch cap fails closed before an over-budget call ([plan_orchestrator.py:301-305](../../scripts/plan/plan_orchestrator.py) [VERIFIED]); INV-CRITICAL-NON-OVERRIDABLE holds through the inner gate ([INVARIANTS.md](../../INVARIANTS.md) [VERIFIED]). The data subject's safety, not only the operator's convenience, rests on that loop being one source of truth: the project's own integration mandates (CLAUDE.md "Factory-to-Component Wiring", "No Tautological Tests", the fail-closed crown-jewel posture) make a forked safety loop a latent failure vector. The extend-not-rebuild constraint has TWO tiers, and the distinction is load-bearing here: the **byte-frozen INNER ENGINE** is the S70–S91 set — `orchestrate` / `pipeline` / `assemble` / `generate_plan` / `adjudicate` / `adjust` / `track` / `router` (numstat=0, untouched, the engine WRAPS it) — whereas `run_orchestrated` (in `plan_orchestrator.py`) is the **S92-authored orchestrator WRAPPER**, NOT in the byte-frozen set, and so MAY take a bounded, behavior-preserving refactor under test-suite protection ([session-92.md](../../vault/sessions/session-92.md): "the S70–S91 inner engine byte-unchanged; the engine WRAPS it" [VERIFIED]). The structural snag the driver decision must clear: the revise loop's gate→branch→re-dispatch sequencing is INLINE in `run_orchestrated`'s `while True:` ([plan_orchestrator.py:260-300](../../scripts/plan/plan_orchestrator.py) [VERIFIED]) — it synchronously calls `dispatch` mid-loop ([plan_orchestrator.py:294](../../scripts/plan/plan_orchestrator.py) [VERIFIED]) and computes WHICH domains to re-author from the gate disposition of the previous pass ([plan_orchestrator.py:286](../../scripts/plan/plan_orchestrator.py) [VERIFIED]). That data-dependent mid-loop re-dispatch is WHY sharing only the LEAF helpers cannot avoid a fork of the LOOP, and why a skill cannot synchronously drive the inline `dispatch` — the loop CONTROL FLOW, not just its leaves, must become a single shared inverted driver. So the decision is constrained to: pick a driver that runs subscription specialists WITHOUT forking the Python control flow AND without editing the byte-frozen inner engine, accepting that a bounded behavior-preserving refactor of the WRAPPER is the seam the inversion lives in.

### Decision

Adopt the **skill-as-orchestrator, control-flow-inverted (A′)** driver model for V1. A `/generate-plan` skill session is the live runtime: it de-ids the raw intake via the ADR-0027 no-train API client (a synchronous Python call), then dispatches each plan-domain specialist and each safety lens as a SUBSCRIPTION Claude Code agent (full role profile inlined per INV-ROLE-INLINING) over the de-identified summary, captures each structured envelope, and feeds those envelopes back into the SINGLE Python control flow. The mechanism is a **behavior-preserving control-inversion refactor of `run_orchestrated`** (the S92-authored WRAPPER, not the byte-frozen inner engine): the bounded revise-loop control flow that is today INLINE in `run_orchestrated`'s `while True:` — the gate→branch→re-dispatch sequencing, the fail-closed `safety_passed is True` disposition, the cap accounting, the de-id halt, scratch-and-promote — is EXTRACTED into ONE shared driver (a generator/coroutine that yields dispatch-requests and receives envelopes via `.send()`, or an explicit step state-machine with `.next_action()`/`.submit()`; the exact shape is OQ-1). BOTH consumers drive that one driver: (a) the V1 `/generate-plan` SKILL drives it by dispatching a subscription agent per yielded request and feeding each captured envelope back; (b) `run_orchestrated` (API-mode + the test harness) drives it with a programmatic/fixture `dispatch`. The loop logic therefore exists EXACTLY ONCE (no fork), `run_orchestrated`'s public behavior is preserved (proven by the full existing test suite — 1600+ tests — staying green), and the **byte-frozen inner engine** (`pipeline.run_generation` etc.) is untouched (numstat=0). The composed `gate_dispatch` adapter and the specialist/lens dispatch wiring are folded into this driver model (this ADR also fixes the composed `gate_dispatch` topology and the subscription dispatch wiring as direct consequences of the A′ choice — see Related Decisions 0023/0024). The model rides the ADR-0015 seam: the all-API path stays reachable as a backend swap.

### Rationale

The driver model was evaluated across four criteria the constraint and the built engine make load-bearing: **fidelity to the built fail-closed loop (no-fork-the-safety-control-flow)**, **subscription-vs-metered cost**, **swappability to the future all-API path**, and **buildability under extend-not-rebuild**. The candidates are A′ (chosen), A-naive (skill re-implements the loop), and B (Python-driven dispatch adapter). The future all-API path is treated as the swap target, not a V1 candidate.

On **no-fork fidelity**, A′ is decisive. The entire safety floor already lives in `run_orchestrated` ([plan_orchestrator.py:229-305](../../scripts/plan/plan_orchestrator.py) [VERIFIED]), but the floor is not just the leaf helpers — it is the INLINE loop CONTROL FLOW (the `while True:` gate→branch→re-dispatch at [plan_orchestrator.py:260-300](../../scripts/plan/plan_orchestrator.py) [VERIFIED]), and the revise re-dispatch is DATA-DEPENDENT: which domains re-author is computed mid-loop from the previous pass's gate disposition ([plan_orchestrator.py:286](../../scripts/plan/plan_orchestrator.py) [VERIFIED]). Sharing only the leaf helpers (`_dispatch_domains`, `_safe_gate`, `_promote_plans`, `_honest_no_plan`) does NOT avoid forking that loop — the fork would be in the loop sequencing, not the leaves. A′ therefore EXTRACTS the loop control flow itself into ONE shared inverted driver: the skill drives it by dispatching subscription agents per yielded request, `run_orchestrated` drives it with a programmatic `dispatch`, and there is exactly one definition of "a non-True safety disposition surfaces 0 plans." This is what the data-dependent revise re-dispatch FORCES — a shared inverted driver, not leaf-helper-sharing alone. A-naive instead re-implements the bounded loop, the `safety_passed is True` check, and scratch-and-promote in skill prose at the agent-dispatch level — two copies of the safety-critical logic that can drift, the exact "No Tautological Tests" / fail-closed-crown-jewel failure class the project's mandates forbid. B keeps the loop in Python but needs a Python adapter that programmatically invokes a subscription agent — which the synchronous-dispatch impossibility blocks (below). So only A′ preserves the single-source-of-truth loop while running subscription specialists.

On **subscription-vs-metered cost**, A′ and A-naive both run on the subscription session (no marginal per-call API charge for the agent dispatches), matching the operator constraint; the de-id call is the only metered egress (one call per plan-gen, ADR-0027). B's natural realization is the Agent SDK, which is metered/API — conflicting with "subscription for everything else" — and its subscription-capable form (a headless `claude` CLI subprocess the Python adapter spawns per dispatch) is fragile and complex (process lifecycle, prompt marshalling, output parsing per dispatch) [UNVERIFIED: the headless-CLI subprocess path is a documented future option, not prototyped here]. On **swappability**, all three dispatch through the ADR-0015 `ModelClient` seam for the de-id call, and the future all-API path is the same `run_orchestrated` Python loop driven with a programmatic `dispatch`/`gate_dispatch` — which `run_orchestrated` already supports as its API-mode driver and test harness today ([plan_orchestrator.py:136-305](../../scripts/plan/plan_orchestrator.py) [VERIFIED]). A′ keeps that target reachable: the all-API cutover swaps the skill's agent-staged envelopes for programmatic backend calls, re-using the same shared driver. A-naive forecloses the cleanest cutover — the all-API path would either re-converge on `run_orchestrated`'s loop (orphaning the skill's forked copy) or re-fork it again.

On **buildability under extend-not-rebuild**, A′ extracts the inline revise loop into ONE shared inverted driver and re-points `run_orchestrated` at it — a bounded, behavior-preserving refactor of the S92-authored WRAPPER (not a free lunch: a new seam plus a refactor, but executed under the protection of the full existing test suite, so the public behavior is held constant — 1600+ tests stay green). The byte-frozen INNER ENGINE (`pipeline`/`orchestrate`/`assemble`/`generate_plan`/`adjudicate`/`adjust`/`track`/`router`) is untouched (numstat=0 on it). A-naive touches no Python but pays the forked-loop debt forever. B requires the subprocess machinery, the largest new surface. Long-term, A′ accepts that the V1 live runtime is a Claude Code session rather than a headless service, and that the shared inverted driver is a new seam to maintain — a 1+ year structural cost the all-API cutover later retires by collapsing the skill consumer onto the same programmatic driver.

### Consequences

**Positive:**
- The fail-closed safety loop stays a single source of truth. The skill drives the agent dispatches but the bounded revise loop, the `safety_passed is True` disposition, scratch-and-promote, the de-id halt, and the dispatch cap all live in ONE shared control-inversion driver that BOTH the skill (subscription mode) and `run_orchestrated` (API/test mode) drive — verifiable as **0 duplicated copies of the revise-loop control flow** by grep ([plan_orchestrator.py:260-305](../../scripts/plan/plan_orchestrator.py) [VERIFIED]). The no-fork property is ACHIEVED (not merely asserted): the loop sequencing itself, not only its leaf helpers, is the single definition.
- Subscription cost posture is honored: the specialists, judge, and safety lenses dispatch as subscription agents with no marginal per-call API charge; the only metered egress is the single ADR-0027 de-id call per plan-gen.
- The all-API North-Star path stays a backend swap, not a rewrite: `run_orchestrated` already drives the loop with a programmatic `dispatch`/`gate_dispatch` (it IS the API-mode driver + test harness today), and post-extract it drives the SAME shared driver, so the cutover swaps the skill's agent-staged envelopes for programmatic calls and re-uses the one driver ([plan_orchestrator.py:136-305](../../scripts/plan/plan_orchestrator.py) [VERIFIED]); the model boundary stays the single ADR-0015 swap point — backend injected at construction with no caller-side edit ([client.py:44-45](../../scripts/model/client.py) [VERIFIED]; [ADR-0015, Decision](ADR-0015-swappable-no-train-model-client.md) [VERIFIED]).

**Negative:**
- The V1 live runtime is a Claude Code SUBSCRIPTION SESSION, not a headless service — plan generation cannot run truly unattended (no human session present); it is "autonomous within a session," a real and permanent (1+ year) coupling of the V1 driver to the subscription-session execution model, the live form of the subscription-coupling negative ADR-0022 recorded ([ADR-0022, Consequences Negative-3](ADR-0022-programmatic-subscription-orchestrator.md) [VERIFIED]). This REFINES ADR-0022's "unattended" claim: A′ delivers "autonomous WITHIN a subscription session (no per-dispatch human checkpoint)," not headless/scheduled — a human starts the session, which then drives all dispatches autonomously. Truly headless execution is the all-API North-Star cutover via the ADR-0015 seam, not V1.
- A bounded, behavior-preserving REFACTOR of `run_orchestrated` is required, and the shared inverted driver is a NEW seam to maintain: extracting the inline loop into the shared driver and re-pointing `run_orchestrated` at it is a real refactor of the S92 wrapper (NOT a free lunch — the no-fork property is bought with a new seam + a refactor). It is executed under the protection of the full existing test suite (1600+ tests must stay green — the behavior-preservation proof), and two consumers (the skill for subscription V1, the programmatic `run_orchestrated` for API-mode + tests) must be kept driving the one driver. The mitigation — the loop logic is defined ONCE in the shared driver — narrows the drift surface to the orchestration glue, but does not erase the cost of the refactor or the second consumer.
- Subscription dispatch is NON-DETERMINISTIC relative to the mock harness: where the test harness injects fixture-author envelopes for byte-stable assertions, a live subscription specialist returns model-authored content that varies per run. The quality judge + safety review gates are the standing check on that variance, but the live path cannot be asserted byte-for-byte the way the mock path is.

**Neutral:**
- `/generate-plan` is repurposed, not deleted: its current text describes the superseded runtime-A interactive single-plan dispatch ([generate-plan/SKILL.md L17-21, L137-142](../../.claude/skills/generate-plan/SKILL.md) [VERIFIED]); under this ADR it becomes the V1 subscription DRIVER of the programmatic engine, and its prose is reconciled to the built orchestrator (a follow-on documentation task, not a decision).
- A second instance of the skill-drives-Python-substrate pattern joins the project alongside the autonomous build pipeline's execute-plan orchestrator — the same control shape the operator named as the analogue, not a novel one.

### Alternatives Considered

#### Alternative A′: Skill-as-orchestrator, control-flow-inverted (Chosen)
The `/generate-plan` skill de-ids via the ADR-0027 API client and dispatches each specialist + safety lens as a subscription agent; the inline revise loop is EXTRACTED into one shared control-inversion driver (a behavior-preserving refactor of the S92-authored `run_orchestrated` WRAPPER, the byte-frozen inner engine untouched), and BOTH the skill (subscription mode) and `run_orchestrated` (API/test mode) drive that one driver — the loop is not forked, the inner engine is not edited.
- **Supporting evidence:** Keeps the fail-closed loop a single source of truth (the loop CONTROL FLOW, not only the leaf helpers, is the one definition — [plan_orchestrator.py:260-305](../../scripts/plan/plan_orchestrator.py) [VERIFIED]); the data-dependent revise re-dispatch ([plan_orchestrator.py:286-294](../../scripts/plan/plan_orchestrator.py) [VERIFIED]) is WHY a shared inverted driver (not leaf-helper-sharing) is required; runs subscription specialists at no marginal per-call charge; rides the ADR-0015 seam so the all-API path is a backend swap onto the same driver ([client.py:44-45](../../scripts/model/client.py) [VERIFIED]); builds under extend-not-rebuild (numstat=0 on the byte-frozen inner engine; the wrapper refactor is behavior-preserved by the full test suite).
- **Trade-offs:** The V1 runtime is a subscription session not a headless service (Negative-1); the bounded behavior-preserving `run_orchestrated` refactor + the shared-driver seam are a real cost (Negative-2); live dispatch is non-deterministic vs the mock harness (Negative-3). Accepted because the no-fork fidelity dominates — a forked safety loop is the latent failure vector the project's mandates exist to prevent.
- **When this becomes the right choice:** It is, for V1, when the constraint is subscription execution for the agents, the engine is byte-frozen, and the safety loop must stay one definition.

#### Alternative A-naive: Skill-as-orchestrator that re-implements the control flow in skill prose
A `/generate-plan` skill reimplements the bounded revise loop, the `safety_passed is True` disposition, the de-id halt, scratch-and-promote, and the dispatch-cap accounting at the agent-dispatch level, in skill prose — driving the agents AND owning the control flow itself.
- **Supporting evidence:** Genuinely viable and the simplest single-surface story — one artifact (the skill) drives everything, no shared Python driver to maintain, and it runs subscription specialists at no marginal per-call charge exactly like A′. For a system without a safety-critical loop it would be the lighter design.
- **Trade-offs:** It FORKS the safety-critical control flow — the bounded loop, the `safety_passed is True` surface gate, and scratch-and-promote now live in BOTH the Python control flow AND the skill prose, which can drift. A skill-prose copy of "a non-True disposition surfaces 0 plans" that silently diverges from the Python definition is the exact "No Tautological Tests" / fail-closed-crown-jewel failure class the project's integration mandates forbid (a forked safety loop is a latent failure vector). It also forecloses the cleanest all-API cutover, which would re-converge on the Python loop and orphan the skill's copy. (A′ avoids this fork precisely BY extracting the loop into the one shared driver both consumers drive — A-naive copies it into prose instead.)
- **When this becomes the right choice:** If the engine had NO safety-critical control flow to fork — i.e. if the loop were trivial enough that a second copy could not meaningfully diverge — the single-surface simplicity would win. For a fail-closed health-plan loop with a CRITICAL-non-overridable floor, it does not.

#### Alternative B: Python-driven dispatch adapter
Wire `run_orchestrated`'s `dispatch` seam to a Python adapter that programmatically invokes a subscription agent and returns its envelope into the call stack — making `run_orchestrated` itself the single live driver for subscription mode.
- **Supporting evidence:** The strongest no-fork story in principle — the loop never leaves Python and there is no skill control flow at all. `run_orchestrated` already supports this shape: with a programmatic `dispatch`/`gate_dispatch` it IS the API-mode driver + test harness today ([plan_orchestrator.py:136-305](../../scripts/plan/plan_orchestrator.py) [VERIFIED]), so the loop is provably driveable from Python.
- **Trade-offs:** Its natural realization (the Agent SDK) is metered/API — it conflicts with the operator's "subscription for everything else" constraint, paying per-token for every specialist/judge/lens dispatch the per-plan-plus-revise loop multiplies. Its subscription-capable realization (a headless `claude` CLI subprocess spawned per dispatch) is fragile and complex — process lifecycle, prompt marshalling, and output parsing for every dispatch — a large new surface for V1 [UNVERIFIED: the subprocess path is not prototyped here]. Python cannot otherwise synchronously spawn a subscription Task agent and pull its output back ([plan_orchestrator.py:369](../../scripts/plan/plan_orchestrator.py) [VERIFIED]).
- **When this becomes the right choice:** When the runtime moves to all-API (or a local model), `dispatch`/`gate_dispatch`/`deid_client` all become programmatic and `run_orchestrated` becomes the single live driver — this IS the documented future all-API path the ADR-0015 seam carries; it is the V1-rejected, future-adopted form, not a straw man.

#### Dissent: Keep the S68 interactive per-dispatch human checkpoint (inherited from ADR-0022)
**Source:** ADR-0022's recorded Alternative-B dissent — the interactive `/generate-plan` session put a human in the loop on EVERY safety-relevant dispatch, the strongest safety posture for a health plan ([ADR-0022, Alternative B](ADR-0022-programmatic-subscription-orchestrator.md) [VERIFIED]). A′ drives the specialist + lens + adjudicator dispatches autonomously within the session, so a reviewer can hold that the per-dispatch human checkpoint should be preserved over within-session autonomy.
**Conditions under which this becomes the right choice:** If the operator decides no plan should ever be assembled without a human reviewing each safety-relevant dispatch in real time — then the within-session autonomy is rejected and the multi-agent safety-review tier (ADR-0024) does not substitute for the per-dispatch human gate. ADR-0022 already adjudicated this against autonomy/repeatability; this ADR wires the driver that decision settled, shifting the safety burden onto the ADR-0024 whole-plan review tier as ADR-0022 made load-bearing.

### Validation Approach

**Confirmation criteria:**
- The revise-loop control flow lives in ONE shared driver that BOTH consumers drive, and is NOT re-implemented: grep the skill AND `run_orchestrated`'s call site for a second copy of the `while True:` gate→branch→re-dispatch sequencing, the `safety_passed is True` surface gate, the bounded-revise cap check, and the scratch-and-promote logic. Expected: **exactly 1 definition** of the loop control flow (in the shared driver), **0 duplicated copies** in the skill or in `run_orchestrated`'s call site — `run_orchestrated` drives the shared driver, it does not re-host the loop ([plan_orchestrator.py:260-305](../../scripts/plan/plan_orchestrator.py) [VERIFIED]).
- The composed `gate_dispatch` adapter preserves the loop's surface contract: over the assembled result it runs `quality_judge` AND `review_plan` (both gate at this stage; order/concurrency is the OQ-2 composition; the loop consumes one composed disposition) and returns `{accept: verdict==ACCEPT, safety_passed: review.passed, revise_domains: ...}`; a malformed/missing composite (a raised lens, a non-dict) yields a disposition that is NOT `safety_passed is True`. Expected: a malformed composite → `SAFETY_BLOCKED` → **0 plans surfaced** ([plan_orchestrator.py:261-266, 373-395](../../scripts/plan/plan_orchestrator.py) [VERIFIED]).
- Every subscription specialist/lens dispatch carries the full role profile inlined (INV-ROLE-INLINING) over the de-identified summary only: inspect each dispatch prompt the driver issues. Expected: **the full `.claude/agents/<role>/agent.md` text present in every dispatch** ([plan_orchestrator.py:95-133](../../scripts/plan/plan_orchestrator.py) [VERIFIED]), and **0 raw-PII fields** in any dispatch payload (the dispatch only ever holds the `deid_in` summary).
- `core-capability-audit.sh` asserts the DETERMINISTIC PYTHON SPINE is wired — and is HONEST about what a shell check can and cannot prove of a skill-driven path (the resolved split, OQ-4). The audit's `CALLER` pin (currently `scripts/plan/generate_plan.py`, [core-capability-audit.sh:47](../../scripts/core-capability-audit.sh) [VERIFIED]) moves to a module ON the A′ SPINE (`plan_orchestrator.py` / the new shared driver — NOT `generate_plan.py`, which is the Wave-2 single-domain caller and is NOT on the A′ path), and (a) STRUCTURALLY asserts the spine is wired (the shared driver exists, drives `pipeline.run_generation`, and the disposition gate is present), and (b) BEHAVIORALLY runs a `--self-test` that drives the shared driver de-id→loop→promote→render end-to-end with a FIXTURE `dispatch` AND asserts the A′ inversion behaviors — **promotion-on-accept** and **0-plans-on-safety-not-True** — so the pass is NON-tautological (it exercises the inverted loop, not just "a plan renders"). The audit CANNOT assert the skill drives REAL subscription agents over the de-identified summary — that is the S94 operator-present LIVE-test attestation (a release-gating record, not a shell check). Expected: the repointed audit exits 0 on the wired SPINE; the live skill-driven dispatch is attested separately at S94. INV-CORE-CAPABILITY / PF-S63-02 is thereby honest — the guard proves the spine is wired (not a tautology) and does not falsely claim to verify the live dispatch.

**Falsification criteria:**
- **Forked-loop probe (the no-fork threshold):** if a grep over the skill + `run_orchestrated`'s call site finds **≥1 duplicated copy** of the `while True:` gate→branch→re-dispatch sequencing, the bounded-revise cap check, the `safety_passed is True` gate, or scratch-and-promote (a second definition that can drift from the shared driver), the safety loop has been forked — halt and re-route both consumers through the ONE shared driver before release.
- **Injected-safety-not-True probe:** inject a composed `gate_dispatch` that returns a disposition with `safety_passed` not boolean-True (`False` / `None` / absent / non-dict / a raised lens), and run the driver end-to-end. Threshold: **0 plans surfaced** (terminal `SAFETY_BLOCKED`, nothing promoted into `root`). If ≥1 plan surfaces, the inverted control flow has broken the fail-closed floor — halt and restore the disposition gate ([plan_orchestrator.py:261-266](../../scripts/plan/plan_orchestrator.py) [VERIFIED]).
- **Frozen-engine + behavior-preservation probe (three thresholds):** (i) **numstat=0 on the byte-frozen INNER ENGINE** — if the build edits any of `pipeline` / `orchestrate` / `assemble` / `generate_plan` / `adjudicate` / `adjust` / `track` / `router` (numstat > 0 on any inner-engine module) to realize the driver, the extend-not-rebuild constraint is breached — halt and re-route the inversion into the WRAPPER, not the engine. (ii) **0 duplicated copies of the revise-loop control flow** by grep (the no-fork proof — see the forked-loop probe). (iii) **the full existing test suite stays green** (1600+ tests) across the `run_orchestrated` refactor — if any test that passed before the extract now fails, the refactor is NOT behavior-preserving and `run_orchestrated`'s public contract has drifted; halt and restore behavior before release. (The `run_orchestrated` WRAPPER may take numstat > 0 — it is the seam the inversion lives in; the inner engine may NOT.)
- **Swap-seam probe:** if the future all-API cutover (the same loop driven with a programmatic `dispatch`/`gate_dispatch`) requires editing the driver's control flow in more than the dispatch-seam injection point — i.e. >1 file outside the `ModelClient` seam + the dispatch staging — the substitution seam has ossified at the drive layer; re-open the seam before adopting the new backend ([ADR-0015, Falsification](ADR-0015-swappable-no-train-model-client.md) [VERIFIED]).
- Time horizon: run the forked-loop probe, the injected-safety-not-True probe, the frozen-engine + behavior-preservation probe (the full test suite green across the `run_orchestrated` refactor), and the repointed core-capability `--self-test` at the first build of the driver, at the operator-present LIVE test (S94), and at every release thereafter, and before the July-2026 physician-visit deliverable ships.

**Review triggers:**
- The subscription session's rate/concurrency ceiling blocks the generate→judge→safety-review→revise loop's aggregate dispatch volume per plan (ADR-0022 OQ-2/OQ-4) — re-open Alternative B (the all-API path) against the cost trade-off.
- The North-Star transition to all-API / local-model is initiated — the runtime swaps the `dispatch`/`gate_dispatch`/`deid_client` seams to programmatic and `run_orchestrated` becomes the single live driver; re-validate the drive layer against the new execution model.
- The composed `gate_dispatch` topology (SHARED OQ-2: one combined gate vs two, ordering, re-trigger, joint cap) is re-opened at spec/build-plan — re-verify the composite preserves `safety_passed is True` as the only surface path.
