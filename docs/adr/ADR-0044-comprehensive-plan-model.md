## ADR-0044: Comprehensive Plan Model Superseding the Thin plan_schema

> **Y-Statement:** In the context of a plan zone that stores flat, day-keyed per-domain plan documents through a thin record model — the closed `PLAN_DOMAINS` 4-tuple, four per-domain validators accepting only `{exercises}` / `{calorie_goal, macros, meals}` / `{items}` / `{compound, dose, route}` (a grep for monitoring/adjustment/labs/seams/periodization/GRADE/rationale over the module returns 0 hits), `record_plan` appending one document per date, and `resolve_plan` resolving the latest same-dated reading as standing ([plan_schema.py:49,178-275,371-396,462-498](../../scripts/store/plan_schema.py) [VERIFIED]) — while ADR-0041 now defines a seven-field periodized DOMAIN PROGRAM per specialist and the design fixes a quality plan as one integrated, periodized, self-monitoring program, facing the tension that the flat day-keyed structure structurally cannot hold a periodized program, an integrated cross-domain narrative, dated milestones, or a compiled monitoring config, yet the record model that would carry them is the byte-frozen record spine ADR-0032 held across the project's ~15-session EXTEND-NOT-REBUILD era ([ADR-0032:26,43,107](ADR-0032-dna-aware-planning.md) [VERIFIED]), we decided to adopt a comprehensive Plan Model that stores, per active domain, the full DOMAIN PROGRAM plus an integrated narrative, dated milestones, the compiled monitoring config, and the adjustment rules — superseding the thin `PLAN_DOMAINS` + validators + `record_plan` write path + `resolve_plan` resolver — to achieve a stored plan that IS a periodized program carrying its own monitoring and autoregulation, accepting that this BREAKS the ADR-0032 EXTEND-NOT-REBUILD freeze on the record spine (the single biggest one-way door in the set — classified HARD, operator sign-off OBTAINED at the Phase-1 gate), forces re-basing ADR-0038's horizon composition and ADR-0040's confirmation-pointer + `resolve_plan` skip onto the comprehensive resolver, requires migrating the append-only store contract, and produces materially larger stored plans.

### Context

The plan zone stores each domain's plan as a flat, day-keyed document. `PLAN_DOMAINS = ("workout", "nutrition", "supplements", "peptides")` is a closed four-tuple ([plan_schema.py:49](../../scripts/store/plan_schema.py) [VERIFIED]); four per-domain validators define the entire stored field surface — `_validate_workout_plan` accepts `{exercises}` (each exercise `{name, sets}` + optional `load`/`reps`/`detail`), `_validate_nutrition_plan` accepts `{calorie_goal, macros, meals}`, `_validate_supplements_plan` accepts `{items}`, and `_validate_peptides_plan` accepts `{compound, dose, route}` plus a few optional keys ([plan_schema.py:178-275](../../scripts/store/plan_schema.py) [VERIFIED]). `record_plan` appends exactly one such document per `(domain, date, specialist)` via `store.append` ([plan_schema.py:371-396](../../scripts/store/plan_schema.py) [VERIFIED]), and `resolve_plan` resolves "today" by DATE EQUALITY against the render date, returning the latest same-dated reading or a published absence state ([plan_schema.py:462-498](../../scripts/store/plan_schema.py), the equality at [plan_schema.py:486](../../scripts/store/plan_schema.py) [VERIFIED]).

That surface carries none of the fields a periodized, self-monitoring plan needs. A grep over the module for `monitoring` / `adjustment_rule` / `required_lab` / `cross_domain` / `periodiz` / `GRADE` / `rationale` returns 0 hits [VERIFIED] — the thin schema has no periodization structure (dated blocks/phases), no milestones, no monitoring signals, no adjustment rules, no cross-domain seams, and no GRADE rationale. The stored plan is a flat single-shot list per domain per day; it is not a program. Two upstream decisions make this the binding constraint now. ADR-0041 defines a uniform seven-field DOMAIN PROGRAM every specialist emits — `{prescription (periodized/dated), rationale (GRADE certainty×strength + causal-vs-associational), monitoring_signals (validity-tiered), adjustment_rules, required_labs, refusal/escalation, cross_domain_seams}` ([ADR-0041 Decision](ADR-0041-uniform-specialist-domain-program-schema.md) [VERIFIED]) — and there is no stored model that can hold it: the four thin validators would reject or silently drop every field beyond the flat payload. And ADR-0038 established that a quality plan spans daily/weekly/monthly horizons and evolves toward dated goals ([ADR-0038 Context](ADR-0038-plan-time-horizons.md) [VERIFIED]), which the flat schema can only approximate by a derived date-range query, never a stored periodized structure.

Two forces pull against changing this. The maintainer's cost is the ADR-0032 record-spine freeze: ADR-0032's EXTEND-NOT-REBUILD posture holds the store (`scripts/store/*`) byte-frozen, and its Validation names the byte-frozen WRITE surface explicitly — `git diff --numstat` = 0 changed lines on `scripts/store/keying.py` / `store.append` and the inner plan engine ([ADR-0032:26,43,107](ADR-0032-dna-aware-planning.md) [VERIFIED]). The record model in `plan_schema.py` — `PLAN_DOMAINS`, the validators, `record_plan`, `resolve_plan` — sits inside that `scripts/store/*` freeze glob and has been held byte-frozen across the project's ~15-session EXTEND-NOT-REBUILD era; ADR-0036/0038/0040 are all built ON TOP of it. Superseding it is a one-way door. The second force is downstream coupling: `resolve_plan`'s absence states drive the dashboard plan zone, `track.resolve_plan_progress`, the ADR-0037 tailoring emit-gate, the ADR-0038 `horizons.window_block` range-query, and the ADR-0040 confirmation-pointer skip all read the thin record model ([ADR-0040 Decision §3](ADR-0040-large-change-hold-until-confirm.md) [VERIFIED]) — so replacing the model migrates every one of those consumers. Because this redefines the stored shape of the plan itself — the data model every plan reader, writer, and renderer depends on — and deliberately breaks a frozen one-way-door surface, it is an architecture decision, not an implementation detail.

### Decision

**Adopt a comprehensive Plan Model as the stored plan, superseding the thin `plan_schema` record model. The stored plan holds, per active domain, the full ADR-0041 DOMAIN PROGRAM, plus an integrated cross-domain narrative, dated milestones, the compiled monitoring config, and the adjustment rules — replacing the flat day-keyed per-domain documents, the four thin validators, and the standing-plan resolver built on them.**

The comprehensive model's shape, stated generically (the same model whether the plan spans a training domain, a compound domain, or the wider roster):

1. **Per-domain periodized DOMAIN PROGRAM** — for each active domain, the model stores the ADR-0041 seven-field program (prescription with dated blocks/phases, GRADE rationale, validity-tiered monitoring signals, adjustment rules, required labs, refusal/escalation, cross-domain seams) intact, not reduced to a flat payload.
2. **Integrated cross-domain narrative** — the orchestrator-synthesized coherent plan across domains (the reconciled whole), stored as a first-class part of the plan, not derived per-render.
3. **Dated milestones** — the plan's dated waypoints toward the operator's goals, stored as first-class structure rather than assembled by a cross-owner join at render time.
4. **Compiled monitoring config** — the deterministic monitoring/adjustment configuration compiled from the domains' `monitoring_signals` + `adjustment_rules`, stored IN the plan so a daily tier reads it from one place (the ADR-0045 input/output home).
5. **Adjustment rules** — the plan-level autoregulation rules that let the config adjust the plan without re-running the authoring front door.

This SUPERSEDES the thin record model in `plan_schema.py`: the closed `PLAN_DOMAINS` 4-tuple, the four per-domain validators (`_validate_workout_plan` / `_validate_nutrition_plan` / `_validate_supplements_plan` / `_validate_peptides_plan`), the `record_plan` write path, and the `resolve_plan` date-equality resolver ([plan_schema.py:49,178-275,371-396,462-498](../../scripts/store/plan_schema.py) [VERIFIED]). It does NOT decide the specialist-output contract (ADR-0041 — the model STORES those programs) nor the monitoring-config compiler (ADR-0045 — its compiled output LIVES IN this model); those are decided separately and consume/are consumed by this model.

**Freeze break (HARD, one-way door — stated honestly per the set's freeze-break-honesty rule).** This BREAKS the ADR-0032 EXTEND-NOT-REBUILD freeze on the record spine — the single biggest data-model door in the re-architecture set. The exact frozen surfaces it supersedes are the `plan_schema.py` record model: `PLAN_DOMAINS` (the closed domain set, [plan_schema.py:49](../../scripts/store/plan_schema.py)), the four thin validators ([plan_schema.py:178-275](../../scripts/store/plan_schema.py)), the `record_plan` WRITE path → `store.append` ([plan_schema.py:371-396](../../scripts/store/plan_schema.py)), and the `resolve_plan` standing-plan RESOLVER ([plan_schema.py:462-498](../../scripts/store/plan_schema.py)) — all within ADR-0032's `scripts/store/*` EXTEND-NOT-REBUILD glob, held byte-frozen across the project's ~15-session era ([ADR-0032:26,43](ADR-0032-dna-aware-planning.md) [VERIFIED]). This is strictly larger than ADR-0040's touch: ADR-0040 preserved the record WRITE path byte-unchanged and added only a read-side pre-filter outside ADR-0032's Validation-named write surface ([ADR-0040 Decision §1](ADR-0040-large-change-hold-until-confirm.md) [VERIFIED]); ADR-0044 supersedes the write path and the resolver themselves. Whether the underlying `store.append` / `keying.py` primitive (ADR-0032's Validation-named WRITE surface, [ADR-0032:107](ADR-0032-dna-aware-planning.md) [VERIFIED]) is itself edited to carry the comprehensive value, or the value rides that primitive unchanged while only the `plan_schema.py` record model changes, is a spec-level question (OQ-2) — but the record MODEL freeze is broken either way. Reversibility is HARD (an append-only store-contract migration every downstream consumer depends on); operator sign-off on breaking the freeze was OBTAINED at the Phase-1 discovery gate, where the whole-set supersession of the ADR-0032 frozen spine is the load-bearing decision the operator accepted before Tier authoring proceeded ([.pipeline/discovery.md](.pipeline/discovery.md); [.pipeline/state.md](.pipeline/state.md) [VERIFIED]). The safety-critical inner plan engine (`scripts/plan/{orchestrate,pipeline,assemble,generate_plan,adjudicate,adjust,track}.py`) is NOT superseded by THIS decision (ADR-0044) and stays byte-unchanged in ADR-0044's own commit. Where a SIBLING decision in this set supersedes part of that glob — `generate_plan.py` + `assemble.py` (ADR-0041), `orchestrate.py`'s `orchestrate.reconcile` (ADR-0043), and the `adjust.py` / `track.py` consumer migrations (ADR-0045 / Negative-3 below) — that break is owned, classified, and signed off in THAT sibling, not here; the set does NOT collectively claim the whole inner engine stays frozen. `pipeline.py` and `adjudicate.py` are superseded by no ADR in this set and remain byte-frozen.

### Rationale

Four options were weighed across the criteria the Context makes load-bearing — **program fidelity** (can the stored plan hold a periodized DOMAIN PROGRAM + narrative + milestones as first-class structure?), **single source of truth** (does the plan the resolver/loop/dashboard read carry the rich content, or is the rich content stored elsewhere and able to drift?), **fail-closed autoregulation** (can a monitoring compiler treat the config as a present, load-bearing contract?), and **freeze/migration cost** (what one-way door and migration does it incur?) — against a rich side artifact (Alternative B), additive extras on the thin schema (Alternative C), and the ADR-0038 compose-over-existing dissent.

On **program fidelity**, only the comprehensive model stores the periodized program, narrative, and milestones as first-class structure. The thin validators accept only the flat payload ([plan_schema.py:178-275](../../scripts/store/plan_schema.py) [VERIFIED]); a periodized DOMAIN PROGRAM stored through them would be rejected or, via ADR-0010 D2's ignore-extras seam, silently un-validated. Alternative C (extras on the thin schema) can attach the fields as optional keys, but ADR-0010 D2 keys are "permitted and IGNORED" ([ADR-0010 D2](ADR-0010-plan-content-schemas-plan-zone-render.md) [VERIFIED]) — periodization-as-ignored-extra is exactly the flat structure the design's quality-plan definition rejects, dressed as extras without the structural change.

On **single source of truth**, the comprehensive model keeps the plan the resolver, loop, dashboard, and tailoring all read AS the rich plan. Alternative B (thin schema of record + the rich program in a side artifact) creates two stored surfaces: the resolver, `track.resolve_plan_progress`, the tailoring emit-gate, and the ADR-0040 hold still read the THIN one ([ADR-0040 Decision §3](ADR-0040-large-change-hold-until-confirm.md) [VERIFIED]), while the periodized program lives out-of-band and can drift from the standing plan the moment either updates — the same dual-surface drift ADR-0038 rejected the `plan-arc::` stream for ([ADR-0038 Alternative B](ADR-0038-plan-time-horizons.md) [VERIFIED]).

On **fail-closed autoregulation**, ADR-0045's monitoring compiler needs a stored config it can rely on being present to run a deterministic daily tier. The comprehensive model makes the compiled monitoring config a first-class part of the stored plan (constrains ADR-0045). A side artifact (B) or ignored extras (C) are optional/unenforced, so a compiler reading them cannot fail-closed on absence — the same reason ADR-0041 rejected a monitoring side-channel ([ADR-0041 Rationale](ADR-0041-uniform-specialist-domain-program-schema.md) [VERIFIED]).

The cost is real and is not hidden: it breaks the ADR-0032 record-spine freeze on `plan_schema.py` (the single biggest one-way door in the set), forces re-basing ADR-0038's horizon composition and ADR-0040's confirmation-pointer + `resolve_plan` skip onto the comprehensive resolver, migrates the append-only store contract, and produces larger stored plans (Consequences-Negative). That cost is accepted because program fidelity, a single source of truth, and fail-closed autoregulation are precisely the properties the plan-first re-architecture exists to deliver, and none of the alternatives provides all three without a drift-prone dual surface or an unenforceable optional field.

### Consequences

**Positive:**
- The stored plan becomes a periodized program, not a flat day-plan: dated blocks/phases, an integrated cross-domain narrative, and dated milestones are first-class stored structure — the quality-plan shape the design fixes, faithfully persisting the ADR-0041 DOMAIN PROGRAM instead of reducing it to a thin payload ([ADR-0041 Decision](ADR-0041-uniform-specialist-domain-program-schema.md) [VERIFIED]).
- The compiled monitoring config has a first-class home in the plan (constrains ADR-0045): the deterministic daily tier reads it from the stored model, not a side stream — closing the NO-LOOP root at the storage layer ([.pipeline/discovery.md](.pipeline/discovery.md) [VERIFIED]).
- Milestones + periodization become a stored object rather than a derived cross-owner join: ADR-0038's Negative-1 (horizon state spread across three owners the consumer must re-join) and Negative-2 (no single materialized arc object) ([ADR-0038 Consequences](ADR-0038-plan-time-horizons.md) [VERIFIED]) are reduced — the arc is stored, not re-derived per render.
- The active-domain set can be dynamic (complements ADR-0046 progressive activation): `PLAN_DOMAINS` in its STORED-PLAN-DOMAIN-KEY role — the closed 4-tuple that fixes which domains a plan can carry ([plan_schema.py:49](../../scripts/store/plan_schema.py) [VERIFIED]) — is superseded by a data-driven active-domain set, so the plan is not a fixed four-card template. (This is distinct from `PLAN_DOMAINS` in its DISPATCH-ROSTER-REGISTRY role, which ADR-0046 GROWS from four to the 15+ roster and keeps as a tuple; the disposition of the two roles is disambiguated in the ADR-0046 Related-Decisions row — RT-009.)

**Negative:**
- **Breaks the ADR-0032 EXTEND-NOT-REBUILD freeze on the record spine — the single biggest one-way door, HARD.** It supersedes the `plan_schema.py` record model (`PLAN_DOMAINS`, the four validators, `record_plan`, `resolve_plan`) held byte-frozen across the project's ~15-session era ([ADR-0032:26,43](ADR-0032-dna-aware-planning.md); [plan_schema.py:49,178-275,371-396,462-498](../../scripts/store/plan_schema.py) [VERIFIED]). Once shipped, reverting to the thin schema is itself a migration.
- **Forces re-basing ADR-0038 and ADR-0040 onto the comprehensive resolver.** ADR-0038's horizon composition reads the flat dated `plan::<domain>` history via a date-range query ([ADR-0038 Decision §4](ADR-0038-plan-time-horizons.md) [VERIFIED]); ADR-0040's confirmation-pointer + `resolve_plan`/`window_block` skip were built on the thin resolver ([ADR-0040 Decision §3](ADR-0040-large-change-hold-until-confirm.md) [VERIFIED]). Both must re-base onto the comprehensive model's resolver, or a held/large-change plan surfaces incorrectly and horizons read the wrong structure — a migration the re-base carries, not a free change.
- **Migration of the append-only store contract + every thin-schema consumer.** The dashboard plan zone, `track.resolve_plan_progress`, the ADR-0037 tailoring emit-gate, `horizons.window_block`, and the plan-evolution loop all read the thin record model; each migrates to the comprehensive model, and the append-only history must reconcile pre-existing thin readings with comprehensive readings (OQ-4) — a correctness burden spread across every plan reader.
- **Larger stored plans.** A comprehensive plan carries a full periodized program per active domain + narrative + milestones + monitoring config, materially larger than a flat day-plan document — more bytes per stored plan version, and (with the ADR-0036 loop day-keying a new plan per trigger) a denser store to read and resolve over.

**Neutral:**
- The comprehensive model is a superset that carries today's flat plan content inside each domain's `prescription`, so no currently-renderable field is lost — the render surface reshapes rather than shrinks (mirrors ADR-0041's superset note, [ADR-0041 Consequences](ADR-0041-uniform-specialist-domain-program-schema.md) [VERIFIED]).
- Whether the underlying `store.append` / `keying.py` primitive is edited or the comprehensive value rides it unchanged is deferred to spec (OQ-2); the record-model supersession holds regardless of which realization the spec picks.

### Alternatives Considered

#### Alternative A: Comprehensive Plan Model (Chosen)
The stored plan holds, per active domain, the full ADR-0041 DOMAIN PROGRAM plus an integrated narrative, dated milestones, the compiled monitoring config, and adjustment rules — superseding the thin `PLAN_DOMAINS` + validators + `record_plan` + `resolve_plan`.
- **Supporting evidence:** The only option that stores the periodized program + narrative + milestones as first-class structure, keeps the plan the resolver/loop/dashboard read AS the rich plan (single source of truth), and gives ADR-0045 a present, load-bearing monitoring config to compile against ([ADR-0041 Decision](ADR-0041-uniform-specialist-domain-program-schema.md); [plan_schema.py:178-275](../../scripts/store/plan_schema.py) [VERIFIED]).
- **Trade-offs:** Breaks the ADR-0032 record-spine freeze (HARD one-way door), forces re-basing ADR-0038/0040, migrates the append-only store contract, and enlarges stored plans (Consequences-Negative). Accepted because program fidelity + single source of truth + fail-closed autoregulation are the properties the re-architecture exists to deliver.
- **When this becomes the right choice:** When the stored plan must BE a periodized, self-monitoring program (not a flat day-plan), and the frozen-spine break is operator-sanctioned — the state at the Phase-1 gate ([.pipeline/state.md](.pipeline/state.md) [VERIFIED]).

#### Alternative B: Keep the thin schema of record + store the rich program in a side artifact
Leave `plan_schema.py`'s thin record model unchanged (no freeze break); persist the periodized program + narrative + milestones + monitoring config in a SEPARATE stored artifact alongside the thin plan.
- **Supporting evidence:** Preserves the ADR-0032 record-spine freeze entirely — the write path, resolver, and validators stay byte-frozen ([ADR-0032:26,43](ADR-0032-dna-aware-planning.md) [VERIFIED]) — so it is the lowest-churn path and needs no store-contract migration.
- **Trade-offs:** REJECTED — two sources of truth. The resolver, `track.resolve_plan_progress`, the tailoring emit-gate, and the ADR-0040 hold still read the THIN plan ([ADR-0040 Decision §3](ADR-0040-large-change-hold-until-confirm.md) [VERIFIED]), while the rich program lives out-of-band and drifts from the standing plan the moment either updates — the dual-surface drift ADR-0038 rejected the `plan-arc::` stream for ([ADR-0038 Alternative B](ADR-0038-plan-time-horizons.md) [VERIFIED]) — and a monitoring compiler reading an optional side artifact cannot fail-closed on its absence.
- **When this becomes the right choice:** If the resolver/loop/dashboard never needed the rich content (they read only the thin plan and the rich artifact is a human-only export), the side artifact's freeze preservation would outweigh the drift risk.

#### Alternative C: Additive rich fields on the thin schema (ADR-0010 D2 open-on-extras)
Keep `PLAN_DOMAINS` + `record_plan` + `resolve_plan`; add `periodization`, `milestones`, `monitoring_config`, and the DOMAIN PROGRAM fields as OPTIONAL extras on the existing thin plan value via the ADR-0010 D2 ignore-extras seam ([plan_schema.py:113-139](../../scripts/store/plan_schema.py) [VERIFIED]).
- **Supporting evidence:** No freeze break and no store-contract migration — the D2 seam was built expressly for additive enrichment ([ADR-0010 D2](ADR-0010-plan-content-schemas-plan-zone-render.md) [VERIFIED]), and it is the path ADR-0038 already uses for horizon extras ([ADR-0038 Decision §3](ADR-0038-plan-time-horizons.md) [VERIFIED]).
- **Trade-offs:** REJECTED — the flat day-keyed structure cannot hold periodization/milestones as first-class, and D2 extras are "permitted and IGNORED," i.e. optional and unenforced ([ADR-0010 D2](ADR-0010-plan-content-schemas-plan-zone-render.md) [VERIFIED]), so the orchestrator/compiler cannot rely on their presence and cannot fail-closed. Periodization-as-ignored-extra is the flat schema with a nested blob bolted on — exactly the "extensible flat value" ADR-0038's Alternative C rejected as insufficient for a structural periodization change ([ADR-0038 Alternative C](ADR-0038-plan-time-horizons.md) [VERIFIED]).
- **When this becomes the right choice:** If the rich fields stayed advisory (rendered when present, never relied on) and the plan never needed to BE a periodized program — then the additive seam's zero-migration cost would dominate.

#### Dissent: Compose horizons over the existing schemas — no new stored model (the ADR-0038 position)
**Source:** ADR-0038's chosen decision and its Alternative C rejection ([ADR-0038 Decision, Alternative C](ADR-0038-plan-time-horizons.md) [VERIFIED]). ADR-0038 decided horizons COMPOSE over `goal_schema` (milestones) + `calendar_schema` (cadences) + the D2-enriched dated `plan::<domain>` history as a date-range query, and explicitly rejected "rewrite the flat `plan_schema` into explicit periodization objects" as high-blast-radius change to a load-bearing shipped schema for a capability the D2 seam supports additively. A purist holds that the same reasoning bars ADR-0044: the periodization rewrite ADR-0038 rejected as Alternative C is exactly what this ADR adopts, and the freeze has served the project across its EXTEND-NOT-REBUILD era.
**Conditions under which this becomes the right choice:** If the plan never needed a materialized, stored monitoring config or arc object — if a monitoring compiler and a loop could function reading a derived composition that may be absent. They cannot: ADR-0045's deterministic daily tier needs a stored, present monitoring config to compile against ([.pipeline/discovery.md](.pipeline/discovery.md) [VERIFIED]), and the orchestrator needs to store one reconciled periodized program, not re-derive it per render. The compose-over-existing path wins only while the plan stays a flat day-plan with no stored autoregulation — the exact limitation the re-architecture set exists to remove; the operator's Phase-1 sign-off on the freeze break resolves the tension in favor of the rewrite ([.pipeline/state.md](.pipeline/state.md) [VERIFIED]).

### Validation Approach

**Confirmation criteria:**
- **A stored plan validates against the comprehensive model (executable).** Author a fixture comprehensive plan for at least two active domains — each carrying its full seven-field DOMAIN PROGRAM — plus an integrated narrative, dated milestones, and a compiled monitoring config; store it and load it back. Threshold: every element (each domain's DOMAIN PROGRAM fields, the narrative, the milestones, the monitoring config) is present and well-typed on load — missing-element count == 0. If any element is absent or rejected, the model does not carry the comprehensive plan — halt.
- **The standing comprehensive plan resolves (executable, the load-bearing probe).** Store a comprehensive plan dated the render date; call the comprehensive resolver. Threshold: it resolves the stored comprehensive plan as standing (the periodized program + narrative + milestones + monitoring config), NOT an absence state. If it returns `NO_PLAN` / `NO_PLAN_TODAY` when a dated comprehensive plan is on file, the resolver re-base regressed — halt.
- **The freeze break is deliberate and scoped to ADR-0044's OWN commit (grep + diff, the freeze-break-honesty probe).** Assert ADR-0044's OWN commit delta supersedes EXACTLY the named record-model surfaces in `plan_schema.py` — `PLAN_DOMAINS`, the four thin validators, `record_plan`, `resolve_plan` ([plan_schema.py:49,178-275,371-396,462-498](../../scripts/store/plan_schema.py) [VERIFIED]) — and touches NO unnamed frozen surface IN ITS OWN COMMIT. Because this decision is built ALONGSIDE sibling supersessions of the same inner-engine glob, the 0-diff assertion is scoped PER-ADR, not set-wide, so the sibling probes do not contradict each other: **explicitly EXCLUDED from ADR-0044's forbidden set** are `generate_plan.py` + `assemble.py` (ADR-0041's translator + `_is_complete` rewrite), `orchestrate.py` (ADR-0043's `orchestrate.reconcile` generalization), and the `adjust.py` / `track.py` consumer migrations (ADR-0045 / this ADR's Negative-3) — each is another commit's INTENDED supersession, not ADR-0044's unnamed edit. What ADR-0044's OWN commit MUST leave byte-unchanged is the remaining frozen inner engine it does not supersede — `pipeline.py` and `adjudicate.py` — plus the `store.append` / `keying.py` primitive per the OQ-2 resolution (edited-and-named, or byte-unchanged with the value riding it). Threshold: ADR-0044's superseded set == the four named `plan_schema.py` surfaces; `git diff --numstat` = 0 changed lines on `pipeline.py` + `adjudicate.py` in ADR-0044's own commit delta; 0 unnamed frozen edits in that delta. (This deliberately inverts ADR-0032's "0 changed lines on the record spine" probe — here the record-model change is intended and bounded; scoping the probe to ADR-0044's own delta is what keeps it from forbidding ADR-0041/0043/0045's sibling supersessions of `generate_plan.py`/`assemble.py`/`orchestrate.py`/`adjust.py`/`track.py`.)

**Falsification criteria:**
- **A comprehensive plan losing periodization/milestones/monitoring on store→load → fail (deterministic).** Store a comprehensive plan whose prescription carries dated periodization blocks, plus dated milestones and a compiled monitoring config; load it. Threshold: 0 loss of periodization, milestones, or monitoring config across the round-trip; if any of the three is dropped or flattened to a thin payload, the model silently degraded to the thin schema — halt and repair before release.
- **The resolver failing to resolve the standing comprehensive plan → fail (deterministic).** With a comprehensive plan dated the render date on file, the comprehensive resolver MUST resolve it as standing. Threshold: standing comprehensive plan → resolved (not absence); if a dated comprehensive plan resolves absent, the resolver regressed — halt.
- **The ADR-0040 hold re-base holds → fail otherwise (deterministic).** Store a held (unconfirmed) large-change comprehensive re-gen; assert the re-based resolver does NOT stand it (the ADR-0040 confirmation-pointer skip re-based onto the comprehensive resolver, [ADR-0040 Decision §3](ADR-0040-large-change-hold-until-confirm.md) [VERIFIED]). Threshold: unconfirmed large-change comprehensive plan → not standing; if it stands pre-confirm, the ADR-0040 hold regressed on the re-base — halt.
- **Time horizon:** run the round-trip-fidelity probe, the standing-resolution probe, and the ADR-0040-re-base probe at the first comprehensive-model build, at the operator-present LIVE run (OQ-5), at every release thereafter, and before the July-2026 physician-visit deliverable.

**Review triggers:**
- ADR-0045 (monitoring compiler) lands — verify the compiled config lives IN the plan model and the daily tier reads it from there, not a side stream (the `constrains` edge).
- ADR-0038's horizon composition is re-based — verify the range-query reads the comprehensive model's stored periodization, not the retired flat dated history.
- ADR-0040's confirmation-pointer + `resolve_plan`/`window_block` skip is re-based — verify the hold re-targets the comprehensive resolver.
- A new plan consumer (dashboard read, export, loop, tailoring pass) is added — verify it reads the comprehensive model, not the superseded thin schema.
- A domain is added to or removed from the active set (ADR-0046 progressive activation) — verify the comprehensive model's active-domain set is dynamic, not the closed `PLAN_DOMAINS` 4-tuple.
