## ADR-0049: Alpha Cost Governance for the Shared-Key Metered Specialist Lane

> **Y-Statement:** In the context of a friction-first alpha where each tester touches only the single shared Anthropic key ADR-0048 D5 ships — so the plan's specialist/judge/lens dispatch cannot ride the per-person Claude subscription (a tester has none), while the built subscription dispatch adapter (`subscription_dispatch.build_dispatch`, [subscription_dispatch.py:45](../../scripts/runner/subscription_dispatch.py) [VERIFIED]) is the ONLY adapter into the injected `run_orchestrated`→`plan_driver.drive` dispatch seam and no metered adapter for that seam exists — facing the tension between the alpha's one-key simplicity (which forces the specialists onto the metered API) and both the flat-rate "0 marginal API spend" economics ADR-0039's subscription lane bought and the hazard of uncontrolled shared-key spend concentrated on one payer, we decided to GOVERN the alpha's model-access cost: BUILD a bounded metered dispatch factory into that existing injected seam (D1, Option B), RULE the routing a no-op on the ADR-0001 egress boundary validated by a wire-scan (D2), accept the metered-cost estimate (D3), gate plan updates behind a manual-default "Update my plan now" trigger plus an optional Off/Weekly/Daily schedule (D4), and cap per-tester spend (D5) — to achieve a one-key alpha whose model-reasoning spend is bounded and operator-controlled, accepting that metered specialists cost more than the flat subscription and that the built ADR-0039 subscription lane goes unused in the alpha (retained as the North-Star path, not deleted).

### Context

The alpha is friction-first and multi-user by per-user local instance: ADR-0048 D5 ships a single shared alpha Anthropic key so a tester "touch[es] nothing" and the operator holds spend with one rotate/revoke point ([ADR-0048:28](ADR-0048-alpha-tester-credential-onboarding.md) [VERIFIED]). That key is the metered no-train lane's credential (`key_source.resolve` reads `ANTHROPIC_API_KEY` → the `a-plus-maxing-api-key` keychain item, [key_source.py:65](../../scripts/model/key_source.py) [VERIFIED]). A tester therefore has NO per-person Claude subscription/OAuth — so the plan's specialist/judge/lens dispatch cannot ride the subscription lane the way the operator's own `/generate-plan` session does.

Two forces pull against each other across more than one stakeholder. ADR-0039 fixed the plan's dispatch economics on the subscription: "the specialist/judge/lens dispatch incurs 0 marginal API spend," with the de-id-IN call the sole metered egress ([ADR-0039:48](ADR-0039-scheduled-agent-runner.md) [VERIFIED]). But that lane is per-person and non-shareable; for a tester who touches only the shared key, the specialists must run on the metered API instead, which bills per call. Against the alpha's one-key simplicity pulls the hazard the sibling ADR-0048 already recorded: a shared key "concentrates … every tester's metered plan-reasoning spend onto one payer" ([ADR-0048:52](ADR-0048-alpha-tester-credential-onboarding.md) [VERIFIED]) — and moving the specialist aggregate onto that key makes the concentrated spend materially larger. The **tester** wants zero setup; the **operator** holds the single shared-key bill and needs it bounded; the **de-id data subject** needs the ADR-0001 egress boundary to hold regardless of which lane authenticates.

The wiring is load-bearing and specific. `run_orchestrated` takes an INJECTED `dispatch` parameter ([plan_orchestrator.py:127](../../scripts/plan/plan_orchestrator.py) [VERIFIED]), so the lane is a dispatch-factory choice at a seam, not plan-engine surgery. But there is no pre-built metered adapter for that seam: `subscription_dispatch.build_dispatch` ([subscription_dispatch.py:45](../../scripts/runner/subscription_dispatch.py) [VERIFIED]) is the ONLY adapter into the `dispatch(name, prompt, context) → envelope` shape, and the metered `ModelClient` is built for de-id (`deidentify`, [client.py:88](../../scripts/model/client.py) [VERIFIED]) and for a SEPARATE screened-only author button (`author` → `orchestrate.generate_plans`, a different shape, [server.py:800,811](../../scripts/serve/server.py) [VERIFIED]) — not as a `run_orchestrated` dispatch adapter. `router.py`, which DEFINES the `SUMMARY_FIELD_SET` whitelist constant the plan-path de-id gate (`deid_in`) mirrors, is one of the ADR-0032 `<always-frozen>` six ([adr-0046-t1.md:86](../task-plan/adr-0046-t1.md) [VERIFIED]).

### Decision

Govern the alpha's model-access cost with five facets (D1–D5). D1 chooses the lane, D2 rules why it is safe, D3 records its cost, and D4/D5 bound that cost; the ADR-0039 subscription lane is RETAINED as the North-Star path throughout.

- **(D1 — Alpha model-access lane. Reversibility: MODERATE.)** For the alpha, route the plan's specialist/judge/lens dispatch to the SHARED METERED API (the ADR-0048 D5 shared key), not the per-person subscription lane, so a tester touches only the one shared key — Option B, operator-chosen. Because no metered adapter exists for the injected `run_orchestrated`→`plan_driver.drive` seam (`subscription_dispatch.build_dispatch` is the ONLY adapter into it, [subscription_dispatch.py:45](../../scripts/runner/subscription_dispatch.py) [VERIFIED]), D1 **BUILDS a bounded metered dispatch factory into that existing injected seam** — it is NOT a one-line swap of a pre-existing metered adapter. The factory lands in `scripts/runner/` or `scripts/serve/` (OUTSIDE the frozen six) and re-points the injection the cadence/loop/daily-monitor path makes ([cadence_runner.py:80-81,119](../../scripts/runner/cadence_runner.py); the `loop_dispatch` seam [server.py:170](../../scripts/serve/server.py) [VERIFIED]). The alpha's in-app plan generation runs server-side through that injected `run_orchestrated`→`drive` seam (the full-composition path), which D1 supplies the metered factory — injected DOWNSTREAM of the `deid_in` de-id boundary ([plan_orchestrator.py:223](../../scripts/plan/plan_orchestrator.py) [VERIFIED]), the placement precondition the D2 no-op ruling rests on (whichever surface OQ-4 selects, the factory MUST sit downstream of that surface's de-id gate); the operator's `/generate-plan` skill — whose specialists are SUBSCRIPTION Agent-tool sub-dispatches ([SKILL.md:3](../../.claude/skills/generate-plan/SKILL.md) [VERIFIED]) — is a DISTINCT surface the alpha tester (who has no subscription) does not use. The ADR-0039 subscription adapter stays built.
- **(D2 — ADR-0001 ruling. A load-bearing RULING, not a design change.)** Routing the specialists to the metered API is a NO-OP on the ADR-0001 crown-jewel egress boundary. `deid_in` — the SOLE de-id-IN gate on the plan path — runs BEFORE any dispatch ([plan_orchestrator.py:223](../../scripts/plan/plan_orchestrator.py) [VERIFIED]), so the dispatch payload is the de-identified summary regardless of lane, and `deid_in`'s OWN fail-closed gate mechanically bounds it: a `set(summary) ⊆ SUMMARY_FIELD_SET` key-whitelist PLUS a non-truncating value-scan for raw PII on every in-set field ([deid_in.py:88-104](../../scripts/plan/deid_in.py) [VERIFIED]). (`router.dispatch`'s identical `⊆ SUMMARY_FIELD_SET` whitelist [router.py:893-897](../../scripts/plan/router.py) is the SEPARATE persisted-store-path gate whose rule `deid_in` mirrors — it has 0 callers on the orchestrator plan path ([deid_in.py:10-11,56](../../scripts/plan/deid_in.py) [VERIFIED]), so it is NOT the gate the specialist payload flows through; it only DEFINES the `SUMMARY_FIELD_SET` constant, in the frozen `router.py`.) **Placement invariant:** D1's metered dispatch factory is injected DOWNSTREAM of `deid_in` on the `run_orchestrated`→`drive` seam — it receives ONLY the already-de-identified summary and the injected `dispatch(name, prompt, context)` seam does not mutate it; the ruling holds IFF the metered adapter sits at that post-`deid_in` seam, never a path that bypasses `deid_in`. The lane choice changes ONLY the authenticating key/token (the `auth_isolation.build_subscription_env` env-scrub, [auth_isolation.py:87](../../scripts/runner/auth_isolation.py) [VERIFIED]), not what the specialist receives — the same shared-key egress-no-op ruling ADR-0048 D5 carries ([ADR-0048:38](ADR-0048-alpha-tester-credential-onboarding.md) [VERIFIED]): a routing/auth change that leaves the de-identified plan-reasoning call unchanged. Validated by a falsifiable wire-scan run end-to-end through `run_orchestrated` with the metered factory injected (Validation Approach), never asserted by prose alone.
- **(D3 — Metered-cost consequence. A CONSEQUENCE, not a decision.)** Specialists on the metered API cost more than the flat subscription; the alpha accepts a bounded tolerance. Every cost figure is an operator/billing ESTIMATE, not a code-grounded fact — the code carries a dispatch-COUNT cap (`dispatch_budget.DEFAULT_DISPATCH_CAP = 64`, [dispatch_budget.py:35](../../scripts/plan/dispatch_budget.py); consumed as `run_orchestrated`'s `dispatch_cap`, [plan_orchestrator.py:129](../../scripts/plan/plan_orchestrator.py) [VERIFIED]), never a dollar figure. Bounded by D4 (cadence) + D5 (per-tester cap); the exact per-plan figure is measured only by the operator-present first LIVE run (Open Questions).
- **(D4 — Plan-update cadence control. Reversibility: EASY.)** Plan updates are MANUAL-DEFAULT: an explicit "Update my plan now" trigger runs the model ONLY on explicit tester request (spend = exactly what is asked), PLUS an OPTIONAL schedule (Off-default / Weekly / Daily) that ARMS the disabled-by-default daily-monitor ([daily_monitor.py:153](../../scripts/runner/daily_monitor.py) [VERIFIED], ADR-0045 — material-event-gated, so bounded even when scheduled) and the weekly cadence runner (ADR-0039). Surfaced in the My Info settings "Plan updates" section and a dashboard affordance. Build dependency, stated honestly: the manual trigger and Off/Weekly options ship now; the daily-INTERVAL enable path is NOT yet built (`activate.py:52` registers the `DAILY_MONITOR_LABEL` but adds no daily enable path — [activate.py:52](../../scripts/runner/schedule/activate.py) [VERIFIED]; deferred to bead `glzi`, itself on `7nw7`/`yeo3`), so the Daily schedule option lights up when `glzi` arms it.
- **(D5 — Per-tester spend cap. Reversibility: EASY.)** Add a cumulative monthly per-tester ceiling on the shared key so one tester cannot exhaust it. A per-RUN dispatch-COUNT cap already exists (`dispatch_budget.DEFAULT_DISPATCH_CAP = 64`, [dispatch_budget.py:35](../../scripts/plan/dispatch_budget.py) [VERIFIED]); the cumulative per-TESTER cap is a new, small concept. Whether it is built in the alpha or a fast follow-on is an Open Question (recommend in-scope for the alpha build if cheap, else a fast follow).

No decision in D1–D5 is a HARD one-way door: D1 is MODERATE (re-point the factory; the subscription adapter is retained), D2 is a load-bearing RULING, D3 is a CONSEQUENCE, and D4/D5 are EASY. The one genuinely irreversible one-way door in the alpha — distributing a shared confidential-client vendor secret — lives in the sibling ADR-0048 D4 ([ADR-0048:48](ADR-0048-alpha-tester-credential-onboarding.md) [VERIFIED]), not in this cluster.

### Rationale

The lane was evaluated across the four axes the alpha makes load-bearing — **onboarding friction**, **cost**, **terms-of-service fit**, and **reversibility** — against each tester bringing their own subscription (Alternative A) and the specialists staying on one shared subscription (Alternative B).

On **friction**, the shared-key metered lane is the only option that keeps ADR-0048 D5's "touch nothing" onboarding: a tester has no Claude subscription, so any subscription-dispatch path reintroduces exactly the per-person credential setup the friction-first alpha exists to remove. On **cost**, the metered lane is the more expensive lane — this is D3's accepted trade — but the code makes the choice reversible at a seam rather than a rebuild: `run_orchestrated`'s `dispatch` is injected ([plan_orchestrator.py:127](../../scripts/plan/plan_orchestrator.py) [VERIFIED]), so re-pointing the factory to the retained subscription adapter reclaims the flat-rate economics at the North-Star cutover with no engine change. On **terms-of-service fit**, one shared consumer subscription serving N testers is not a multi-user arrangement and would run into per-account rate/concurrency limits (Alternative B); the metered API is the contractually-appropriate multi-user lane. On **reversibility**, D1 is MODERATE precisely because the subscription lane is not deleted — `subscription_dispatch.build_dispatch` stays the built adapter, and only the injected factory changes.

The cost the decision accepts is bounded, not open-ended, and the two controls are why the tolerance is acceptable. D4 makes spend deliberate — manual-default means the model runs only on an explicit "Update my plan now," so the day-to-day cost is exactly what a tester asks for, and the optional schedule arms only the disabled-by-default, material-event-gated daily-monitor ([daily_monitor.py:153](../../scripts/runner/daily_monitor.py) [VERIFIED]). D5 caps the cumulative per-tester exposure so a single tester cannot exhaust the shared key. Long-term, the North-Star per-user subscription split reclaims the flat-rate economics ADR-0039 bought; the alpha's metered lane is the bounded interim, not the destination.

### Consequences

**Positive:**
- Testers touch only the shared key: the metered specialist lane preserves ADR-0048 D5's zero-setup onboarding — no per-tester subscription/OAuth to provision ([ADR-0048:28](ADR-0048-alpha-tester-credential-onboarding.md) [VERIFIED]).
- The de-id boundary is unchanged: because `deid_in` runs before dispatch and its OWN `⊆ SUMMARY_FIELD_SET` key-whitelist + value-scan gates the payload ([deid_in.py:88-104](../../scripts/plan/deid_in.py) at [plan_orchestrator.py:223](../../scripts/plan/plan_orchestrator.py) [VERIFIED]), the lane swap — injected downstream of that boundary — moves no PII: the D2 no-op.
- Spend is deliberate and bounded: D4's manual-default makes the model run only on explicit request, and D5 caps per-tester exposure, so the concentrated single-payer bill has two ceilings the un-governed lane lacks.
- The North-Star path is preserved: the ADR-0039 subscription adapter stays built and re-pointable, so the flat-rate economics are reclaimable at the cutover with no engine rebuild.

**Negative:**
- **Metered specialists cost more than the flat subscription — an ongoing per-plan cost on one payer (1+ year while the alpha runs).** The figure is an operator/billing ESTIMATE, never code-grounded: roughly $1–3 per full comprehensive plan on Opus [ESTIMATE], anchored only on the prior old-4-domain walkthrough (de-id-optimized ~$0.07, single-domain ~$0.15 [ESTIMATE]) — the comprehensive plan has NEVER been live-metered. Model tier is the biggest lever (Sonnet vs Opus, ~3–5× [ESTIMATE]) and progressive activation (ADR-0046) means not all specialists fire. The operator accepted a ~$5–10 per-initial-plan tolerance [ESTIMATE]. The exact figure resolves only at the first LIVE run (OQ-2).
- **The built ADR-0039 subscription lane goes UNUSED in the alpha — the subscription-lane-bypass tension.** D1/D3 re-point the dispatch to the metered API, the exact Alternative-C posture ADR-0039 rejected ("arms heavy metered spend … directly contradicts ADR-0026's subscription-dispatch design", [ADR-0039:80](ADR-0039-scheduled-agent-runner.md) [VERIFIED]). `subscription_dispatch.build_dispatch` stays built but un-injected in the alpha; the flat-rate "0 marginal API spend" economics ([ADR-0039:48](ADR-0039-scheduled-agent-runner.md) [VERIFIED]) are forgone until the North-Star split re-points the factory back.
- **D5's per-tester cap is a new invariant to police:** a cumulative spend ledger and its enforcement point are net-new surface, and a mis-set or bypassed cap is a latent way for one tester to over-run the shared key.
- **The D4 Daily-schedule option is partially unbuilt at ship:** the daily-INTERVAL enable path depends on bead `glzi` ([activate.py:52](../../scripts/runner/schedule/activate.py) [VERIFIED]), so the alpha ships the manual trigger + Off/Weekly and lights up Daily only when `glzi` arms — an honestly-deferred capability, not a shipped one.

**Neutral:**
- The per-instance multi-user model is unchanged: each tester's local instance touches the SAME shared key; only whose key pays the specialist dispatch changes, not the per-instance architecture ([ADR-0048:55](ADR-0048-alpha-tester-credential-onboarding.md) [VERIFIED]).
- A metered-lane author path already exists in the serve layer — the screened-only `_do_generate_plan` button uses `self.client.author` on the metered `ModelClient` ([server.py:800](../../scripts/serve/server.py) [VERIFIED]); D1's factory is the full-composition analog on the `run_orchestrated` seam, not the first metered call in the app.

### Alternatives Considered

#### Alternative A: Each tester brings their own Claude subscription
Have every tester authenticate their own Claude subscription/OAuth, so the specialist dispatch rides the flat-rate subscription lane per tester and no metered specialist spend lands on the shared key.
- **Supporting evidence:** Reclaims ADR-0039's "0 marginal API spend" dispatch economics per tester ([ADR-0039:48](ADR-0039-scheduled-agent-runner.md) [VERIFIED]), and isolates spend per tester rather than concentrating it on one payer — the North-Star direction.
- **Trade-offs:** Reintroduces exactly the per-person credential setup the friction-first alpha exists to remove — not every tester has a Claude subscription, and requiring one is the highest-friction onboarding path, contradicting ADR-0048 D5's "touch nothing" default.
- **When this becomes the right choice:** For a developer-only alpha where every tester already holds a Claude subscription, or at the North-Star per-user cutover where each user's own subscription pays.

#### Alternative B: Specialists stay on one shared subscription
Route every tester's specialist dispatch through a single shared Claude subscription (one account, N testers) instead of the metered API.
- **Supporting evidence:** Keeps the flat-rate subscription economics AND the one-credential simplicity — no per-tester setup and no metered per-call bill.
- **Trade-offs:** One consumer subscription serving N testers is not a multi-user arrangement and hits per-account rate/concurrency limits under concurrent testers; it is the wrong terms-of-service shape for shared multi-user use. The shared-key metered API is the appropriate multi-user lane.
- **When this becomes the right choice:** For a single-operator alpha (the author's own machine), where the operator's own subscription session hosts the dispatch and no sharing occurs — the exact case the `/generate-plan` skill's subscription path already serves.

#### Alternative C: Auto-update every tester's plan by default (no cadence control)
Re-generate each tester's plan automatically on a default schedule with no manual-default trigger and no per-tester cap.
- **Supporting evidence:** Simplest UX — the plan stays fresh with zero tester action, and the closed loop (ADR-0036) closes on its own for every tester.
- **Trade-offs:** Uncontrolled shared-key spend — every tester's plan re-generating on a timer multiplies the metered specialist cost across the whole pool onto one payer, with no ceiling. It removes exactly the two controls (D4 manual-default, D5 cap) that make the metered lane's concentrated spend acceptable.
- **When this becomes the right choice:** Once the per-tester cap (D5) and a measured metered-spend budget prove the auto-cadence cost bounded in practice — i.e. after the LIVE run quantifies D3 and the caps are shown to hold.

#### Dissent: Do not govern cost at the ADR level — let the alpha's spend float
**Source:** The operator's accepted ~$5–10 per-plan tolerance [ESTIMATE] and the small trusted-tester pool. A dissenter holds that for a handful of trusted alpha testers on a key the operator can rotate/revoke at will ([ADR-0048:28](ADR-0048-alpha-tester-credential-onboarding.md) [VERIFIED]), the D4 schedule-gating and D5 cap add ceremony for spend that is negligible in practice.
**Conditions under which this becomes the right choice:** If the tester pool stays very small and the measured shared-key spend after the LIVE run (OQ-2) is trivially below the tolerance, the manual-default trigger alone suffices and the per-tester cap can defer to a fast follow-on (the OQ-1 scope call) rather than shipping in the alpha.

### Validation Approach

**Confirmation criteria:**
- **The metered factory injects into the seam and the frozen six stays byte-frozen.** D1's metered dispatch factory is injected into the `run_orchestrated`→`drive` seam (the alpha's plan generation dispatches specialists via it), and `git diff --numstat origin/main -- scripts/store/store.py scripts/store/keying.py scripts/plan/pipeline.py scripts/plan/adjudicate.py scripts/plan/adjust.py scripts/plan/router.py` prints nothing. Expected: ≥1 metered specialist dispatch on the seam; frozen-six numstat == 0.
- **A tester touches only the shared key.** A plan runs end-to-end for a tester with 0 subscription/OAuth credential reads — the specialist dispatch authenticates only via the shared `a-plus-maxing-api-key` metered lane ([key_source.py:65](../../scripts/model/key_source.py) [VERIFIED]). Expected: 0 subscription-lane reads on the alpha plan path.
- **Manual-default cadence.** The "Update my plan now" trigger fires exactly one re-gen per explicit request and 0 re-gens with no request and no armed schedule. Expected: 1 re-gen per explicit press; 0 re-gens otherwise.

**Falsification criteria:**
- **D2 crown-jewel wire-scan (load-bearing; mirrors ADR-0048 D5).** Seed a synthetic raw identifier (a legal name) + a store-content sentinel into `raw_intake`, run `run_orchestrated` END-TO-END WITH THE METERED DISPATCH FACTORY INJECTED (never `router.dispatch` in isolation — it has 0 plan-path callers, so exercising it would bind a fixture, not the production adapter), capture the `(name, prompt, context)` the metered seam actually receives, and assert (a) `set(context) ⊆ SUMMARY_FIELD_SET` with 0 raw-PII hits and 0 store-sentinel hits in the payload, and (b) a lane-swap (metered ↔ subscription factory) changes ONLY the authenticating key/token — 0 change to what the specialist receives. **Threshold:** ≥1 raw-PII or store-sentinel hit on the specialist wire, OR ≥1 payload field outside `SUMMARY_FIELD_SET`, OR any change to the specialist payload on a lane-swap, REDs the D2 ruling → halt and re-scope before release.
- **Frozen-six tripwire.** If the frozen-six numstat is non-empty after D1's build, the metered factory touched the frozen engine → halt and relocate the factory to `scripts/runner/`/`scripts/serve/`.
- **Per-tester cap (D5).** With the per-tester ceiling reached, assert further dispatch is refused for that tester. **Threshold:** ≥1 dispatch past the cap → the cap failed; repair before release.
- **Time horizon:** run the wire-scan, the frozen-six check, and the cadence/cap checks at D1's first build, at the operator-present first LIVE run (the first real metered-cost measurement), and at every release thereafter.

**Review triggers:**
- The operator-present LIVE run completes — reconcile the D3 estimate against the first measured per-plan metered cost (OQ-2).
- Bead `glzi` (the daily-interval enable path) lands — re-validate the D4 Daily-schedule arming against ADR-0045's daily-monitor ([activate.py:52](../../scripts/runner/schedule/activate.py) [VERIFIED]).
- The North-Star per-user subscription split begins — re-point the injected factory back to the retained ADR-0039 subscription adapter and re-run the not-metered dispatch checks.
- Anthropic's metered-API pricing or the subscription rate/concurrency ceiling changes — re-evaluate the metered-vs-flat cost trade (Alternatives A/B).
