## ADR-0025: Adopt a Unified Maintained HTML Output Format

> **Y-Statement:** In the context of a plan-generation engine whose output today is ADR-0004's on-demand single-file render — each `run(artifact_name)` reads the current store and drives exactly one `render.emit`, writing a fresh self-contained HTML file that runs to completion and exits — facing the tension that the S91 full target wants one LIVING plan the orchestrator re-emits and adjusts incrementally as wearables and labs arrive (so the operator holds a single maintained artifact, not a pile of dated stateless regenerations) and wants the tracking and testing sub-surfaces to render into that same format, we decided to adopt a unified maintained HTML output format the orchestrator RE-EMITS and adjusts on new data — AMENDING (not replacing) ADR-0004's generation mechanism, inheriting its single-file portability budget, with the PII-bearing maintained artifact being the gitignored local one ADR-0021 re-inserts onto — to achieve one followable living plan plus folded tracking/testing surfaces, accepting that a maintained artifact carries STATE (staleness, partial-update, and divergence-from-store risk a stateless regeneration never had) and that the gitignored maintained-HTML output path falls in an operator-NAME scan-SCOPE hole in the commit/push PII hooks (`vault/artifacts/generated/` is outside their `DATA_BEARING_PREFIXES` name scan) that must be fixed — by extending the scan scope, not merely adding a fixture — before it ships.

### Context

The plan engine's output boundary is ADR-0004's on-demand, single-file render. `generate.run(artifact_name)` is "a THIN entry point" that reads the store read model via `store.read_all`, selects a template from `_TEMPLATES` (`dashboard`, `handout`, `intake`, `report`), and "drives exactly ONE `render.emit`", which "writes the single self-contained HTML file and returns its path" and is "run-to-completion-and-exit" ([generate.py run L34-98](../../scripts/generate/generate.py) [VERIFIED]). `render.emit` inlines everything into one offline file with 0 external asset references and writes it to the engine-owned `DEFAULT_OUT_DIR = vault/artifacts/generated/` ([render.py emit L149-184, L23](../../scripts/generate/render.py) [VERIFIED]). Each render is stateless: a new reading is reflected only by regenerating, "not by a page that updates itself" ([ADR-0004, Decision + Consequences Negative-2](ADR-0004-on-demand-single-file-artifact-generation.md) [VERIFIED]).

Several forces pull against each other. The S91 full target wants a MAINTAINED artifact: the orchestrator re-emits and adjusts one living plan incrementally as wearables and labs arrive, so the operator holds a single artifact that stays current rather than a directory of dated stateless regenerations whose annotations are lost on each re-run ([discovery.md decision 7 L73-74](.pipeline/engine/discovery.md) [VERIFIED]). The tracking and testing sub-surfaces want to live in that same format — the MEASURE leg (`track.record_tracking` / `resolve_plan_progress`, the plan-vs-actual substrate the dashboard reads) renders into the maintained output rather than its own one-off file ([track.py L1-23](../../scripts/plan/track.py) [VERIFIED]; [discovery.md decision 6 / §7 L72-73](.pipeline/engine/discovery.md) [VERIFIED]). Against the living-artifact pull stands ADR-0004's stateless-regeneration simplicity: a stateless render has no state to go stale, no partial-update window, and cannot silently diverge from the store — a maintained artifact reintroduces exactly those risks ([ADR-0004, Consequences Negative-2](ADR-0004-on-demand-single-file-artifact-generation.md) [VERIFIED]). And the public-repo posture constrains it: the maintained artifact is the one ADR-0021 re-inserts real operator PII onto, so it must be a local gitignored output the commit/push hooks deny ([ADR-0021, Decision + OQ-1](ADR-0021-pii-reinsertion-local-artifact-out.md) [VERIFIED]). Because this changes the artifact LIFECYCLE rather than implementing the settled single-file render, and amends an accepted ADR's generation posture, it is a decision, not a code change.

### Decision

Adopt a unified maintained HTML output format: the orchestrator RE-EMITS and adjusts one living plan artifact as new wearable/lab data arrives, preserving prior content (annotations, tracking history) across re-emits rather than producing a fresh stateless file each run. This AMENDS — does not replace — ADR-0004's on-demand single-file generation mechanism: each emitted artifact stays a single self-contained offline file within ADR-0004's <500KB / inline-everything / WCAG-AA / 0-external-request budget, and the on-demand `generate.run` single-file path survives for any one-off render. The folded tracking and testing sub-surfaces render into this same maintained format. The PII-bearing maintained artifact is the LOCAL, gitignored output (`vault/artifacts/generated/`) ADR-0021 re-inserts real operator PII onto; the persisted store and every TRACKED render stay de-identified.

### Rationale

The output lifecycle was evaluated against ADR-0004's stateless single-file regeneration (status quo) and a live server-rendered format across two criteria the target makes load-bearing: **plan continuity** (does the operator hold one living artifact across data arrivals, or a pile of regenerations) and the **maintenance/staleness cost** (what STATE the lifecycle reintroduces, and whether it stays within ADR-0004's portability budget and the no-egress boundary).

On **plan continuity**, the maintained format wins decisively for the S91 target. ADR-0004's stateless render writes a fresh `<name>.html` each run, so a re-run on new wearable data produces a NEW file and loses any annotation the operator added to the prior one — "a new reading is reflected only by regenerating" ([ADR-0004, Consequences Negative-2](ADR-0004-on-demand-single-file-artifact-generation.md) [VERIFIED]). A maintained artifact re-emits the SAME living plan with the update folded in and prior content preserved, which is exactly the "one living plan, adjusted as data arrives" the operator described ([discovery.md decision 7 L73-74](.pipeline/engine/discovery.md) [VERIFIED]). A live server-rendered format would also give continuity (always-fresh), but at a cost the boundary forbids (below).

On the **maintenance/staleness cost**, the maintained format pays a real price the stateless render did not: an artifact with state can go stale (the emitted file lags the store between re-emits), can be left in a partial-update window mid-re-emit, and can diverge from the store if a re-emit fails halfway — none of which a write-once-and-exit render can do ([ADR-0004, Consequences Negative-2](ADR-0004-on-demand-single-file-artifact-generation.md) [VERIFIED]). The decision accepts this cost because it is bounded: each re-emit still goes through `render.emit`, so every emitted file inherits ADR-0004's single-file/offline/<500KB/0-external-request budget unchanged ([render.py emit L172-184](../../scripts/generate/render.py) [VERIFIED]) — the maintained format is a lifecycle ON TOP of the single-file render, not a new render engine, so the portability and no-egress guarantees ride through. The live server-rendered alternative was rejected on this same criterion: it reintroduces a running-server surface ADR-0013 deliberately scoped the engine away from (loopback intake only), violating the no-live-server posture for the output path ([ADR-0004, Decision "Run no live, always-on server"](ADR-0004-on-demand-single-file-artifact-generation.md) [VERIFIED]).

Long-term, the maintained format keeps the North-Star path reachable: it re-emits through the same `render.emit` boundary the engine already owns, so a future hosted live surface consumes the same store + template inputs without re-deciding the output model, while V1 stays a portable offline artifact ([ADR-0004, Rationale "the same store and template inputs feed a hosted live surface"](ADR-0004-on-demand-single-file-artifact-generation.md) [VERIFIED]).

### Consequences

**Positive:**
- The operator holds ONE living plan the orchestrator re-emits as wearables/labs arrive, with prior annotations and tracking history preserved across re-emits, replacing the stateless "regenerate-loses-annotations" file-per-run model ([ADR-0004, Consequences Negative-2](ADR-0004-on-demand-single-file-artifact-generation.md) [VERIFIED]; [discovery.md decision 7 L73-74](.pipeline/engine/discovery.md) [VERIFIED]).
- The tracking and testing sub-surfaces render into the SAME maintained format instead of separate one-off artifacts: the MEASURE-leg plan-vs-actual substrate (`track.resolve_plan_progress`) becomes a folded view of the living plan, so the operator and physician scan one artifact, not a scattered set ([track.py L14-19](../../scripts/plan/track.py) [VERIFIED]; [discovery.md decision 6 L72-73](.pipeline/engine/discovery.md) [VERIFIED]).
- Each emitted artifact inherits ADR-0004's portability budget unchanged — still one self-contained offline file, <500KB, WCAG-AA, 0 external requests — because every re-emit goes through `render.emit` ([render.py emit L172-184](../../scripts/generate/render.py) [VERIFIED]).

**Negative:**
- A maintained artifact carries STATE the stateless render did not: it can go stale (the emitted file lags the store between re-emits), can sit in a partial-update window mid-re-emit, and can diverge from the store if a re-emit fails partway — a standing 1+ year correctness surface (does the artifact match the store at read time?) that ADR-0004's write-once-and-exit render structurally could not have ([ADR-0004, Consequences Negative-2](ADR-0004-on-demand-single-file-artifact-generation.md) [VERIFIED]).
- The maintained artifact WIDENS the local-PII surface: it is the long-lived gitignored file ADR-0021 re-inserts real operator PII onto, so real PII now persists in a maintained local artifact across re-emits rather than living only in a fresh transient render — every re-emit must hold the gitignored-only boundary, and a misrouted or force-added re-emit leaks PII that cannot be cleanly scrubbed ([ADR-0021, Decision + Consequences Negative-1](ADR-0021-pii-reinsertion-local-artifact-out.md) [VERIFIED]; [ADR-0005, Falsification](ADR-0005-operator-agnostic-clonable-pii-free-trunk.md) [VERIFIED]).
- The `block-pii-commit.sh` + `pre-push-pii-scan.sh` hooks have an operator-NAME scan-SCOPE hole on the `vault/artifacts/generated/` maintained-HTML output path, not merely a missing fixture: `pii_scan.scan_scoped` runs the name tokens ONLY over the `data_bearing` subset, and `DATA_BEARING_PREFIXES` excludes the artifacts path ([pii_scan.py scan_scoped L375-406](../../scripts/guard/pii_scan.py), [lib/pii-scan-scope.sh L30](../../.claude/hooks/lib/pii-scan-scope.sh) [VERIFIED]), so a committed maintained-HTML artifact carrying the re-inserted NAME is scanned only for trunk-wide CONTACT tokens by both hooks. The new output path's name-token coverage is absent until the scan SCOPE is extended to cover the artifacts path AND a fixture proves the change denies a name-bearing artifact (the shared Open Question, OQ-1) ([ADR-0021, Consequences Negative-2 + OQ-1](ADR-0021-pii-reinsertion-local-artifact-out.md) [VERIFIED]).

**Neutral:**
- The on-demand single-file `generate.run` path is NOT deleted: it survives for any one-off render, with the maintained re-emit lifecycle layered over it for the living plan ([generate.py run L34-98](../../scripts/generate/generate.py) [VERIFIED]).
- The output target is unchanged — both the stateless render and the maintained re-emit write to `vault/artifacts/generated/`, already gitignored ([render.py L23](../../scripts/generate/render.py), [.gitignore L6](../../.gitignore) [VERIFIED]).

### Alternatives Considered

#### Alternative A: Unified maintained / re-emit-on-new-data format (Chosen)
The orchestrator re-emits and adjusts one living plan artifact as wearables/labs arrive, preserving prior content across re-emits, with the tracking/testing surfaces folded into the same format — each emitted file still single-file via `render.emit`.
- **Supporting evidence:** Delivers the S91 "one living plan, adjusted as new data arrives" target ([discovery.md decision 7 L73-74](.pipeline/engine/discovery.md) [VERIFIED]); folds the tracking/testing sub-surfaces into one artifact ([discovery.md decision 6 L72-73](.pipeline/engine/discovery.md) [VERIFIED]); inherits ADR-0004's portability budget because every re-emit goes through `render.emit` ([render.py emit L172-184](../../scripts/generate/render.py) [VERIFIED]).
- **Trade-offs:** Reintroduces artifact STATE (staleness, partial-update, store-divergence) the stateless render had none of (Consequences Negative-1), and widens the local-PII surface to a long-lived gitignored maintained file (Negative-2).
- **When this becomes the right choice:** It is, for the S91 target, when the operator needs one current living plan that absorbs new wearable/lab data without losing annotations — exactly the engine's full-target output.

#### Alternative B: Keep ADR-0004 on-demand single-file regeneration (status quo)
Leave the output as ADR-0004's stateless render — each `run(artifact_name)` reads the store and writes a fresh self-contained file that runs to completion and exits, with no living artifact maintained across data arrivals.
- **Supporting evidence:** Simplest possible lifecycle and the current, tested, shipped behavior: a write-once-and-exit render has no state to go stale, no partial-update window, and cannot diverge from the store — the artifact is always a clean snapshot at generation time ([ADR-0004, Decision + Consequences](ADR-0004-on-demand-single-file-artifact-generation.md) [VERIFIED]; [generate.py run L34-98](../../scripts/generate/generate.py) [VERIFIED]). It carries the narrowest PII surface: a fresh transient render, not a long-lived maintained file.
- **Trade-offs:** Has no single living artifact — a re-run on new data produces a NEW file and loses any annotation on the prior one ([ADR-0004, Consequences Negative-2](ADR-0004-on-demand-single-file-artifact-generation.md) [VERIFIED]) — so the operator accumulates a pile of dated regenerations instead of one maintained plan, and the tracking/testing surfaces stay separate one-off artifacts rather than folding into one format. It cannot deliver the S91 "adjusted as data arrives" target.
- **When this becomes the right choice:** If the operator decides one-off snapshots suffice and a living maintained artifact's state-correctness cost is not worth the continuity — then the stateless render remains correct and the maintained lifecycle is rejected (it is also the retained one-off path under the chosen option).

#### Alternative C: Live server-rendered format
Stand up a running local server (or app) that renders the plan live in a browser and updates as new readings arrive, giving an always-fresh maintained view without an emitted file.
- **Supporting evidence:** Richest continuity — an always-fresh live view reflects new wearable/lab data with no re-emit step at all, the natural home for interactive drill-down, and the surface the North-Star hosted product eventually builds ([ADR-0004, Alternative A](ADR-0004-on-demand-single-file-artifact-generation.md) [VERIFIED]).
- **Trade-offs:** Reintroduces a running-server surface ADR-0013 deliberately scoped the engine AWAY from — the engine's only server carve-out is the operator-started loopback INTAKE server, not an output-serving surface — violating ADR-0004's no-live-server output posture and reintroducing a network surface the no-egress PII boundary forbids ([ADR-0004, Decision "Run no live, always-on server" + Alternative A trade-offs](ADR-0004-on-demand-single-file-artifact-generation.md) [VERIFIED]). A served page also breaks the clonable/offline/emailable artifact V1 commits to.
- **When this becomes the right choice:** At the North-Star transition to a hosted product with a clinician-facing live surface and the regulated-PHI trust model built, where an always-fresh served view is required — the same condition ADR-0004 names for its Alternative A.

### Validation Approach

**Confirmation criteria:**
- New wearable/lab data arrives → the orchestrator re-emits the maintained artifact with the update folded in, and the prior content (annotations, tracking history) is PRESERVED across the re-emit — verified by emitting the maintained plan, adding an annotation/tracking entry, re-emitting after a new data point, and asserting the new data point is present AND the prior annotation/tracking entry survives in the re-emitted file (expected: both present, 0 lost) ([discovery.md decision 7 L73-74](.pipeline/engine/discovery.md) [VERIFIED]).
- Each emitted/re-emitted artifact stays one self-contained offline file with 0 external asset requests and <500KB — verified by `render.emit` raising on any external reference and a size check on the re-emitted file (expected: 0 external requests, size < 500KB), the same checks ADR-0004 fixes ([render.py emit L172-184](../../scripts/generate/render.py) [VERIFIED]).
- The tracking/testing surfaces render INTO the maintained format — verified by re-emitting after `track.record_tracking` records a snapshot and asserting the plan-vs-actual view appears as a folded section of the maintained artifact, not a separate file ([track.py L14-19](../../scripts/plan/track.py) [VERIFIED]).

**Falsification criteria:**
- **Re-inserted-PII-in-a-committed-render probe (threshold 0):** craft a maintained-HTML re-emit carrying re-inserted real operator PII (the ADR-0021 OUT side), stage/commit it and stage/push it. Assert the `block-pii-commit.sh` PreToolUse hook DENIES the commit AND the `pre-push-pii-scan.sh` hook DENIES the push — **0 real-PII values reach any tracked/committed file** ([ADR-0021, Falsification](ADR-0021-pii-reinsertion-local-artifact-out.md) [VERIFIED]). If the count exceeds 0, a maintained render leaked PII to public history that cannot be cleanly scrubbed — halt and restore the gitignored-only boundary before the format ships (release-blocking). The PII-bearing maintained artifact must be the gitignored `vault/artifacts/generated/` output only ([.gitignore L6](../../.gitignore) [VERIFIED]).
- If a re-emit fails partway and leaves the maintained artifact diverged from the store (the artifact shows a plan/tracking state the store no longer holds), the maintained-state correctness floor has broken — halt and re-emit from the store's current state (a stale/partial maintained artifact silently misrepresenting the store is the state cost this lifecycle accepts; ≥1 such divergence at read time is the threshold to fix the re-emit atomicity) ([ADR-0004, Consequences Negative-2](ADR-0004-on-demand-single-file-artifact-generation.md) [VERIFIED]).
- Time horizon: run the re-inserted-PII probe at the first maintained re-emit and at every release thereafter, and before the July-2026 physician-visit deliverable ships; run the store-divergence check on every re-emit.

**Review triggers:**
- The maintained-HTML output path reaches build — extend the name-token scan SCOPE to cover `vault/artifacts/generated/` and re-verify the `block-pii-commit.sh`/`pre-push-pii-scan.sh` hooks deny a name-bearing artifact on that surface before it ships (OQ-1, shared with ADR-0021; a fixture under the current scope is insufficient).
- A maintained re-emit would exceed ADR-0004's <500KB budget as the living plan accumulates tracking history — re-evaluate the size budget vs. the maintained content (ADR-0004's standing size-headroom concern, now compounded by maintained accumulation).
- ADR-0021's OUT mechanism changes (deterministic → model-backed) — re-confirm the maintained artifact's re-inserted-PII source still lands only on the gitignored output path.
