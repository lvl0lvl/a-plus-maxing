## ADR-0038: Time Horizons Composed Over Existing Schemas — No New Stored Schedule

> **Y-Statement:** In the context of a plan zone that stores flat, day-keyed per-domain `plan::<domain>` documents ([plan_schema.py:49,371-396](../../scripts/store/plan_schema.py) [VERIFIED]) while the operator wants a plan that spans daily / weekly / monthly horizons and evolves toward goals — and facing the temptation to introduce a NEW `plan-arc::` stored stream to carry milestones + cadences + periodization — we decided to COMPOSE horizons over what already exists: milestone-progress via `goal_schema` (`{label, baseline, current, target}` → a read-DERIVED 0-100 percent, [goal_schema.py:122-137,189-218](../../scripts/store/goal_schema.py) [VERIFIED]), dated cadences (lab recheck, check-in) via `calendar_schema` (`calendar::events` dated `{category, label}`, [calendar_schema.py:44,91-116](../../scripts/store/calendar_schema.py) [VERIFIED]), and weekly/monthly framing by enriching the existing dated `plan::<domain>` values through the ADR-0010 D2 "open on extras" seam ([plan_schema.py:113-139](../../scripts/store/plan_schema.py) [VERIFIED]) — so that "this week's block / the month arc" is a DATE-RANGE QUERY over the dated plan history, NOT a second stored schedule; peptides stays untracked (ADR-0010 D3, [plan_schema.py:50](../../scripts/store/plan_schema.py) [VERIFIED]) and rides the existing watch-out stream; and an open-ended goal with no deadline degrades gracefully to rolling maintenance cycles — to achieve horizons + goal-evolution with ZERO new store schema and no duplicated progress surface, accepting that horizon state is now spread across three owners that must stay coherent and that there is no single "plan-arc" object to render.

### Context

The operator's ask (design §1, [dynamic-plan-loop-design.md:33-35](../../design/dynamic-plan-loop-design.md) [VERIFIED]) is a plan that "spans daily/weekly/monthly horizons and evolves toward goals." Three forces meet at this decision.

- **The plan is FLAT and day-keyed today.** A `plan::<domain>` reading carries one plan document at one declared `YYYY-MM-DD` timepoint, and `resolve_plan` resolves "today" by DATE EQUALITY against the render date ([plan_schema.py:462-498](../../scripts/store/plan_schema.py) [VERIFIED], the equality at [plan_schema.py:486](../../scripts/store/plan_schema.py) [VERIFIED]). There is no week/month object; the store holds a sequence of dated day-plans, nothing that frames a week's block or a month's arc.

- **The operator wants HORIZONS + goal-directed evolution.** Daily action, this-week's block, the month arc, and progress toward a target — the shape of "am I on track, behind, or ahead" that the plan-evolution loop (ADR-0036) needs to evaluate a re-generation against.

- **The review found the machinery ALREADY EXISTS, and the flat-schema framing was wrong.** Design finding G ([dynamic-plan-loop-design.md:21](../../design/dynamic-plan-loop-design.md) [VERIFIED], verified against the live tree) established three facts. (1) `plan_schema` is NOT "frozen flat": ADR-0010 D2 is "closed on required fields, **open on extras**" ([ADR-0010, D2](ADR-0010-plan-content-schemas-plan-zone-render.md) [VERIFIED]), realized in `_check_fields`, which enumerates ONLY the required and optional dicts and so **permits and ignores any key absent from both** — extras are allowed by OMISSION, because the function never scans `mapping` for unknown keys to reject ([plan_schema.py:113-139](../../scripts/store/plan_schema.py) [VERIFIED]; the closed-on-required / open-on-extras contract is stated in its docstring, [plan_schema.py:116-118](../../scripts/store/plan_schema.py) [VERIFIED]) — a deliberate forward-compatibility seam, not an accident to route around. (2) `goal_schema` already OWNS milestones + progress: it stores `{label, baseline, current, target}` and DERIVES a direction-agnostic 0-100 percent on read (`_percent`, clamped floor-0 / ceil-100, [goal_schema.py:122-137](../../scripts/store/goal_schema.py) [VERIFIED]; `resolve_goal` returns `{label, percent, baseline, current, target, unit, on_date}` from the latest-dated snapshot, [goal_schema.py:189-218](../../scripts/store/goal_schema.py) [VERIFIED]). (3) `calendar_schema` already OWNS dated cadences: `calendar::events` stores dated `{category, label}` over the four categories `training / lab-draw / check-in / appointment` ([calendar_schema.py:44,91-116](../../scripts/store/calendar_schema.py) [VERIFIED]), read back grouped by date ([calendar_schema.py:119-135](../../scripts/store/calendar_schema.py) [VERIFIED]) — lab-recheck and check-in cadences are already first-class. (4) Peptides is NOT a `TRACKED_DOMAIN`: `TRACKED_DOMAINS = (workout, nutrition, supplements)`, and while `PLAN_DOMAINS` includes peptides, ADR-0010 D3 declined a fourth tracked domain ([plan_schema.py:49-50](../../scripts/store/plan_schema.py) [VERIFIED]; [ADR-0010, D3](ADR-0010-plan-content-schemas-plan-zone-render.md) [VERIFIED]).

The decision the Context forces: given milestones, cadences, and an extensible plan value ALL already exist and are owned, does "horizons" justify a NEW stored stream, or is it a COMPOSITION over the three existing owners? The cross-document ownership matrix (CLAUDE.md) says each fact lives in exactly one document; a `plan-arc::` stream carrying progress + cadence would DUPLICATE goal_schema's and calendar_schema's ownership and create two progress surfaces that can disagree.

### Decision

**Horizons are COMPOSED over the three existing schema owners; no new stored stream is introduced.**

1. **Milestone-progress = `goal_schema`.** "Evolving toward goals" reads the already-derived progress percent: each goal's `{label, baseline, current, target}` → `_percent` ([goal_schema.py:122-137](../../scripts/store/goal_schema.py) [VERIFIED]). No progress value is stored or recomputed elsewhere — the derivation stays in its one owner ([goal_schema.py:212](../../scripts/store/goal_schema.py) [VERIFIED]).

2. **Dated cadences = `calendar_schema`.** Lab-recheck / check-in / appointment cadences are `calendar::events` dated `{category, label}` ([calendar_schema.py:44,91-116](../../scripts/store/calendar_schema.py) [VERIFIED]). "The next recheck / check-in" is a read over `read_events` grouped by date ([calendar_schema.py:138-147](../../scripts/store/calendar_schema.py) [VERIFIED]), not a new schedule object.

3. **Weekly/monthly framing = the ADR-0010 D2 "open on extras" seam.** The existing dated `plan::<domain>` values are ENRICHED with horizon extras (e.g. a `phase` / `week_intent` key), which `_check_fields` permits by OMISSION — the horizon keys are in no domain's required or optional dict, and the function rejects only missing/mistyped DECLARED fields, never an unknown key ([plan_schema.py:113-139](../../scripts/store/plan_schema.py) [VERIFIED]) — closed on the domain's required fields, open on these extras — so the enrichment needs ZERO schema change and ZERO writer change (the D2 seam ADR-0010 built on purpose).

4. **"This week's block / the month arc" = a DATE-RANGE QUERY, not a second stored schedule.** The dated plan history already IS the timeline: a week/month view is a query over `plan::<domain>` readings whose `timepoint` falls in the range, resolved by the same date semantics `resolve_plan` uses ([plan_schema.py:462-498](../../scripts/store/plan_schema.py) [VERIFIED]). "Today" stays the single-date equality resolution ([plan_schema.py:486](../../scripts/store/plan_schema.py) [VERIFIED]); "this week"/"this month" widen the same predicate to a range. No week-object or month-object is stored.

5. **Peptides carries NO cadence/tracking domain.** Peptides is untracked (ADR-0010 D3, [plan_schema.py:50](../../scripts/store/plan_schema.py) [VERIFIED]); it has no `plan-track::` snapshot and gets no horizon cadence — it rides the existing watch-out stream, unchanged.

6. **Open-ended goals degrade gracefully.** A goal with no deadline (longevity/maintenance) has no target-date to frame a horizon against, so the horizon view falls back to ROLLING MAINTENANCE CYCLES rather than fabricating a deadline. `goal_schema` already tolerates this: its progress percent is derived from `baseline/current/target` with no date requirement ([goal_schema.py:84-106,122-137](../../scripts/store/goal_schema.py) [VERIFIED]), so an open-ended goal still resolves an honest progress reading; the horizon layer simply presents rolling cycles instead of a countdown.

The horizon layer is therefore a READ/QUERY composition over `goal_schema` + `calendar_schema` + the D2-enriched `plan::<domain>` history. It writes no new stream and defines no new key.

### Consequences

**Positive:**
- **Zero new store schema.** Horizons reuse three existing owners and the D2 extras seam; no `plan-arc::` stream, no new key, no new writer/reader I/O. The ownership matrix stays clean — progress lives only in `goal_schema`, cadence only in `calendar_schema`, plan content only in `plan::<domain>`.
- **The evolution loop (ADR-0036) gets its on-track / behind / ahead signal for free.** A re-generation's evaluation reads the SAME derived goal percent + the SAME dated cadence + the SAME date-range plan history; a declared per-week expectation is machine-comparable against the actual trend without any new stored surface.
- **The enrichment is forward-compatible by construction.** Because the week/month framing rides the D2 open-on-extras seam — keys allowed by their absence from the required/optional dicts ([plan_schema.py:113-139](../../scripts/store/plan_schema.py) [VERIFIED]) — a plan writer that omits the horizon extras still validates and renders — the flat day-plan is the graceful floor, the enriched plan is the horizon-aware view.

**Negative (accepted):**
- **Horizon state is SPREAD across three owners that must stay coherent.** "Am I on track" is assembled from goal_schema (progress), calendar_schema (the next cadence), and the plan-history range query (the week/month blocks) — three reads that must agree at render time. There is no single object that holds "the horizon"; a consumer that reads one owner and not the others sees a partial horizon. The mitigation is that each owner is already the single source for its fact (no duplication to drift), but the COMPOSITION coherence is now the consumer's burden, not a stored invariant.
- **There is NO single "plan-arc" object to render or hand off.** A UI or export that wants "the month arc" as one artifact must run the date-range query + join the goal + join the cadence itself; nothing serializes the assembled horizon. This is the deliberate cost of not storing a second schedule — the arc is always derived, never materialized.
- **The evolution loop (ADR-0036) DENSIFIES the plan history this ADR's range query reads.** ADR-0036 day-keys a NEW dated `plan::<domain>` set on every trigger (all domains, even ones that did not change), so several same-week automated re-generations can leave MULTIPLE dated plans inside one week/month window. The date-range horizon query therefore cannot assume one plan per window — it must SELECT among multiple same-window readings (latest-in-window wins, mirroring the today-by-date-equality rule at [plan_schema.py:486](../../scripts/store/plan_schema.py) [VERIFIED]), which is OQ-2's charge. ADR-0036's debounce (minimum re-generation interval) BOUNDS the trigger frequency and thus the density, but does not by itself resolve the selection; the range query must be written to tolerate the denser history the loop can produce.

**Neutral:**
- The set of horizon-extra keys on `plan::<domain>` (e.g. `phase`, `week_intent`) is a naming convention layered on the D2 seam, not a schema — it can grow without a schema migration, and an unknown extra is ignored, so a typo'd horizon key silently no-ops rather than raising (the standing D2 tradeoff, not new to this ADR).

### Alternatives Considered

#### Alternative A: Compose over goal_schema + calendar_schema + the ADR-0010 extras seam (Chosen)
Milestones from `goal_schema`, cadences from `calendar_schema`, week/month framing from D2-enriched `plan::<domain>` values, and the week/month view as a date-range query over the dated plan history.
- **Supporting evidence:** All three owners already exist and are verified ([goal_schema.py:189-218](../../scripts/store/goal_schema.py), [calendar_schema.py:91-116](../../scripts/store/calendar_schema.py), [plan_schema.py:113-139](../../scripts/store/plan_schema.py) [VERIFIED]); the D2 seam was built expressly for this kind of enrichment ([ADR-0010, D2](ADR-0010-plan-content-schemas-plan-zone-render.md) [VERIFIED]). No new store schema, no duplicated progress surface.
- **Trade-offs:** Horizon state is spread across three owners (Negative-1); no single materialized arc object (Negative-2). Accepted because it is the only option that adds horizons with zero new schema and keeps each fact in its one owner.

#### Alternative B: A new `plan-arc::` STORED stream carrying milestones + cadences + periodization
Introduce a dedicated stream that stores the goal progress, the cadence schedule, and the week/month periodization as one arc object per plan.
- **Supporting evidence:** A single stored object is the most direct thing to render — one read yields "the horizon," no cross-owner join.
- **Trade-offs:** REJECTED. It reinvents `goal_schema` (progress) and `calendar_schema` (cadence) inside a third stream — a direct Cross-Document Ownership Matrix violation (CLAUDE.md): progress would live in BOTH `goal::<slug>` and `plan-arc::`, creating TWO progress surfaces that can disagree the moment a goal snapshot updates but the arc does not. It is exactly the "new store stream reinventing what already exists" that design finding E/G rejects ([dynamic-plan-loop-design.md:19,21](../../design/dynamic-plan-loop-design.md) [VERIFIED]). The single-render-object convenience does not justify a duplicated, drift-prone progress source.

#### Alternative C: Rewrite the flat `plan_schema` into explicit periodization objects
Replace the flat day-keyed `plan::<domain>` document with a nested week→day / month→week periodization structure so the schema itself carries horizons.
- **Supporting evidence:** Horizons would be first-class in the plan value, not a query — the week/month structure is explicit in storage.
- **Trade-offs:** REJECTED. ADR-0010 designed the plan value flat-and-extensible ON PURPOSE — closed on required fields, open on extras ([ADR-0010, D2](ADR-0010-plan-content-schemas-plan-zone-render.md) [VERIFIED]) — precisely so the shape stays stable while producers enrich it. A periodization rewrite is a big, risky change to a load-bearing, already-shipped schema with existing writers/readers/renders ([plan_schema.py:371-517](../../scripts/store/plan_schema.py) [VERIFIED]), breaking the date-equality "today" resolution and every consumer, to buy a structure the D2 seam already supports additively. High blast radius for a capability the chosen option gets for free.

#### Alternative D: Add a peptide tracking domain to carry a peptide cadence
Make peptides a fourth `TRACKED_DOMAIN` so it can carry its own horizon cadence + progress like workout/nutrition/supplements.
- **Supporting evidence:** Peptides would get the same horizon treatment as the other domains — symmetric coverage.
- **Trade-offs:** REJECTED. ADR-0010 D3 explicitly DECLINED a fourth tracked domain and routed peptide tracking to the existing watch-out stream ([plan_schema.py:50](../../scripts/store/plan_schema.py) [VERIFIED]; [ADR-0010, D3](ADR-0010-plan-content-schemas-plan-zone-render.md) [VERIFIED]). Re-adding it here would reverse a standing decision (and a "fifth plan domain / new tracked domain" is an ADR-0010 review trigger, [ADR-0010, Review triggers](ADR-0010-plan-content-schemas-plan-zone-render.md) [VERIFIED]) with no new evidence — this ADR's scope is horizons, not re-litigating the tracked-domain set. Peptides rides the watch-out stream, unchanged.

### Validation Approach

**Confirmation criteria:**
- **Four-horizon composition (fixture run):** a horizon-aware run over a seeded store yields, for a single render date, ALL of: (a) today's action — the `plan::<domain>` reading whose `timepoint` EQUALS the render date ([plan_schema.py:486](../../scripts/store/plan_schema.py) [VERIFIED]); (b) this-week's block — the set of `plan::<domain>` readings whose `timepoint` falls in the 7-day range; (c) the month arc — the same range query widened to the month; and (d) a milestone — a `goal_schema` progress reading with a derived percent ([goal_schema.py:212](../../scripts/store/goal_schema.py) [VERIFIED]). Expected: all four present from the SAME store, zero new store keys written (grep the store for `plan-arc::` → 0 hits).
- **Derived, deterministic progress (unit):** for a seeded goal `{baseline, current, target}`, the horizon milestone percent EQUALS `_percent(baseline, current, target)` exactly ([goal_schema.py:122-137](../../scripts/store/goal_schema.py) [VERIFIED]) — no second progress computation. Expected: exact equality; a second progress site anywhere → fail (ownership-matrix violation).
- **Machine-comparable expectation vs actual (deterministic):** given a declared per-week expectation (e.g. `-0.4 kg/wk`) enriched onto the plan via the D2 extras seam and an actual trend of `-0.1 kg/wk` from the goal/biomarker reads, the evaluation classifies "behind" deterministically (expected slope steeper than actual → behind; equal/faster → on-track/ahead). Expected: the (expectation, actual) pair maps to a fixed verdict with no model call — a pure comparison.
- **Enrichment rides D2 with zero schema change:** a `plan::<domain>` document carrying horizon extras (`phase` / `week_intent`) validates through `record_plan` UNCHANGED, and a document WITHOUT them still validates (the flat floor). Expected: both pass `_check_fields` ([plan_schema.py:113-139](../../scripts/store/plan_schema.py) [VERIFIED]); no writer/schema edit in the diff.

**Falsification criteria:**
- **No-new-stream probe:** grep the horizon build + store for any new `::`-prefixed item id (a `plan-arc::` / `horizon::` / `periodization::` stream) or a second key definition. Threshold: **0 new store streams**, **0 second progress-derivation sites**. Concrete targets: a store-scan assertion `grep -RE 'plan-arc::|horizon::|periodization::' scripts/store` → 0 hits, and a single-progress-site assertion that the only `_percent` caller feeding a horizon reading is `resolve_goal` ([goal_schema.py:212](../../scripts/store/goal_schema.py) [VERIFIED]). If ≥1 new stored stream carries progress or cadence, the composition was replaced by a duplicated surface — halt and re-route through `goal_schema` / `calendar_schema` / the D2 seam.
- **Open-ended-goal degradation probe:** seed a goal with NO deadline/target-date and run the horizon view. Threshold: the view presents ROLLING MAINTENANCE CYCLES and FABRICATES NO deadline — assert no synthesized target-date appears anywhere in the horizon output, and the goal still resolves an honest progress percent ([goal_schema.py:122-137](../../scripts/store/goal_schema.py) [VERIFIED]). If a deadline is invented, graceful degradation broke — halt.
- **Peptides-untracked probe:** run the horizon composition over a store containing a `plan::peptides` document. Threshold: peptides receives NO cadence and NO `plan-track::` horizon (it is not in `TRACKED_DOMAINS`, [plan_schema.py:50](../../scripts/store/plan_schema.py) [VERIFIED]); it appears only via the watch-out stream. If a peptide cadence/tracking horizon is emitted, D3 was reversed — halt.
- **Today-by-date-equality probe:** the "today's action" horizon resolves by DATE EQUALITY, not proximity: a plan dated yesterday and a plan dated the render date both on file → the render-date plan wins, and with NO render-date plan the today slot reads absent (`NO_PLAN_TODAY`), never the nearest ([plan_schema.py:462-498](../../scripts/store/plan_schema.py) [VERIFIED]). Threshold: exact date-equality selection; a nearest-date fallback → fail.

**Review triggers:**
- A horizon consumer needs a materialized single arc object (export/UI) frequently enough that the cross-owner join becomes a bottleneck — re-open Alternative B against the ownership-matrix cost.
- A goal type genuinely requires stored (not derived) progress — re-examine whether the derived-percent composition still holds.
- A fifth plan domain or a new tracked domain lands (an ADR-0010 review trigger) — re-validate the peptides-untracked assumption.
