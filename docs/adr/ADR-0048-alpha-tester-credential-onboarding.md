## ADR-0048: Alpha-Tester Credential Onboarding via App-Mediated OAuth

> **Y-Statement:** In the context of a friction-first alpha that must onboard each tester's tracker and model credentials in-app — where the intake's Step-9 "API key" step and the `My Info` settings surface already exist but the one-time OAuth authorize is still an out-of-band operator step (the tracker design note) and no OAuth callback route exists in the loopback server — facing the tension between a one-click connect flow (which needs a new inbound callback surface and, for confidential-client vendors, a shared secret on testers' machines) and both the ADR-0001 crown-jewel egress boundary and the ADR-0005 PII-free trunk, we decided to bring credential provisioning in-app: an app-mediated OAuth authorization-code flow with a localhost-only PKCE callback, app-mediated credential writes that extend ADR-0013's single-key keychain write to N per-source tokens through the ADR-0047 store, shared vendor client credentials distributed only via an out-of-band alpha-build config (never a tracked file; the one-click flow's shared secret scoped by grounding to the confidential-client vendors — at least Whoop, the exact per-vendor set `[VERIFY-AT-BUILD]`) with a shared alpha Anthropic key as the default, all reached by EXTENDING the Step-9 and `My Info` surfaces rather than a new wizard — and we RULE that the authorization/token exchange carries only OAuth artifacts (0 store bytes, 0 model-lane calls) so it is not a new ADR-0001 egress class — to achieve one-click cross-platform onboarding, accepting a new inbound trust boundary, an expanded credential-write surface, and a shared confidential-client secret that is extractable on testers' machines and revocable only globally (a one-way door requiring operator sign-off).

### Context

The alpha is friction-first: a tester should connect a wearable and set a model key without leaving the app or running a shell. Two onboarding surfaces already exist. The intake stepper's final step is Step-9 "API key" — a static mockup panel today ([intake-onboarding-mockup.html:487](../../prototype/intake-onboarding-mockup.html) [VERIFIED]), while the LIVE first run composes the real `POST /settings/key` seam inside the gated flow (ADR-0033). The post-onboarding `My Info` settings surface also exists: the served shell carries a `screen-profile` section ([app_shell.py:80](../../vault/design/templates/app_shell.py) [VERIFIED]) referenced as "My Info" ([app_shell.py:513](../../vault/design/templates/app_shell.py) [VERIFIED]), and the server hosts API-key management there via `_key_status` / `_save_key` ([server.py:916,925,973](../../scripts/serve/server.py) [VERIFIED]).

Several forces pull against each other across more than one stakeholder. The **tester** wants a one-click connect on both Mac and Windows — but the `security`-only credential path returns nothing off macOS, so the flow first depends on the ADR-0047 cross-platform store. Bringing OAuth in-app opens a **new inbound surface**: no OAuth callback/redirect route exists in `scripts/serve/` today (routing is `if self.path == …` chains at [server.py:178,194](../../scripts/serve/server.py) [VERIFIED]; grep for any `oauth`/`callback`/`redirect_uri` in `scripts/serve/` is clean [VERIFIED]). The tracker design note assumed the operator runs the one-time authorize out-of-band — floating either a manual keychain write or an in-app "connect" affordance for the token write itself ([tracker-ingestion-api-adapters.md §3](../design/tracker-ingestion-api-adapters.md) [VERIFIED]); this decision brings the authorize + per-tester token write in-app, leaving only the shared app credentials (D4) as out-of-band build config. The **data subject** needs credentials to stay off the tracked tree — the PII-free trunk that ADR-0005's `block-pii-commit` / `pre-push-pii-scan` hooks enforce. The **maintainer** already crossed the keychain-WRITE boundary once: ADR-0013 was amended to serve `POST /settings/key`, "the FIRST keychain-WRITE side-effect class," for a single key ([ADR-0013:26](ADR-0013-operator-started-loopback-intake-server.md) [VERIFIED]) — this decision expands that class to N per-source tokens. And the **vendors** set the client-type shape: some require a confidential-client secret, some are PKCE public clients, and Garmin as-built is OAuth 1.0a ([oauth_pull.py:584](../../scripts/ingest/oauth_pull.py) [VERIFIED]).

### Decision

Bring alpha-tester credential provisioning in-app as one onboarding mechanism with six facets (D1/D3–D7; D2 — cross-platform secret storage — is ADR-0047's scope, the storage foundation these facets sit on); all credential I/O routes through the ADR-0047 cross-platform store, and no facet edits the frozen ingest/store spine.

- **(D1 — app-mediated OAuth authorization-code flow.** Reversibility: HARD.) Add an app-mediated authorization-code flow with a localhost-only callback: 127.0.0.1-bind only, PKCE for public clients, a `state`/CSRF parameter, and a short-lived one-shot listener. It is a new INBOUND surface under ADR-0013's loopback posture, not a new egress class (see D7).
- **(D3 — app-mediated credential writes.** Reversibility: HARD.) The serve process provisions credentials — extending ADR-0013's single-key keychain-write class ([ADR-0013:26](ADR-0013-operator-started-loopback-intake-server.md) [VERIFIED]) to N per-source OAuth tokens, written through the ADR-0047 store.
- **(D4 — shared-alpha-credential distribution.** Reversibility: HARD — OPERATOR SIGN-OFF OBTAINED — Option A (accept the shared confidential-client secret for the trusted alpha), operator-signed-off 2026-07-14; the North-Star hosted token-broker supersedes it behind the ADR-0047 seam.) Vendor `client_id`/`client_secret` (and the optional shared Anthropic key) reach each instance only via an out-of-band alpha-build config, NEVER a tracked file. Accept the shared confidential-client secret for the trusted alpha. Its scope is **the confidential-client vendors — at least Whoop, possibly Oura**; whether Oura/Google/Garmin are confidential (shared-secret), public/PKCE (no secret), or PAT (the tester's own token) is `[VERIFY-AT-BUILD]` at dev-app registration (OQ-5). Garmin-1.0a as-built is excluded from the one-click alpha flow ([oauth_pull.py:584](../../scripts/ingest/oauth_pull.py) [VERIFIED]).
- **(D5 — Anthropic-key model.** Reversibility: Moderate.) Default to a shared alpha Anthropic key carried in the build — testers touch nothing, the operator holds spend and can rotate/revoke — reversible to bring-your-own. A shared key is an ADR-0001 egress no-op (D7).
- **(D6 — onboarding integration.** Reversibility: Easy.) EXTEND the intake Step-9 "API key" step into the credential step (key + one-click tracker connects + a paste-a-token fast-path where a vendor uses one, e.g. an Oura PAT `[VERIFY-AT-BUILD]` + Apple "Get the Shortcut") and EXTEND `My Info` with a "Connections & Keys" panel for post-onboarding updates; both write the same ADR-0047 store; skippable + resumable; NOT a new standalone wizard.
- **(D7 — ADR-0001 ruling.** A ruling, not a design choice.) The OAuth authorization + token exchange carries only OAuth artifacts (`client_id` + PKCE + auth code + tokens); its outbound leg reaches only the vendor's own authorize/token endpoint, carrying 0 store-content bytes and 0 model-lane calls, so it is NOT a new ADR-0001 egress class — the same "outbound-to-vendor-carrying-only-OAuth-artifacts" class the tracker note ruled inbound-not-egress. The localhost callback is a new inbound (security-scoped) surface, not egress.

Concrete listener lifecycle, endpoint paths, and per-vendor scope strings are spec/build details (Open Questions), not fixed here.

### Rationale

The choice was evaluated against the alpha's load-bearing criteria: onboarding friction, cross-platform reach, secret-distribution exposure, and crown-jewel fit.

On **friction and reach**, the status quo — the operator runs the OAuth authorize + a `security add-generic-password` write by hand ([tracker-ingestion-api-adapters.md §3](../design/tracker-ingestion-api-adapters.md) [VERIFIED]) — cannot deliver a one-click connect and is macOS-only; the in-app flow over the ADR-0047 store is the only option that works for a Windows tester without a shell. On **secret-distribution exposure**, the confidential-client secret is the hazard, so the flow narrows it to the confidential-client vendors only — at least Whoop, possibly Oura; whether Oura/Google/Garmin are confidential (shared-secret), PKCE-public (no secret), or PAT (the tester's own token) is `[VERIFY-AT-BUILD]` at dev-app registration (OQ-5), so the one-way-door (D4) surface is "≥Whoop" pending that confirmation rather than an assumed all-four. A shared secret is accepted for the trusted alpha only because the alternatives each fail a harder constraint (Alternatives): a hosted token-broker that keeps the secret server-side breaks local-first and adds a backend, and per-tester app registration reintroduces exactly the setup friction this decision exists to remove. On **crown-jewel fit** (D5/D7), routing whose Anthropic key pays does not change what reaches the model — the de-identified plan-reasoning call is unchanged, so a shared key is an ADR-0001 egress no-op ([ADR-0001:24](ADR-0001-pii-trust-boundary-no-train-routing.md) [VERIFIED]) — and the authorization flow never touches the model lane. Extending Step-9 and `My Info` rather than building a wizard reuses surfaces the tester already meets ([app_shell.py:80,513](../../vault/design/templates/app_shell.py) [VERIFIED]). Long-term, the ADR-0047 seam lets the North-Star hosted broker replace the local shared secret behind the same interface.

### Consequences

**Positive:**
- One-click cross-platform connect: a Mac or Windows tester authorizes a tracker in-browser and the token lands through the ADR-0047 store, with no shell and no per-tester app registration ([tracker-ingestion-api-adapters.md §3](../design/tracker-ingestion-api-adapters.md) [VERIFIED]).
- The shared Anthropic-key default means testers set nothing to reach the model, and the operator holds spend with a single rotate/revoke point (D5).
- The two entry points reuse existing surfaces (Step-9, `My Info`) and the existing `key_source.store` write ([server.py:973](../../scripts/serve/server.py) [VERIFIED]), adding 0 new standalone wizard and 0 store-key changes.

**Negative:**
- **The D4 shared confidential-client secret is a one-way door (HARD; sign-off).** A shared confidential-client `client_secret` — at least Whoop, possibly Oura (`[VERIFY-AT-BUILD]`, OQ-5) — distributed to external testers is EXTRACTABLE from any tester's machine and revocable only GLOBALLY — there is no per-tester revocation, so a single leak forces a rotate-and-re-push affecting every tester. This cost cannot be undone once distributed; it is the strongest one-way-door in the cluster (its exact vendor set resolves at OQ-5; the posture holds regardless of the count).
- **D1 opens a new inbound trust boundary:** a callback route that accepts a browser redirect from an external vendor is a network-facing surface the system never had; ripping out a shipped browser-OAuth + callback is a rewrite of the connect UX, so it carries per-release loopback-bind + `state`/PKCE verification (1+ year horizon).
- **D3 expands the credential-write trust boundary** from the single ADR-0013 `/settings/key` write to N per-source secrets the serve process now provisions ([ADR-0013:26](ADR-0013-operator-started-loopback-intake-server.md) [VERIFIED]) — more at-rest secrets, more write paths to keep off the tracked tree.
- **Garmin is excluded from the one-click flow:** the as-built path is OAuth 1.0a HMAC-SHA1, not authorization-code+PKCE ([oauth_pull.py:584](../../scripts/ingest/oauth_pull.py) [VERIFIED]), so a Garmin tester falls to a manual token setup or a deferred connect until a Garmin OAuth-2.0 tier is adopted (Open Questions).
- **D5 concentrates spend AND ships a shared extractable secret:** a shared alpha key routes every tester's metered plan-reasoning spend onto one payer, an exposure a bring-your-own key would isolate per tester. Like the D4 vendor secret, the shared Anthropic key ships in the SAME out-of-band alpha-build config, is EXTRACTABLE from any tester's machine, and is revocable only GLOBALLY — a rotate-and-re-push to every tester, during which a leaked key bills the operator's account until rotation (the same cost class as D4, not merely a spend-concentration). Unlike D4 the *design* stays reversible to bring-your-own (Moderate — the de-identified plan-reasoning call is unchanged, so it is an ADR-0001 egress no-op and less severe than the D4 one-way-door), but the distributed key itself, once shipped, cannot be clawed back (OQ-2 already tees up the shared-vs-BYO decision this negative rests on).

**Neutral:**
- The per-instance multi-user model is unchanged: each tester holds their own refresh tokens in their own ADR-0047 store; only the vendor client credentials (and optionally the Anthropic key) are shared.
- The North-Star hosted token-broker (secret server-side) supersedes D4's shared secret behind the same ADR-0047 seam — a documented direction, not a V1 build.

### Alternatives Considered

#### Alternative A: Accept the shared alpha secret, one-click narrowed to the confidential-client vendors (Chosen)
See Decision (D4). Delivers one-click connect for the trusted alpha at the minimum confidential-client surface.
- **Supporting evidence:** No backend and no per-tester registration; the shared-secret surface is only the confidential-client vendors (at least Whoop; the exact per-vendor set is `[VERIFY-AT-BUILD]`, OQ-5), and any PKCE-public or PAT vendor carries no shared secret.
- **Trade-offs:** The shared secret is extractable and globally-revocable-only — recorded as the HARD one-way-door above, flagged for operator sign-off.

#### Alternative B: Hosted token-broker (secret kept server-side)
Run a small backend that holds the confidential-client secret and brokers per-tester tokens, so no secret reaches a tester's machine.
- **Supporting evidence:** Strictly stronger secret posture — the client secret never leaves the server, and revocation is centralized; this is the North-Star path.
- **Trade-offs:** Adds a hosted backend and breaks the local-first / clonable-instance posture V1 requires (ADR-0005) — a service every clone would depend on. Rejected FOR ALPHA; retained as the North-Star cutover behind the ADR-0047 seam.
- **When this becomes the right choice:** At the North-Star transition to a hosted product, where a server-side broker under the regulated-PHI trust model is the intended design.

#### Alternative C: Each tester registers their own vendor app
Have every tester create a developer app per vendor and paste their own `client_id`/`client_secret`.
- **Supporting evidence:** No shared secret at all — each tester holds only their own credentials, so there is no global-revocation hazard.
- **Trade-offs:** It reintroduces exactly the multi-step per-vendor setup friction the friction-first alpha exists to remove — the highest-friction option, and unrealistic for non-developer testers. Rejected as failing the load-bearing onboarding-friction criterion.
- **When this becomes the right choice:** For a developer-only alpha, or if the shared-secret exposure were judged unacceptable regardless of the friction cost.

#### Dissent: Keep credential setup out-of-band (status quo)
**Source:** The tracker design note's model — the operator runs the one-time authorize (and a manual keychain write) out-of-band, and the app only reads the resulting token ([tracker-ingestion-api-adapters.md §3](../design/tracker-ingestion-api-adapters.md) [VERIFIED]). A dissenter holds that keeping OAuth out-of-band opens no new inbound surface and distributes no shared secret, at the cost of the one-click capability.
**Conditions under which this becomes the right choice:** If the alpha stayed macOS-only and single-operator (the author's own machine), the out-of-band setup opens 0 inbound surface and distributes 0 secret — the zero-surface path — and the in-app flow's costs would not be worth the convenience.

### Validation Approach

**Confirmation criteria:**
- Both entry points write through the ADR-0047 store: a key set from Step-9 and a token stored from the `My Info` "Connections & Keys" panel each round-trip through the abstraction (store-then-resolve recovers the value) — expected: ≥1 successful write→read per entry point, 0 direct `security` shell-outs outside the abstraction.
- The localhost callback binds 127.0.0.1 only (never `0.0.0.0`/`""`), the authorization request carries a `state` parameter and a PKCE challenge, and the callback rejects a mismatched `state` — expected: 0 non-loopback binds, 1 `state` + 1 PKCE per authorization, `state` mismatch rejected.
- The shared vendor secret and the shared Anthropic key resolve only from the out-of-band alpha-build config — expected: a content scan of all tracked files returns 0 hits for either secret (ADR-0005 `block-pii-commit` / `pre-push-pii-scan`).

**Falsification criteria:**
- **Crown-jewel wire-scan (D7, load-bearing):** run the authorization + callback path under a recording network seam and assert (a) 0 bytes of store content in any outbound request body/header, (b) 0 calls to the no-train model lane, (c) the only outbound host is the vendor's own authorize/token endpoint. Threshold: ≥1 store-content byte OR ≥1 model-lane call on the auth/callback path reds the D7 ruling → halt and re-scope the flow before release.
- If the callback binds any non-loopback address (≥1 non-127.0.0.1 bind), the inbound surface is reachable off-machine → block and repair the bind.
- If the shared `client_secret` or the shared Anthropic key appears in any tracked file (≥1 hit on a fresh-clone scan), the ADR-0005 out-of-band constraint failed → block the commit and restore the boundary (git history cannot be cleanly scrubbed).
- Time horizon: run the wire-scan, the loopback-bind check, and the tracked-secret scan at the first build of the flow, at the operator-present LIVE run, and at every release thereafter.

**Review triggers:**
- A Garmin OAuth-2.0 tier becomes available — re-decide whether Garmin joins the one-click flow (Open Questions).
- A new tracker source is added — confirm it adopts the ADR-0047 store and the shared-vs-PKCE client-type split, and that its secret (if any) stays out-of-band.
- The North-Star hosted-broker cutover begins — the shared secret is superseded by a server-side broker behind the ADR-0047 seam.
- The alpha closes or a tester leaves — rotate the shared secret (the only revocation available, per the D4 negative).
