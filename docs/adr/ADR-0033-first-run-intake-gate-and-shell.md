## ADR-0033: First-Run Completeness Gate + Platform-Unlock State + Post-Intake Shell Changes

> **Y-Statement:** In the context of the served single-file SPA front-end (ADR-0029), where GET `/` serves the full shell unconditionally — its `Dashboard` / `Plan` / `Chat with Team` / `Profile` nav and its right-panel `My Plan | Build Plan | Generate` tabs all reachable on first run even though the operator has provided no profile, so the plan/dashboard surfaces show fabricated demo or empty content before any intake (ADR-0029 OQ-3) — facing the tension between forcing an intake-first first run (so no surface is reached before it has honest operator data) and the cost of a hard wall before any value is visible, plus the need to persist the unlocked/locked state per-user-locally without introducing a drift-prone duplicate of state the store already holds, we decided that "complete" is a DERIVED, store-grounded predicate over ADR-0034's required de-identified field set (NOT a stored boolean, NOT the conversation loop's `chat.plan_next_turn.intake_complete`), that an incomplete profile HARD-gates GET `/` to a Create-Profile (intake) surface with every other surface hidden, and that the final intake save lands the last required tokens — flipping the predicate true, unlocking the platform, and opening the Chat-with-Team screen with the right panel on a renamed, editable `My Info` tab (`My Plan | Build Plan | Generate` → `My Plan | My Info | Generate Plan`) whose edits re-run ADR-0034's capture→de-identify path, composing the existing `/upload` / `/confirm-extraction` / DNA-land and `/settings/key` seams inside the gated flow, to achieve an intake-first front end that never shows a surface before it has honest data, accepting a hard first-run wall before any value is visible, a derived predicate that re-locks a previously-complete operator if the required set later grows, and an edit→re-de-identify round-trip cost on every My-Info change.

### Context

The served front-end is the single-file SPA `app_view.html`, rendered by `vault/design/templates/app_shell.render(store_read, *, status, _today)` and returned as the GET `/` body by the loopback server's `_render_intake` → `generate.run('app')` seam ([app_shell.py:258-288](../../vault/design/templates/app_shell.py) [VERIFIED]; [server.py:88-101,142-149](../../scripts/serve/server.py) [VERIFIED]). That render is UNCONDITIONAL: GET `/` always serves the complete shell — the four-item top nav `Dashboard` / `Plan` / `Chat with Team` / `Profile` ([app_view.html:350-353](../../vault/design/templates/app_view.html) [VERIFIED]) and, inside the Chat-with-Team screen's right column, the workspace tabs `My Plan | Build Plan | Generate` ([app_view.html:456-458](../../vault/design/templates/app_view.html) [VERIFIED]). There is no first-run gate: a brand-new operator with an empty store reaches every surface, and the as-built `Dashboard` / `Plan` screens carry fabricated demo or empty-placeholder content until their own live-wiring lands — the open reconciliation ADR-0029 records as OQ-3 ([ADR-0029 OQ-3](ADR-0029-unified-spa-front-end-shell.md) [VERIFIED]).

Several forces pull against each other across more than one perspective. From the operator's side, a plan or dashboard surface reached before any intake is either empty or shows sample data presented as theirs — the operator-rejected fragmentation/placeholder problem the S98 design phase and ADR-0009's honest-data discipline (D1/D2) exist to remove ([ADR-0009 Decision](ADR-0009-dashboard-visual-shell-seven-zones.md) [VERIFIED]) — so the operator wants the platform to stay hidden until intake is done. Pulling the other way, a hard intake-first wall makes the platform's value invisible until the operator completes a comprehensive clinical intake (the longer, higher-friction intake ADR-0034 introduces), a completion-rate cost against the evidence-driven principle of not adding structure ahead of friction evidence. From the data subject's side, whatever records the locked/unlocked decision must not become a second source of truth that can desync from the actual stored data, and it must stay per-user-local under the crown-jewel boundary — the project's store-grounded discipline already refuses a model-supplied or turn-count "done" flag (`chat.plan_next_turn` derives `domain_done`/`intake_complete` from store-present `SUMMARY_FIELD_SET` tokens, never a count or model say-so — the PF-S87-01 anti-gap, [chat.py:4-9,196-208](../../scripts/serve/chat.py) [VERIFIED]). From the maintainer's side, the candidate predicate the discovery flagged — `chat.plan_next_turn.intake_complete` — is computed over the COVERED chat domains only: with zero coverage `open_domains` is empty and `intake_complete` is vacuously True ([chat.py:183-188,207](../../scripts/serve/chat.py) [VERIFIED]), so it is a conversation-loop terminator, not a sound first-run completeness check over a required field set. Because this defines a new app-state machine — what "complete" means, where its state lives, the hidden-until-complete behavior, and the unlock transition — and amends which front-end shell is served, it is a decision, not a render-time detail.

### Decision

Define "complete" as a DERIVED, store-grounded predicate over the REQUIRED subset of ADR-0034's de-identified field→destination contract: the platform is unlocked iff every required token is present in the store (resolved through the existing `router.summarize` read the shell already takes), computed locally on each GET `/` — no stored "intake-finalized" boolean is introduced, and the predicate is NOT `chat.plan_next_turn.intake_complete`. The unlock-REQUIRED set is the DIRECTLY-CAPTURED intake tokens; it EXCLUDES any token filled only POST-UNLOCK — specifically `rx-interaction-classes`, which is filled by the ADR-0035 care-agent meds curation that is itself TRIGGERED by this unlock transition (requiring it would DEADLOCK the gate, since it is provably empty until after the save that unlocks), and any other always-set / review-derived token; the predicate requires the operator-captured intake fields, not the care-agent-curated or review-derived ones. Completeness ALSO requires that the safety-critical SCREENS be ANSWERED (regardless of value): the ADR-0034 exercise-safety contraindication screen, PHQ-2, and apnea route to referral/gate signals — ADR-0034 destination (b), which are NOT `SUMMARY_FIELD_SET` tokens — so the predicate is BROADENED beyond a pure `SUMMARY_FIELD_SET` token-presence check to ALSO test a presence-of-answer signal for each safety screen. The platform is unlocked iff every required directly-captured token is present in the store AND every safety-critical screen has been answered. With the predicate false, GET `/` HARD-gates to a Create-Profile (intake) surface and every other surface — `Dashboard`, `Plan`, the unlocked Chat-with-Team platform, and `Generate` — is hidden; section-level saves write partial data and do not unlock. The final intake save lands the last required tokens, flips the predicate true, unlocks the platform, and opens the Chat-with-Team screen with the right panel on the `My Info` tab. The right-panel workspace tabs are renamed `My Plan | Build Plan | Generate` → `My Plan | My Info | Generate Plan`; the `My Info` tab shows all intake questions and their answers and is EDITABLE, where an edit re-runs ADR-0034's capture→de-identify path so no edit can bypass the boundary, and "add docs" routes through the existing upload seam. Uploads and API-key entry happen INSIDE the gated intake by composing the EXISTING seams — `route.route_upload` / POST `/confirm-extraction` / DNA-land for documents and POST `/settings/key` → `key_source.store` for the key — adding no new route and no new outbound class. The state is per-user-local; the new screens' pixel design is a separate downstream step, out of scope here.

### Rationale

The gate's state model was evaluated against three criteria the context makes load-bearing: **drift resistance** (can the locked/unlocked verdict desync from the operator's actual stored data?), **soundness** (does the predicate actually test profile completeness, not something correlated?), and **boundary fit** (does it add per-user-local state under the crown jewel, or a new persisted surface?). A derived predicate over the required field set wins on all three. On **drift resistance**, the verdict is a pure function of the stored de-identified tokens, re-read each GET `/`, so there is no separate boolean to fall out of sync with the data — the same store-grounded posture `chat.plan_next_turn` already uses to refuse a model-supplied or turn-count flag (PF-S87-01, [chat.py:196-208](../../scripts/serve/chat.py) [VERIFIED]). A stored "intake-finalized" flag (Alternative A) would be a second source of truth that can desync — set true while data is later cleared, or stale after a store edit. On **soundness**, the predicate is defined over ADR-0034's REQUIRED set, not over covered chat domains, so it cannot pass vacuously the way `chat.plan_next_turn.intake_complete` does for an operator who covered zero domains ([chat.py:183-188,207](../../scripts/serve/chat.py) [VERIFIED]); the conversation-loop terminator and the first-run gate are deliberately kept distinct. On **boundary fit**, the predicate reads only the de-identified `summarize` output the shell already consumes ([app_shell.py:258-288](../../vault/design/templates/app_shell.py) [VERIFIED]), so it introduces no new state and no new flow.

The final-save event is the unlock TRANSITION, not the source of truth: section saves write partial tokens and leave the predicate false; the final save lands the last required tokens, which is precisely what flips the predicate true, so "final save" and "complete" coincide without a separate finalized marker. This keeps the operator-approved "section saves are fine; the final save unlocks" semantics while staying drift-resistant — the cost, owned in Consequences, is that a future enlargement of the required set re-locks a previously-complete operator until they supply the new field.

The hard gate (hide) is chosen over a soft gate (show-but-disable) because the platform's pre-intake surfaces have no honest content to show: ADR-0029's as-built `Dashboard` / `Plan` screens carry fabricated demo data or empty placeholders pending OQ-3 ([ADR-0029 OQ-3](ADR-0029-unified-spa-front-end-shell.md) [VERIFIED]), and rendering them — even disabled — collides with ADR-0009's honest-data D1/D2 ([ADR-0009 Decision](ADR-0009-dashboard-visual-shell-seven-zones.md) [VERIFIED]); hiding them avoids the empty-surface honesty problem entirely. The shell amendment reuses the existing seams rather than inventing new ones: the intake form already POSTs the four gate-bound capture tokens to `/upload` from the current `Build Plan` panel ([app_view.html:463-471](../../vault/design/templates/app_view.html) [VERIFIED]), the upload/confirm/DNA-land and `/settings/key` routes already exist in the server's fixed route table ([server.py:142-166](../../scripts/serve/server.py) [VERIFIED]), and key entry already writes only to the keychain via `key_source.store` with no egress ([key_source.py:135-157](../../scripts/model/key_source.py) [VERIFIED]) — so composing key entry and uploads into the gated intake moves WHERE these affordances appear, not WHAT crosses any boundary. Long-term, the gate becomes a property of every future surface: a new screen is reachable only behind the same required-set predicate, so the intake-first discipline holds as the platform grows.

### Consequences

**Positive:**
- The platform is never reached before it has honest operator data: an incomplete profile serves only the Create-Profile surface, so no `Dashboard` / `Plan` / `Generate` surface renders fabricated demo or empty-placeholder content as the operator's data — the ADR-0029 OQ-3 / ADR-0009 D1-D2 honesty hazard is closed for the first-run case ([ADR-0029 OQ-3](ADR-0029-unified-spa-front-end-shell.md), [ADR-0009 Decision](ADR-0009-dashboard-visual-shell-seven-zones.md) [VERIFIED]).
- The locked/unlocked state cannot desync from the data: it is a derived function of ADR-0034's required de-identified tokens present in the store, re-read each GET `/` via the existing `router.summarize` seam ([app_shell.py:258-288](../../vault/design/templates/app_shell.py) [VERIFIED]), so there is no stored boolean to maintain, migrate, or fall stale — the same store-grounded discipline that refuses a turn-count/model flag (PF-S87-01, [chat.py:196-208](../../scripts/serve/chat.py) [VERIFIED]).
- No new front-end-route egress and no new route: the gate is a render-time branch keyed on the predicate, and uploads + key entry compose the existing `route.route_upload` / `/confirm-extraction` / DNA-land and `/settings/key` → keychain seams ([server.py:142-166](../../scripts/serve/server.py), [key_source.py:135-157](../../scripts/model/key_source.py) [VERIFIED]) — the served front-end's OWN ROUTES carry exactly ADR-0029's amended outbound classes (the ADR-0016 `/chat` turn, the ADR-0030 upload-extraction egress, the no-train `/generate-plan` author), 0 new front-end-route classes. The unlock transition itself TRIGGERS ADR-0035's separately-decided care-agent review, which carries its own named de-associated meds-curation egress class — that class is OWNED and falsified by ADR-0035, outside this front-end-route enumeration (a cross-reference, not a new front-end class; see Related Decisions).
- My-Info edits cannot bypass the boundary: an edit re-runs ADR-0034's single capture→de-identify path (`persist_capture` → `summarize`), so an edited raw value is re-de-identified rather than written straight to a field-set token ([capture.py:1-30](../../scripts/serve/capture.py) [VERIFIED]; [ADR-0034 Decision](ADR-0034-intake-content-deid-safety-mapping.md) [VERIFIED]).

**Negative:**
- A hard first-run wall before any value is visible: with no progressive-disclosure path, the operator must complete the comprehensive clinical intake (ADR-0034's longer, higher-friction content) before seeing the dashboard, a plan, or the team — a completion-rate cost and an abandonment risk that a soft gate would soften, accepted because the pre-intake surfaces have no honest content to show.
- The derived predicate re-locks a previously-complete operator if the required set grows: because "complete" is recomputed each GET `/` over the current required-set definition, a later ADR that adds a required field would flip an already-finished operator back to locked until they supply it — a hazard a stored finalized flag would avoid (the migration/grandfather policy is OQ-3).
- A My-Info edit→re-de-identify round-trip cost on every change: an edit is not a cheap in-place mutation — it re-runs `persist_capture` → `summarize` each time, and a rich-domain or medication edit additionally needs a fresh chat turn or the ADR-0035 care-agent re-curation (raw meds → `rx-interaction-classes`), so editing carries the same boundary-crossing cost as first capture ([ADR-0034 Consequences](ADR-0034-intake-content-deid-safety-mapping.md) [VERIFIED]).
- Per-user-local only: the gate state is the single operator's store, so a shared/authenticated multi-operator instance would re-open where the locked/unlocked state and required-set live — deferred (OQ-1), a 1+ release constraint on any North-Star multi-tenant move.

**Neutral:**
- The gate adds no route and no template file: it is a branch inside the existing `app_shell.render` / `generate.run('app')` render seam keyed on the store-derived predicate ([app_shell.py:258-288](../../vault/design/templates/app_shell.py) [VERIFIED]); the served body changes from the full shell to the Create-Profile-only view when the predicate is false, the same single GET `/` route on the unchanged loopback transport.
- The unlock retargets the opening view only: the SPA currently opens on the `Dashboard` screen (the `#dashboard` hash default, [app_view.html:628](../../vault/design/templates/app_view.html) [VERIFIED]) with the right panel defaulting to the `Build Plan` tab ([app_view.html:457,463](../../vault/design/templates/app_view.html) [VERIFIED]); under this decision the post-unlock opening view is the Chat-with-Team screen with the right panel on `My Info` — a default-active retarget, not a new screen.
- Key entry moves from the standalone `Profile` screen's API-connection card ([app_view.html:501-520](../../vault/design/templates/app_view.html) [VERIFIED]) into the gated intake, reusing the same POST `/settings/key` → `key_source.store` keychain write; whether the `Profile` card is retained as a second entry point post-unlock is a UI-placement detail (OQ-4), not a boundary change.

### Alternatives Considered

#### Alternative A: A stored "intake-finalized" boolean flag as the gate state
Persist an explicit boolean when the operator presses the final save, and read that flag (not the data) to decide locked/unlocked.
- **Supporting evidence:** Captures the explicit final-save EVENT as a first-class fact, distinct from data presence; survives a later enlargement of the required field set without re-locking a previously-finalized operator (it has no Negative-2 re-lock hazard); a simple boolean read with no per-token derivation.
- **Trade-offs:** It is a second source of truth that can desync from the actual stored data — set true while data is later edited or cleared, or stale relative to what the store holds — exactly the drift the project's store-grounded discipline refuses for `domain_done`/`intake_complete` (PF-S87-01, [chat.py:196-208](../../scripts/serve/chat.py) [VERIFIED]); it adds a new persisted state to keep correct and migrate. Rejected as the sole source of truth on drift-resistance grounds.
- **When this becomes the right choice:** If the required-field set is expected to churn often (making the re-lock hazard frequent), OR if an explicit, auditable "the operator finalized intake on date D" record is itself required — then a flag layered ON TOP of the derived predicate (data-complete AND finalized) captures the event without becoming the sole truth.

#### Alternative B: A soft gate (show all surfaces, disable the locked ones)
Render the full nav on first run and grey/disable the locked surfaces with a "complete intake to unlock" affordance rather than hiding them.
- **Supporting evidence:** The operator sees the platform's shape immediately (a motivation/preview benefit), the first run is less jarring than a hard wall, and it leaves a single nav model rather than two render modes.
- **Trade-offs:** The pre-intake surfaces have no honest content to render — ADR-0029's `Dashboard` / `Plan` ship fabricated demo data or empty placeholders pending OQ-3 ([ADR-0029 OQ-3](ADR-0029-unified-spa-front-end-shell.md) [VERIFIED]) — so even a disabled-but-visible surface still has to display something, colliding with ADR-0009's honest-data D1/D2 ([ADR-0009 Decision](ADR-0009-dashboard-visual-shell-seven-zones.md) [VERIFIED]). Rejected because a visible locked surface re-introduces the placeholder-as-data hazard the hard gate removes.
- **When this becomes the right choice:** Once each platform surface has an honest no-data awaiting-state (the ADR-0009 D2 direction, ADR-0029 OQ-3 resolved), a soft gate could preview the real (empty-but-honest) surfaces and drive completion without showing fabricated data.

#### Alternative C: Keep the `Build Plan` tab label (no rename)
Leave the right-panel tabs as `My Plan | Build Plan | Generate` and host the editable intake under the existing `Build Plan` label.
- **Supporting evidence:** Zero shell churn — the `Build Plan` panel already hosts the intake form and uploads ([app_view.html:463-494](../../vault/design/templates/app_view.html) [VERIFIED]) — and no tab-label migration is needed.
- **Trade-offs:** `Build Plan` mislabels what the tab IS post-intake: an editable record of the operator's own information (demographics, documents, the chat Q&A and answers), not a plan-building surface — the plan is built from the `Generate Plan` tab / POST `/generate-plan` ([server.py:161,383-489](../../scripts/serve/server.py) [VERIFIED]). The operator-approved model names this surface `My Info`. Rejected because the label would misdescribe the surface's role.
- **When this becomes the right choice:** If the tab's role stayed plan-building (assembling the plan) rather than displaying and editing the operator's stored info, `Build Plan` would remain the accurate label.

#### Dissent: The no-gate / progressive-disclosure position
**Source:** The evidence-driven product-design principle (defer friction-adding structure until friction evidence justifies it) and ADR-0029's honest-awaiting-state direction (a surface renders the real `dashboard.py` output or an ADR-0009 D2 awaiting-state, never fabricated data; [ADR-0029 OQ-3](ADR-0029-unified-spa-front-end-shell.md) [VERIFIED]). A dissenter holds that a hard first-run wall is structure added ahead of evidence: the operator should enter the platform immediately and each surface should show its own honest no-data awaiting-state until intake fills it, rather than being blocked from the platform entirely.
**Conditions under which this becomes the right choice:** If operator-use evidence shows the hard wall depresses intake completion, OR once every surface has an honest no-data awaiting-state (ADR-0009 D2 / ADR-0029 OQ-3 resolved), the gate should be retracted to progressive disclosure — keeping only the safety-critical fields (ADR-0034's exercise-safety / referral screens) gated, and letting the rest of the platform be explored with honest empty states.

### Validation Approach

**Confirmation criteria:**
- Hidden-until-complete: with an empty or partial store (the required field set not present), GET `/` serves ONLY the Create-Profile (intake) surface and the platform surfaces — `Dashboard`, `Plan`, the unlocked Chat-with-Team platform, `Generate` — are NOT in the served body. Expected — **0 of the platform surfaces reachable** with an incomplete profile; the intake surface present.
- Unlock target: with a complete profile (the required set present), GET `/` serves the full shell with **exactly 1 active screen = Chat-with-Team** and **exactly 1 active right-panel tab = My Info**; the served body carries the tab labels `My Plan | My Info | Generate Plan` and **0 occurrences** of the old `Build Plan` / bare `Generate` tab labels ([app_view.html:456-458](../../vault/design/templates/app_view.html) [VERIFIED]).
- Store-grounded predicate: the "complete" verdict is a function of ADR-0034's required directly-captured de-identified `SUMMARY_FIELD_SET` tokens present in the store (via `router.summarize`) AND a presence-of-answer signal for each safety-critical screen (exercise-safety / PHQ-2 / apnea — ADR-0034 destination-(b) referral signals, NOT `SUMMARY_FIELD_SET` tokens, so the predicate is broadened beyond token-presence to include them); it EXCLUDES post-unlock-filled tokens such as `rx-interaction-classes` — **0 turn-counts and 0 model-supplied flags** read as the verdict, and it is NOT `chat.plan_next_turn.intake_complete` (which is vacuously True at zero domain coverage, [chat.py:183-188,207](../../scripts/serve/chat.py) [VERIFIED]).
- No-new-front-end-route-egress / no-new-route: enumerate the gated front-end's OWN route table outbound classes — expected the FRONT-END ROUTES' outbound classes are exactly ADR-0029's amended set (the ADR-0016 `/chat` turn + the ADR-0030 upload-extraction egress + the no-train `/generate-plan` author), **0 new front-end-route classes**, and the route table is unchanged at the seven existing routes ([server.py:142-166](../../scripts/serve/server.py) [VERIFIED]); key entry writes only to the keychain ([key_source.py:135-157](../../scripts/model/key_source.py) [VERIFIED]). (ADR-0035's care-agent-review egress, including its named de-associated meds-curation class, fires at the unlock transition and is enumerated + falsified in ADR-0035, not here.)

**Falsification criteria (quantitative; the crown-jewel probe is load-bearing):**
- Gate-bypass falsification: with an incomplete profile, **≥1** of `Dashboard` / `Plan` / `Generate` / the unlocked Chat-with-Team platform is served or reachable → the gate failed → block release until the incomplete profile serves only the intake surface.
- Unlock-without-data falsification: the platform unlocks while the required field set is NOT present (**≥1** unlock with the predicate false), OR a safety-critical screen (exercise-safety / PHQ-2 / apnea) is unanswered at unlock (**≥1** unlock with a required safety screen unanswered), OR the verdict is read from a non-store source — a turn count, a model say-so flag, or a stored boolean that can desync from the data → the store-grounded predicate is breached → block.
- Crown-jewel edit probe: seed a known raw-PII value (a raw drug name, a free-text answer) into a My-Info edit, re-save, and scan the store — threshold **0 de-identified field-set writes that skipped `persist_capture` / `summarize`**; **≥1** edit that writes a raw value straight to a field-set token reds the boundary → halt and restore the re-de-identify path ([capture.py:1-30](../../scripts/serve/capture.py), [ADR-0034 Decision](ADR-0034-intake-content-deid-safety-mapping.md) [VERIFIED]).
- New-front-end-route-egress falsification: the gate or the key-entry-in-intake adds **≥1** outbound class to the FRONT-END's OWN ROUTES beyond ADR-0029's amended set, OR **≥1** new server route → block (the front-end routes' egress posture is unchanged by this decision; ADR-0035's separately-decided de-associated meds-curation egress class fires at the unlock transition and is owned + falsified by ADR-0035, NOT a front-end-route class introduced here).
- Time horizon: run the gate-bypass probe, the unlock-state probe, the no-new-egress probe, and the My-Info-edit re-de-identify probe at the first build of the gate, at the operator-present LIVE run, at every release thereafter, and before the July-2026 physician-visit deliverable.
