## ADR-0039: A Local Scheduled Headless Runner Hosts the Cadence Trigger for the Plan-Evolution Loop

> **Y-Statement:** In the context of the built plan-evolution loop (ADR-0036), whose one debounced entry `plan_loop.signal(root, *, trigger, dispatch, deid_client, tailor_client)` and full-composition front door `regenerate(...)` are wired but SEAM-UNSUPPLIED in production — the standalone `python -m scripts.serve` process supplies NEITHER the subscription `dispatch` nor the `deid_client` (it documents that a plain Python server hosts no subscription runtime, so `/plan-loop` degrades `loop-dispatch-unavailable`, [__main__.py:69-83](../../scripts/serve/__main__.py); [server.py:744-746](../../scripts/serve/server.py) [VERIFIED]) — and where the loop's cadence trigger is the ONE trigger with no in-process host (the data-event and free-text triggers fire from the running server's route/care_chat/confirm sites, but the weekly cadence has no natural firing site), facing the decisive tension that the loop re-reads the operator's LOCAL, gitignored store (`_read_raw_intake` → `store.read_all(root)`, [plan_loop.py:112-126](../../scripts/serve/plan_loop.py) [VERIFIED]) — so a runtime that cannot see that local store either cannot run or would have to EXPORT local PII to a cloud runtime, a new egress class that breaches the crown-jewel (ADR-0001/0016) — while ADR-0026's binding constraint keeps specialist/judge/lens dispatch on the operator's Claude SUBSCRIPTION (0 marginal API spend) with the de-id-IN call the SOLE metered egress (ADR-0027), we decided to adopt a LOCAL scheduled headless Claude-Code runner — a local OS scheduler (launchd on the operator's macOS; cron the portable fallback), DISABLED BY DEFAULT, that on the loop's cadence launches a local headless Claude-Code subscription session which reads the local store, supplies the ADR-0027 `deid_client`, dispatches each specialist/judge/lens as a subscription sub-agent, and calls the BUILT `plan_loop.signal(trigger=CADENCE_TRIGGER, ...)` (the runner supplies the seams; it does not re-host the loop, the debounce, or the safety composition) — to achieve an autonomously-closing cadence leg that keeps the store and raw PII local and adds no new egress surface, accepting that ENABLING the schedule (an explicit operator-owned action) arms recurring metered de-id spend, that the run fires only when the operator's machine is awake, and that the concrete headless shape + the subscription-auth isolation from any `ANTHROPIC_API_KEY` in the process environment are spec-stage open questions.

### Context

The plan-evolution loop is built but has no runtime for its cadence trigger. `plan_loop.signal(root, *, trigger, dispatch=None, deid_client=None, plan_date=None, tailor_client=None)` is the ONE debounced entry every trigger calls; on a gate-pass it invokes `regenerate(...)`, which drives the full-composition front door (`run_orchestrated` → `plan_driver.drive` → the composed `gate_dispatch` + the five `orchestrate` cross-domain holds) ([plan_loop.py:129,431-471](../../scripts/serve/plan_loop.py) [VERIFIED]). Both seams — the subscription-agent `dispatch(name, prompt, context)` that answers every specialist/judge/lens class, and the ADR-0027 `deid_client` for the crown-jewel `deid_in` boundary — must be SUPPLIED to the loop; the loop does not construct them ([plan_loop.py:129-169](../../scripts/serve/plan_loop.py) [VERIFIED]).

Production supplies neither. The standalone operator entry `main()` builds the server passing NO `loop_dispatch`/`loop_deid_client`, and documents why: "the loop's A′ aggregate dispatch (every specialist + judge + lens on the subscription session) has no runtime in a plain Python server process. Fabricating a dispatch here would either be a fake or would arm heavy no-train spend by default" ([__main__.py:69-83](../../scripts/serve/__main__.py) [VERIFIED]). The server's `_do_plan_loop` route therefore degrades honestly to `loop-dispatch-unavailable` when the seams are absent ([server.py:744-746](../../scripts/serve/server.py) [VERIFIED]). No OS scheduler / launchd / cron runner, and no plan-evolution-loop cadence runner, exists under `scripts/serve/` (the ingestion `scripts/ingest/scheduler.py` is an unrelated unattended wearable-import batch seam — no OS timer, no plan-loop, no Claude-Code session) ([.pipeline/discovery.md](.pipeline/discovery.md) [VERIFIED]).

Two forces pull against each other. **The dispatch must be a subscription session.** ADR-0026 fixed the operator's binding constraint — "subscription for the specialists, judge, and safety lenses (not metered), API only for the PII de-id call" — and inverted the control flow so the fail-closed loop runs ONCE while a Claude Code session drives the subscription dispatch ([ADR-0026, Y-Statement](ADR-0026-v1-subscription-runtime-driver.md) [VERIFIED]). A subscription specialist is a Claude Code Task agent that a plain Python process cannot synchronously spawn and pull output back from. **Against that, the loop is local-first PII-bound.** `regenerate` re-reads the operator's CURRENT store live every re-gen — `_read_raw_intake(root)` returns `{"operator_state": store.read_all(root)}` ([plan_loop.py:112-126](../../scripts/serve/plan_loop.py); [store.py:263](../../scripts/store/store.py) [VERIFIED]) — and that store is the gitignored, PII-bearing local surface ADR-0001/0005 keep off the tracked tree. A runtime that is not local-store-adjacent cannot read that intake without the operator's raw local data being shipped to it — the exact egress the crown-jewel forbids.

The decision binds two stakeholders, not only the operator. For the OPERATOR the axes are recurring metered spend (each automated re-gen fires one metered de-id-IN call) and machine-availability (a scheduled job fires only when the machine is on). For the DE-ID DATA SUBJECT the axis is containment: the runtime must keep the raw store local and route only the de-identified summary to the specialist dispatch, adding no new raw-egress class beyond the ADR-0027 de-id-IN call. Because the runtime choice fixes where the subscription session runs, whether raw local PII can reach a non-local runtime, and what arms recurring spend — not just a code path — it is an architecture decision, and it partially resolves ADR-0036 OQ-2 (the cadence trigger's host; the data-event/free-text triggers stay open — OQ-5).

### Decision

Adopt a **local scheduled headless Claude-Code runner** for the loop's cadence trigger: a local OS scheduler (launchd on the operator's macOS; cron as the portable fallback), **disabled by default**, that on the loop's cadence launches a local headless Claude-Code SUBSCRIPTION session. That session reads the local store, supplies the ADR-0027 `deid_client`, dispatches each plan-domain specialist + the quality judge + each safety lens as subscription sub-agents over the unified `dispatch` seam, and calls the built `plan_loop.signal(root, trigger=plan_loop.CADENCE_TRIGGER, dispatch=..., deid_client=..., tailor_client=...)` — supplying the seams to the built loop, never re-hosting the loop, the debounce, or the safety composition. **Binding raw-PII containment constraint on the top-level session:** the raw `store.read_all` intake read and the ADR-0027 `deid_in` de-identification MUST execute in the Python DRIVER layer (exactly as they do on the `/generate-plan` A′ path), so the raw store content NEVER enters the top-level subscription session's transmitted context — the subscription lane carries ONLY PII-free orchestration plus the de-identified summary (ADR-0001 + vision principle 2: the subscription/consumer lane is the PII-FREE lane, distinct from the no-train de-id lane; the sole raw-PII egress stays the ADR-0027 no-train `deid_in` call). A runner realization that reads raw PII into the DRIVING session's own context (e.g. a naïve `claude -p "read the store and run the loop"`) would transit raw PII over the consumer subscription lane and is DISQUALIFIED. **INSTALLING/ENABLING the schedule is an explicit operator-owned action;** designing and building the runner arms nothing. As a named guard against IMPLICIT activation: no build, provisioning, or `init_instance` step may load the launchd/cron entry — ONLY the explicit, documented operator enable action arms the schedule (the PF-S63-02 guard-loosening sensitivity applied to a future provisioning path; the concrete guard is OQ-4).

### Rationale

The runtime was evaluated across four axes the loop makes load-bearing — **local-first PII fit** (can the runtime read the local gitignored store without a new egress class), **cost** (marginal API spend per automated re-gen), **security** (raw-PII containment; the sole-metered-egress posture), and **portability / buildability under extend-not-rebuild** — against a cloud scheduled routine (Alternative B) and API-backed in-server dispatch (Alternative C / "B2").

**Local-first PII fit is decisive, and it eliminates the cloud runtime outright.** The loop re-reads `store.read_all(root)` from the operator's local gitignored store every re-gen ([plan_loop.py:126](../../scripts/serve/plan_loop.py) [VERIFIED]). A cloud scheduled routine cannot see that store; running the loop there would require exporting the raw local store to the cloud runtime — a new raw-PII egress class beyond ADR-0016's named carve-out and ADR-0027's single de-id-IN egress, the precise breach ADR-0001's "route only plan reasoning to the model over summaries rather than raw PII" forbids ([ADR-0001, Y-Statement](ADR-0001-pii-trust-boundary-no-train-routing.md) [VERIFIED]). So the runtime must run LOCALLY. Given that, only a local runtime can be BOTH a real Claude-Code subscription session (satisfying ADR-0026's not-metered dispatch) AND local-store-adjacent (satisfying the crown-jewel).

The runtime mechanism is available and first-party. Claude Code exposes a documented headless / print mode, `claude -p "<prompt>"` (`--print`), that runs a single agent turn to completion and exits — the non-interactive one-shot a scheduler needs [VERIFIED: Claude Code docs, headless.md]. An official Claude Agent SDK (`@anthropic-ai/claude-agent-sdk` for TypeScript, `claude-agent-sdk` for Python) runs the same agent harness — tools, MCP, and sub-agents via the `Agent` tool — programmatically [VERIFIED: Claude Code docs, agent-sdk/overview]. Subscription auth is established interactively via `/login` or non-interactively via a long-lived OAuth token from `claude setup-token` (valid ~1 year, supplied as `CLAUDE_CODE_OAUTH_TOKEN`) [VERIFIED: Claude Code docs, authentication.md]. On subscription auth the specialist/judge/lens sub-agent turns draw from the subscription, not per-token API billing — the ADR-0026 posture the loop inherits [VERIFIED: agent-sdk/overview; subagents in the CLI `-p` path specifically are UNVERIFIED — see OQ-1].

**This non-interactive `setup-token` capability is where ADR-0039 REFINES ADR-0026 — and this ADR does NOT claim clean consistency with it.** ADR-0026 Negative-1 held that the V1 subscription runtime "cannot run truly unattended (no human session present)" and reserved "truly headless execution [as] the all-API North-Star cutover … not V1" ([ADR-0026, Consequences Negative-1](ADR-0026-v1-subscription-runtime-driver.md) [VERIFIED]). ADR-0026's premise — that a subscription session requires a human present to start it — did not account for the non-interactive `claude setup-token` → `CLAUDE_CODE_OAUTH_TOKEN` capability, which authenticates a headless subscription session with no human present [VERIFIED: authentication.md]. Because that capability now exists, ADR-0039 **refines / partially-reverses ADR-0026 Negative-1**: truly-headless, unattended, scheduled SUBSCRIPTION execution is viable in V1 for the cadence leg WITHOUT the all-API cutover. This is a refinement of ADR-0026's premise on the attended-vs-unattended axis (not the persistent-daemon-vs-one-shot axis), parallel to how ADR-0026 itself openly refined ADR-0022's "unattended" claim. The MECHANISM's viability does not settle its PERMISSIBILITY under the subscription's acceptable-use terms — that stays open (OQ-6).

**Cost and security are the two remaining axes, and they favor the local subscription runner over B2.** ADR-0026 kept the de-id-IN call the SOLE metered egress by inverting the specialist/judge/lens aggregate onto the subscription; routing that aggregate back through the metered no-train API (Alternative C) re-arms exactly the spend ADR-0026 removed — the whole author + judge + per-lens fan-out × the bounded revise iterations, per re-gen, metered by default. One load-bearing verified fact sharpens the security axis: Claude Code's auth precedence puts `ANTHROPIC_API_KEY` ABOVE subscription OAuth, so a scheduled process that still carries the API key in its environment would silently bill the API key instead of the subscription [VERIFIED: authentication.md, authentication-precedence]. The runner must isolate the subscription session's auth from that env key (while the de-id `ModelClient` still resolves the keychain item, [key_source.py resolve](../../scripts/model/key_source.py) [VERIFIED]) — a real operational hazard the design must close (OQ-2), but one that keeps the ONE metered egress the de-id call, not a re-armed dispatch aggregate.

On **buildability under extend-not-rebuild**, the runner is a scheduler plus a thin entry that supplies the three already-built seams (`dispatch`, `deid_client`, `tailor_client`) to `plan_loop.signal`; the debounce (`MIN_REGEN_INTERVAL_DAYS=7` + the sustained-signal window, [plan_loop.py:357-428](../../scripts/serve/plan_loop.py) [VERIFIED]), the fail-closed composition, and the cross-domain holds all stay in the built loop. The long-term cost the decision accepts is the recurring metered de-id spend once the schedule is enabled and the local-machine-awake dependency (both below).

### Consequences

**Positive:**
- The cadence trigger gains its only viable host: a local subscription session that satisfies BOTH ADR-0026's not-metered dispatch and the crown-jewel's local-store-adjacency, so the loop's weekly leg closes autonomously instead of degrading `loop-dispatch-unavailable` ([server.py:744-746](../../scripts/serve/server.py) [VERIFIED]).
- The raw store stays local and the runner adds ZERO new egress surface: it reads the same gitignored local store the server reads ([plan_loop.py:126](../../scripts/serve/plan_loop.py) [VERIFIED]) and dispatches only the de-identified summary, so the ADR-0027 de-id-IN call remains the SOLE metered/no-train egress on the automated path (finding-C containment inherited from ADR-0036).
- On subscription auth, the specialist/judge/lens dispatch incurs 0 marginal API spend, so the entire ADR-0026 subscription-dispatch posture holds on the AUTOMATED re-gen exactly as on an operator `/generate-plan` press [VERIFIED: agent-sdk/overview subscription billing].
- Designing and building the runner is $0 and arms nothing — the schedule is disabled by default, so the build itself triggers no de-id call and no dispatch (the PF-S63-02 guard-loosening corollary is honored: activation is a separate, operator-owned act).

**Negative:**
- **Enabling the schedule arms recurring metered de-id spend, permanently (1+ year) while it is on.** Each cadence tick that passes the debounce fires one metered ADR-0027 de-id-IN call (the sole egress, but a real recurring cost); the `MIN_REGEN_INTERVAL_DAYS=7` floor bounds the frequency to at most weekly ([plan_loop.py:357](../../scripts/serve/plan_loop.py) [VERIFIED]), but the standing spend obligation is the price of an autonomously-closing loop and does not exist while the schedule is disabled.
- **The run fires only when the operator's local machine is awake.** launchd and cron fire on a local clock: a cadence window that opens while the Mac is asleep/off is not run on time — launchd may coalesce a missed job to the next wake, cron simply drops it, so the loop's "weekly" cadence degrades in practice to "weekly, when the machine is on" [UNVERIFIED: the exact launchd missed-job / `StartCalendarInterval` coalescing behavior for this runner is a spec-stage scheduler-selection detail, OQ-3]. A missed window is silently skipped unless the design adds a catch-up-on-next-run rule.
- **Auth-precedence footgun (VERIFIED).** If `ANTHROPIC_API_KEY` is present in the scheduled process's environment, the Claude Code session bills the API key rather than the subscription [VERIFIED: authentication.md], silently converting the 0-marginal-spend dispatch into metered spend — the opposite of the ADR-0026 posture. The runner design MUST isolate the subscription session's auth from the env key (OQ-2); this is an operational hazard introduced by the choice, not a free lunch.
- **Non-interactive subscription-token durability is not fully pinned.** The `claude setup-token` OAuth token is documented as ~1-year-lived, but whether it refreshes non-interactively across scheduled runs (vs. eventually requiring an interactive re-login) is not confirmed from first-party docs [UNVERIFIED: authentication.md documents the 1-year token but not scheduled-run refresh behavior, OQ-2]. An expired token would fail the scheduled run silently — a reliability constraint the design must surface, not swallow.
- **New at-rest secret + operator-specific surfaces (tensions-with ADR-0005).** The runner introduces two persistent local artifacts ADR-0005's clonable / PII-free-trunk posture must keep OFF the tracked tree: (1) the ~1-year `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token` — a long-lived subscription secret whose leak into a committed/tracked file is a real exposure — and (2) the launchd plist / crontab entry, which also hardcodes operator-specific paths (the recurring multi-user no-operator-specific-hardcoding concern). Both must stay gitignored / keychain-held and runtime-injected, denied at commit by the existing `block-pii-commit.sh` + `pre-push-pii-scan.sh` scans, and the plist must not hardcode operator-specific paths into a tracked file ([ADR-0005, Decision](ADR-0005-operator-agnostic-clonable-pii-free-trunk.md) [VERIFIED]) — the same at-rest-secret tension ADR-0027 carried for the no-train API key. [AMENDED 2026-07-07 (bead `aque`/`8s7i`, SEC-02): the "denied at commit" clause was ASPIRATIONAL for the `CLAUDE_CODE_OAUTH_TOKEN` at ADR-0039 acceptance — `scripts/guard/pii_scan.py` was an operator-PII scanner (name/contact/health-line) with NO secret/credential detection, so a `sk-ant-oat…`-shaped token in a tracked file passed BOTH hooks clean (only the ADR-0039-T2 AC-5 pytest tree-scan caught it — a backstop over already-tracked files that misses a new-file commit, `--no-verify`, and human-terminal commits). Bead `aque` BUILT it: the OAuth-token pattern is now in `pii_scan.SECRET_PATTERNS`, applied trunk-wide AND unconditionally by `scan_scoped` (the single policy both hooks run), so the hooks now DO deny the token at commit + pre-push. The launchd/cron plist is kept off the tree by `.gitignore` (gitignored placeholder-only templates, T3) — a DISTINCT mechanism from the PII/secret content scans, which do not detect arbitrary operator-specific filesystem paths.] The token-at-rest storage location (keychain vs. launchd env) is folded into OQ-2.
- **The concrete headless shape carries a verification gap.** Sub-agent dispatch is documented for the Agent SDK but NOT explicitly for the CLI `-p` path [UNVERIFIED for CLI `-p`; VERIFIED for the SDK], so the exact runner shape that guarantees subscription sub-agent dispatch (SDK vs. `claude -p`) is spec-stage (OQ-1), not settled here.

**Neutral:**
- The data-event and free-text triggers keep firing in-process from the running server's route/care_chat/confirm sites; the scheduled runner hosts ONLY the cadence trigger. Those in-process triggers ALSO need a subscription-dispatch host — which the standalone Python server does not provide either (it degrades `loop-dispatch-unavailable`, [server.py:744-746](../../scripts/serve/server.py) [VERIFIED]) — so wiring them to a live subscription runtime is separate downstream work (OQ-5); the cadence runner neither hosts nor blocks them.
- The in-app `_do_plan_loop` route and the built `plan_loop.signal` debounce are unchanged; the runner is an additional caller of `signal`, not a replacement. `adjust.py` and the other loop legs are untouched.

### Alternatives Considered

#### Alternative A: Local scheduled headless Claude-Code runner (Chosen)
A local OS scheduler (launchd / cron), disabled by default, launches a local headless Claude-Code subscription session on the cadence that reads the local store, supplies the `deid_client`, dispatches specialists/judge/lenses as subscription sub-agents, and calls the built `plan_loop.signal(trigger=CADENCE_TRIGGER, ...)`.
- **Supporting evidence:** The only runtime that is BOTH local-store-adjacent (reads `store.read_all(root)` with no PII egress, [plan_loop.py:126](../../scripts/serve/plan_loop.py) [VERIFIED]) AND a real Claude-Code subscription session (0 marginal dispatch spend, ADR-0026 posture) [VERIFIED: headless.md, agent-sdk/overview]. Reuses the built loop + debounce + composition wholesale — a scheduler + a thin seam-supplying entry, nothing re-hosted.
- **Trade-offs:** Recurring metered de-id spend once enabled (Negative-1), a local-machine-awake dependency (Negative-2), and the auth-isolation hazard (Negative-3). Accepted because local-first PII fit dominates and the de-id-IN call stays the sole metered egress.
- **When this becomes the right choice:** For V1, when the loop's cadence must close autonomously on a single operator's local machine and the subscription-dispatch / local-PII constraints both bind.

#### Alternative B: Cloud scheduled routine / hosted Claude cron agent
A hosted scheduled agent (a cloud routine) fires the loop's re-gen on the cadence with no dependence on the operator's machine being awake.
- **Supporting evidence:** Genuine advantages the local runner lacks — no local-machine-awake dependency, managed scheduler reliability, and no local launchd/cron setup. The cloud is where the North-Star hosted product's per-tenant data already lives.
- **Trade-offs:** It cannot see the operator's LOCAL gitignored store; running the loop there would require exporting the raw local store to the cloud runtime — a NEW raw-PII egress class beyond ADR-0016's carve-out and ADR-0027's single de-id-IN egress, breaching ADR-0001's summaries-not-raw boundary ([ADR-0001, Y-Statement](ADR-0001-pii-trust-boundary-no-train-routing.md) [VERIFIED]). It is a North-Star-hosted-product candidate, explicitly out of V1's single-operator local-artifact scope ([vision.md, V1/North-Star boundary](../../design/vision.md) [VERIFIED]).
- **When this becomes the right choice:** In the North-Star GP product, where each tenant's PHI already resides server-side under HIPAA + a BAA + per-tenant isolation — there the data is already in the cloud runtime, so the new-egress disqualifier does not apply.

#### Alternative C (B2): API-backed in-server dispatch
Route the specialists/judge/lens through the no-train API from inside the standalone server on a timer, the way `_do_generate_plan` already gathers each domain's author envelope through the instance no-train `ModelClient` ([server.py:597,667-683](../../scripts/serve/server.py) [VERIFIED]) — no scheduler process, no subscription session, reusing the running server.
- **Supporting evidence:** The smallest new runtime — no OS scheduler, no headless-session auth, no subscription-token durability question. It reuses the built, tested in-server author path (`_do_generate_plan`), which already runs the frozen cross-domain orchestrator over metered author calls ([server.py:672-683](../../scripts/serve/server.py) [VERIFIED]).
- **Trade-offs:** It arms heavy metered spend BY DEFAULT — every specialist + judge + lens becomes a metered API call, the exact aggregate ADR-0026 inverted onto the subscription to keep the de-id-IN call the sole metered egress ([ADR-0026, Y-Statement](ADR-0026-v1-subscription-runtime-driver.md) [VERIFIED]). It directly contradicts ADR-0026's subscription-dispatch design and the crown-jewel single-metered-egress posture, and `_do_generate_plan` is deliberately the screened-only path with NO reauthor/adjudicator hook ([server.py:606-611](../../scripts/serve/server.py) [VERIFIED]) — so it would ALSO regress the ADR-0028 composition ADR-0036 requires on every evolved plan. It is more metered surface and less safety composition, not less.
- **When this becomes the right choice:** Only if ADR-0026's subscription-dispatch constraint is explicitly re-opened and metered dispatch is accepted (e.g. a measured finding that the subscription rate/concurrency ceiling cannot host the loop's cadence aggregate — see Review triggers).

#### Dissent: No scheduled runner — keep the loop operator-triggered only
**Source:** The operator-gated-activation posture (PF-S63-02 guard-loosening corollary) and the vision's single-operator, operator-owns-the-plans framing ([vision.md, Physician-ready](../../design/vision.md) [VERIFIED]). A reviewer can reasonably hold that automating a health-plan re-gen on a timer — arming recurring spend and re-planning without the operator present — is a step the operator should always take by hand, via the in-app loop tick, so no plan ever changes without a deliberate press.
- **Conditions under which this becomes the right choice:** If the operator decides the automated cadence's value does not justify the standing spend + unattended-re-plan trade-off, the schedule stays disabled permanently and the loop closes only on an operator-driven tick — which this decision fully supports, since the runner is disabled by default and the in-app trigger path is retained.

### Validation Approach

**Confirmation criteria:**
- **The runner supplies the seams to the BUILT loop (extend-not-rebuild):** the runner calls `plan_loop.signal(root, trigger=plan_loop.CADENCE_TRIGGER, dispatch=..., deid_client=..., tailor_client=...)` as its single entry to the loop. Expected: exactly 1 call site into `plan_loop.signal`; a grep of the runner for `_should_regenerate` / `compose_disposition` / `orchestrate.generate_plans` / a re-declared `MIN_REGEN_INTERVAL_DAYS` returns 0 — the runner re-hosts NONE of the debounce, composition, or holds ([plan_loop.py:414,357](../../scripts/serve/plan_loop.py) [VERIFIED]).
- **Disabled by default (activation-gated):** a fresh clone/install has 0 active launchd/cron entries for the runner until the operator runs the documented enable step; building the runner triggers 0 de-id calls and 0 dispatch. Expected: 0 scheduled jobs and 0 metered calls before the operator-owned enable action.
- **The cadence trigger reaches `signal` with the right label:** a fired tick calls `signal` with `trigger == plan_loop.CADENCE_TRIGGER` ([plan_loop.py:350](../../scripts/serve/plan_loop.py) [VERIFIED]), so an absent-signal tick returns the hold+prompt receipt (`log_prompt=True`, 0 new plans) rather than a bare no-op — the cadence-specific path.

**Falsification criteria:**
- **Not-metered dispatch probe (the ADR-0026-parity + auth-precedence test):** run the scheduled runner against a seeded raw-PII intake on subscription auth and count metered API calls by lane. Threshold: **exactly the de-id-IN call is metered (1 per gate-pass), and 0 metered calls on the specialist/judge/lens dispatch.** If ≥1 metered dispatch call is observed, the subscription session picked up an API key (the auth-precedence footgun, [VERIFIED: authentication.md]) — halt and isolate the session's auth from `ANTHROPIC_API_KEY` before release.
- **Crown-jewel non-egress (wire-scan, inherited from ADR-0036):** seed a synthetic raw identifier (a legal name) + raw meds into the local raw intake, fire one scheduled cadence tick, dump the specialist-lane dispatch payload, and assert the raw tokens are ABSENT. Threshold: **0 raw-PII hits** in any specialist dispatch payload. ≥1 hit means raw local PII reached the dispatch — halt.
- **Local-store-only (no new egress):** assert the runner reads the local gitignored store ([plan_loop.py:126](../../scripts/serve/plan_loop.py) [VERIFIED]) and sends 0 bytes of raw store content to any non-local/cloud runtime — the ONLY off-device call on the re-gen is the ADR-0027 de-id-IN call. Threshold: 0 raw/store-content network sends outside the de-id-IN call. ≥1 means the runtime introduced a new egress class (the Alternative-B disqualifier realized) — halt.
- **Activation gate (never default-on):** with the schedule disabled, assert the cadence never fires (0 re-gens over a multi-week window); after the operator runs the enable step, assert exactly the debounced cadence fires (a single reading in-window → 0 re-gen; a sustained signal past `MIN_REGEN_INTERVAL_DAYS` → 1 re-gen). Threshold: 0 re-gens while disabled; the built debounce pair holds once enabled.
- **Time horizon:** run the not-metered probe, the non-egress wire-scan, the local-store-only scan, and the activation-gate check at the first build of the runner, at the operator-present LIVE test, at every release thereafter, and before the July-2026 physician-visit deliverable ships.

**Review triggers:**
- The subscription session's rate/concurrency ceiling blocks the cadence aggregate (author + judge + per-lens dispatch × the bounded revise iterations, per re-gen) — re-open the subscription-runner-vs-metered-dispatch trade-off (Alternative C) against the measured cost.
- Claude Code's headless mode, Agent-SDK sub-agent support, subscription-auth precedence, or setup-token lifetime/refresh behavior changes [VERIFIED: headless.md / agent-sdk/overview / authentication.md] — re-verify the not-metered probe and the token-durability assumption (OQ-1/OQ-2).
- `plan_loop.signal`'s seam signature changes ([plan_loop.py:431](../../scripts/serve/plan_loop.py) [VERIFIED]) — re-verify the runner supplies every seam (`dispatch`, `deid_client`, `tailor_client`) and still calls the built entry, not a re-hosted loop.
