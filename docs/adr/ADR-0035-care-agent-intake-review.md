## ADR-0035: Care-Agent Review-on-Intake Trigger + Meds Curation

> **Y-Statement:** In the context of the intake/onboarding set where ADR-0034's field→destination contract fills the de-identified planner tokens but a filled profile sits inert (no agent engages it) and the raw medications it captures are record-only-local with `rx-interaction-classes` left at its empty `""` default until a curation step runs, facing the tension between the operator wanting the ONLY the de-identified class token persisted as a planner input), where the clarifying review reuses the existing no-train lane (ADR-0016 / ADR-0027) as a NEW TRIGGER carrying only the de-identified ### Context

ADR-0034 set the field→destination contract: a filled intake feeds the de-identified `SUMMARY_FIELD_SET` planner tokens, routes safety signals to referral, and keeps raw medications RECORD-ONLY local — `rx-interaction-classes` is DELIBERATELY ABSENT from the wired set because the serve layer cannot de-identify a raw drug name (the `pii_scan` value gate does not catch drug names) and there is no pharmacology DB in serve-layer code by design ([capture.py:65-72](../../scripts/serve/capture.py) [VERIFIED], [router.py:144-153](../../scripts/plan/router.py) [VERIFIED]). ADR-0034 therefore hands its meds curation to "the care-agent (ADR-0035), which proposes class tokens and confirms with the operator when unsure" ([ADR-0034 Decision](ADR-0034-intake-content-deid-safety-mapping.md) [VERIFIED]), and the `rx-interaction-classes` token stays at its empty no-Rx default `""` until that curation runs ([router.py:231](../../scripts/plan/router.py) [VERIFIED, per ADR-0034]). The live chat path already exists: `chat.dispatch_turn` builds the de-identified `router.summarize` summary, makes ONE outbound `client.converse` call (the single egress class), and routes the model's extraction through the unchanged gate ([chat.py:363-390](../../scripts/serve/chat.py) [VERIFIED]); the served SPA's default chat persona IS the Care Assistant ([app_view.html:385,601](../../vault/design/templates/app_view.html) [VERIFIED]), reached through the `/chat` route ([server.py:152,282-330](../../scripts/serve/server.py) [VERIFIED]).

Two forces pull against each other across more than one stakeholder. The operator needs the Care Assistant to ENGAGE the profile, not merely store it — a filled profile with no agent reading it is inert, and the medication-interaction surface the supplement↔Rx BPMH screen consumes ([router.py:180-197](../../scripts/plan/router.py) [VERIFIED, per ADR-0034]) is blind until something curates the raw meds. The data subject's crown-jewel containment binds the opposite force: ADR-0001 admits ONLY de-identified tokens to the no-train planner, with raw PII held locally; ADR-0016 already scoped a SINGLE carve-out — the live intake conversation may egress raw on the no-train lane, and "future readers must not silently widen" it ([ADR-0016 Decision](ADR-0016-intake-conversation-egress-relaxation.md) [VERIFIED]). The clarifying-question review carries only the de-identified profile, so it rides the existing no-train lane as a new TRIGGER and adds no egress class. The meds curation is different: there is no local pharmacology DB (ADR-0034) and no local model at V1 (ADR-0001 Alt C deferred), so curating raw drug names into interaction classes requires sending those raw names to the no-train model. Rather than launder that as a "reuse" of ADR-0016's conversation carve-out — which explicitly excludes raw store-content egress — this decision names it honestly as a NEW, bounded egress class: de-associated raw medication names, with NO operator identity and NO name↔med linkage attached, an operator-signed-off EXTENSION of ADR-0001 on the same de-association principle ADR-0032 set for variant queries (PF-S63-02: the loosened-boundary failure class is named and signed off, not default-accepted). The maintainer's clinical-safety force binds a third: a mis-classified medication is the false-clean risk ADR-0034 refused for serve-auto and user-self classification, so the curation's output must stay operator-confirmable rather than silently applied. Because this sets WHEN the care-agent runs, WHAT it sends to the model, and how its meds output reaches the planner — not a code comment beside the chat route — it is a decision.

### Decision

The FINAL intake save triggers a new server action that invokes the EXISTING care-assistant model path (`client.converse`, the seam `chat.dispatch_turn` already drives) over the de-identified `router.summarize` profile to produce clarifying questions, which land as Care-Assistant turns in the Chat-with-Team thread. This reuses the existing model client and the existing no-train egress lane (ADR-0016 / ADR-0027) — for the clarifying review it is a NEW TRIGGER, not a new model client and not a new egress class. The clarifying-question review sends ONLY the de-identified profile to the model (no raw PII). (The meds curation, below, is a separate matter — it introduces a named de-associated egress class.) The review is an async, operator-visible operation: a loading bar plus a text status under the Care Assistant card runs during the review, matching the existing upload-ticker progress pattern; its pixel design is a separate downstream step, out of scope here.

The same review performs the ADR-0034 meds curation. There is no local pharmacology DB and no local model at V1 (ADR-0034's serve layer holds no pharmacology DB; ADR-0001 Alternative C deferred), so the curation sends DE-ASSOCIATED raw drug names — the drug names only, with NO operator identity and NO name↔med linkage attached — to the no-train model to propose interaction classes. It does so in a DISTINCT de-associated curation request (its own meds-only payload), NOT a turn through `converse` / `_model_messages` — whose "0 store content" contract ([chat.py:247-295](../../scripts/serve/chat.py) [VERIFIED]) is left intact (see Rationale). The model proposes the de-identified `rx-interaction-classes` class token; the review confirms with the operator when unsure. ONLY the resulting de-identified class token is persisted as a planner input; the raw medications stay record-only-local (ADR-0034) and never become a planner token, never enter the `dispatch` payload to the specialist authors.

This meds-curation egress is a NEW, NAMED, bounded egress class — *de-associated raw medication names → the no-train model for interaction-class curation* — an operator-signed-off EXTENSION of ADR-0001, directly analogous to ADR-0032's de-associated variant-query egress. **PF-S63-02 sign-off (2026-06-30):** the failure class this boundary prevents is IDENTIFIABLE operator PII leaving the machine — the operator's identity and the identity↔fact (name↔med) linkage. The operator gave informed sign-off that DE-ASSOCIATED raw drug names (no name attached) are out-of-scope of that failure class and MAY egress to the no-train model for interaction-class curation ("the raw names can go to the regular models — they don't have a name attached"); the operator's identity and the name↔med linkage stay 100% local. This is NAMED, not default-accepted — the guard-loosening corollary is satisfied (ADR-0032 is the de-association precedent). With no connected key the review does not run and does not spend — it degrades honestly to the no-key state (the same `_key_available` predicate the `/generate-plan` no-key guard uses, [server.py:431,491-506](../../scripts/serve/server.py) [VERIFIED]), deferring the review until a key is connected.

Beyond the final save, a MATERIAL profile change — specifically a medication EDIT (and a new safety-screen answer) made through the My-Info tab (ADR-0033) — RE-TRIGGERS this review and its meds curation over the changed profile, so an edited medication is re-curated into `rx-interaction-classes` and the clarifying review re-runs; ADR-0033's editable My-Info path DEPENDS on this re-review trigger ([ADR-0033 Consequences-Negative#3](ADR-0033-first-run-intake-gate-and-shell.md) [VERIFIED]). The exact granularity (which edits count as material) may remain a spec detail, but the trigger's EXISTENCE is decided here, not implied.

### Rationale

Three options were weighed on three criteria the governing decisions make load-bearing: **engagement** (does a filled profile get actively reviewed?), **egress posture** (does the trigger add a new model-bound path or reuse an authorized one?), and **clinical safety of the meds output** (can a mis-classified med ship unseen?). On engagement, only an actual review turns an inert profile into clarifying questions — showing the profile back to the operator (Alternative A) adds no signal. On egress posture, the two legs differ honestly. The clarifying review carries only the de-identified `router.summarize` profile (the same de-identified context `chat._model_messages` already places on the wire — token NAMES and booleans, 0 raw store value, [chat.py:247-295](../../scripts/serve/chat.py) [VERIFIED]) — it reuses `converse` on the existing no-train lane and adds NO egress class. The meds curation cannot do the same: `_model_messages` carries the de-identified context plus the raw live conversation and `0 store content` by contract ([chat.py:247-295](../../scripts/serve/chat.py) [VERIFIED]), so injecting raw record-only drug names into a `converse` turn would BREACH that contract. The curation therefore rides a DISTINCT de-associated request — a meds-only payload outside `_model_messages` — and is named as a NEW, bounded egress class (de-associated raw drug names → the no-train model), an operator-signed-off EXTENSION of ADR-0001, NOT a reuse of ADR-0016's conversation carve-out (which excludes raw store-content egress, [ADR-0016 Decision](ADR-0016-intake-conversation-egress-relaxation.md) [VERIFIED]). This is the PF-S63-02 discipline made concrete — the widening is NAMED and signed off (the de-association precedent is ADR-0032), not laundered as a reuse. On clinical safety, the curation confirms-when-unsure and surfaces its proposal as operator-visible questions, so a mis-classification is caught by the operator rather than silently applied — exactly the asymmetric posture ADR-0034 chose over serve-auto / user-self classification ([ADR-0034 Alternatives A/B](ADR-0034-intake-content-deid-safety-mapping.md) [VERIFIED]).

Reusing the existing seam over building a new one also keeps the single-egress-class boundary intact: the only model egress remains `scripts/model/` via the swappable `ModelClient` ([client.py:33-60](../../scripts/model/client.py) [VERIFIED]), and the no-key guard already proven on `/generate-plan` ([server.py:431](../../scripts/serve/server.py) [VERIFIED]) gives the review a tested degrade path. Long-term, the review's spend and latency are paid once per final save (and on a re-review trigger), not per chat open — bounding the metered cost the live key carries.

### Consequences

**Positive:**
- The filled profile is actively reviewed: after final save, the Chat-with-Team thread carries the Care Assistant's clarifying questions derived from the de-identified profile, instead of an inert stored profile the operator must prompt unaided ([app_view.html:385,601](../../vault/design/templates/app_view.html) [VERIFIED]).
- The planner's medication-interaction surface gets populated: the care-agent curates raw-local meds into the de-identified `rx-interaction-classes` token, so the supplement↔Rx BPMH screen finally has an operator Rx surface to screen against ([router.py:180-197](../../scripts/plan/router.py) [VERIFIED, per ADR-0034]) — closing the ADR-0034 "first plan is Rx-blind" gap once the review runs.
- The clarifying review adds no new egress class: it reuses `client.converse` on the existing no-train lane (ADR-0016 / ADR-0027) and the existing `ModelClient` over the de-identified profile only — a new trigger, not a new model client ([chat.py:370](../../scripts/serve/chat.py), [client.py:47-60](../../scripts/model/client.py) [VERIFIED]).
- The meds crown-jewel holds on the identity + planner prongs: only the de-identified class token is persisted as a planner input; raw drug names never enter the `dispatch` payload to the specialist authors, and the operator's identity + the name↔med linkage never leave the machine — only the DE-ASSOCIATED drug names (no identity) reach the no-train model for class curation ([capture.py:65-72](../../scripts/serve/capture.py) [VERIFIED]).
- A tested no-key degrade: with no connected key the review does not spend and does not fail silently — it reuses the `_key_available` predicate the `/generate-plan` guard already exercises ([server.py:431,491-506](../../scripts/serve/server.py) [VERIFIED]).

**Negative:**
- De-associated raw medication names DO leave the machine: the meds curation is a NEW egress surface beyond the prior de-identified-summary-only boundary — raw drug names (de-associated, no identity, no name↔med linkage) read from the record-only store now reach the no-train model for class curation. Accepted as not-a-big-deal-because-de-associated (operator sign-off, 2026-06-30), but it is a WIDER surface than ADR-0001's original de-identified-only routing: a faithless model could log the de-associated drug-name set (a weak residual — the med set with no identity attached), mitigated only by the no-train / no-retention lane terms, never zero. This is the same shape of residual ADR-0032 owns for de-associated variant queries.
- Added first-review latency and metered spend: the final save now blocks on (or runs visibly alongside) a no-train model call, so the operator's first arrival in Chat-with-Team carries the round-trip wall-clock and per-call cost that a no-review save did not — a recurring metered cost on the live key for every final save and every re-review.
- A hard dependency on a connected live key: with no key the review cannot run, so the clarifying questions and the meds curation are DEFERRED until the operator connects a key — the first post-intake experience is degraded (no questions, `rx-interaction-classes` still empty) exactly when the operator has just finished a long intake.
- The care-agent can mis-classify a medication: an LLM curating raw drug names into interaction classes can propose a wrong class, the false-clean clinical-safety risk ADR-0034 named — mitigated by confirm-when-unsure plus the operator-visible questions, but not eliminated; an over-confident wrong classification the operator does not catch ships into the BPMH surface.
- Agent-initiated turns are new to the chat surface: the live chat is operator-turn-driven (`dispatch_turn` runs per operator turn, [chat.py:315](../../scripts/serve/chat.py) [VERIFIED]); a server-initiated review that pushes Care-Assistant turns with no preceding operator turn needs a delivery mechanism the current per-turn loop does not have (OQ-4) — a standing integration cost.

**Neutral:**
- The review reads the SAME de-identified `router.summarize` summary the chat loop already builds ([chat.py:363](../../scripts/serve/chat.py) [VERIFIED]) — one de-identification path, not a second.
- The progress affordance reuses the existing app-shell progress pattern (the `.chat-progress` bar under the Care Assistant card and the upload `.upload-status` ticker, [app_view.html:187-189,394,784-818](../../vault/design/templates/app_view.html) [VERIFIED]) — a styling reuse, neither a new component nor a redesign.

### Alternatives Considered

#### Alternative A: No review — just show the filled profile back
On final save, render the captured profile (the My-Info Q&A) and let the operator drive any conversation unaided, with no agent-generated questions.
- **Supporting evidence:** Zero added model spend or latency on save; no live-key dependency for the first post-intake experience; the simplest path — the profile is already captured and renderable.
- **Trade-offs:** The profile stays INERT — the exact dead state the operator wants to fix; `rx-interaction-classes` is never curated, so the first plan ships Rx-blind permanently (the ADR-0034 gap is never closed). Rejected: it does not engage the profile at all.
- **When this becomes the right choice:** If operator-use evidence shows the proactive questions are unwelcome or ignored — then retract to a profile view plus an operator-initiated "review my profile" action (the Dissent direction).

#### Alternative B: Review on EVERY chat open, not once on final save
Run the care-agent review each time the operator opens Chat-with-Team, regenerating clarifying questions from the current profile.
- **Supporting evidence:** Always reflects the latest profile edits without a separate edit-triggered re-review; no "stale questions" between a profile change and the next review.
- **Trade-offs:** Repeated metered spend and latency on every chat open, mostly regenerating the same questions when the profile has not changed between opens — cost with no new signal. Rejected as the default. The right granularity is once on final save (plus a re-review when the profile materially changes), not per open.
- **When this becomes the right choice:** The material-change re-review IS adopted (see the Decision + Review-triggers) — a re-review TRIGGERED by a material profile change (an edited med, a new safety answer), NOT this Alternative's unconditional per-open run; only the per-open form is rejected.

#### Alternative C: Auto-apply the curated meds class without operator confirmation
Let the care-agent classify raw meds into `rx-interaction-classes` and persist the class token directly, with no confirm-when-unsure step.
- **Supporting evidence:** Fewer operator interruptions; the interaction surface populates immediately with no back-and-forth; the smoothest curation flow.
- **Trade-offs:** A wrong auto-applied class is the false-clean clinical-safety risk ADR-0034 explicitly refused for serve-auto and user-self classification — a missed interaction reads as "no interaction" and the operator never sees it. Rejected on the same clinical-safety grounds. Confirm-when-unsure keeps the operator in the loop on exactly the uncertain classifications.
- **When this becomes the right choice:** Only if a validated, complete, maintained pharmacology source backed the classification (the same condition ADR-0034 set for its Alternative A) — then high-confidence classes could auto-apply with uncertain ones still confirmed.

#### Dissent: The no-proactive-agent position
**Source:** The question-economy and intake-friction concerns inherited from ADR-0018 / the operator-feedback record — some operators experience an agent that greets them with unsolicited questions as intrusive rather than helpful, preferring to drive the conversation themselves.
**Conditions under which this becomes the right choice:** If operator-use evidence shows the proactively-generated questions are ignored, dismissed, or rated unwelcome, the trigger should be retracted to an operator-initiated review (a "review my profile" control) while keeping the meds curation as a confirm-when-unsure step the operator opts into — proactive engagement traded for operator control.

### Validation Approach

**Confirmation criteria:**
- The review fires and produces questions: after a final intake save with a connected key and a filled profile, the Chat-with-Team thread contains **≥1** Care-Assistant clarifying question derived from the profile — expected ≥1; 0 means the trigger did not fire or the review produced nothing.
- The meds curation populates the token: with a raw medication in the local record, the review proposes a de-identified `rx-interaction-classes` class token (persisted as the planner input) and surfaces a confirm-when-unsure question — expected the token transitions off its empty `""` default for a supplied medication, **0** raw drug strings persisted as a planner token.
- The progress affordance is visible: during the review the loading bar + status text shows under the Care Assistant card (matching the existing upload-ticker pattern, [app_view.html:187-189,784-818](../../vault/design/templates/app_view.html) [VERIFIED]) — expected an operator-visible async status, not a silent block.

**Falsification criteria (quantitative; the crown-jewel probe is load-bearing):**
- Crown-jewel probe (load-bearing — covers BOTH legs): seed a known raw-PII token (legal name, DOB digits, a raw drug name) into a filled intake, fire the review, and inspect (a) the clarifying-review model request, (b) the de-associated meds-curation request, and (c) every persisted planner input + the `dispatch` payload to the specialist authors. Thresholds — **0 raw-PII / raw-drug strings in the clarifying-review request** (it carries only the de-identified `router.summarize` profile); **0 operator-identity tokens and 0 name↔med linkage in the meds-curation request** (it carries de-associated drug names only — the drug name MAY appear, the operator's identity MUST NOT); AND **0 raw-drug strings persisted as a planner token or present in the `dispatch` payload** (only the de-identified `rx-interaction-classes` class token crosses to the authors). The boundary statement covers both egress legs and the planner: the operator's identity and the identity↔fact (name↔med) linkage NEVER leave the machine, and only the de-identified `rx-interaction-classes` token persists as a planner input. ≥1 identity crossing on either request, or ≥1 raw-drug string reaching the planner, reds the boundary → halt and repair before release.
- Meds-curation request probe (load-bearing — the named de-associated egress class): inspect the meds-curation model request directly. It MUST carry the drug names but ZERO operator-identity tokens and ZERO name↔med linkage — run `pii_scan` over the curation request. Threshold — **0 operator-identity hits and 0 name↔med-linkage statements in the meds-curation request** (it is DE-ASSOCIATED — drug names only, never "the operator [name] takes X"); ANY operator-identity token in the meds-curation request → FAIL → halt and repair before release. Also assert the curation request is a DISTINCT meds-only payload and is NOT injected into a `converse` / `_model_messages` turn (which keeps its `0 store content` contract, [chat.py:247-295](../../scripts/serve/chat.py) [VERIFIED]).
- No-UNNAMED-egress falsification: scan the review path for a model-client construction other than the existing `ModelClient` / no-train backend, or any outbound call outside `scripts/model/`. Threshold — **0 new model clients and 0 egress classes BEYOND the two named here** (the clarifying review's de-identified-profile reuse + the named de-associated meds-curation class); ≥1 unnamed/unauthorized egress path means the boundary was widened WITHOUT sign-off (the PF-S63-02 guard-loosening failure) → halt and restore. (This decision's meds-curation egress is the named, signed-off class — not an unnamed widening.)
- No-key falsification: fire a final save with NO connected key. Threshold — **0 model spend and 0 silent failures** — the review degrades honestly to the no-key state (the `_key_available` guard, [server.py:431,491-506](../../scripts/serve/server.py) [VERIFIED]); any spend on a keyless save, or a dropped/stack-traced request, is a breach → restore the no-key degrade.
- Auto-apply falsification: enter a medication the care-agent is uncertain about and scan for an `rx-interaction-classes` write that landed with no operator-confirm step. Threshold — **0 unconfirmed-when-unsure class writes** (confirm-when-unsure holds); ≥1 means the curation auto-applied an uncertain class (the rejected Alternative C) → restore the confirm gate.
- Time horizon: run the crown-jewel probe, the new-egress-class scan, the no-key check, and the auto-apply check at the first build of the review trigger (mock / fixture, 0 live spend), at the operator-present LIVE run, at every release thereafter, and before the July-2026 physician-visit deliverable.

**Review triggers:**
- A change to the no-train provider's no-train or retention terms — re-verify BOTH egress legs (the clarifying review's de-identified profile + the de-associated meds-curation class). The meds class leans on the no-train / no-retention lane as its only mitigation, so a terms change re-opens the PF-S63-02 sign-off.
- Any proposal to attach the operator's identity or the name↔med linkage to the meds-curation request — re-open this decision. The named class is DE-ASSOCIATED drug names ONLY and must stay bounded (the ADR-0016 / ADR-0027 "never silently widen the named class" discipline applied to this class).
- A change to `client.converse`, `chat.dispatch_turn`, or `router.summarize` — re-confirm the review reuses the seam and sends only the de-identified profile.
- A change to `capture.py`'s rx record-only routing — re-confirm raw meds stay record-only-local and only the curated class token persists as a planner input.
- The ADR-0033 platform-unlock transition landing — confirm the final-save trigger fires the review at unlock.
- A MATERIAL profile edit through the My-Info tab (a medication change, or a new safety-screen answer) — DECIDED to RE-TRIGGER this care-agent review + meds curation over the changed profile (ADR-0033's editable My-Info path depends on it); re-confirm the re-review fires and re-curates `rx-interaction-classes` on a material edit. The exact material-change granularity is a spec detail.
