## ADR-0004: On-Demand (+Cron) Generation of Single-File Self-Contained Local Artifacts

> **Y-Statement:** In the context of a local-first single-operator health system that must put a tracking dashboard and a physician-ready report in front of the operator and a time-constrained doctor, facing the tension between the richness an interactive live surface affords and the clonable/offline/no-server constraint V1 commits to, we decided to generate dashboards and reports on demand (and optionally on an unattended cron schedule) by reading the local store and rendering through a pre-designed template library built from the artifact-design-protocol component set into a single self-contained local HTML file — offline, no external asset requests, inline CSS/SVG, under 500KB, WCAG-AA, colorblind-safe, print-safe — with no running server, to achieve a portable artifact a physician can open or print anywhere, accepting that interactivity and render-richness are bounded by the single-file/size/offline budget and that there is no always-fresh live view (the artifact must be regenerated to reflect new readings).

### Context

The system holds operator data and must turn it into two things a human reads: a Whoop-style tracking dashboard showing where the operator's markers are heading, and a physician-ready report shared at the July-2026 visit ([PRD-v1, US-6 L87-93, US-7 L95-101](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). Today none exists — LM-04, the first HTML artifact, is unstarted ([PRD-v1, Goal 1 baseline L26](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]) — so the delivery model is genuinely open: what is the artifact, who serves it, and what does "generate" mean.

Several forces pull against each other across more than one stakeholder. The operator wants a dashboard rich enough to scan trends and projections, which an interactive live surface serves well; the physician needs a report that opens or prints anywhere, with no app to log into, no network, and no dependency on a running service ([PRD-v1, US-7 AC L98-101, NG-7 L283](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). V1 is deliberately clonable and serverless: no hosted, live, always-on web application or server — a *local* store IS in scope, but a running surface that serves it live is deferred to v2+ ([PRD-v1, NG-4 L280](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]; [vision.md, boundary table L44](../../design/vision.md) [VERIFIED]). Each generated file must be self-contained, render fully with the network disabled, stay under 500KB, and pass WCAG-AA, colorblind-safe, and print-safe checks ([PRD-v1, NFR-4 AC L249-251](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). The PII boundary from ADR-0001 forbids any render path that ships operator data to an external asset, CDN, or server ([ADR-0001, Decision + Related Decisions](ADR-0001-pii-trust-boundary-no-train-routing.md) [VERIFIED]). And output must stay consistent generation-to-generation: the operator and his doctor should scan a familiar layout without re-learning it each time, which argues for rendering through a fixed pre-designed template set rather than bespoke per-artifact layout ([artifact-design-protocol.md, Purpose L16-19](../../vault/design/artifact-design-protocol.md) [VERIFIED]; [PRD-v1, FR-8 AC L186](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). The artifact-design-protocol already pre-specifies the component set and file conventions these forces imply, and assigns Daily/Weekly/Monthly/Quarterly frequencies to its review artifacts — the basis for unattended scheduled generation ([artifact-design-protocol.md, Artifact Types L28-37, File Conventions L60-65](../../vault/design/artifact-design-protocol.md) [VERIFIED]; [PRD-v1, Finding 4 L357, Finding 12 L373](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).

### Decision

Generate dashboards and reports on demand — and optionally on an unattended cron schedule — by reading the local time-series store and rendering through a pre-designed template library, each output written as a single self-contained local HTML file with inline CSS and inline SVG, no external asset requests, under 500KB, offline, WCAG-AA, colorblind-safe, and print-safe. Render through pre-designed templates built from the artifact-design-protocol component set rather than ad-hoc per-artifact layout. Run no live, always-on server or daemon: "scheduled" means an unattended cron-style run that produces the file and exits, not a process that stays up to serve it.

### Rationale

The delivery model was evaluated against three options — a live always-on web app/server (A), a multi-file artifact bundle with external asset references (B), and the chosen on-demand single self-contained file (C) — across four criteria the PRD and vision make load-bearing: clonability/serverlessness, offline/portability, the PII no-egress boundary, and render-consistency.

On **clonability/serverlessness**, option C requires nothing to deploy or keep running: a fresh clone generates a file and exits, satisfying the "0 runtime dependency on any shared service, host, account" criterion ([PRD-v1, NFR-3 AC L242-243](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]) and NG-4's no-live-server rule directly ([PRD-v1, NG-4 L280](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). A live server (A) would be exactly the deferred hosted surface. On **offline/portability**, a single file with everything inlined opens from disk with the network disabled and can be emailed or printed as one attachment ([PRD-v1, US-7 AC L98, NFR-4 AC L249](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]); a multi-file bundle (B) breaks the moment one asset path is missing — it does not survive being emailed as a single attachment or opened from an arbitrary directory. On the **PII no-egress boundary**, option C renders entirely locally with zero external requests, so the artifact cannot leak store contents to a CDN or server, satisfying ADR-0001's render-side constraint ([ADR-0001, Related Decisions D4](ADR-0001-pii-trust-boundary-no-train-routing.md) [VERIFIED]; [PRD-v1, NFR-1 AC L227](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]); A and B both reintroduce a network surface (a served page, fetched external assets) that this boundary forbids. On **render-consistency**, rendering through the fixed component-set template library makes two generations of the same type produce the same layout ([PRD-v1, FR-8 AC L186](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]; [artifact-design-protocol.md, Purpose L16-19](../../vault/design/artifact-design-protocol.md) [VERIFIED]) — the property a time-constrained doctor relies on to scan a familiar handout.

The accepted trade-off is that richness and interactivity are bounded by the single-file/<500KB/offline budget: inline-everything caps how much chart and interaction a file can carry, and there is no always-fresh live view — a new reading is reflected only by regenerating the artifact, not by a page that updates itself. We accept this because the V1 deliverable is a portable artifact a physician opens or prints, not a live application ([vision.md, boundary table L44, L48](../../design/vision.md) [VERIFIED]), and the live surface is an explicit North-Star deferral, not a foreclosed capability ([PRD-v1, NG-4 L280](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). Long-term, the same store and template inputs feed a hosted live surface at the North Star without re-deciding the data or component model — the generation path is the V1 realization of an output layer the product phase extends, not a dead end.

### Consequences

**Positive:**
- A generated dashboard or report opens locally as one self-contained file with 0 network calls and renders fully with the network disabled — verified directly against the NFR-4 single-file/offline criterion ([PRD-v1, NFR-4 AC L249, US-6 AC L90, US-7 AC L98](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- No server or daemon is deployed or kept running, so a fresh clone generates artifacts with 0 hosted-service runtime dependency, satisfying the clonable/serverless guarantee and NG-4 ([PRD-v1, NFR-3 AC L242, NG-4 L280](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- Rendering through the fixed component-set template library makes two generations of the same type produce the same layout and component set, so the operator and doctor scan a familiar artifact each time ([PRD-v1, FR-8 AC L186, NFR-7 AC L271](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]; [artifact-design-protocol.md, Purpose L16-19](../../vault/design/artifact-design-protocol.md) [VERIFIED]).
- The same generation runs unattended on a cron schedule (the protocol's Daily/Weekly/Monthly/Quarterly frequencies) and produces the file with no running server ([PRD-v1, FR-7 AC L177, NFR-7 AC L273](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]; [artifact-design-protocol.md, Artifact Types L28-37](../../vault/design/artifact-design-protocol.md) [VERIFIED]).

**Negative:**
- The <500KB / self-contained / offline budget caps interactivity and render-richness: every chart is inline SVG with no chart library and no external JS framework, so rich interactive views (zoomable, drill-on-click, large multi-series matrices) cannot exceed what fits inline under the size ceiling — the most asset-heavy artifacts press directly against this budget (see Open Questions, the D7 tension) ([PRD-v1, NFR-4 AC L250](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]; [artifact-design-protocol.md, File Conventions L61-64](../../vault/design/artifact-design-protocol.md) [VERIFIED]).
- No live server means no real-time or always-fresh view: a generated artifact is a snapshot of the store at generation time, so a new reading is reflected only by regenerating — the operator cannot watch a value update live, and a stale artifact silently misrepresents the current store until re-run ([PRD-v1, NG-4 L280, US-6 statement L87](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- Inline-everything increases per-file size pressure as a standing 1+ year constraint: as the store accumulates more timepoints and the template set grows, each file carries more inlined SVG/CSS toward the same fixed 500KB ceiling, so size headroom shrinks over time and a future high-density render may need capping or pagination ([PRD-v1, NFR-4 AC L250, Goal 2 L34](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]; ceiling-vs-real-render headroom [UNVERIFIED] — no realistic render measured pre-build).
- Generation is constrained downstream by the store's read model and the PII boundary: it can only read the local store ADR-0002 fixes and must render with no egress per ADR-0001, so the generation design has no freedom to fetch remote data or assets ([ADR-0001, Related Decisions D4](ADR-0001-pii-trust-boundary-no-train-routing.md) [VERIFIED]; [ADR-0002, Related Decisions D4](ADR-0002-local-first-time-series-store.md) [VERIFIED]).

**Neutral:**
- The pre-designed template library becomes a shared contract between this generation path and the plan-assembly (D5) and lab-flow/matrix/projection (D7) decisions, which both render through it; the specific V1 template list is a fixed input resolved in the PRD, not re-decided here ([PRD-v1, FR-8 AC L184, OQ-6 L347](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- The cron/unattended-run mechanism is shared with the import routine (D3); the specific scheduler is a reversible implementation detail, not part of this decision ([dag.md §2 D3–D4](.pipeline/dag.md) [VERIFIED]).

### Alternatives Considered

#### Alternative A: Live always-on web app/server that serves the store
Stand up a running web application (or local server process) that reads the store and serves dashboards/reports live in a browser, updating as new readings arrive.
- **Supporting evidence:** A live surface is the natural home for rich interactivity — zoomable charts, drill-down, an always-fresh view that reflects new readings without regenerating — and it is exactly the surface the North-Star GP product builds ([vision.md, boundary table L44, "Build now? No — architected-for, not built"](../../design/vision.md) [VERIFIED]). It removes the regenerate-to-refresh limitation option C accepts.
- **Trade-offs:** It is a server to deploy and keep running, which breaks the clonable/serverless guarantee (a fresh clone would need to stand up a service) and reintroduces a network surface the PII no-egress boundary forbids ([PRD-v1, NFR-3 AC L242-243](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]; [ADR-0001, Related Decisions D4](ADR-0001-pii-trust-boundary-no-train-routing.md) [VERIFIED]). It is precisely the hosted, live, always-on surface NG-4 and the vision boundary table defer to v2+ ([PRD-v1, NG-4 L280](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]; [vision.md, L44, L48](../../design/vision.md) [VERIFIED]). Rejected as a direct scope violation, not as an inferior surface.
- **When this becomes the right choice:** At the North-Star transition to a hosted GP product with per-account login and a clinician-facing surface, where a served, always-fresh view is required and the regulated-PHI trust model is built.

#### Alternative B: Multi-file artifact bundle with external asset references
Generate each dashboard/report as an HTML file plus separate external CSS, JS, and chart-asset files referenced by URL or relative path.
- **Supporting evidence:** Separating assets from markup is the conventional web pattern — shared CSS/JS across artifacts avoids duplicating inline payload in every file, keeps each HTML file smaller, and lets a chart library do richer rendering than hand-inlined SVG. It would ease the per-file size pressure option C accepts.
- **Trade-offs:** It is not self-contained: emailing the report as one attachment, printing it, or opening it from an arbitrary directory breaks the moment an asset path is missing, and external asset requests fail with the network disabled — failing NFR-4's single-file/offline/0-external-request criterion outright ([PRD-v1, NFR-4 AC L249](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). External fetches are also a PII egress surface the boundary forbids ([ADR-0001, Related Decisions D4](ADR-0001-pii-trust-boundary-no-train-routing.md) [VERIFIED]). The artifact-design-protocol's File Conventions already settle inline-everything for exactly these reasons ([artifact-design-protocol.md, File Conventions L61-62](../../vault/design/artifact-design-protocol.md) [VERIFIED]). Rejected because portability and offline are load-bearing for a physician-facing emailable/printable artifact.
- **When this becomes the right choice:** If artifacts were only ever opened in place from a fixed directory with a guaranteed asset path and never emailed, printed, or opened offline — a constraint V1's physician-share path violates.

### Validation Approach

**Confirmation criteria:**
- A generated dashboard and a generated report each open locally as one file with 0 external asset requests and render fully with the network disabled — verified by opening each with the network off and inspecting for 0 outbound requests (expected: 0) ([PRD-v1, NFR-4 AC L249, US-6 AC L90, US-7 AC L98](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- Each generated file is < 500KB and passes WCAG-AA contrast and colorblind-safe + print-safe checks — verified by file size and an accessibility/contrast check on the rendered file (expected: size < 500KB, WCAG-AA pass) ([PRD-v1, NFR-4 AC L250-251](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- Two generations of the same artifact type produce the same layout and component set — verified by generating the same type twice and diffing the structural layout (expected: identical template/component structure) ([PRD-v1, FR-8 AC L186](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- An unattended scheduled (cron) run produces the artifact file with no server process running — verified by running the generation on a schedule with no daemon up and confirming the file is produced (expected: file written, 0 server process) ([PRD-v1, FR-7 AC L177, NFR-7 AC L273](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).

**Falsification criteria:**
- If a generated file makes ≥1 external asset request (any outbound call for CSS/JS/font/image/data) or fails to render with the network disabled, the self-contained/offline guarantee has failed — halt generation and inline the missing asset before release ([PRD-v1, NFR-4 AC L249](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- If a generated file exceeds 500KB, the size budget has been breached — block release of that artifact and reduce payload (minify/cap, see OQ-1) before it ships ([PRD-v1, NFR-4 AC L250](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- If producing or viewing an artifact requires a running server or daemon (≥1 always-on process needed to generate or open the file), the no-live-server decision has been violated — a direct NG-4 breach; revert to the serverless generate-and-exit path before release ([PRD-v1, NG-4 L280](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- Time horizon: run all four checks at the first generate cycle (before the July-2026 visit, when the first artifact ships) and at every release thereafter.

**Review triggers:**
- The first real biomarker-matrix or multi-timepoint projection render is measured against the 500KB ceiling (the D4↔D7 tension, OQ-1) — re-evaluate the size budget vs. the render if it exceeds.
- An interactive/live view becomes a required V1 capability (rather than a North-Star deferral) — re-open the live-server alternative (A), which currently fails NG-4.
- The artifact-design-protocol component set or File Conventions change (size ceiling, inline-everything rule, accessibility floor) — re-validate generated artifacts against the revised conventions.
- The North-Star transition is initiated — the hosted live surface (Alternative A) supersedes the single-file delivery model for the product phase.
