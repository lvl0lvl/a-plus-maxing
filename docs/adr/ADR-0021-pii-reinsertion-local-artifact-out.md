## ADR-0021: Adopt PII Re-Insertion onto the Local Rendered Artifact (De-Id OUT)

> **Y-Statement:** In the context of a plan-generation engine whose data-out boundary today renders the operator as INITIALS only — so the operator cannot get a personally-addressed plan and a doctor-facing SBAR handout reads as "Patient JM" rather than a usable referral — facing the tension that a followable plan and an SBAR handout benefit from real identifiers while the repository is public and alpha-shared so committed operator PII is forbidden and cannot be cleanly scrubbed once landed, we decided to re-insert the necessary real operator PII onto the LOCAL, gitignored rendered artifact only — sourced deterministically from the gitignored identity config, with the persisted store and every tracked render staying de-identified — to achieve a usable name-bearing operator-facing and physician-facing artifact without relaxing the no-committed-PII trunk invariant, accepting that real PII now materializes in a local artifact whose non-leak depends on the gitignore boundary plus the commit/push PII hooks holding, and that the maintained-HTML output path falls in a name-token scan-SCOPE hole (`vault/artifacts/generated/` is outside the hooks' `DATA_BEARING_PREFIXES` name scan) that must be fixed — by extending the scan scope, not merely adding a fixture — before it ships.

### Context

The plan-generation engine's data-out boundary renders the operator as **INITIALS only — never the full name**. Both physician artifacts enforce this at a single shared point: `component_set.read_profile` parses the profile header and returns `initials` (the first letter of each name word), the age BAND, and the issue status — "INITIALS (from the profile title — never the full name; the data-out PII rule)" ([component_set.py read_profile L736-767](../../vault/design/templates/component_set.py) [VERIFIED]). The handout header renders `f"Patient {profile['initials'] or '—'}"` ([handout.py L120-128](../../vault/design/templates/handout.py) [VERIFIED]), and the module docstring fixes the rule: "The operator renders as INITIALS only — never the full name … a public-repo health-tool rule that must not diverge between templates" ([handout.py L26](../../vault/design/templates/handout.py); [component_set.py L709-714](../../vault/design/templates/component_set.py) [VERIFIED]). `generate.run` reads operator data only from the de-identified store via `store.read_all(root)` and threads no identity source into any template ([generate.py run L34-98](../../scripts/generate/generate.py) [VERIFIED]).

Two forces pull against each other. A plan the operator actually follows, and an SBAR handout a physician can act on, both benefit from real identifiers: a referral sheet addressed to "Patient JM" is materially less useful to a doctor than one bearing the operator's name, and a personally-addressed plan is the difference between a generic document and the operator's own. Against that stands the trunk's most permanent invariant: the repository is public and alpha-shared, every tracked file must carry zero operator PII, and once operator PII lands in a tracked commit git history cannot be cleanly scrubbed — so the exclusion must hold at every commit, not be fixed after a leak ([ADR-0005, Context L3, Decision](ADR-0005-operator-agnostic-clonable-pii-free-trunk.md) [VERIFIED]; [ADR-0005, Falsification](ADR-0005-operator-agnostic-clonable-pii-free-trunk.md) "≥1 operator-PII value in a tracked file … release-blocking" [VERIFIED]).

A second tension is who re-inserts. The OUT side is the inverse of ADR-0020's de-id IN: what the IN boundary strips, the OUT boundary restores. The real identifier already exists locally and gitignored — `read_profile` already reads initials from the ADR-0005 filled copy `vault/scaffold/filled/operator-profile.md` (preferred) falling back to the tracked scaffold ([handout.py _PROFILE_PATHS L43-46](../../vault/design/templates/handout.py) [VERIFIED]) — so the engine can substitute the real name from that same gitignored source without a model on the OUT path at all. Whether the OUT side NEEDS a model, or is a deterministic local template-fill, is the load-bearing decision this ADR resolves. Because re-inserting real PII reverses a settled data-out posture rather than implementing one, it is a decision, not a code change.

### Decision

Re-insert the necessary real operator PII (full name, and the identifiers an SBAR handout requires) onto the rendered plan artifact at render time, sourced deterministically from the gitignored identity config (`vault/scaffold/filled/operator-profile.md` / the `vault/meta/operator-identity.txt` token set), and write that artifact ONLY to a gitignored local output target (`vault/artifacts/generated/`). The persisted store and every TRACKED render stay de-identified — initials-only survives unchanged for any committed artifact. Re-insertion is fail-closed: if the render target cannot be confirmed gitignored, no PII is re-inserted and the render falls back to initials-only.

### Rationale

The decision was evaluated across two criteria the public-repo posture makes load-bearing: the **PII-handling surface** (how many places real PII can be mishandled or leak), and **render-format adaptivity** (can the OUT side adjust the artifact as new data arrives). Two re-insertion mechanisms were weighed: a model-backed re-insertion at render, and a deterministic local re-insertion (template-fill from the gitignored identity config, no model on the OUT path).

On the **PII-handling surface**, deterministic local re-insertion wins decisively. It reads the real name from the same gitignored source `read_profile` already uses and substitutes it into the rendered HTML — no real PII is ever sent to a model on the OUT path, so the egress class stays exactly one: real PII → local gitignored artifact, never the model, never a tracked file ([component_set.py read_profile L736-767](../../vault/design/templates/component_set.py) [VERIFIED]). A model-backed OUT pass would route the operator's real name through the model to format it, adding a second PII-handling surface (the model send) that the deterministic pass does not have — and the OUT side's job (substitute the real identifier the IN side stripped) is a pure string substitution that needs no model reasoning.

On **render-format adaptivity**, a model could in principle adjust the artifact's layout as wearables and labs arrive (the maintained-HTML lifecycle ADR-0025 introduces). But that adaptivity is a property of the FORMAT-MAINTENANCE step, not of the PII RE-INSERTION step: the maintained format can be model-maintained while the re-insertion itself stays deterministic — the name fill is the last, local, model-free pass over whatever HTML the format step produced. Coupling re-insertion to a model only to gain adaptivity the format step already provides buys nothing and costs a PII surface.

Deterministic local re-insertion therefore wins for the re-insertion itself. The decision adopts it as the OUT mechanism and pins the substitution as a render-time seam that the maintained-HTML format step (ADR-0025) feeds but does not own — keeping the model off the OUT PII path while leaving the format step free to be model-maintained. Long-term, this keeps the strictest privacy story (no real PII to any model on the OUT side) reachable even as the North-Star runtime swaps API for a local model, because the re-insertion source and target never change shape.

### Consequences

**Positive:**
- The operator-facing plan and the SBAR handout carry the real name and identifiers a physician referral needs, replacing the "Patient JM" initials-only render ([handout.py L120-128](../../vault/design/templates/handout.py) [VERIFIED]) — the followable-plan and doctor-facing-handout capability gain.
- No real PII touches a model on the OUT path: the egress class is exactly one — real PII → the gitignored `vault/artifacts/generated/` artifact ([.gitignore L6](../../.gitignore) [VERIFIED]) — sourced from the gitignored identity config, never the model, never a tracked file.
- The IN/OUT envelope is symmetric and source-aligned: re-insertion reads the same gitignored `vault/scaffold/filled/operator-profile.md` source `read_profile` already uses ([handout.py _PROFILE_PATHS L43-46](../../vault/design/templates/handout.py) [VERIFIED]), so what ADR-0020 strips, this restores from a source already trusted gitignored.

**Negative:**
- Real operator PII now materializes in a local rendered artifact where today none does — the artifact's non-leak depends entirely on the gitignore boundary (`vault/artifacts/generated/`, [.gitignore L6](../../.gitignore) [VERIFIED]) plus the `block-pii-commit.sh` + `pre-push-pii-scan.sh` hooks denying any path/token hit ([block-pii-commit.sh L1-25](../../.claude/hooks/block-pii-commit.sh) [VERIFIED]). If that chain fails — a `git add -f` past `.gitignore`, a `--no-verify` push, a render misrouted to a tracked path — a real-PII leak reaches public history that cannot be cleanly scrubbed ([ADR-0005, Context L3](ADR-0005-operator-agnostic-clonable-pii-free-trunk.md) [VERIFIED]).
- The maintained-HTML output path ADR-0025 introduces has a hook scan-SCOPE hole for the operator NAME, not merely a missing fixture: `pii_scan.scan_scoped` runs the operator-name tokens ONLY over the `data_bearing` subset, and `DATA_BEARING_PREFIXES` excludes `vault/artifacts/generated/` ([pii_scan.py scan_scoped L375-406](../../scripts/guard/pii_scan.py), [lib/pii-scan-scope.sh L30](../../.claude/hooks/lib/pii-scan-scope.sh) [VERIFIED]). A committed maintained-HTML artifact carrying the re-inserted full NAME is therefore scanned only for trunk-wide CONTACT tokens, not for the name, by both the commit hook and the pre-push backstop. Until the scan SCOPE is extended to cover the artifacts path AND a fixture proves the change denies a name-bearing committed maintained-HTML artifact (Open Questions OQ-1), the new output path's name-token coverage is absent — a missing fixture alone would not close it.

**Neutral:**
- The render gains a second template seam (the deterministic name-fill pass) distinct from the existing de-identified `store_read` read; `generate.run`'s `store.read_all` de-identified read is unchanged ([generate.py run L72](../../scripts/generate/generate.py) [VERIFIED]).
- Initials-only `read_profile` remains the code path for any tracked render; re-insertion is an added gitignored-only path, not a replacement of the initials logic.

### Alternatives Considered

#### Alternative A: Model-backed re-insertion at render
The render-time model agent re-inserts the operator's real PII as part of producing the maintained/adjust-as-data-arrives format, formatting name and identifiers into the artifact in one model pass.
- **Supporting evidence:** Couples re-insertion to the maintained-HTML format step (ADR-0025), so a single model pass produces a layout that adapts as wearables/labs arrive — the operator's stated "the API agent adjusts the format as new data arrives" target ([discovery.md decision 7 / §7](.pipeline/engine/discovery.md) [VERIFIED]). One agent owns both format and fill.
- **Trade-offs:** Routes the operator's real name through the model to format it — a SECOND PII-handling surface beyond the gitignored artifact, in a public-repo posture where every additional real-PII surface is a leak vector. The re-insertion itself is a pure string substitution needing no model reasoning, so the model buys format adaptivity the FORMAT step already provides while adding a PII send the deterministic pass avoids.
- **When this becomes the right choice:** If the OUT side must reason over the PII to format it (e.g. locale-specific name rendering, or composing identifiers the gitignored config does not already hold) AND the model runs as a local model so the real-PII send never leaves the device — then the deterministic source no longer suffices and a model pass is warranted.

#### Alternative B: Deterministic local re-insertion (chosen)
Read the real name and identifiers from the gitignored identity config and template-substitute them into the rendered HTML at render time — no model on the OUT path. Mirrors how `component_set.read_profile` already reads initials from that gitignored source.
- **Supporting evidence:** Keeps the model off the OUT PII path entirely: the egress class is exactly one (real PII → gitignored artifact). Reuses the existing gitignored-source read pattern `read_profile` established ([component_set.py read_profile L736-767](../../vault/design/templates/component_set.py) [VERIFIED]), so the privacy story is "the same source that holds initials now also yields the full name, locally, gitignored." Lower-risk and simpler for the re-insertion itself even if a model maintains the surrounding format.
- **Trade-offs:** The deterministic pass does not, by itself, adapt the artifact's layout as new data arrives — that adaptivity must come from the maintained-HTML format step (ADR-0025), which feeds the deterministic fill rather than replacing it. Re-insertion and format-maintenance become two seams, not one.

#### Alternative C: Keep initials-only (no re-insertion)
Leave the data-out boundary as it stands — every artifact renders the operator as initials, never the full name.
- **Supporting evidence:** The strongest possible no-committed-PII posture: with no real PII ever materialized in any artifact, there is nothing for the gitignore/hook chain to fail open on. It is the current, tested, shipped behavior ([handout.py L120-128](../../vault/design/templates/handout.py) [VERIFIED]).
- **Trade-offs:** Insufficient for the artifacts' actual jobs. A doctor-facing SBAR handout addressed to "Patient JM" is a weaker referral than a named one — the physician cannot file it against a patient record without re-identifying it by hand, defeating the handout's purpose ([handout.py docstring L1-10](../../vault/design/templates/handout.py) [VERIFIED]). A followable operator plan addressed to initials reads as a generic template, not the operator's own. The capability gap the engine's full target names — a personally-addressed plan and a usable handout — is exactly what initials-only forecloses.
- **When this becomes the right choice:** If the operator's threat model rejects any local real-PII materialization (e.g. a shared machine where the gitignored artifact is itself readable by others), initials-only remains the correct strict posture — and is the fail-closed fallback this ADR's Decision already defaults to when the render target cannot be confirmed gitignored.

### Validation Approach

**Confirmation criteria:**
- A render with re-insertion enabled produces an artifact under `vault/artifacts/generated/` whose header shows the operator's full name (not initials), sourced from the gitignored `vault/scaffold/filled/operator-profile.md`; the same template with no gitignored target falls back to the initials-only `read_profile` output.
- The persisted store (`vault/store/`) and every tracked file contain 0 real-PII values after a re-inserting render, verified by `pii_scan.scan` returning 0 on the tracked set ([pii_scan.py scan L210](../../scripts/guard/pii_scan.py) [VERIFIED]).
- With no gitignored target confirmable, re-insertion is suppressed and the artifact renders initials-only (the fail-closed default), verified on a crafted render whose target path is a tracked location.

**Falsification criteria:**
- **Raw-PII-leak probe (threshold 0):** craft a render that produces an artifact carrying re-inserted real PII, stage/commit it, and stage/push it. Assert the `block-pii-commit.sh` PreToolUse hook DENIES the commit AND the `pre-push-pii-scan.sh` hook DENIES the push — **0 real-PII values reach any committed file** ([block-pii-commit.sh L1-25](../../.claude/hooks/block-pii-commit.sh), [pre-push-pii-scan.sh L1-25](../../.claude/hooks/pre-push-pii-scan.sh) [VERIFIED]). Simultaneously assert the persisted store after the render holds **0 real-PII values** (`pii_scan.scan` over `vault/store/` returns 0). If either count exceeds 0, the boundary has failed — halt and restore the gitignored-only re-insertion (release-blocking).
- If, over any render cycle, a re-inserted-PII value is found in a tracked/committed file on a fresh-clone scan (`pii_scan.scan` ≥ 1 hit), the OUT boundary leaked — halt, revert the leaking path, and re-verify the hook chain before re-enabling.
- If the maintained-HTML output path (ADR-0025) ships before the name-token scan SCOPE is extended to cover `vault/artifacts/generated/` AND a fixture proves `block-pii-commit.sh`/`pre-push-pii-scan.sh` deny a committed maintained-HTML artifact carrying the re-inserted NAME, the new output path's name-token coverage is absent — block the format's release (OQ-1).

**Review triggers:**
- ADR-0025 (maintained HTML) reaches build — extend the name-token scan SCOPE to cover `vault/artifacts/generated/` and re-verify the hooks deny a name-bearing artifact on the new output path before it ships (OQ-1; a fixture under the current scope is insufficient).
- The render output target moves off `vault/artifacts/generated/` or a new operator-facing artifact is added — re-confirm the new target is gitignored and within the hooks' path-denial set.
- The OUT mechanism is proposed to move from deterministic to model-backed — re-open this ADR against the single-egress-class invariant (real PII would then touch the model).
