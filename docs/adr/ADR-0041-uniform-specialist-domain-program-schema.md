## ADR-0041: Uniform Specialist Domain-Program Output Schema

> **Y-Statement:** In the context of the live plan-generation engine, where every domain specialist emits the thin "universal recommendation contract" `{claim, source, confidence_tier, reversibility, category, grounding, numbers, payload}` that four bespoke per-domain translators reduce to flat plan shapes (`{exercises}` / `{calorie_goal, macros, meals}` / `{items}` / `{compound, dose, route}`) carrying no monitoring, adjustment, labs, or cross-domain-seam fields ([generate_plan.py:24-38,123-291](../../scripts/plan/generate_plan.py); [plan_schema.py:178-275](../../scripts/store/plan_schema.py) [VERIFIED]), facing the tension that (a) a one-shot thin payload cannot carry the autoregulation a live 24/7 health plan needs and (b) differently-shaped per-domain payloads cannot be reconciled mechanically — each cross-domain interaction is a hard-coded reconciler branch fed by a bespoke side-channel ([orchestrate.py:337-456](../../scripts/plan/orchestrate.py) [VERIFIED]) — we decided that every domain specialist emits ONE uniform DOMAIN PROGRAM shape `{prescription (periodized/dated), rationale (GRADE certainty×strength + causal-vs-associational), monitoring_signals (validity-tiered), adjustment_rules, required_labs, refusal/escalation, cross_domain_seams}`, superseding the recommendation contract + the thin per-domain translators, to achieve a single reconcilable audit surface the orchestrator collects+reconciles mechanically and a plan that carries its own autoregulation, accepting that this BREAKS the ADR-0032 EXTEND-NOT-REBUILD freeze on the specialist-output surface (a HARD one-way door, operator-signed-off at the Phase-1 gate), a migration that rewrites the four translators + the `assemble` completeness filter, and a requirement that every downstream component (orchestrator, plan model, monitoring compiler, dispatch runtime) consume the uniform shape.

### Context

The live plan-generation engine defines one shape every domain author emits — the "universal recommendation contract" `{claim, source, confidence_tier, reversibility, category, grounding, numbers, payload}` ([generate_plan.py:24-38](../../scripts/plan/generate_plan.py) [VERIFIED]). Four registered per-domain translators reduce each recommendation's `payload` to a flat plan document: `_to_workout_plan` maps one rec to one exercise (`{exercises}`), `_to_nutrition_plan` aggregates N recs into `{calorie_goal, macros, meals}`, `_to_supplements_plan` maps one rec to one item (`{items}`), and `_to_peptides_plan` records a single compound (`{compound, dose, route}`) ([generate_plan.py:123-291](../../scripts/plan/generate_plan.py) [VERIFIED]). The stored per-domain validators confirm those are the entire field surface — `_validate_workout_plan` / `_validate_nutrition_plan` / `_validate_supplements_plan` / `_validate_peptides_plan` accept only those keys plus a few optional extras ([plan_schema.py:178-275](../../scripts/store/plan_schema.py) [VERIFIED]).

That surface carries none of the fields a live health plan needs to autoregulate. There is no `monitoring_signals` field (what to watch to know the plan is working), no `adjustment_rules` field (how the plan changes when a signal moves), no `required_labs` field (what the program needs to run safely), and no `cross_domain_seams` field (what one domain needs from or imposes on another). Evidence quality is a single flat `confidence_tier` scalar plus one `grounding` flag consumed only to set a population-mismatch marker for animal/in-vitro claims ([assemble.py:26,116-124,263-265](../../scripts/plan/assemble.py) [VERIFIED]) — not a structured GRADE certainty×strength rationale, and not a causal-vs-associational basis per claim. And the plan is a one-shot artifact: `record_plan` appends once and `resolve_plan` resolves the latest date as standing ([plan_schema.py:371-396,462-498](../../scripts/store/plan_schema.py) [VERIFIED]); no monitoring config is compiled, so nothing lets the plan adjust without re-running the full authoring front door — the "NO-LOOP" root the design set exists to fix ([.pipeline/discovery.md](.pipeline/discovery.md) [VERIFIED]).

The second force is reconciliation. Only four plan domains are wired, each with a differently-shaped `payload` and a different arity — 1:1 for workout, aggregate-N-to-1 for nutrition, 1:1 for supplements, first-only-single-compound for peptides ([generate_plan.py:48-57,286-291](../../scripts/plan/generate_plan.py); [plan_schema.py:49](../../scripts/store/plan_schema.py) [VERIFIED]). Because the shapes differ, cross-domain reconciliation cannot read the payloads uniformly: `orchestrate.reconcile` is five hard-coded behaviors bound to specific domain pairs (a RED-S/LEA nutrition→workout short-circuit, a nutrition→workout energy bounce, overlap detection, a supplement↔peptide additive-AE screen, a supplement↔Rx BPMH screen), and each reads author-declared interaction data not from the plan payload at all but from a separate `reconciliation` envelope lifted into a candidate `meta` side-channel — `ae_profile.additive_classes`, `interactions`, `conflicts`, `energy_budget`, `energy_cost_kcal` ([generate_plan.py:375-376](../../scripts/plan/generate_plan.py); [orchestrate.py:101-165,337-456](../../scripts/plan/orchestrate.py) [VERIFIED]). Adding a fifth specialist, or a new interaction between two existing ones, means a new bespoke payload shape, a new translator, and a new hard-coded reconciler branch reading a new bespoke `meta` key. Reconciliation is per-pair code, not a mechanical pass over a uniform shape — and the design's fuller specialist roster (the plan is meant to scale well beyond four domains [UNVERIFIED — design/specialist-plan-contracts.md, not read in full; roster scale-up per ADR-0046 in [.pipeline/discovery.md](.pipeline/discovery.md)]) makes that per-pair cost the binding constraint.

Two stakeholders pull against changing this. The maintainer's cost is the ADR-0032 EXTEND-NOT-REBUILD freeze: `generate_plan.py` and `assemble.py` — where the recommendation contract, the translators, and the completeness/HALT filters live — are named in ADR-0032's byte-frozen inner-engine set ([ADR-0032:26,43,107](ADR-0032-dna-aware-planning.md) [VERIFIED]), held byte-frozen across the project's EXTEND-NOT-REBUILD era. The data subject's boundary is unaffected on its face — this decision changes the shape a specialist emits, not what crosses the model lane (the coarse-token de-id INPUT boundary, `router.summarize` over the closed `SUMMARY_FIELD_SET` whitelist enforced by `dispatch`, is ADR-0042's concern, [router.py:23-60,738-918](../../scripts/plan/router.py) [VERIFIED]) — but the richer output is authored by a model dispatch, so a wider required-field contract is a costlier author call. Because this redefines the shared data contract every specialist emits and every downstream component consumes (orchestrator, plan model, monitoring compiler, dispatch runtime), it is an architecture decision, not an implementation detail.

### Decision

**Every domain specialist emits ONE uniform DOMAIN PROGRAM output schema — the same seven required fields for every domain — replacing the thin per-domain `payload` and the universal recommendation contract, so the orchestrator collects and reconciles the outputs mechanically and the plan carries its own autoregulation.**

The seven fields, stated generically (a "training domain program", a "compound domain program", a "nutrition domain program" — the same shape for each):

1. **`prescription`** — the domain's actionable program, PERIODIZED and DATED (dated blocks/phases), not a flat single-shot list: a training domain program carries dated progression blocks; a compound domain program carries a dated titration/cycle schedule; a nutrition domain program carries dated targets across phases.
2. **`rationale`** — the evidence basis per claim: a GRADE certainty-of-evidence × strength-of-recommendation pair, plus whether each claim rests on CAUSAL or merely ASSOCIATIONAL evidence.
3. **`monitoring_signals`** — the signals the program watches to know whether it is working, each carrying a VALIDITY TIER (a validated instrument vs a coarse proxy) so a downstream compiler can weight them.
4. **`adjustment_rules`** — the deterministic if-signal-then-change rules that let the program autoregulate without re-running the authoring front door.
5. **`required_labs`** — the labs the program needs to run safely or to gate progression (empty where a domain needs none; present where the domain's safety depends on them).
6. **`refusal/escalation`** — the conditions under which the specialist refuses to prescribe or escalates to a human/medical gate — the fail-closed boundary carried in the program itself.
7. **`cross_domain_seams`** — the program's declared interactions with other domains (what it needs from, and what it imposes on, other domains), so the orchestrator reconciles seams by reading ONE uniform field rather than per-pair hard-coded branches over a bespoke side-channel.

This SUPERSEDES the specialist-output surface: the universal recommendation contract `{claim, source, confidence_tier, reversibility, category, grounding, numbers, payload}` and the four thin per-domain payload translators (`_to_workout_plan` / `_to_nutrition_plan` / `_to_supplements_plan` / `_to_peptides_plan`, wired in `_PLAN_TRANSLATORS`) ([generate_plan.py:24-38,123-291](../../scripts/plan/generate_plan.py) [VERIFIED]). It does NOT decide the stored plan model (ADR-0044) nor the monitoring-config compiler (ADR-0045) — those consume this shape and are decided separately.

**Freeze break (HARD, one-way door — stated honestly per the set's freeze-break-honesty rule).** This BREAKS the ADR-0032 EXTEND-NOT-REBUILD freeze on the specialist-output surface: the recommendation contract and translators live in `generate_plan.py`, and the completeness/HALT filters that read them (`_is_complete`, `_compose_claim`) live in `assemble.py` — both named in ADR-0032's byte-frozen inner-engine set (`scripts/plan/{orchestrate,pipeline,assemble,generate_plan,adjudicate,adjust,track}.py`) ([ADR-0032:26,43,107](ADR-0032-dna-aware-planning.md); [assemble.py:116-124,250-275](../../scripts/plan/assemble.py) [VERIFIED]). Reversibility is HARD (a data-contract migration every downstream component depends on); operator sign-off on breaking the freeze was OBTAINED at the Phase-1 discovery gate, where this is one of the load-bearing supersession decisions the operator accepted before Tier-1 authoring proceeded ([.pipeline/discovery.md](.pipeline/discovery.md) [VERIFIED]). The store WRITE path and the safety-critical inner engine remain frozen where THIS decision (ADR-0041) does not supersede them — ADR-0041's own commit touches only `generate_plan.py` + `assemble.py`. The set does NOT collectively claim the rest of the inner engine stays frozen: sibling supersessions are owned in their own ADRs (ADR-0044 the `plan_schema.py` record-model surfaces; ADR-0043 the `orchestrate.reconcile` safety-reconciler), each classified and signed off there.

### Rationale

Three options were weighed across four criteria the Context makes load-bearing — **mechanical reconciliation** (is there ONE shape the orchestrator collects+reconciles, or N bespoke readers?), **autoregulation capacity** (does the plan carry monitoring + adjustment, or is it a one-shot document?), **roster scalability** (what does adding the Nth specialist cost?), and **downstream uniformity** (do the plan model, monitoring compiler, and dispatch runtime consume one shape?) — against keeping the thin payload with a monitoring side-channel (Alternative A) and per-domain bespoke rich schemas (Alternative B).

On **mechanical reconciliation**, only the uniform schema gives the orchestrator a single reconcilable surface. Today the reconciler reads cross-domain interactions from a bespoke `meta.ae_profile` / `meta.conflicts` / `meta.energy_budget` side-channel through five hard-coded, pair-specific branches ([orchestrate.py:101-165,337-456](../../scripts/plan/orchestrate.py) [VERIFIED]); a uniform `cross_domain_seams` field lets the orchestrator collect every domain's declared seams and reconcile them in one pass, so a new domain adds zero new bespoke reader code. Alternative A keeps the payload thin and bolts monitoring/seams onto a second stream — but then the orchestrator reconciles across TWO shapes (payload + side-channel), which is exactly today's `meta` side-channel problem re-institutionalized, not removed. Alternative B makes each domain's schema richly expressive but differently-shaped, so the orchestrator still needs one adapter per domain to collect+reconcile — the `_PLAN_TRANSLATORS` + hard-coded-branch pattern, just richer.

On **autoregulation capacity**, the thin payload carries no monitoring or adjustment field at all ([plan_schema.py:178-275](../../scripts/store/plan_schema.py) [VERIFIED]), so the plan cannot self-adjust and the loop must re-run the whole authoring front door on every trend — the NO-LOOP root ([.pipeline/discovery.md](.pipeline/discovery.md) [VERIFIED]). Making `monitoring_signals` + `adjustment_rules` first-class, REQUIRED fields is what lets ADR-0045 compile a deterministic daily adjustment tier from the plan itself. A side-channel (Alternative A) can carry the same content but, being optional and separate, cannot be relied on as a fail-closed contract — a compiler reading it cannot assume presence.

On **roster scalability** and **downstream uniformity**, the uniform schema means every specialist (a training domain program, a compound domain program, and beyond) validates against the SAME seven-field contract, and the plan model (ADR-0044), monitoring compiler (ADR-0045), orchestrator (ADR-0043), and dispatch runtime (ADR-0046) each consume ONE shape rather than N. The cost is real and is not hidden: it breaks the ADR-0032 freeze on `generate_plan.py` + `assemble.py`, forces a migration of the four translators + the `assemble` completeness filter, and constrains four downstream ADRs to the uniform shape (Consequences-Negative). That cost is accepted because mechanical reconciliation and plan-carried autoregulation are the two properties the whole re-architecture set exists to deliver, and neither alternative provides both without reproducing the per-domain-adapter or side-channel problem the uniform schema removes.

### Consequences

**Positive:**
- Single reconcilable audit surface: the orchestrator collects+reconciles one shape across all domains through the uniform `cross_domain_seams` field, so a newly-added specialist adds 0 bespoke reconciler branches and 0 bespoke `meta` keys — versus today's five pair-specific hard-coded behaviors over a `meta` side-channel ([orchestrate.py:337-456](../../scripts/plan/orchestrate.py) [VERIFIED]).
- The plan carries its own autoregulation: `monitoring_signals` + `adjustment_rules` are first-class required fields, so the plan is self-adjusting at the schema level — the source ADR-0045 compiles into a deterministic daily tier, closing the NO-LOOP root without a per-trend model re-run.
- Evidence quality becomes first-class and comparable across domains: a GRADE certainty×strength rationale plus a causal-vs-associational basis per claim replaces the flat `confidence_tier` scalar and the single animal/in-vitro `grounding` flag ([assemble.py:116-124,263-265](../../scripts/plan/assemble.py) [VERIFIED]).
- Safety-gating and fail-closed refusal become explicit in the program: `required_labs` and `refusal/escalation` are carried in the schema, not implicit in downstream code.

**Negative:**
- Breaks the ADR-0032 EXTEND-NOT-REBUILD freeze on the specialist-output surface (`generate_plan.py` + `assemble.py`), held byte-frozen across the project's EXTEND-NOT-REBUILD era — a HARD, one-way door ([ADR-0032:26,43,107](ADR-0032-dna-aware-planning.md) [VERIFIED]). Once shipped, reverting to the thin contract is itself a migration.
- Migration cost, measurable: all four translators (`_to_*_plan`, [generate_plan.py:123-291](../../scripts/plan/generate_plan.py) [VERIFIED]) plus the `assemble` completeness filter `_is_complete`, which today reads `source`/`confidence_tier`/`reversibility`/`numbers` ([assemble.py:116-124](../../scripts/plan/assemble.py) [VERIFIED]), must be rewritten to the uniform seven-field contract before the schema is load-bearing.
- Constrains four downstream decisions: ADR-0043 (orchestrator), ADR-0044 (plan model), ADR-0045 (monitoring compiler), and ADR-0046 (dispatch runtime) MUST each consume/store/compile the uniform shape — the orchestrator cannot reconcile a non-uniform output ([.pipeline/dag.md](.pipeline/dag.md) [VERIFIED]). The schema is not usably shipped until those consumers exist.
- Richer, costlier author call: every specialist dispatch must now author seven required fields instead of a thin payload, increasing model output per domain per plan; a specialist that under-delivers a required field now fails closed (the program is rejected — Validation), producing MORE honest no-plan states during rollout, not a degraded thin plan.

**Neutral:**
- The DOMAIN PROGRAM is a superset that carries today's payload content inside `prescription`, so no current renderable field is lost — the render surface reshapes rather than shrinks.
- The `reconciliation`/`meta` side-channel the orchestrator reads today (`ae_profile`, `conflicts`, `energy_budget`, [orchestrate.py:101-124,383,414](../../scripts/plan/orchestrate.py) [VERIFIED]) folds into `cross_domain_seams`; the five hard-coded behaviors re-base onto the uniform field — an ADR-0043 concern, not a new stream.

### Alternatives Considered

#### Alternative A: Keep the thin payload + a monitoring/seams side-channel
Leave the recommendation contract + the four thin translators unchanged; add `monitoring_signals`, `adjustment_rules`, and `cross_domain_seams` as a SEPARATE side-channel stream/envelope alongside the payload.
- **Supporting evidence:** Does not break the ADR-0032 freeze on the payload shape ([ADR-0032:26](ADR-0032-dna-aware-planning.md) [VERIFIED]); it also mirrors a pattern already in the tree — the orchestrator already reads cross-domain data from the `reconciliation`/`meta` side-channel ([generate_plan.py:375-376](../../scripts/plan/generate_plan.py) [VERIFIED]) — so it is the lower-churn path.
- **Trade-offs:** REJECTED — there is no single reconcilable audit surface. The orchestrator would reconcile across TWO shapes (payload + side-channel), which is precisely today's `meta` side-channel problem institutionalized rather than removed, and a monitoring compiler reading an OPTIONAL side stream cannot treat presence as a fail-closed contract, so plan-carried autoregulation is not guaranteed. The very reason the reconciler is five hard-coded pair-specific branches is that the cross-domain data lives in a bespoke side-channel; a second side-channel keeps that shape.
- **When this becomes the right choice:** If monitoring were a small, bounded add and reconciliation stayed within the fixed four domains forever (no roster growth, no new cross-domain interactions), the side-channel's lower churn could outweigh the reconciliation cost.

#### Alternative B: Per-domain bespoke rich schemas
Each specialist emits a rich shape TAILORED to its domain — a training-shaped rich schema, a compound-shaped rich schema — each maximally expressive, none uniform.
- **Supporting evidence:** Maximally expressive per domain, with no lowest-common-denominator compromise — a training program's structure and a compound program's structure differ genuinely, and bespoke schemas model each faithfully; it also extends the existing per-domain-translator pattern rather than replacing it.
- **Trade-offs:** REJECTED — it defeats the mechanical reconciliation that is the entire point. To collect+reconcile N differently-shaped rich outputs, the orchestrator needs one adapter per domain — exactly today's `_PLAN_TRANSLATORS` + hard-coded reconciler branches ([generate_plan.py:286-291](../../scripts/plan/generate_plan.py); [orchestrate.py:337-456](../../scripts/plan/orchestrate.py) [VERIFIED]), just richer — and the plan model + monitoring compiler + dispatch runtime each gain per-domain special cases. Roster scalability regresses: the Nth specialist costs a new schema + a new adapter + new reconciler branches.
- **When this becomes the right choice:** If domains never needed cross-domain reconciliation and no uniform monitoring compiler were wanted — then per-domain expressiveness would dominate, since there would be no uniform consumer to serve.

#### Dissent: Ride ADR-0010 D2's open-on-extras seam — no freeze break
**Source:** ADR-0010 D2, the forward-compatibility seam ([ADR-0010:31-33](ADR-0010-plan-content-schemas-plan-zone-render.md); [plan_schema.py:113-139](../../scripts/store/plan_schema.py) [VERIFIED]). A purist holds that the ADR-0010 freeze has served the project across its EXTEND-NOT-REBUILD era and that the richer fields should ride D2 — "unknown extra keys are permitted and ignored" — so specialists add `monitoring_signals`, `adjustment_rules`, and the rest as OPTIONAL extras on the existing thin schema, no contract change, no freeze break, no migration.
**Conditions under which this becomes the right choice:** If the downstream components did not need to RELY on the fields being present — if a monitoring compiler and an orchestrator could function when a field is sometimes absent. They cannot: D2 extras are "permitted and IGNORED," i.e. optional and unenforced, so the orchestrator cannot mechanically reconcile on a field a specialist may omit, and the monitoring compiler cannot fail-closed on missing autoregulation. Mechanical reconciliation and fail-closed autoregulation require the fields be REQUIRED and uniform — a contract change — which is what forces the (signed-off) freeze break. The dissent wins only if the fields stay advisory rather than load-bearing.

### Validation Approach

**Confirmation criteria:**
- **A specialist payload validates against all seven fields (executable).** Author a fixture output for at least two domains (a training domain program AND a compound domain program) and run a conformance validator. Threshold: every one of the seven required fields (`prescription`, `rationale`, `monitoring_signals`, `adjustment_rules`, `required_labs`, `refusal/escalation`, `cross_domain_seams`) is present and well-typed — missing-required-field count == 0 for a conformant program.
- **The orchestrator reconciles ≥2 domains mechanically (executable, the load-bearing probe).** Seed two domains whose programs declare a seam in `cross_domain_seams`; assert the orchestrator detects and holds/reconciles the seam by reading the UNIFORM field through ONE code path. Threshold: 0 new per-domain-pair hard-coded branches are required to reconcile the seam (the reconciliation reads `cross_domain_seams`, not a bespoke `meta.ae_profile`-style side-channel key). If reconciliation still requires a pair-specific branch, the mechanical-reconciliation property is unmet — halt.

**Falsification criteria:**
- **A payload missing a field is rejected (deterministic).** Author a program omitting any ONE of the seven required fields; assert the validator REJECTS it (raises / fails closed) and no plan is admitted for that domain. Threshold: missing-required-field count ≥1 → reject; if an incomplete program is admitted as a plan, the uniform-contract guarantee is broken — halt and repair before release.
- **A non-uniform output breaks reconciliation (deterministic).** Feed the orchestrator a specialist output in the OLD thin-payload shape (or any bespoke non-uniform shape); assert it cannot be collected into the uniform reconcile pass — it is rejected at the collection boundary, never silently adapted. Threshold: 0 non-uniform outputs may reach the reconcile step; ≥1 non-uniform output silently reconciled means the per-domain-adapter regression has returned — halt.
- **Autoregulation is required where the domain needs it (deterministic).** A domain program whose safety depends on monitoring (a compound domain program) with 0 `monitoring_signals` or 0 `adjustment_rules` is rejected/flagged, not admitted as a static plan. Threshold: such a program → rejected; if it stands, the plan-carries-autoregulation property (the ADR-0045 input contract) is unmet — halt.
- **Time horizon:** run the missing-required-field-rejection probe, the non-uniform-output reconciliation probe, and the autoregulation-required probe at the first schema/translator build, at the operator-present LIVE run (OQ-4), and at every release thereafter, and before the July-2026 physician-visit deliverable.

**Review triggers:**
- A new specialist domain is added to the roster — verify it emits the uniform seven-field DOMAIN PROGRAM (ADR-0046).
- ADR-0043 (orchestrator), ADR-0044 (plan model), or ADR-0045 (monitoring compiler) lands — re-confirm each consumes/stores/compiles the uniform shape, not a per-domain special case.
- A field is proposed for addition to or removal from the seven-field schema — a schema-contract change is a Tier-1 review trigger touching every downstream consumer.
- The operator-present LIVE run is scheduled — the mock/fixture build wires up to the live specialist dispatch only; a real dispatch that authors DOMAIN PROGRAMs from live specialists spends model budget (OQ-4).
