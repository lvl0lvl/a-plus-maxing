## ADR-0003: Source-Extensible Import/Ingestion Interface

> **Y-Statement:** In the context of a local-first single-operator health system that must refresh its time-series store from several wearable/health platforms (HealthKit, Apple Watch, Whoop, Garmin, Oura) plus export-less manual sources, with only a subset wired in the first cut, facing the tension between wiring each source as its own bespoke routine (fast for the first source, a rewrite for every next one) and a pluggable adapter seam over a common export pattern (more design up front, no rewrite per source), we decided to define ingestion as a pluggable per-source adapter interface over a common export contract — carrying an idempotency contract (re-runs append only readings new since the last run, keyed by the D2 item+timepoint key), a schedulability contract (runs unattended), and a manual-entry fallback for export-less sources — writing only into the local D2 store, to achieve add-a-source-without-reworking-the-routine extensibility, no-duplicate refreshes, and unattended scheduling, accepting per-source adapter maintenance, idempotency-key brittleness across export-format changes, and a first cut where only a subset of sources is actually wired.

### Context

The store accumulates readings, but nothing brings them in: the operator's record must refresh from device and app exports without re-keying every reading, run unattended on a schedule, and never duplicate a reading already stored ([PRD-v1, US-3 L63-69, FR-4 L146-154](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). The set of sources is plural and not all available at once: the design must be prepared for HealthKit, Apple Watch, Whoop, Garmin, and Oura exports over a common export pattern, with only a subset wired and actionable in the first cut and the remainder pluggable later without reworking the routine ([PRD-v1, FR-4 AC L154, OQ-5 L346](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). Today only one wearable is even named in the data layer — `current-state.md` models a Wearable (Oura) section pending purchase, while the HealthKit/Apple Watch export named in the locked scope has no codebase surface and is marked [INTAKE-DIRECTED] ([current-state.md, L36-45](../../vault/meta/current-state.md) [VERIFIED]; [PRD-v1, Finding 12 L373](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]; [landmarks.md, LM-02 L50-57](../../vault/meta/landmarks.md) [VERIFIED]).

Several forces pull against each other across more than one party. The operator wants a low-friction routine: one invocation brings an export in, and a scheduled run refreshes without attention ([PRD-v1, US-3 AC L66-67, NFR-7 AC L272-273](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). The builder faces an extensibility-vs-effort trade-off: wiring each source bespoke is the fastest path to the first source but forces a rewrite for every next one, whereas a shared adapter seam costs more design up front and pays back only as sources accumulate. The integration boundary is fixed by neighbors, not free: ingestion writes only into the local D2 store and must route no raw reading through a model step ([ADR-0001, Decision + Related Decisions](ADR-0001-pii-trust-boundary-no-train-routing.md) [VERIFIED]), and the no-duplicate contract is a store-schema concern — the store's per-item (item, timepoint) keying fixes the idempotency-key surface and the write target ([ADR-0002, Decision + Related Decisions](ADR-0002-local-first-time-series-store.md) [VERIFIED]). Confidence in any single export is bounded: the exact export the operator will use is not yet exercised, so a design that blocks on one source is fragile ([PRD-v1, A-2 L297-300](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). And export-less sources are unavoidable: labs, food, and weight have no device export and must enter the same store by manual entry ([PRD-v1, US-3 AC L69, FR-4 AC L153](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]; [NG-5 L281](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED] — V1 ingests via import/export, not native device sync).

### Decision

Define ingestion as a pluggable per-source adapter interface over a common export pattern: each source (HealthKit, Apple Watch, Whoop, Garmin, Oura, …) is an adapter that maps that source's export into the store's reading shape, and a new source plugs in by adding an adapter without reworking the shared routine. The interface carries three contracts: an idempotency contract — a re-run appends only readings new since the last run and never duplicates a reading already stored, with the dedupe key derived from the D2 store's (item, timepoint) keying; a schedulability contract — the same routine runs unattended on a schedule; and a manual-entry fallback — export-less sources (labs, food, weight) enter the same store by hand. Ingestion writes only into the local D2 store and routes no raw reading through a model step. In the first cut only a subset of adapters is wired and actionable; the remainder are pluggable later.

### Rationale

Three interface shapes were evaluated against four criteria the PRD makes load-bearing: cost to add the Nth source, fit with the no-duplicate refresh contract (FR-4), the schedulability/unattended-run contract (FR-4/NFR-7), and the first-cut reality that only a subset of sources is wired (OQ-5).

On **cost to add the Nth source**, the pluggable adapter seam is the only shape where a not-yet-wired source slots in by adding one adapter against a common export contract, leaving the shared routine, the dedupe step, and the scheduler untouched — directly satisfying FR-4's "remainder pluggable later without reworking the routine" ([PRD-v1, FR-4 AC L154, OQ-5 L346](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). Per-source bespoke scripts (Alternative A) pay zero up-front design but rewrite the routine per source; a single rigid importer (Alternative B) hardcodes one or two sources and cannot admit a third without surgery. On the **no-duplicate contract**, placing dedupe once in the shared routine — keyed by the store's (item, timepoint) key ([ADR-0002, Decision](ADR-0002-local-first-time-series-store.md) [VERIFIED]) — means every adapter inherits idempotency for free, so the FR-4 "re-running does not duplicate readings already in the store" criterion holds uniformly across sources rather than being re-implemented (and re-bugged) per script ([PRD-v1, FR-4 AC L152](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). On **schedulability**, one shared unattended routine over all adapters means the scheduled run refreshes every wired source in a single invocation, satisfying FR-4/NFR-7's unattended-completion criterion; N bespoke scripts would each need their own scheduling, multiplying the unattended surface ([PRD-v1, FR-4 AC L151, NFR-7 AC L273](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). On the **subset-wired-first reality**, the adapter seam is what de-risks the Medium-confidence single-export assumption: a source not yet wired plugs in later rather than blocking ingestion, exactly the de-risking A-2 records ([PRD-v1, A-2 L299](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).

The idempotency mechanism is decided here at the contract level — re-runs add only readings new since the last run, deduped against the store's existing (item, timepoint) keys — while the precise key field (timestamp granularity, source tag) is an implementation detail downstream of D2's per-item layout and is left to the build, not fixed in this ADR ([ADR-0002, OQ-1 L111](ADR-0002-local-first-time-series-store.md) [VERIFIED]). Long-term, the adapter seam is the asset: as the operator adds Whoop or Garmin alongside Oura, or HealthKit becomes available, each is an adapter addition, not a routine rewrite — the up-front seam cost is repaid the moment a second source is wired, and avoided cost compounds with each further source.

### Consequences

**Positive:**
- A new source is added by writing one adapter against the common export contract, with 0 changes to the shared routine, the dedupe step, or the scheduler — so the "remainder pluggable later without reworking the routine" criterion is met structurally, not per-source ([PRD-v1, FR-4 AC L154](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- An export is brought in in ≤1 invocation with 0 per-reading manual entry for exported sources, and the same routine completes unattended on a schedule — satisfying FR-4's single-routine + unattended criteria and NFR-7's ≤1-invocation / unattended-completion targets ([PRD-v1, FR-4 AC L150-151, NFR-7 AC L272-273](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- Re-running the routine appends 0 duplicate readings for readings already stored, because dedupe is placed once in the shared routine keyed by the store's (item, timepoint) key — every adapter inherits idempotency uniformly ([PRD-v1, FR-4 AC L152](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- Export-less sources (labs, food, weight) enter the same store by manual entry, so the store accumulates from ≥1 import source and ≥1 manual source as Goal 2 requires ([PRD-v1, FR-4 AC L153, Goal 2 target L34](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).

**Negative:**
- Per-source adapter maintenance is a standing cost: every wired source is an adapter to keep working, and a source's export format changing (a wearable platform revising its export schema) breaks that adapter and can break the idempotency-key derivation (e.g., a changed timestamp field or unit), silently duplicating or dropping readings until the adapter is repaired — a per-source, ongoing-maintenance burden that grows with the source count (1+ year horizon as sources accumulate; format-change frequency [UNVERIFIED] — no platform history measured pre-build).
- The first cut wires only a subset of sources: FR-4's "without per-reading manual entry" is met only for the wired sources; for an unwired source (or one whose export the operator has not yet exercised) ingestion narrows to manual entry until its adapter is built, exactly the A-2 "if wrong" fallback ([PRD-v1, A-2 L300-301, FR-4 AC L154](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- The interface is constrained by two upstream decisions: it must write only to the local D2 store with no model-egress step (ADR-0001) and its dedupe key must fit the D2 (item, timepoint) line model (ADR-0002) — so the idempotency contract cannot be finalized independently of D2's keying, and a later change to that keying re-opens the dedupe design ([ADR-0001, Related Decisions](ADR-0001-pii-trust-boundary-no-train-routing.md) [VERIFIED]; [ADR-0002, Related Decisions](ADR-0002-local-first-time-series-store.md) [VERIFIED]).

**Neutral:**
- "Common export contract" (the reading shape an adapter maps to) becomes a shared contract the ingestion side and the D2 store side must agree on, alongside D2's "one reading per line, keyed by item+timepoint."
- The unattended-run mechanism is shared with generation (D4): both ingestion and on-demand+cron generation run on the same scheduling seam, so the scheduler is chosen once for both (cron/scheduler choice itself is a reversible implementation detail, not an ADR — [dag.md §2 D3–D4, exclusions item 7](.pipeline/dag.md) [VERIFIED]).

### Alternatives Considered

#### Alternative A: Per-source bespoke import scripts (no shared seam)
Write a separate import script for each source — one for the Oura export, another for an Apple Watch export — each parsing its source and writing to the store on its own, with no common adapter contract.
- **Supporting evidence:** Lowest up-front design cost and fastest path to the first wired source: the Oura script can be written directly against the Oura export with no abstraction to design first. Each script is independently simple and reads end-to-end without indirection.
- **Trade-offs:** Adding the Nth source rewrites or clones the routine each time, and the no-duplicate dedupe + the unattended-scheduling logic are re-implemented (and independently re-bugged) per script rather than placed once — directly failing FR-4's "remainder pluggable later without reworking the routine" and multiplying the unattended surface every script must each schedule ([PRD-v1, FR-4 AC L152 L154, NFR-7 AC L273](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). It scales the maintenance burden linearly with no shared dedupe/idempotency guarantee.
- **When this becomes the right choice:** If V1 were certain to ingest exactly one source for the life of the product (e.g., only Oura, never a second wearable or a HealthKit export), the seam would be pure overhead and a single script would be the simpler choice.

#### Alternative B: Single rigid importer hardcoded to one or two sources
Build one importer that handles the first one or two sources inline — branching internally on source type — without an extension point for sources beyond those hardcoded.
- **Supporting evidence:** A single routine (not N scripts) does centralize dedupe and scheduling, so the no-duplicate and unattended contracts are placed once and inherited by the hardcoded sources — strictly better than Alternative A on those two criteria. It is also less abstract than a full adapter seam, so it is quicker to build for the known first sources.
- **Trade-offs:** It is not source-extensible: a third source (Whoop, Garmin, or the [INTAKE-DIRECTED] HealthKit/Apple Watch export) cannot be admitted without editing the importer's internals, which is the "reworking the routine" FR-4/OQ-5 explicitly forbid — and the PRD names five prepared sources, not one or two, so the hardcoded ceiling is breached by the stated scope ([PRD-v1, FR-4 AC L154, OQ-5 L346, current-state Finding 12 L373](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- **When this becomes the right choice:** If the full source set were genuinely fixed and small (exactly the one or two sources, no future additions anticipated) — but the PRD's five prepared sources + the pluggable-later requirement contradict that premise.

#### Alternative C: Pluggable per-source adapter interface over a common export contract (Chosen)
Each source is an adapter mapping its export to the store's reading shape; a shared routine runs the adapters, dedupes once against the D2 key, and schedules unattended; export-less sources fall back to manual entry. A new source is an adapter addition.
- **Supporting evidence:** The only shape that satisfies all four criteria — Nth-source cost is one adapter (no routine rewrite), dedupe and scheduling are placed once and inherited by every adapter, and the subset-wired-first reality is handled by wiring a subset now and plugging the rest in later, exactly de-risking the Medium-confidence single-export assumption ([PRD-v1, FR-4 AC L150-154, OQ-5 L346, A-2 L299](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- **Trade-offs:** Highest up-front design cost (the common export contract + the adapter boundary must be designed before the first source is wired), and each wired adapter is a standing maintenance surface that an export-format change can break (carried as a Negative consequence). The cost is repaid once a second source is wired.
- **When this becomes the right choice:** When more than one source will ever be ingested and the full set is not fixed up front — the V1 situation (five prepared sources, subset wired first, remainder pluggable later).

### Validation Approach

**Confirmation criteria:**
- An export file from a device or app is brought into the store in a single routine invocation, with 0 per-reading manual entry for that exported source — verified by running the routine on one export and inspecting the store for the imported readings (expected: readings present, 0 manual keystrokes per reading) ([PRD-v1, FR-4 AC L150, US-3 AC L66](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- A scheduled, unattended run refreshes the store with only readings new since the last run — verified by running the routine unattended after new readings exist (expected: only the new readings appended, completion with no operator interaction) ([PRD-v1, FR-4 AC L151, NFR-7 AC L273](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- Re-running the routine over already-stored readings appends 0 duplicates — verified by re-running an import and counting store lines for the already-present readings (expected: line count unchanged) ([PRD-v1, FR-4 AC L152](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- A new source is wired by adding one adapter with 0 edits to the shared routine, dedupe step, or scheduler — verified by adding a second source adapter and diffing the shared routine (expected: 0 lines changed in the shared routine) ([PRD-v1, FR-4 AC L154, OQ-5 L346](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- Labs, food, and weight (export-less) are entered manually into the same store — verified by a manual entry landing in the store alongside imported readings (expected: manual reading present in the same store) ([PRD-v1, FR-4 AC L153](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).

**Falsification criteria:**
- If a re-run duplicates ≥1 already-stored reading (store line count grows for readings already present), the idempotency contract has failed — block scheduled re-runs and repair the dedupe before unattended import is enabled ([PRD-v1, FR-4 AC L152](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- If wiring a new source requires editing the shared routine (≥1 line changed in the shared routine, dedupe step, or scheduler to admit the source), the design is not source-extensible — the adapter seam has leaked, and the interface boundary must be repaired before more sources are wired ([PRD-v1, FR-4 AC L154](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- If ingestion sends ≥1 raw operator reading to the model (any reading routed through a model step rather than written to the local store), the ADR-0001 constraint is violated — halt ingestion and re-route to the local store ([ADR-0001, Related Decisions](ADR-0001-pii-trust-boundary-no-train-routing.md) [VERIFIED]).
- Time horizon: run all four checks at the first import-and-refresh cycle (before the July-2026 visit) and at every release thereafter; re-run the no-duplicate and new-adapter checks whenever a source's export format changes.

**Review triggers:**
- A wired source's export format changes (a wearable platform revising its export schema) — re-validate the affected adapter's parse and the idempotency-key derivation against the no-duplicate criterion.
- A new source is added to the prepared set beyond HealthKit/Apple Watch/Whoop/Garmin/Oura — confirm it plugs in as an adapter with 0 shared-routine edits.
- D2's per-item keying or timepoint granularity changes (D2 OQ-1 resolves) — re-confirm the dedupe key still fits the store's line model without a routine change.
- The shared scheduling seam (shared with D4) is chosen or changed — confirm unattended ingestion still completes.
