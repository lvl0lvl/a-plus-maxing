## ADR-0045: Plan-Compiled Monitoring Config + Tiered Adjustment Executor

> **Y-Statement:** In the context of the automated plan-evolution loop (ADR-0036), whose ONLY automated adjustment surface is a debounced FULL-front-door re-gen — `regenerate` drives `plan_orchestrator.run_orchestrated` through the shared driver, composes the gate verdicts, applies the fail-closed safety gate, and runs the five `orchestrate` cross-domain holds on every firing ([plan_loop.py:1-30,130-180](../../scripts/serve/plan_loop.py) [VERIFIED]), the debounce bounding only FREQUENCY (a 7-day min-interval + a sustained-signal window, [plan_loop.py:380-391,440-454](../../scripts/serve/plan_loop.py) [VERIFIED]) while every firing pays the whole A′ model composition ADR-0036 records as "materially more expensive than a per-domain patch" ([ADR-0036 Consequences-Negative-1](ADR-0036-automated-plan-evolution-loop.md) [VERIFIED]) and fires the sole metered ADR-0027 de-id-IN egress the ADR-0039 runner meters ([ADR-0039 Consequences](ADR-0039-scheduled-agent-runner.md); [plan_loop.py:113-127](../../scripts/serve/plan_loop.py) [VERIFIED]) — and where the only cheaper surface, the per-domain `adjust.py` re-plan leg, is a manual one-off that by its own docstring does NOT re-run the `orchestrate` cross-domain holds nor the composed gate (the "finding A" safety gap, [adjust.py:15-23,144](../../scripts/plan/adjust.py) [VERIFIED]), facing the tension that a health plan needs cheap daily autoregulation yet must never route a material, cross-domain, or safety-crossing change around the safety composition or the operator confirm, now that ADR-0041 makes `monitoring_signals` + `adjustment_rules` first-class required fields and ADR-0044 gives the compiled config a home in the plan, we decided that the plan's specialist-authored `monitoring_signals` + `adjustment_rules` COMPILE into a config a daily loop runs DETERMINISTICALLY with zero model calls, escalating through a TIERED executor — auto-apply (deterministic, in-domain) → specialist re-plan (material, in-domain) → care-agent reconcile (cross-domain) → medical-liaison human-gate (safety, reusing ADR-0040's confirm hold) — to achieve cheap/instant in-domain autoregulation on a no-event day while preserving safety-composition parity on every material change, accepting a new runtime compiler + executor + the tiering complexity, a coupling to the HARD ADR-0041/0044 it consumes, and the burden that the deterministic tier be PROVABLY safe to run without a model — a mis-compiled rule auto-applying is a risk the fail-closed escalation and the human-gate tier bound, at MODERATE reversibility (a new runtime component, not a data-model migration, and NOT itself a break of the ADR-0032 freeze).

### Context

The automated plan-evolution loop (ADR-0036) has ONE automated adjustment surface: a debounced full-composition re-gen. `regenerate` is the loop's single entry into the front door — it drives `plan_orchestrator.run_orchestrated` with a composed gate producer injected, so the run enters the shared `plan_driver.drive`, composes the gate verdicts, applies the fail-closed `safety_passed is True` surface gate, and runs the five `orchestrate` cross-domain holds ([plan_loop.py:1-30,130-180](../../scripts/serve/plan_loop.py) [VERIFIED]). The debounce bounds only FREQUENCY — a re-gen fires only when the pinned `MIN_REGEN_INTERVAL_DAYS = 7` floor has elapsed AND a single `biomarker::` stream carries a sustained directional signal over its recent window ([plan_loop.py:380-391,440-454](../../scripts/serve/plan_loop.py) [VERIFIED]) — but every FIRING is the whole model composition: the A′ dispatch aggregate (every plan-domain author + the quality judge + each safety lens + any reauthor/adjudicator round, multiplied by the bounded revise iterations), which ADR-0036 itself records as "materially more expensive than a per-domain patch," a "real and permanent" per-trigger cost ([ADR-0036 Consequences-Negative-1](ADR-0036-automated-plan-evolution-loop.md) [VERIFIED]; the loop's own debounce comment cites it, [plan_loop.py:359-367](../../scripts/serve/plan_loop.py) [VERIFIED]).

There is no cheap, deterministic daily tier below that model re-gen. Every automated adjustment is one of two things. Either (a) the full front-door re-gen — a model round-trip that also fires the sole metered egress: the crown-jewel `deid_in` boundary de-identifies the raw intake before any specialist dispatch ([plan_loop.py:113-127](../../scripts/serve/plan_loop.py) [VERIFIED]), and that ADR-0027 de-id-IN call is the SINGLE metered/no-train egress the ADR-0039 scheduled runner arms, each debounced cadence tick firing one such call ([ADR-0039 Consequences Positive/Negative](ADR-0039-scheduled-agent-runner.md) [VERIFIED]). Or (b) the per-domain `adjust.py` re-plan leg — a MANUAL operator one-off that calls single-domain `generate_plan` ([adjust.py:144](../../scripts/plan/adjust.py) [VERIFIED]) and, by its own docstring, "does not re-run" the `orchestrate` cross-domain reconciliation (energy-bounce / additive-AE / conflict / Rx-BPMH holds) nor the composed gate ([adjust.py:15-23,63-64](../../scripts/plan/adjust.py) [VERIFIED]) — the exact "finding A" safety gap ADR-0036 names: automating that bare per-domain path would strip the safety composition off every plan after the first ([ADR-0036 finding A](ADR-0036-automated-plan-evolution-loop.md) [VERIFIED]). So the loop has no way to apply a bounded in-domain adjustment WITHOUT either paying a metered model round-trip or routing around the safety composition.

Two upstream decisions have now put the raw material for a deterministic tier into the plan itself. ADR-0041 makes `monitoring_signals` (each carrying a validity tier) and `adjustment_rules` (deterministic if-signal-then-change rules) first-class REQUIRED fields every domain specialist emits ([ADR-0041 Decision fields 3-4](ADR-0041-uniform-specialist-domain-program-schema.md) [VERIFIED]), and ADR-0044 gives the COMPILED monitoring config a first-class home inside the stored comprehensive plan model ([ADR-0044 Decision field 4](ADR-0044-comprehensive-plan-model.md) [VERIFIED]). Where the thin `plan_schema` carried no monitoring or adjustment field at all, the plan now carries the signals to watch, the rules to apply, and a stored home for a compiled config.

Two forces pull against each other. First, cost/latency versus safety-composition parity: a deterministic tier avoids the metered model round-trip and its latency on a no-event day, but a health plan must NEVER route a materially-large, cross-domain, or safety-crossing change around the safety composition (finding A) or the operator confirm (ADR-0040). Second, determinism versus the mis-compile risk: a rule compiled wrong and auto-applied with no model in the loop is a real health-safety risk, so the deterministic tier must be provably safe to run un-modelled. Because this defines a new adjustment ARCHITECTURE — a runtime compiler, a deterministic executor, and an escalation ladder that constrains HOW the loop adjusts — and because it REFINES ADR-0036's "re-run the front door on every debounced trigger" rather than leaving it, it is an architecture decision, not an implementation detail.

### Decision

**The plan's specialist-authored `monitoring_signals` + `adjustment_rules` compile into a monitoring config that a daily loop runs DETERMINISTICALLY (no model call), and a TIERED executor escalates to a model re-plan only on material or scheduled events. The four escalation tiers, cheapest-and-safest first, are: (1) auto-apply — deterministic, in-domain; (2) specialist re-plan — material, in-domain; (3) care-agent reconcile — cross-domain; (4) medical-liaison human-gate — safety.**

Stated generically (the same ladder whether the plan spans a training domain program, a compound domain program, or the wider roster):

1. **Auto-apply (deterministic, in-domain).** The compiled config's if-signal-then-change `adjustment_rules` apply a bounded IN-DOMAIN adjustment with ZERO model calls when a `monitoring_signal` crosses a threshold a specialist-authored rule already covers — cheap, instant, and safe because the specialist AUTHORED the rule at plan time (it is not invented at runtime). This is the new tier below the model re-plan.
2. **Specialist re-plan (material, in-domain).** A material in-domain event the deterministic rules do not cover escalates to a single-domain specialist re-plan — but routed THROUGH the safety composition (the composed gate + the per-domain safety floor), NOT the bare `adjust.py` leg that skips it (finding A), consistent with ADR-0036's front-door resolution.
3. **Care-agent reconcile (cross-domain).** An adjustment whose `cross_domain_seams` reach another domain escalates to the care-agent orchestrator (ADR-0043) to reconcile the seams — this tier IS a call into ADR-0043's orchestrator (its generalized `cross_domain_seams` reconciliation, which re-bases `orchestrate.reconcile`'s five holds onto the uniform field, [ADR-0043, Decision §3](ADR-0043-care-agent-plan-orchestrator.md); [orchestrate.py:1-54,337-456](../../scripts/plan/orchestrate.py) [VERIFIED]), NOT the pre-0043 flat `run_orchestrated` reconciler; a cross-domain change is never auto-applied in-domain. This tier is therefore a runtime dependency on ADR-0043 (depends-on).
4. **Medical-liaison human-gate (safety).** A safety-threshold event (a `refusal/escalation` condition or a medical-liaison watchlist match) HOLDS at the human-gate and NEVER auto-advances — reusing ADR-0040's bounded confirmation-pointer hold, so the change does not stand and is not tailored/egressed until an explicit operator/liaison confirm, backed by the terminal `adjudicate` clinical safety gate ([orchestrate.py:5-7,37-39](../../scripts/plan/orchestrate.py) [VERIFIED]).

The executor is fail-closed BY DIRECTION: an event the deterministic tier cannot safely handle escalates UP the ladder, never applies a guess; materiality, cross-domain scope, and safety risk each move the disposition to a higher tier, and the top tier never auto-advances. This REFINES ADR-0036: the loop's "re-enter the full front door on every debounced trigger" becomes "run the compiled config daily with 0 model calls; escalate to the model re-plan only on material/scheduled events."

**Reversibility + freeze scope (MODERATE — stated honestly).** This decision does NOT itself break the ADR-0032 EXTEND-NOT-REBUILD freeze — it is a NEW runtime component (a compiler + a deterministic executor + the tiering), not a data-model migration and not an edit to the byte-frozen record spine. It COUPLES to the HARD ADR-0041 (the source fields) and ADR-0044 (the config's stored home), both of which do break the freeze on their own surfaces and carry their own operator sign-off; ADR-0045 consumes their shipped shapes and adds no further freeze break. Reversibility is MODERATE: reverting to "always re-run the front door" is rework of a runtime component (delete the compiler + collapse the executor to Tier-2/3), not a store-contract migration. It does NOT decide the specialist-output schema (ADR-0041) nor the plan model (ADR-0044); it consumes both.

### Rationale

Three options were weighed across the four criteria the Context makes load-bearing — **daily cost** (does a no-event day pay the metered model round-trip, or 0 model calls?), **safety-composition parity** (does a material/cross-domain/safety change still run the composition + confirm, or route around it?), **single source of truth** (does the tier adjust against the plan's OWN authored signals/rules, or a separable copy that can drift?), and **mis-compile containment** (is an un-modelled auto-apply bounded so a bad rule cannot advance a risky change?) — against keeping the full-model re-gen every trigger (Alternative A) and a monitoring service separate from the plan (Alternative B).

On **daily cost**, only the compiled deterministic tier makes a no-event day free. Today every automated adjustment is the whole A′ composition ([ADR-0036 Consequences-Negative-1](ADR-0036-automated-plan-evolution-loop.md) [VERIFIED]) plus the metered ADR-0027 de-id-IN egress the ADR-0039 runner arms per tick ([ADR-0039 Consequences](ADR-0039-scheduled-agent-runner.md) [VERIFIED]); a deterministic tier that reads the compiled config and applies a specialist-authored in-domain rule makes 0 model calls and 0 de-id-IN egress on a day no signal crosses a material threshold, so it directly REDUCES the runner's metered spend (the ADR-0039 complements edge). Alternative A pays that cost and latency on every trend, forever.

On **safety-composition parity**, the tiered ladder KEEPS the composition where it matters: a material in-domain change runs the specialist re-plan through the composed gate (not the finding-A bare leg, [adjust.py:15-23](../../scripts/plan/adjust.py) [VERIFIED]), a cross-domain change runs the `orchestrate` reconciler ([orchestrate.py:1-54](../../scripts/plan/orchestrate.py) [VERIFIED]), and a safety-threshold change HOLDS at the ADR-0040 human-gate. The deterministic tier only auto-applies the narrow class of bounded, in-domain, specialist-pre-authored rules — the class where a model round-trip would re-derive exactly what the specialist already authored. On **single source of truth**, the config compiles from the plan's OWN `monitoring_signals` + `adjustment_rules` stored in the ADR-0044 model, so the tier adjusts against the same artifact the specialist authored — no separable monitoring copy that can drift (the exact reason Alternative B is rejected, below).

On **mis-compile containment**, the risk that a rule compiled wrong auto-applies a bad change is bounded three ways and is not hidden (Consequences-Negative): the auto-apply tier is confined to in-domain, specialist-authored, bounded rules; any change crossing a safety threshold escalates to the human-gate (never auto-advances); and the executor fails closed by direction (an event it cannot classify as safely-deterministic escalates up, never applies a guess). The cost the decision accepts is real — a new runtime compiler + executor + the tiering complexity, coupled to the HARD ADR-0041/0044 — and is accepted because cheap daily autoregulation WITH preserved safety-composition parity is exactly the property the plan-first re-architecture set exists to deliver, and neither alternative provides both.

### Consequences

**Positive:**
- A no-event day costs 0 model calls and 0 metered egress: the deterministic tier reads the compiled config and applies (or holds) without re-entering the front door, so it does NOT fire the ADR-0027 de-id-IN call the front-door re-gen fires ([plan_loop.py:113-127](../../scripts/serve/plan_loop.py) [VERIFIED]) — directly reducing the recurring metered spend ADR-0039's runner arms per debounced tick ([ADR-0039 Consequences-Negative-1](ADR-0039-scheduled-agent-runner.md) [VERIFIED]).
- Instant in-domain autoregulation: a specialist-authored `adjustment_rule` applies the moment a `monitoring_signal` crosses its threshold, with no model round-trip latency — the plan self-adjusts at the cadence its own signals move, closing the NO-LOOP root at the daily tier rather than only at the weekly model re-gen.
- Safety-composition parity is preserved on every material change: a material in-domain re-plan runs the composed gate (not the finding-A bare `adjust.py` leg, [adjust.py:15-23,144](../../scripts/plan/adjust.py) [VERIFIED]), a cross-domain change runs the `orchestrate` reconciler ([orchestrate.py:1-54](../../scripts/plan/orchestrate.py) [VERIFIED]), and a safety-threshold change holds at the ADR-0040 human-gate — so the deterministic tier adds a cheaper path WITHOUT weakening the composition ADR-0026/0028 bought.
- Risk never auto-advances: the top tier HOLDS a safety-crossing change on ADR-0040's confirm hold, so the "never auto-advance a risky change" property is first-class in the executor, not implicit in downstream code.

**Negative:**
- **A new runtime compiler + deterministic executor + the tiering complexity.** The compiler (translate `monitoring_signals` + `adjustment_rules` into an executable config) and the four-tier executor (classify each event and route it) are net-new runtime surface with net-new failure modes — a mis-classification that escalates too little (applies a change that should have held) or too much (pays a model round-trip on a deterministic event). This is real added complexity, not a free refinement.
- **The deterministic tier must be PROVABLY safe to run without the model — a mis-compiled rule auto-applying is a live risk.** An `adjustment_rule` compiled wrong could auto-apply an out-of-bounds or safety-crossing change with no model in the loop. The risk is bounded (auto-apply confined to in-domain specialist-authored bounded rules; safety-threshold changes escalate to the human-gate; fail-closed-by-direction escalation) but it is the load-bearing negative: the human-gate tier BOUNDS the mis-compile risk, it does not eliminate the need to prove the compiler correct (Validation).
- **Couples to the HARD ADR-0041/0044.** The compiler's input contract IS ADR-0041's `monitoring_signals` + `adjustment_rules` sub-schema and the config's home IS ADR-0044's stored plan model; a change to either is a schema-contract change to this decision's input/output. The deterministic tier cannot ship until those shapes are load-bearing, and it re-bases if they change.
- **The escalation boundary is a new invariant to police.** "Which events are safely-deterministic vs material vs cross-domain vs safety-threshold" is a classification every new signal/rule must be placed against; a mis-placed rule is a latent over- or under-escalation. The correctness burden is spread across every authored rule, an invariant to enforce in review (OQ-2).

**Neutral:**
- The deterministic tier reuses the existing debounce and cadence host: it runs under ADR-0039's disabled-by-default local runner (which still hosts the weekly cadence) and the ADR-0036 debounce ([plan_loop.py:380-391](../../scripts/serve/plan_loop.py) [VERIFIED]); ADR-0045 changes what the loop DOES between model re-gens, not whether or how it is scheduled.
- The specialist-re-plan tier maps onto the same single-domain re-author `adjust.py` performs today ([adjust.py:144](../../scripts/plan/adjust.py) [VERIFIED]) but routed through the safety composition; whether it re-uses that module (re-based onto the composition) or the front-door single-domain path is a spec-level realization (OQ-1), not a new mechanism.

### Alternatives Considered

#### Alternative A: Keep re-running the full model front door on every (debounced) trigger — no deterministic daily tier
Leave the loop as ADR-0036 built it: every automated adjustment is the debounced full-composition re-gen (`regenerate` → `run_orchestrated`), with no cheaper tier below it.
- **Supporting evidence:** It is the BUILT loop and reuses the shared driver with no new component, keeping the ONE definition of the safety composition + fail-closed loop on every plan ([plan_loop.py:130-180](../../scripts/serve/plan_loop.py) [VERIFIED]); the debounce (7-day floor + sustained-signal window) already bounds how often the cost is paid ([plan_loop.py:380-391](../../scripts/serve/plan_loop.py) [VERIFIED]).
- **Trade-offs:** REJECTED — every automated adjustment pays the whole A′ dispatch aggregate ADR-0036 calls "materially more expensive" ([ADR-0036 Consequences-Negative-1](ADR-0036-automated-plan-evolution-loop.md) [VERIFIED]) PLUS a metered ADR-0027 de-id-IN egress per tick ([ADR-0039 Consequences-Negative-1](ADR-0039-scheduled-agent-runner.md) [VERIFIED]), and a model round-trip's latency, with NO cheap daily autoregulation — the plan cannot self-adjust to its own monitoring signals between weekly re-gens even when the specialist already authored the exact rule.
- **When this becomes the right choice:** If NO adjustment could ever be bounded safely enough to auto-apply without a model — if every in-domain change genuinely needed the full composition to be safe — then a deterministic tier would add risk for no benefit and re-running the front door would dominate.

#### Alternative B: A monitoring service separate from the plan
Build a standalone monitoring/adjustment engine that reads signals and applies changes, decoupled from the plan model — its own component, independently scaled.
- **Supporting evidence:** Clean separation of concerns (monitoring as its own service), independently deployable and scalable, and a familiar control-system shape (a monitor distinct from the artifact it monitors).
- **Trade-offs:** REJECTED — two sources of truth. The signals and rules that drive adjustment are AUTHORED BY the specialist and MUST live with the plan that authored them ([ADR-0041 Decision fields 3-4](ADR-0041-uniform-specialist-domain-program-schema.md); [ADR-0044 Decision field 4](ADR-0044-comprehensive-plan-model.md) [VERIFIED]); a separate service reads a COPY that can drift from the plan the moment either updates — the same dual-surface drift ADR-0044 rejected a rich side artifact for ([ADR-0044 Alternative B](ADR-0044-comprehensive-plan-model.md) [VERIFIED]) — and it cannot fail-closed on the plan's own `refusal/escalation` contract because that contract lives in the plan, not the service.
- **When this becomes the right choice:** If the plan and its monitoring were genuinely independent lifecycles authored by different owners — they are not; the specialist authors the prescription and its monitoring/adjustment together as one DOMAIN PROGRAM (ADR-0041).

#### Dissent: A deterministic tier is unsafe for a health plan — always keep a model in the loop
**Source:** A safety-first position generalizing the project's fail-closed-crown-jewel posture (the same posture that motivated ADR-0036's finding-A safety gap, [ADR-0036 finding A](ADR-0036-automated-plan-evolution-loop.md) [VERIFIED]). A purist holds that ANY un-modelled auto-apply is a health-safety risk: a rule compiled wrong applies a bad change with no model to catch it, so every adjustment — however small — should re-enter the model composition.
**Conditions under which this becomes the right choice:** If even a specialist-PRE-AUTHORED, in-domain, bounded `adjustment_rule` cannot be trusted to apply deterministically — if the act of compiling a rule the specialist already wrote is itself unsafe. It is not: a bounded in-domain rule the specialist authored at plan time and the human-gate tier backstops is exactly as safe as the specialist re-issuing it, minus the model round-trip; a safety-crossing change never reaches auto-apply (it escalates to the human-gate). The dissent wins only if the auto-apply class cannot be bounded safely at all — in which case every tier collapses to the model re-plan (Alternative A). The mitigation is to keep the auto-apply class narrow and prove the compiler correct (Validation), not to abandon the deterministic tier.

### Validation Approach

**Confirmation criteria:**
- **The daily tier runs with 0 model calls on a no-event day (executable, the load-bearing probe).** Seed a plan carrying a compiled monitoring config; run the daily tier on a day where NO `monitoring_signal` crosses a material threshold. Assert 0 model dispatches (0 specialist calls, 0 quality-judge calls, 0 safety-lens calls) AND 0 metered ADR-0027 de-id-IN egress calls AND 0 front-door re-entries. Threshold: model-call-count == 0 and de-id-IN-count == 0 on a no-event day. If the daily tier makes ANY model call or de-id-IN call on a no-event day, the deterministic-tier property is unmet (the tier is silently re-entering the front door) — halt.
- **A material in-domain event escalates to specialist re-plan THROUGH the composition (executable).** Feed a signal that crosses a material-but-in-domain threshold no `adjustment_rule` covers; assert the executor escalates to Tier-2 and the re-plan runs the composed gate + the per-domain safety floor, NOT the bare `adjust.py` leg ([adjust.py:15-23](../../scripts/plan/adjust.py) [VERIFIED]). Threshold: 0 material re-plans bypass the safety composition (finding-A parity). If a Tier-2 re-plan records without the composition, the finding-A gap has re-opened — halt.
- **A cross-domain adjustment escalates to care-agent reconcile (executable).** Feed an adjustment whose `cross_domain_seams` reach another domain; assert it escalates to Tier-3 and runs the `orchestrate` cross-domain reconciler ([orchestrate.py:1-54](../../scripts/plan/orchestrate.py) [VERIFIED]), never auto-applied in-domain. Threshold: 0 cross-domain adjustments auto-applied at Tier-1.

**Falsification criteria:**
- **A risky change auto-advancing past the human-gate → fail (deterministic).** Feed a safety-threshold event (a `refusal/escalation` condition or a medical-liaison watchlist match); assert it HOLDS at Tier-4 on ADR-0040's confirm hold and does NOT auto-advance — the change does not stand, is not tailored/egressed, and is not applied until an explicit operator/liaison confirm ([ADR-0040 Decision](ADR-0040-large-change-hold-until-confirm.md) [VERIFIED]). Threshold: a safety-threshold change → held (0 auto-advance). If a risky change advances past the human-gate, the never-auto-advance-risk property is broken — halt and repair before release.
- **The daily tier making a model call on a no-event day → fail (deterministic).** The paired inverse of the load-bearing confirmation probe: on a day no signal crosses a material threshold, model-call-count MUST be 0. Threshold: ≥1 model call on a no-event day → fail (the tier is not deterministic) — halt.
- **A mis-compiled / out-of-bounds rule auto-applying → fail (deterministic).** Author an `adjustment_rule` that would drive an out-of-domain-bounds or safety-crossing change; assert the compiler REJECTS it at compile time OR the executor ESCALATES it (never auto-applies at Tier-1). Threshold: 0 out-of-bounds auto-applies; an out-of-bounds change must escalate or be rejected, never applied deterministically. If a mis-compiled rule auto-applies, the mis-compile-containment guarantee is broken — halt.
- **Time horizon:** run the no-event-day 0-model-call probe, the finding-A-parity probe, the human-gate-hold probe, and the out-of-bounds-rejection probe at the first compiler/executor build, at the operator-present LIVE run (OQ-4), at every release thereafter, and before the July-2026 physician-visit deliverable.
