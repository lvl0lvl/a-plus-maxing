## ADR-0036: Automated Plan-Evolution Loop Re-Runs the Front Door

> **Y-Statement:** In the context of the closed loop (`design/vision.md`: plan → act → measure → adjust) whose MEASURE + ADJUST-read legs are wired (`track.record_tracking` records `plan-track::`, `track.resolve_plan_progress` joins plan-vs-actual, [track.py:34,81](../../scripts/plan/track.py) [VERIFIED]) but whose only ADJUST re-plan surface is the per-domain `adjust.py` — a manual operator one-off that calls the SINGLE-domain `generate_plan` ([adjust.py:144](../../scripts/plan/adjust.py) [VERIFIED]) and by its own docstring "does not re-run" the `orchestrate` cross-domain holds ([adjust.py:15-23,63-64](../../scripts/plan/adjust.py) [VERIFIED]) nor the ADR-0028 composed `gate_dispatch` (judge + safety lenses + fail-closed `safety_passed is True` loop + liaison adjudication) — facing that automating that per-domain path would make every plan after week 1 never see the safety composition again (finding A), that the per-domain adjust keys on `plan-track::` adherence and no-ops on a wearable trend that lands in the separate `biomarker::` namespace (finding B), and that a care-chat free-text trigger is RAW operator text `adjust.py` does not de-identify (finding C), we decided that the automated dynamic-adjustment loop RE-ENTERS THE FRONT DOOR — `plan_driver.drive` / `run_orchestrated` → the composed `gate_dispatch` + `orchestrate.generate_plans` cross-domain reconciliation ([plan_driver.py:144,263,272](../../scripts/plan/plan_driver.py) [VERIFIED]) — producing a NEW dated plan for ALL domains, mechanically debounced (a minimum re-gen interval + a sustained-signal window over the `biomarker::` series; free-text rate-limited) and firing only when data is present (absent data → hold + prompt, never re-gen on nothing), with the trigger routing ONLY de-identified / derived tokens (free-text through `care_chat`'s gated capture → derived tokens → the `router.summarize` whitelist, [care_chat.py:284](../../scripts/serve/care_chat.py) [VERIFIED]) so raw text is structurally incapable of reaching the specialist dispatch, to achieve a plan that evolves with the same safety composition as the first while re-summarizing the store re-derives the `biomarker::` trend for free ([router.py:753-758](../../scripts/plan/router.py) [VERIFIED]), accepting that re-running the full gate every trigger is materially more expensive than a per-domain patch and that `adjust.py` stays the manual one-off.

### Context

The system's stated shape is a closed loop — `design/vision.md`: it "closes the loop — plan → act → measure → adjust — tracking interventions, biomarkers, and outcomes over time so each plan is backed by what actually happened" ([track.py:2-4](../../scripts/plan/track.py) [VERIFIED]). Three of the four legs are built, and one automated behavior is missing between them:

- **The GENERATE leg is the A′ front door.** ADR-0026 selected the subscription-runtime driver and ADR-0028 completed the control-inversion: the initial plan is generated by `plan_driver.drive` (or its programmatic twin `run_orchestrated`), which yields the AUTHOR + GATE + REAUTHOR + ADJUDICATOR dispatch classes, composes the raw judge/lens verdicts into the 3-key disposition via `compose_disposition`, and applies the fail-closed `safety_passed is True` surface gate — all in ONE definition ([plan_driver.py:144,263,272,278](../../scripts/plan/plan_driver.py); [gate_dispatch.py:118,165](../../scripts/plan/gate_dispatch.py) [VERIFIED]). The driver runs `orchestrate.generate_plans`, whose reconciliation applies the FIVE cross-domain holds — RED-S/LEA short-circuit, the nutrition→workout energy bounce, cross-domain-conflict, supplement↔peptide additive-AE, and supplement↔Rx BPMH ([orchestrate.py:337-456,482](../../scripts/plan/orchestrate.py) [VERIFIED]).
- **The MEASURE leg is wired.** `track.record_tracking` records one observed snapshot against a domain's plan into `plan-track::<domain>`, with the honest no-plan-to-track boundary ([track.py:34-78](../../scripts/plan/track.py) [VERIFIED]); `resolve_plan_progress` joins the recorded plan with its tracking snapshot into the plan-vs-actual view ([track.py:81-126](../../scripts/plan/track.py) [VERIFIED]).
- **The ADJUST re-plan leg exists ONLY per-domain, and off the safety composition.** `adjust.py` is the only re-plan caller. It reads `resolve_plan_progress` for the honest "nothing to progress from" boundary, then records the specialist's adjusted output through the SINGLE-domain `generate_plan` ([adjust.py:122,144](../../scripts/plan/adjust.py) [VERIFIED]). Its own docstring states the boundary plainly: "Cross-domain reconciliation (`orchestrate`'s energy-bounce / additive-AE / conflict / Rx-BPMH holds) is a SEPARATE orchestrator step the per-domain adjust does not re-run" ([adjust.py:15-23,63-64](../../scripts/plan/adjust.py) [VERIFIED]), and it never touches `gate_dispatch`. As a rare operator one-off this is a documented V1 boundary, not a bypassed floor (the initial per-domain step does not run those holds either). But there is no automated trigger that re-plans on new data — the loop does not yet close on its own.

Three forces make automating this non-trivial, each verified against the live tree by the six-agent design review (`design/dynamic-plan-loop-design.md` §0 findings A/B/C, all CONFIRMED):

- **The per-domain safety gap (finding A).** If the automated loop simply called `adjust.py` per domain, every evolved plan after the first would skip the ADR-0028 judge + safety lenses + fail-closed loop + medical-liaison adjudication AND the five `orchestrate` cross-domain holds — the exact composition ADR-0026/0028 bought. A plan that fires an energy bounce, an additive-AE stack, or an Rx-BPMH match on the NEW data would record un-reconciled. This is the drift the project's own fail-closed-crown-jewel posture exists to prevent.
- **The wearable-vs-plan-track mismatch (finding B).** The per-domain adjust keys on `plan-track::` — operator-LOGGED, same-date adherence read by `resolve_plan_progress` ([track.py:113-125](../../scripts/plan/track.py) [VERIFIED]). But wearables and labs land in the SEPARATE `biomarker::` namespace, surfaced as `recent-trend-direction` ONLY through `router.summarize`'s registry-driven worst-wins over the `biomarker::` polarity feed ([router.py:41,326,464,753-758](../../scripts/plan/router.py) [VERIFIED]). A per-domain adjust keyed on `plan-track::` therefore sees `has_tracking=False` and no-ops on a wearable trend — the "money shot" cannot fire.
- **Raw free-text (finding C).** A care-chat trigger (e.g. "my shoulder's flaring and I changed a dose this week") is RAW operator text. `adjust.py` is a recorder with no de-identification; nothing on that path stops raw text reaching the de-id specialist lane. The care agent, by contrast, already de-identifies BY DATA CLASS at capture: `care_chat.respond` writes proposed facts through `extract.persist_extraction` → `capture.persist_capture`, the SAME gate the intake chat uses ([care_chat.py:20-25,284](../../scripts/serve/care_chat.py) [VERIFIED]).

So the decision must clear: close the loop with an automated trigger that re-plans on new data WITHOUT routing any plan around the safety composition (finding A), WITHOUT missing the `biomarker::` trend (finding B), and WITHOUT any raw operator text reaching the specialist dispatch (finding C).

### Decision

The automated dynamic-adjustment loop **re-enters the front-door generation** — `plan_driver.drive` (subscription/skill mode) or `run_orchestrated` (programmatic/test mode), which drives the composed `gate_dispatch` + `orchestrate.generate_plans` cross-domain reconciliation ([plan_driver.py:144-307](../../scripts/plan/plan_driver.py); [gate_dispatch.py:165-201](../../scripts/plan/gate_dispatch.py) [VERIFIED]) — producing a NEW dated plan for ALL domains that passed the FULL safety composition. It does **not** call the per-domain `adjust.py` (which the review confirmed skips both `gate_dispatch` and the five cross-domain holds, [adjust.py:15-23](../../scripts/plan/adjust.py) [VERIFIED]); `adjust.py` remains the manual operator one-off.

The mechanism is mechanical (in code, on ALL triggers):

- **Trigger → one action.** The trigger is the union of (a) cadence (e.g. weekly), (b) a data-event — new labs/wearables mirrored to `biomarker::`, and (c) free-text via the care agent's existing gated capture. All three converge on ONE action: re-run the driver against the CURRENT store state. There is no per-domain fan-out.
- **Re-summarize for free (finding B).** Re-entering the driver re-runs `router.summarize`, which re-derives `recent-trend-direction` from the `biomarker::` polarity feed ([router.py:753-758](../../scripts/plan/router.py) [VERIFIED]) — so the wearable trend AND the goal progress reach the re-generation with NO bridge to `plan-track::`. Adherence (`plan-track::`) is a separate, additional input, not the trigger's carrier.
- **De-identified / derived tokens only (finding C).** The free-text trigger routes ONLY through `care_chat`'s gated capture (`extract.persist_extraction` → `capture.persist_capture`, [care_chat.py:284](../../scripts/serve/care_chat.py) [VERIFIED]): the model PROPOSES facts, the gate DISPOSES by data class into DERIVED tokens (e.g. `recovery-status-band`, [care_chat.py:42-53](../../scripts/serve/care_chat.py) [VERIFIED]) → the store → `summarize`'s whitelist → the specialist dispatch, which the A′ author seam only ever hands the de-identified summary ([care_chat.py:11-18](../../scripts/serve/care_chat.py) [VERIFIED]). Raw free-text is STRUCTURALLY incapable of reaching the specialist dispatch: it never leaves the care lane / the store's de-id derivation.
- **Debounce (mechanical).** A minimum re-generation interval PLUS a sustained-signal requirement — a window/threshold over the `biomarker::` series, NOT a single reading; a second trigger inside the window is dropped. Free-text is rate-limited too.
- **Absent data → hold + prompt.** No new signal in the window → hold and prompt to log; never re-generate on nothing.
- **Multi-domain coherence.** Re-entering the driver regenerates ALL domains on the new date and re-runs cross-domain reconciliation — a held domain is re-derived per re-gen (clearance is NOT inherited), and the fail-closed `safety_passed is True` surface gate applies exactly as to the first plan ([plan_driver.py:272-273](../../scripts/plan/plan_driver.py) [VERIFIED]).
- **Fired through the SERVE entry point — the full-composition front door (BUILD PREREQUISITE).** The loop MUST invoke the full-composition front door — `run_orchestrated` → `plan_driver.drive` → the composed `gate_dispatch` + `orchestrate.generate_plans` cross-domain reconciliation ([plan_driver.py:144-307](../../scripts/plan/plan_driver.py) [VERIFIED]), the A′ live path the `/generate-plan` skill drives — NOT by importing the module in isolation, and NOT the in-app `_do_generate_plan` route, which TODAY calls `orchestrate.generate_plans` DIRECTLY with NO reauthor/adjudicator hook (the screened-only, strictly-more-conservative path, [server.py:677-678](../../scripts/serve/server.py) [VERIFIED]). Because that screened-only route is the serve layer's current re-gen call, **wiring the automated serve trigger to the driver front door is a stated BUILD PREREQUISITE** (and a Validation criterion below), not an open ambiguity: finding-A safety-parity FAILS outright if the trigger reaches the screened-only path, so the trigger binds to the A′ driver and the build names the mechanical guard that prevents it from degrading to `_do_generate_plan`.
- **Tailoring on an automated (non-operator) re-gen.** The automated triggers — the cadence timer and the `biomarker::` write-event — do NOT host a care-chat turn, so nothing on those paths would otherwise fire the [ADR-0037](ADR-0037-care-agent-plan-tailoring.md) care-lane tailoring pass (the operator's core personalization ask). The loop therefore invokes the tailoring pass DIRECTLY after it records the plan (`plan_driver` → record `plan::<domain>` → tailoring pass → `reemit_maintained`), reusing the care-lane raw read, independent of any operator care-chat turn. Tailoring stays idempotent per (plan, date) and fail-safe to the un-tailored plan (the ADR-0037 constraint this decision propagates), so a re-gen never leaves duplicate/stale tailored artifacts.

### Rationale

The choice was evaluated against the four forces the review made load-bearing — **safety-composition parity** (every evolved plan sees the same `gate_dispatch` + cross-domain holds as the first), **the trend actually reaching re-gen** (finding B), **the de-id boundary holding on the trigger** (finding C), and **buildability under extend-not-rebuild** — against automating the per-domain `adjust.py` (Alternative B), a bespoke incremental patcher (Alternative C), and keeping the loop manual (Alternative D).

On **safety-composition parity** the re-run-the-front-door choice is decisive and the others fail. `adjust.py` calls single-domain `generate_plan` and, by its docstring, does not re-run the `orchestrate` holds ([adjust.py:15-23,144](../../scripts/plan/adjust.py) [VERIFIED]) and never invokes `gate_dispatch`; automating it (Alternative B) would strip the ADR-0028 composition off every plan after week 1 — the review's finding A. Re-entering `plan_driver.drive` reuses the ONE definition of the disposition composition + fail-closed loop ([plan_driver.py:263-273](../../scripts/plan/plan_driver.py) [VERIFIED]), so the evolved plan is gated identically. On **the trend reaching re-gen**, re-entry re-summarizes the store, and `recent-trend-direction` is a `router.summarize`-derived field over the `biomarker::` feed ([router.py:464,753-758](../../scripts/plan/router.py) [VERIFIED]) — so the wearable trend arrives for free, where a `plan-track::`-keyed per-domain adjust would no-op (`has_tracking=False`). On **the de-id boundary**, the trigger carries only tokens the care-agent gate already de-identified by data class ([care_chat.py:284](../../scripts/serve/care_chat.py) [VERIFIED]); the raw text stays in the care lane. On **buildability**, re-entry REUSES the built driver + reconciler + gate with no new safety mechanism and no new store stream — the loop is a trigger + a debounce + a driver call, the cheapest and safest first move (the review's re-sequencing, finding I). The cost the decision accepts permanently is the per-trigger expense of the full composition (below).

### Consequences

**Positive:**
- Every evolved plan passes the SAME safety composition as the first: re-entering `plan_driver.drive` runs the composed `gate_dispatch` (judge + safety lenses + fail-closed `safety_passed is True`) AND the five `orchestrate` cross-domain holds — verifiable because the loop calls the driver, not `adjust.py` (0 `adjust.adjust_plan` call sites on the loop path). Finding A is closed by construction.
- The wearable/lab trend reaches the re-generation with no new plumbing: re-summarizing re-derives `recent-trend-direction` from `biomarker::` ([router.py:753-758](../../scripts/plan/router.py) [VERIFIED]), so the "money shot" (finding B) fires without bridging `biomarker::` to `plan-track::`.
- The de-id boundary holds on the trigger: raw free-text routes through the care agent's gated capture into derived tokens ([care_chat.py:284](../../scripts/serve/care_chat.py) [VERIFIED]) — the specialist dispatch never sees raw operator text (finding C), and the automated loop adds NO new raw-egress surface.
- The debounce makes evolution honest: absent a sustained signal in the window the loop holds and prompts rather than churning a new plan on a single noisy reading.

**Negative:**
- **Re-running the full front door every trigger is materially more expensive than a per-domain patch.** Each re-gen is the whole A′ dispatch aggregate on the subscription session — every plan-domain author + the quality judge + each safety lens + any reauthor/adjudicator round, MULTIPLIED by the bounded revise iterations ([plan_driver.py:242-307](../../scripts/plan/plan_driver.py) [VERIFIED]) — where `adjust.py` would have re-authored ONE domain with no gate. The debounce (minimum interval + sustained-signal window) is the bound on trigger frequency, but the per-trigger cost is real and permanent (1+ year): the loop trades per-patch cheapness for safety-composition parity. If the subscription rate/concurrency ceiling is reached at the loop's cadence, the cost trade-off that favored re-running the composition is re-opened (see Review triggers).
- Regenerating ALL domains on each trigger day-keys a NEW dated plan for domains that did not change; the prior dated plan + tracking stay immutable history, but the operator sees a full re-plan, not a targeted delta (the coherence cost of not fanning out per-domain).
- **Whole-plan re-gen on every trigger densifies the day-keyed `plan::` history that [ADR-0038](ADR-0038-plan-time-horizons.md)'s date-range horizon query reads.** Several same-window automated re-gens produce several dated `plan::<domain>` sets inside one week, so ADR-0038's "this week's block / month arc" range query can face multiple same-window dated plans and must select among them (latest-in-window wins, mirroring the today-by-date-equality rule). The debounce (minimum re-gen interval) is the mitigation — it bounds re-gen FREQUENCY so the dated history is not flooded — but the interaction is real: ADR-0038's horizon consumer must resolve same-window selection (see Open Questions and ADR-0038's window-boundary OQ), not be left to guess which of N same-window dated plans is "the block."

**Neutral:**
- `adjust.py` is retained unchanged as the manual operator one-off; the automated loop neither calls nor deletes it. The per-domain path and the automated whole-plan path coexist, keyed by who invokes them (operator vs trigger).

### Alternatives Considered

#### Alternative A: Re-run the front door (Chosen)
The automated loop re-enters `plan_driver.drive` / `run_orchestrated` → composed `gate_dispatch` + `orchestrate.generate_plans`, producing a new dated plan for all domains, mechanically debounced, with the trigger carrying only de-identified/derived tokens.
- **Supporting evidence:** The only option that keeps the ADR-0028 safety composition + the five cross-domain holds on EVERY evolved plan (finding A) while re-deriving the `biomarker::` trend for free (finding B) and holding the de-id boundary on the trigger (finding C), reusing the built driver with no new safety mechanism or store stream ([plan_driver.py:144-307](../../scripts/plan/plan_driver.py) [VERIFIED]).
- **Trade-offs:** The full-composition per-trigger cost (Negative-1) and a whole-plan re-gen rather than a targeted per-domain delta (Negative-2). Accepted because safety-composition parity dominates a health-plan loop.
- **When this becomes the right choice:** For V1, when the initial plan is generated through the A′ front door's fail-closed composition and every evolved plan must carry the same floor.

#### Alternative B: Automate the per-domain `adjust.py`
Wire the trigger to fan out `adjust.py` per changed domain — cheap, targeted, reusing the built ADJUST leg directly.
- **Supporting evidence:** The smallest change and the cheapest per trigger (one domain, no gate); `adjust.py` already records through `generate_plan`'s per-domain safety floor (the four `assemble` filters + the workout clearance gate + the domain veto, [adjust.py:57-64](../../scripts/plan/adjust.py) [VERIFIED]).
- **Trade-offs:** It is the review's finding-A safety REGRESSION. `adjust.py`'s own docstring states it "does not re-run" the `orchestrate` cross-domain holds ([adjust.py:15-23](../../scripts/plan/adjust.py) [VERIFIED]) and it never calls `gate_dispatch` — so every automated plan after the first would skip the ADR-0028 judge + safety lenses + fail-closed loop + liaison adjudication AND the energy-bounce / additive-AE / conflict / Rx-BPMH holds. A plan that develops an additive-AE stack or an Rx-BPMH match on the NEW data would record un-reconciled. It ALSO fails finding B: `adjust.py` keys on `resolve_plan_progress`'s `plan-track::` read ([adjust.py:122](../../scripts/plan/adjust.py) [VERIFIED]), so a wearable trend in `biomarker::` yields `has_tracking=False` and the adjust no-ops. And it fails finding C: `adjust.py` is a recorder with no de-identification of a free-text trigger.
- **When this becomes the right choice:** Never for the AUTOMATED loop; `adjust.py` is correct only as the MANUAL operator one-off it already is (where the operator, not a trigger, has accepted the per-domain boundary).

#### Alternative C: A bespoke incremental patcher
Build a new component that diffs the new data against the standing plan and emits a targeted patch, with its own lightweight safety check.
- **Supporting evidence:** Would give the targeted per-domain delta the whole-plan re-gen lacks (Negative-2), potentially cheaper than the full composition.
- **Trade-offs:** A new safety check is a SECOND copy of the disposition composition + fail-closed loop — the exact forked-safety-loop failure class ADR-0026/0028 rejected (the no-fork crown jewel, [plan_driver.py:1-9](../../scripts/plan/plan_driver.py) [VERIFIED]); it can drift from the one definition. A patch that renders operator-tailored content is ALSO a new named raw-egress surface requiring its own ADR carve-out (the discipline ADR-0025/[ADR-0037](ADR-0037-care-agent-plan-tailoring.md) enforce). It is more new surface, not less, and re-introduces the drift the project's mandates forbid.
- **When this becomes the right choice:** If a future measurement shows the whole-plan re-gen cost is untenable AND a patcher could be proven to route through the SAME single-definition composition (not a second copy) — a spec-stage question, not a V1 design.

#### Alternative D: Keep `adjust.py` manual; no automated loop
Leave re-planning as the operator-invoked `adjust.py` one-off and add no automated trigger.
- **Supporting evidence:** Zero new code; the built legs stay exactly as-is, and the operator retains full control over when a re-plan happens.
- **Trade-offs:** The closed loop never closes on its own — `design/vision.md`'s "dynamically re-adjusts as new data arrives" stays unrealized, and a wearable/lab trend or a stated symptom never re-plans without the operator manually driving each domain. It leaves the core dynamic-adjustment capability unbuilt.
- **When this becomes the right choice:** If V1 explicitly scopes out automated evolution and ships only operator-driven re-planning — a scope the design (VETTED, ready for ADR) has not chosen.

### Validation Approach

**Confirmation criteria:**
- **Loop fires through the SERVE entry point via the full-composition front door (BUILD PREREQUISITE):** ingest a wearable/free-text signal at the REAL serve route and assert a NEW dated plan is produced for the current date. Expected: exactly one new `plan::<domain>` dated set appears for the trigger date, generated via `run_orchestrated` / `plan_driver.drive` (the A′ front door running the composed `gate_dispatch` + reauthor/adjudicator hooks), NOT via `adjust.py` AND NOT via the screened-only `_do_generate_plan` route (which calls `orchestrate.generate_plans` with no hook, [server.py:677-678](../../scripts/serve/server.py) [VERIFIED]). This makes the build prerequisite testable — the serve trigger must reach the driver front door — and drives the assembled system, not a hand-configured driver (catching the unwired state, PF-S63-02).
- **Tailoring fires on an automated re-gen (no care-chat turn):** fire the loop via the cadence / `biomarker::` trigger with NO operator care-chat turn and assert the [ADR-0037](ADR-0037-care-agent-plan-tailoring.md) tailoring pass runs after `record_plan` (the maintained artifact is re-emitted tailored). Fire twice for the same (plan, date) and assert idempotence (no duplicate/stale tailored artifact); inject a tailoring error and assert fail-safe to the un-tailored plan. Threshold: tailoring runs on the automated path exactly as on an operator press, idempotent per (plan, date) — if it silently never runs on an automated re-gen, the personalization pass regressed; halt.
- **Full-composition parity on re-gen:** the re-gen runs the composed `gate_dispatch` and the five `orchestrate` holds. Expected: a domain HELD by a cross-domain check on the new data (e.g. an additive-AE stack, an Rx-BPMH match) STAYS HELD on the re-gen — clearance is re-derived per re-gen ([plan_driver.py:272-273](../../scripts/plan/plan_driver.py); [orchestrate.py:576-631](../../scripts/plan/orchestrate.py) [VERIFIED]), NOT inherited from the prior plan.
- **No `adjust.py` on the loop path (no-fork/no-bypass):** grep the loop's driver path for a call to `adjust.adjust_plan`. Expected: **0 call sites** — the automated loop re-enters the driver, it never per-domain-adjusts (the finding-A guard).

**Falsification criteria:**
- **Mutation control (behind → de-load AND on-track → NOT de-load):** seed a `biomarker::` series trending BEHIND goal, fire the loop, assert the re-gen expresses a de-load (or hold) branch; then seed a series ON-TRACK/AHEAD, fire the loop, assert the re-gen does NOT de-load. Threshold: the two branches DIFFER (a falsifiable pair). If both produce the same disposition, the loop is not reading the trend — halt and re-verify the `recent-trend-direction` re-derivation ([router.py:753-758](../../scripts/plan/router.py) [VERIFIED]).
- **Debounce (single reading → NO re-gen):** fire the trigger with a SINGLE new `biomarker::` reading inside the window; assert NO new dated plan is produced. Then supply a SUSTAINED signal over the window; assert a new dated plan IS produced. Threshold: single reading → 0 re-gen; sustained week → 1 re-gen. A re-gen on a single reading means the sustained-signal window is not enforced — halt and restore the threshold/window function (a deterministic unit test of that function pins it).
- **Absent-data (no signal → no re-gen):** fire the cadence trigger with NO new signal in the window; assert the loop HOLDS + prompts and produces 0 new plans. Threshold: 0 re-gen on nothing (never a re-gen on absent data).
- **Crown-jewel non-egress (wire-scan):** seed a synthetic raw identifier (a legal name) + raw meds into the raw intake, fire the loop through the free-text trigger, dump the specialist-lane dispatch payload, and assert the raw tokens are ABSENT. Threshold: **0 raw-PII hits** in any specialist dispatch payload (finding C). If ≥1 hit, a raw token reached the specialist lane past the care-agent gate — halt and harden the capture/summarize boundary.
- **Held-domain persistence:** a domain held on the prior plan, with no clearing signal on the new data, STAYS held on the re-gen (the fail-closed floor is re-applied, not inherited). If a re-gen silently un-holds a still-unsafe domain, the composition was bypassed — halt.
- **Time horizon:** run the mutation-control, debounce, absent-data, non-egress, and held-domain probes at the first build of the loop, at the S94-class operator-present LIVE test, at every release thereafter, and before the July-2026 physician-visit deliverable ships.

**Review triggers:**
- The subscription session's rate/concurrency ceiling blocks the per-trigger aggregate dispatch volume (author + judge + per-lens + reauthor + adjudicator × revise iterations, per re-gen × trigger cadence) — re-open the whole-plan-re-gen-vs-incremental-patch trade-off (Alternative C) against the cost.
- A change to the debounce policy (minimum interval or sustained-signal window) is proposed — re-verify single-reading → NO re-gen and sustained → re-gen stay a falsifiable pair.
- The care-agent gated-capture boundary (`persist_capture` field routing) changes — re-run the non-egress wire-scan against the new derivation.
