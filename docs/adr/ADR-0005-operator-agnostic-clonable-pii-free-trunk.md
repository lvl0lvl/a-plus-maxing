## ADR-0005: Operator-Agnostic Clonable Distribution — PII-Free Trunk + Gitignored Local Operator Data

> **Y-Statement:** In the context of a single-operator health system whose scaffolds today hold only placeholder prompts but become PII the moment an operator fills them, and which friends must be able to clone into their own independent instances, facing the tension that the repository must both ship a fully fillable engine and carry zero operator PII in version-control history that — once committed — cannot be cleanly removed, we decided to adopt an operator-agnostic clonable distribution where the trunk ships engine + scaffolds + templates + ingestion + governance with the scaffolds tracked only in their empty placeholder state, every filled-scaffold value and the entire time-series store excluded from version control, and a fresh clone is a fully independent local instance with no cross-operator data path, to achieve a clonable PII-free starting point that initializes by local fill, accepting that gitignored operator data carries no version-control backup or history and that the scaffold-vs-value split plus the content-scan guarantee impose a discipline burden with no enforcement mechanism yet built.

### Context

The system reasons over and renders the operator's private health data, yet it must ship as a repository friends can clone into their own independent single-operator instances with none of the first operator's data present ([PRD-v1, Goal 3 L38-43, US-8 L103-109](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]; [PRD-v1, Finding 9 L367](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). The personalization data layer is fully scaffolded, not greenfield: `operator-profile.md`, `goals.md`, and `current-state.md` exist as `status: scaffold` pages holding placeholder prompts and no real values — filling them is precisely what creates the PII surface ([PRD-v1, Finding 2 L353](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). The current `.gitignore` tracks the whole vault except two raw dropzones (`vault/dna/raw/`, `vault/labs/raw/`), so those scaffold pages are committed today in their empty placeholder state ([.gitignore](../../.gitignore) [VERIFIED]).

Two forces pull against each other. The repository must remain operator-agnostic — zero committed operator PII, including stored readings, in any tracked file, verifiable by a content scan returning zero hits on a fresh clone ([PRD-v1, NFR-2 L231-236](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). Against that, the trunk must still ship a complete, fillable engine: scaffolds, templates, ingestion, generation, and governance, all present and operable in their initial un-filled state so a new operator can initialize from them ([PRD-v1, FR-6 L163-169](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). A repository that committed nothing could not be cloned into a working instance; a repository that committed filled scaffolds would leak the first operator's PII. The scaffold-vs-value split is the seam where these forces meet: the empty scaffold is shippable, the filled value is not.

The decision binds more than the authoring operator. The data subject needs assurance their DNA and labs never enter version-control history, and a second operator cloning the repository must inherit none of the first's PII and have no path to read another clone's data ([PRD-v1, NFR-3 L238-243, NG-3 L279](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). The constraint is permanent in a way the model-routing boundary is not: once operator PII lands in a tracked commit, git history cannot be cleanly scrubbed, so the exclusion must hold at every commit, not be fixed after a leak ([PRD-v1, NFR-2 L235-236](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]; [ADR-0001, Validation Approach](ADR-0001-pii-trust-boundary-no-train-routing.md) [VERIFIED]). And the distribution is bounded out of the multi-tenant North Star: no shared hosting, accounts, or cross-operator aggregation — that scale is architected-for, not built ([PRD-v1, NG-1 L277, NG-3 L279](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]; [vision.md, boundary table L40-48](../../design/vision.md) [VERIFIED]).

### Decision

Adopt operator-agnostic clonable distribution. The trunk ships engine, scaffolds, templates, ingestion routine, and governance with zero committed operator PII; the scaffolds are tracked only in their empty placeholder (`status: scaffold`) state, and every filled-scaffold value together with the entire time-series store is excluded from version control. A fresh clone is a fully independent local single-operator instance with no cross-operator data path; a new operator goes from `git clone` to a fillable, PII-free instance by initializing the store and filling the scaffolds locally. The operator-agnostic property is guaranteed by a content scan of all tracked files for operator PII tokens returning zero hits on a fresh clone.

[AMENDED 2026-06-06 (bead `qwj` + `ko5`, Walter-adjudicated option iii)]: the content scan is scoped by what each check detects. **"PII-free trunk" means the tracked trunk is free of operator HEALTH DATA** — lab and biomarker VALUES, DNA/genotype data, symptom/intake answers, the time-series store (`vault/store/`), and any filled-scaffold OPERATOR VALUE (a scaffold mutated out of its empty `status: scaffold` state into real readings). It does NOT mean the trunk is free of the operator's NAME: the operator's name in governance, session, and design prose (session notes, `HANDOFF.md`, `INVARIANTS.md`, ADRs/design docs, methodology, decision-maker fields) is accepted authorship PROVENANCE for this single-operator project, not a trunk-PII violation. Accordingly the content scan applies its operator-IDENTITY check (the gitignored `vault/meta/operator-identity.txt` name tokens) ONLY to the data-bearing / gitignored-dropzone paths where health data lives, while its operator-AGNOSTIC checks — the structural `{item, timepoint, value}` store-line patterns and the generic `@gmail.com` contact pattern — run trunk-wide over every tracked file. The "zero hits on a fresh clone" guarantee is unchanged: a fresh clone carries no `vault/meta/operator-identity.txt`, so the identity check is empty there regardless of scope, and the agnostic patterns find no health data in a fresh trunk. Reason: the unscoped trunk-wide identity scan flagged ~984 hits across ~154 tracked files that are the operator's NAME in governance/session/design prose — accepted provenance, not committed health data — while the genuine health-data dropzones (`vault/store/`, `vault/dna/raw/`, `vault/labs/raw/`) are already gitignored. Scoping the identity check to data-bearing paths (agnostic structural + contact checks staying trunk-wide) makes the boundary catch real committed health-data leaks without blocking the project's own authorship prose, and ratifies that the PII-free vault knowledge-graph IS the tracked trunk (resolves `ko5`). The PRD-v1 NFR-2 measurement method (which lists "name" first among operator-PII tokens) is reinterpreted accordingly: "name" is the operator-IDENTITY check (scoped to data-bearing paths), not dropped; aligning the PRD NFR-2 wording to this scoping is tracked as a follow-up bead.

[AMENDED 2026-06-09 (bead `rnm`, filled-scaffold-value path pin)]: the **filled-scaffold-value path is pinned to `vault/scaffold/filled/`** — the single upstream convention the downstream consumers key off, no longer the representative/unpinned glob ADR-0005-T1 chose (resolving the recipe UPSTREAM FLAG / QA-Security Fix 4 / MED-1). A scaffold mutated out of its empty `status: scaffold` state into a real operator value is written under `vault/scaffold/filled/`; that one prefix is (a) excluded by the repo-root `.gitignore` (`vault/scaffold/filled/`), (b) the `SCAFFOLD_PREFIX` literal `block-pii-commit.sh` condition-1 denies a staged commit on, and (c) the path the `block-pii-commit` test fixtures + the Wave 3→4 checkpoint plant under. The three agree on this one literal and move together if it ever changes. There is no competing producer today — `scripts/clone/init_instance.py` surfaces the empty scaffold pages and writes no filled value (the local fill step is the LM-04-gated forward path) — so this pins a forward convention, it does not re-point an existing producer. Distinct and out of scope here: the scaffold-PAGE directory (`SCAFFOLD_DIR = vault/scaffold`, where the `status: scaffold` template pages live) and its `_surface_scaffolds` status-filter + single-imported-constant hardening (PR#66 F5/F8) are a separate scaffold-page-convention follow-up, not this value-path pin.

### Rationale

The distribution model was evaluated against three rejected alternatives across four criteria the PRD and vision make load-bearing: PII-free-trunk guarantee, clonability into an independent instance, history-leak reversibility (whether a mistake can be undone), and V1-fit (the no-hosting, no-accounts, single-operator constraint).

On the **PII-free-trunk guarantee**, the chosen model is the only one that can satisfy NFR-2's "zero committed operator PII" while still shipping a working engine, because it splits the tracked scaffold (empty, shippable) from the gitignored value (filled, PII): the scan passes precisely because no filled value or store file is ever a candidate for commit ([PRD-v1, NFR-2 L235-236, Finding 2 L353](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). Committing everything (Alternative A) fails this outright, and per-operator forks (Alternative B) leak across history. On **clonability**, a fresh clone ships the scaffolds, templates, ingestion, and generation in their un-filled state, so the new operator initializes the store and fills the scaffolds locally and the instance produces a plan and a dashboard from their own inputs alone — directly satisfying FR-6 and US-8 ([PRD-v1, FR-6 L167-169, US-8 L106-109](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). On **history-leak reversibility**, gitignoring operator data is the only model that keeps the leak from happening in the first place: because committed history cannot be cleanly scrubbed, the exclusion must be preventive, and a model that admits PII into history (A) or into per-operator branches (B) cannot undo a leak after the fact ([PRD-v1, NFR-2 L236](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]; [ADR-0001, Validation Approach](ADR-0001-pii-trust-boundary-no-train-routing.md) [VERIFIED]). On **V1-fit**, the chosen model needs no hosting, no accounts, and no shared datastore — every clone is an independent local instance with zero cross-clone data paths — fitting the single-operator constraint that the multi-tenant-hosted alternative (C) violates by definition ([PRD-v1, NFR-3 L242-243, NG-1 L277](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).

This decision is one of the two halves of the PII posture: it keeps PII out of version-control history, complementing ADR-0001, which keeps PII off the model ([ADR-0001, Related Decisions D6 row](ADR-0001-pii-trust-boundary-no-train-routing.md) [VERIFIED]; [dag.md §6 D1-D6 complement](.pipeline/dag.md) [VERIFIED]). Long-term, the gitignore boundary is set by where the store's files live, which ADR-0002 fixes at `vault/store/`; the segregation policy must exclude that directory and every filled-scaffold value, and that boundary moves only if the store substrate moves ([ADR-0002, Decision + Related Decisions D6 row](ADR-0002-local-first-time-series-store.md) [VERIFIED]). Reversing the operator-agnostic posture later (e.g., into the multi-tenant North Star) is a deliberate North-Star transition with its own trust model (HIPAA + BAA + per-tenant isolation), not a V1 regression ([vision.md, boundary table L45-46](../../design/vision.md) [VERIFIED]).

### Consequences

**Positive:**
- A content scan of all tracked files for operator PII tokens returns 0 hits on a fresh clone, and 0 operator-data files (filled scaffolds + the store) are tracked — satisfying NFR-2's operator-agnostic criteria directly from the gitignore boundary ([PRD-v1, NFR-2 L235-236](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- A fresh clone ships scaffolds, templates, ingestion, and generation in their un-filled state, so a new operator can initialize the store and begin entering local data, and the instance produces a plan and dashboard from their own inputs alone — the FR-6 / US-8 clone-init path (the absorbed former D8) ([PRD-v1, FR-6 L167-169, US-8 L106-109](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- Each clone is an independent local instance with 0 cross-clone data paths: no clone can read another's store, because there is no shared service or hosted surface to read through ([PRD-v1, NFR-3 L242-243](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).

**Negative:**
- The gitignored store and filled scaffolds carry no version-control backup or history: an operator who loses the working copy loses their data unless they keep a separate local backup, because the repository deliberately does not track it (a constraint inherited from the ADR-0002 store-gitignore decision and extended here to all filled values) ([ADR-0002, Consequences Negative](ADR-0002-local-first-time-series-store.md) [VERIFIED]; [PRD-v1, NFR-2 L236](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- The tracked-scaffold / gitignored-value split is a standing discipline burden: the same file family exists in two states (empty scaffold = tracked, filled scaffold = not), so the operator must keep filled values out of the tracked scaffold pages and never commit a filled scaffold — there is no substrate-level mechanism stopping a filled scaffold from being staged ([PRD-v1, Finding 2 L353, NFR-2 L236](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- The content-scan guarantee needs an enforcement mechanism that does not yet exist: NFR-2's "0 hits on a fresh clone" is currently a manual claim, and the `.gitignore` does not yet exclude the `vault/store/` directory ADR-0002 specified — so over a 1+ year horizon the operator-agnostic property depends on either a pre-commit scan or a gitignore update being built, and until then a single mis-commit of a filled scaffold lands PII in history that cannot be cleanly removed ([.gitignore](../../.gitignore) [VERIFIED]; [ADR-0002, Decision](ADR-0002-local-first-time-series-store.md) [VERIFIED]; [PRD-v1, NFR-2 L235](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). [AMENDED 2026-06-09 (rnm): the enforcement has since been built — `.gitignore` now excludes both `vault/store/` and `vault/scaffold/filled/`, and `block-pii-commit.sh` condition-1 denies a staged filled-scaffold value (built; registration deferred to bead `3lv`). The full Consequences / OQ-1 / Y-statement freshness reconciliation to the built enforcement is tracked separately.] [AMENDED 2026-06-10 (3lv, PR #84): `block-pii-commit.sh` is now REGISTERED in `.claude/settings.json` and a `pre-push-pii-scan.sh` backstop covers the non-agent push path (bead dv3); the contact-detection model moved from the generic trunk-wide `@gmail.com` pattern (this ADR's v1.3 Decision) to an operator-specific gitignored config (superseding the S37 "keep the protective default" sub-decision, on the S43 14-false-hit evidence). The full v1.5 revision row + Decision/Validation reconciliation is folded into the am4 freshness sweep.]

**Neutral:**
- The gitignore policy grows from two raw dropzones to also exclude `vault/store/` and the filled-scaffold values, extending the existing pattern rather than introducing a new mechanism ([.gitignore](../../.gitignore) [VERIFIED]).
- "Empty scaffold vs. filled value" becomes a shared contract the scaffold pages, the ingestion side, and the clone-init step must all agree on — the same page family is tracked when empty and excluded when filled.

### Alternatives Considered

#### Alternative A: Commit everything, including filled operator data
Track the full vault — scaffolds, the store, and all filled operator values — so a clone carries a complete working instance with the operator's real data already present.
- **Supporting evidence:** Operationally simplest: one tracked tree, no scaffold-vs-value split, no separate backup discipline, and the operator's own data is versioned and recoverable from history like any other file.
- **Trade-offs:** It commits operator PII to version-control history, which cannot be cleanly removed once landed, directly violating NFR-2's zero-committed-PII guarantee ([PRD-v1, NFR-2 L235-236](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). A clone would carry the first operator's labs, DNA, and readings, so it is not operator-agnostic and not clonable PII-free, failing Goal 3 and US-8 entirely ([PRD-v1, Goal 3 L41-42, US-8 L109](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). Rejected because it fails the load-bearing privacy force outright.
- **When this becomes the right choice:** Only for a strictly single-author repository that is never cloned by anyone else and where the operator's own data being versioned is a feature, not a leak — i.e. if the clonability and operator-agnostic requirements were dropped.

#### Alternative B: Per-operator forks or branches holding each operator's data
Give each operator a fork or long-lived branch of the shared engine that carries their own filled data, so the engine is shared but each operator's data lives on their own ref.
- **Supporting evidence:** The engine stays a single shared codebase that all operators pull improvements from, and each operator's data is isolated to their own ref rather than mixed into one tree — superficially closer to per-operator isolation than Alternative A.
- **Trade-offs:** Each operator's filled data still lands in committed history on their ref, so there is no clean PII-free trunk to scan — the operator-agnostic guarantee (NFR-2, zero PII in any tracked file) cannot hold when every operator ref carries PII ([PRD-v1, NFR-2 L235-236](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). Merging engine updates across PII-bearing branches risks cross-operator leakage in history, and the model fragments the shared engine across refs — the exact branch-write-fragmentation failure the project already retired for governance reasons ([2026-06-02-single-trunk-reconciliation.md, Context/problem](../../vault/decisions/2026-06-02-single-trunk-reconciliation.md) [VERIFIED]). Rejected because it admits PII into history and fragments the trunk.
- **When this becomes the right choice:** If operators needed to share and merge each other's *data* (not just the engine) and the PII-free-trunk requirement were dropped — which NG-3 forbids for V1 ([PRD-v1, NG-3 L279](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).

#### Alternative C: Multi-tenant hosted store with per-tenant isolation
Run a hosted backend that stores every operator's data under per-tenant isolation, so the repository ships only engine code and operator data lives in the service.
- **Supporting evidence:** This is the genuine North-Star architecture: a hosted surface with per-account login and per-tenant data isolation is exactly what the GP product requires, and it keeps operator data out of the git repository entirely by moving it to a service ([vision.md, boundary table L44-45](../../design/vision.md) [VERIFIED]).
- **Trade-offs:** It is explicitly out of V1 scope — NG-1 forbids multi-tenancy, shared hosting, accounts, and login, and the vision marks the hosted surface as "architected-for, not built" for V1 ([PRD-v1, NG-1 L277](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]; [vision.md, boundary table L46, L48](../../design/vision.md) [VERIFIED]). It also requires the regulated-PHI trust model (HIPAA + BAA) NG-2 defers, and it breaks NFR-3's independent-local-instance / zero-network-dependency property ([PRD-v1, NFR-3 L242](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). Rejected as a scope violation that solves a V1 problem with the North-Star's machinery, not as an inferior design.
- **When this becomes the right choice:** At the North-Star transition to a multi-tenant GP product handling many patients' regulated PHI, where per-tenant isolation and a hosted store become mandatory ([vision.md, boundary table L45-46](../../design/vision.md) [VERIFIED]).

### Validation Approach

**Confirmation criteria:**
- A content scan of all tracked files for operator PII tokens (name, biomarker values, stored readings, protocol entries) returns 0 hits on a fresh clone — verified by running the scan over a fresh `git clone` (expected: 0 hits) ([PRD-v1, NFR-2 AC L235, Goal 3 measurement L42](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). [AMENDED 2026-06-06 (qwj): per the amended Decision, the `name` token is the operator-IDENTITY check, scoped to data-bearing paths; on a fresh clone it is empty regardless, so the 0-hit-on-fresh-clone criterion is unchanged. The trunk-wide checks are the agnostic structural + `@gmail.com` contact patterns.]
- 0 operator-data files (filled scaffolds + the store) are tracked — verified by checking that `git ls-files` lists no filled-scaffold value and no `vault/store/` file (expected: scaffolds present only in `status: scaffold` placeholder state) ([PRD-v1, NFR-2 AC L236](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- On a fresh clone, the scaffolds are present and fillable in their empty state and a new operator initializes the store and begins entering local data excluded from version control — verified by running the clone-init path and confirming the entered data lands outside `git status` (expected: new data untracked) ([PRD-v1, FR-6 AC L167-168, US-8 AC L106-107](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- The fresh-clone instance generates a plan and a dashboard from the new operator's inputs alone, with 0 cross-clone data paths — verified by producing both artifacts on the clone with no other operator's data present (expected: artifacts render from local inputs only) ([PRD-v1, FR-6 AC L169, US-8 AC L108, NFR-3 AC L243](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).

**Falsification criteria:**
- If ≥1 operator-PII value is found in a tracked file on a fresh-clone scan (≥1 hit), the operator-agnostic guarantee has failed; because git history cannot be cleanly scrubbed, treat as a release-blocking incident and scrub-or-rewrite before any release ([PRD-v1, NFR-2 L235-236](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). [AMENDED 2026-06-06 (qwj): "operator-PII value" = operator HEALTH DATA (the data classes in the amended Decision), NOT the operator NAME in governance/session/design prose, which is accepted provenance and is NOT a falsification.]
- If a clone is observed depending on another operator's data to produce a plan or dashboard (≥1 cross-clone read), the independent-local-instance guarantee has failed; halt and remove the cross-clone path before release ([PRD-v1, NFR-3 L242-243](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- If a filled-scaffold value (or any store file) appears staged or committed (≥1 tracked filled value), the scaffold-vs-value split has failed; block the commit and restore the gitignore boundary before the working tree is pushed ([PRD-v1, NFR-2 L236, Finding 2 L353](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- Time horizon: run all checks at every release and before the July-2026 physician-visit deliverable ships, and whenever a second operator first clones the repository ([PRD-v1, Goal 3 attribution L43](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).

**Review triggers:**
- The content-scan enforcement mechanism (OQ-1) lands — re-validate that the operator-agnostic property is mechanically, not manually, enforced.
- The `vault/store/` exclusion is added to `.gitignore` per ADR-0002 — re-confirm the store is gitignored on a fresh clone.
- A second operator clones the repository — re-run the tracked-file PII scan and the independent-instance checks on the fresh clone.
- The North-Star transition is initiated — the operator-agnostic / PII-free-trunk posture is superseded by the multi-tenant hosted store with per-tenant isolation ([vision.md, boundary table L45-46](../../design/vision.md) [VERIFIED]).
