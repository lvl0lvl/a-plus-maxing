## ADR-0007: Lab-Loop / Biomarker-Matrix / Watch-Out / Projection Data-Flow Placement

> **Y-Statement:** In the context of four closed-loop sub-features (the lab loop, the watch-out check-in, the biomarker matrix, and projections) that the PRD spreads across FR-9/FR-10/FR-11 and that must carry state across timepoints, facing the tension between persisting that state and recomputing derived views at render time, we decided to place the lab loop and watch-out answers as store schemas (recommended-but-undrawn panels stored "pending" not as results; answers stored over time as inputs to the next generation), and the biomarker matrix and projections as render-time views over stored timepoints — with the projection guardrail (≥3 stored timepoints, "naive projection" labeling) a render-time contract — to achieve a clean persistence-vs-presentation split that lets ADR-0002 own state and ADR-0004 own rendering, accepting that early items show trend-only with no projection, that the split adds a contract surface, and that the matrix/projection views are the ones most likely to strain ADR-0004's <500KB budget.

### Context

V1 runs four closed-loop sub-features the PRD spreads across three functional requirements: a lab loop that recommends bloodwork and accepts entered results (FR-9), a watch-out check-in questionnaire that tracks symptoms and contraindications bloodwork cannot catch (FR-10, Should), and projections rendered for tracked items (FR-11, Should) — feeding a biomarker matrix that cross-references each biomarker across the timepoints it was measured ([PRD-v1, FR-9 L188-194, FR-10 L196-202, FR-11 L204-212](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]; [US-4 L71-77, US-5 L79-85, US-6 L87-93](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). Each must hold state honestly: a recommended panel the operator has not yet had drawn must show as pending, never as a result ([PRD-v1, FR-9 AC L194](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]); an unanswered check-in must show as not-yet-answered, not a clear result ([PRD-v1, US-5 AC L85](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]); an item with one stored timepoint must show "no prior" rather than a fabricated trend ([PRD-v1, US-2 AC L60](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).

These features pull in two architectural directions across more than one consumer. The lab loop's pending panels and the watch-out answers must survive across generations — a panel recommended this cycle is still pending next cycle, and answers are "stored over time and available to the next plan generation" ([PRD-v1, FR-10 AC L201, US-5 AC L83](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]) — which argues for persisted state. The biomarker matrix and projections, in contrast, are read-only cross-references and extrapolations *over* stored timepoints: the operator and the time-constrained physician read them, but nothing downstream consumes a stored matrix or a stored projection, which argues for recomputing them at render time rather than persisting a second copy of state. The data model is point-in-time today — `current-state.md` holds latest values plus a `trend` field, and biomarker pages hold a single current value — so there is no accumulated series the matrix or projection can read until the store accumulates one ([current-state.md, L28-34 latest-values, L53-57 Subjective rolling-daily](../../vault/meta/current-state.md) [VERIFIED]; [PRD-v1, Finding 5 L359](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). The watch-out questionnaire is grounded in that same `current-state.md` Subjective (daily, last-7-day rolling) section — Energy/Recovery/Mood/Pain — the un-measurable, periodically-asked check-in it formalizes ([current-state.md, L53-57](../../vault/meta/current-state.md) [VERIFIED]; [PRD-v1, Finding 12 L373](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).

Three further forces constrain the placement. First, the projection method is a fixed input, not a choice this ADR makes: V1 projections use simple trend extrapolation (a linear fit or trailing moving-average slope), render with a widening uncertainty band, carry the label "naive projection from recent trend — not a clinical forecast" with method and datapoint count, mark key dates/milestones on the time axis, and require ≥3 stored timepoints before any projection renders ([PRD-v1, FR-11 AC L209-212, OQ-4 resolved L345, A-4 L307](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). Second, lab values and symptom answers are operator PII, so ADR-0001's no-egress boundary forces them onto the local-store side and off any model-egress projection or analysis step ([ADR-0001, Decision](ADR-0001-pii-trust-boundary-no-train-routing.md) [VERIFIED]; [PRD-v1, NFR-1 AC L227](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). Third, the matrix and projection views are the most asset-heavy artifacts (many series, inline SVG charts over multiple timepoints) and press directly against ADR-0004's single-file <500KB budget — a tension recorded on both sides ([ADR-0004, Open Questions OQ-1](ADR-0004-on-demand-single-file-artifact-generation.md) [VERIFIED]; [dag.md §7 T1](.pipeline/dag.md) [VERIFIED]). The lab loop is also fed from the plan: the assembled plan recommends the bloodwork the loop ingests, and watch-out answers plus post-visit physician feedback (FR-12, Could) feed the *next* plan generation ([PRD-v1, FR-9 AC L192, FR-10 AC L202, FR-12 L214-219](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]; [ADR-0006, Decision](ADR-0006-multi-domain-plan-assembly-via-roster.md) [VERIFIED]; [landmarks.md, LM-01 trigger windows L43-45](../../vault/meta/landmarks.md) [VERIFIED]).

### Decision

Place the lab loop and the watch-out check-in as **store schemas** in the local time-series store (ADR-0002): a recommended-but-undrawn panel is stored as "pending" (never as a result), and watch-out questionnaire answers are stored over time as inputs to the next generation, with the pending / not-yet-answered / no-prior states carried as store state. Place operator-entered post-visit physician feedback (FR-12) as the same kind of **store schema** — recorded after a visit and stored over time as an input available to the next plan/report generation, the same store-schema pattern as the watch-out answers ([PRD-v1, FR-12 L214-219](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). Place the **biomarker matrix and projections as render-time views** (ADR-0004) computed over stored timepoints — the matrix cross-references each biomarker across the timepoints it was measured, and a projection is a render-time extrapolation over stored timepoints, never a stored or precomputed series. The projection guardrail is a render-time contract: a projection renders only when an item has ≥3 stored timepoints, carries the "naive projection from recent trend — not a clinical forecast" label with its method and datapoint count and a widening uncertainty band, and marks key dates/milestones on the time axis. The projection math itself (simple trend extrapolation) is a fixed input, not re-decided here.

[AMENDED 2026-06-12 (#110 review, beads `y0h0` + `i2yw`)]: the five-element projection-honesty contract (fixed label, method, datapoint count, widening uncertainty band, key dates/milestones) is scoped to the `render_views` matrix/projection DETAIL surface. The dashboard trend card realizes the same render-time projection as the operator-signed SHORT-FORM caption — `→ {value} by {date} · naive projection` — gated on the same ≥3-stored-timepoint floor, single-sourced via the shared `biomarker_meta` projection seam (`projection_values` + `PROJECTION_MIN_TIMEPOINTS`), and rendered on the dashboard only (the physician report carries no extrapolation, S52 operator direction). See the `vault/design/dashboard-v1-visual-spec.md` zone-4 amendment (2026-06-12) and PR #110.

### Rationale

The placement was evaluated against three alternatives — render-only views with no persisted loop state (A), projections as a stored/precomputed series (B), and one monolithic tracking module that does not separate persistence from presentation (C) — across three criteria the PRD and the DAG make load-bearing: state-persistence fidelity, single-source-of-truth (no duplicated/stale state), and clean ownership boundaries with ADR-0002 (store) and ADR-0004 (render).

On **state-persistence fidelity**, the lab loop and watch-out answers must carry state across generations that no render-time recomputation can reconstruct: a pending panel is pending *because* a prior generation recommended it and no result has been entered since, and watch-out answers must be "stored over time and available to the next plan generation" ([PRD-v1, FR-10 AC L201](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). This is irreducible store state — option A (render-only) cannot hold it, because there is nothing to recompute a pending-panel or a six-week-old symptom answer *from* at render time. On **single-source-of-truth**, the matrix and projection are pure functions of the stored timepoints: the matrix is a cross-reference and the projection a deterministic extrapolation, so persisting either (option B) creates a second copy of state that goes stale the moment a new reading lands, and the store's append-only keyed history is already the authoritative series ([ADR-0002, Decision](ADR-0002-local-first-time-series-store.md) [VERIFIED]). Recomputing on render keeps one source of truth and matches ADR-0004's existing rule that a generated artifact is a snapshot of the store at generation time ([ADR-0004, Consequences Negative](ADR-0004-on-demand-single-file-artifact-generation.md) [VERIFIED]). On **clean ownership boundaries**, the store-schema-vs-render-view split is exactly what lets ADR-0002 own persistence (the pending/answer/no-prior state lives in its keyed files) and ADR-0004 own presentation (the matrix and projection are template views rendered through the component set); option C's monolith conflates the two and would force one decision to own both, which the DAG explicitly separates into D2 and D4 ([dag.md §3 D7→D2 depends-on, D7→D4 depends-on](.pipeline/dag.md) [VERIFIED]).

The accepted trade-off is that the ≥3-timepoint guardrail means projections are absent early: until an item accumulates three stored timepoints it renders trend-only with no projection, so most items in the first July-visit render will show no projection at all. We accept this because a projection on one or two points is a fabricated forecast the guardrail exists to forbid ([PRD-v1, FR-11 AC L212](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]) — honest absence is the physician-ready behavior. Long-term, the same store-schema and render-view split carries forward unchanged into the North-Star hosted surface: the loop state migrates as store data and the matrix/projection views become live queries over the same series, so the placement is the V1 realization of a data-flow the product phase extends, not a dead end.

### Consequences

**Positive:**
- A recommended-but-undrawn panel renders as "pending" and an unanswered check-in renders as "not yet answered" — verifiable because both are explicit store states, not absent-or-result, satisfying the FR-9 and US-5 honesty criteria ([PRD-v1, FR-9 AC L194, US-5 AC L85](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- The biomarker matrix shows a biomarker measured at ≥2 timepoints side by side, recomputed from the store's keyed history with no second stored copy to go stale ([PRD-v1, FR-9 AC L193, US-4 AC L76](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]; [ADR-0002, Decision](ADR-0002-local-first-time-series-store.md) [VERIFIED]).
- Watch-out answers persist as store schema and feed the next generation, so a contraindication or adverse-symptom answer is surfaced in the next generated plan or report rather than lost between cycles ([PRD-v1, FR-10 AC L201-202](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- The store-schema-vs-render-view split keeps one source of truth: lab values and symptom answers stay local-only (PII off any model-egress path per ADR-0001), and the matrix/projection are recomputed locally with 0 external requests ([ADR-0001, Decision](ADR-0001-pii-trust-boundary-no-train-routing.md) [VERIFIED]; [PRD-v1, NFR-1 AC L227](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).

**Negative:**
- The ≥3-timepoint guardrail means projections are absent early: until an item has 3 stored timepoints it renders trend-only with no projection, so most items in the first July-visit render show no projection at all — a standing 1+ year constraint that only relaxes as the store accumulates timepoints across review cycles ([PRD-v1, FR-11 AC L212, Goal 2 measurement L35](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- The store-schema-vs-render-view split adds a contract surface: the pending / not-yet-answered / no-prior states must be defined in the store schema (ADR-0002) *and* read correctly by the render views (ADR-0004), so a state the store records but the view misreads (or vice-versa) is a defect that spans two decisions rather than one ([dag.md §3 D7→D2, D7→D4 depends-on](.pipeline/dag.md) [VERIFIED]).
- The matrix and projection views are the artifacts most likely to strain ADR-0004's <500KB self-contained budget — many series and inline SVG charts over multiple timepoints — the D4↔D7 tension, unmeasured pre-build because no realistic multi-biomarker dataset exists yet ([ADR-0004, Open Questions OQ-1](ADR-0004-on-demand-single-file-artifact-generation.md) [VERIFIED]; [dag.md §7 T1](.pipeline/dag.md) [VERIFIED]; render-size-vs-ceiling headroom [UNVERIFIED] — no realistic render measured pre-build).
- A watch-out answer signaling a contraindication must be carried into the *next* generation, not the current one, so an adverse symptom answered just after a generation is not surfaced until the following render — an inherent latency of the store-feeds-next-generation loop, not a render bug ([PRD-v1, FR-10 AC L202, US-5 AC L84](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).

**Neutral:**
- The lab loop's input edge depends on the plan: the bloodwork the loop ingests is recommended by the assembled plan (ADR-0006), and watch-out answers plus post-visit physician feedback (FR-12, Could) feed the next plan generation — the loop is bidirectional with plan assembly, not a standalone tracker ([PRD-v1, FR-9 AC L192, FR-12 L214-219](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]; [ADR-0006, Decision](ADR-0006-multi-domain-plan-assembly-via-roster.md) [VERIFIED]).
- The projection math (linear fit / trailing moving-average slope) is a fixed input resolved in the PRD, not re-decided here; this ADR places projections as render-time views but does not choose or change the extrapolation method ([PRD-v1, OQ-4 resolved L345, FR-11 AC L209](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).

### Alternatives Considered

#### Alternative A: Lab loop + watch-out as render-only views with no persisted state
Compute the lab-loop pending list and the watch-out answer history on the fly at render time from whatever is in the store, persisting no dedicated loop state.
- **Supporting evidence:** Fewer schemas to define and maintain — if everything is a render-time view, there is one less store contract surface, and the matrix and projection are render-time views anyway, so a uniform "everything renders from the store" model is conceptually simpler.
- **Trade-offs:** A pending panel and a stored symptom answer are not derivable from other store data — a panel is pending *because* it was recommended and not yet drawn, and an answer-over-time is the raw input itself, so there is nothing to recompute them from at render time. FR-9 (pending, not result) and FR-10 (answers stored over time, available to the next generation) require persisted state across timepoints, which a render-only model cannot hold ([PRD-v1, FR-9 AC L194, FR-10 AC L201](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]). Rejected because the loops' core state is irreducible store state, not a derived view.
- **When this becomes the right choice:** If the lab loop and watch-out were reduced to read-only displays of data persisted by some other mechanism (e.g., panels and answers were entered directly as ordinary readings with no pending/answered lifecycle), the loop state would collapse into ordinary store readings and a render-only view would suffice — a reduction V1's pending-and-answered-over-time lifecycle does not make.

#### Alternative B: Projections as a stored / precomputed series in the store
Compute each projection when a new reading lands and persist the projected series (and the matrix cross-reference) in the store alongside the raw readings.
- **Supporting evidence:** Precomputing means the render path does no math — it reads a ready projection and draws it, which keeps the render fast and could ease the per-file render-size work if the projection were stored pre-shaped. Caching a deterministic computation is a conventional optimization.
- **Trade-offs:** A projection is a pure deterministic function of the stored timepoints, so a persisted projection is a second copy of state that goes stale the instant a new reading lands — every import would have to recompute and rewrite it, and any missed rewrite silently ships a stale forecast. The store's append-only keyed history is already the single source of truth, and ADR-0004 already treats a rendered artifact as a snapshot recomputed at generation time, so recompute-on-render is consistent with the existing delivery model ([ADR-0002, Decision](ADR-0002-local-first-time-series-store.md) [VERIFIED]; [ADR-0004, Consequences Negative](ADR-0004-on-demand-single-file-artifact-generation.md) [VERIFIED]). Rejected because storing a derived view duplicates state and adds a staleness failure mode the render-time computation has no way to incur.
- **When this becomes the right choice:** If projection computation became expensive enough that recomputing it at every render dominated generation time (e.g., a heavy modeled forecast over thousands of points), caching the result would be worth the staleness-management cost — but V1's projection is a simple linear-fit / moving-average-slope extrapolation that is cheap to recompute, so the optimization buys nothing ([PRD-v1, FR-11 AC L209, OQ-4 L345](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).

#### Alternative C: One monolithic tracking module that does not separate persistence from presentation
Build a single "tracking" component that owns the store schemas, the matrix, the projections, and the watch-out loop together, with no architectural seam between persisted state and rendered view.
- **Supporting evidence:** A single module keeps all four sub-features in one place, so a developer changing the lab loop sees the matrix and projection in the same component — fewer cross-component handoffs and a single owner for the whole tracking surface.
- **Trade-offs:** It conflates the store schema with the render view, which is precisely the seam ADR-0002 and ADR-0004 are decided to own separately: the store owns the keyed pending/answer/no-prior state, and generation owns the template views over that state. Merging them would put PII-bearing persisted state and render logic in one component, blurring the ADR-0001 no-egress boundary that must hold on the store side and the ADR-0004 render-side budget that must hold on the view side ([ADR-0002, Decision](ADR-0002-local-first-time-series-store.md) [VERIFIED]; [ADR-0004, Decision](ADR-0004-on-demand-single-file-artifact-generation.md) [VERIFIED]; [dag.md §3 D7→D2, D7→D4](.pipeline/dag.md) [VERIFIED]). Rejected because the clean persistence-vs-presentation split is what makes D2 and D4 independently ownable; the monolith would re-entangle them.
- **When this becomes the right choice:** If the store and the generation path were themselves one component (no ADR-0002/ADR-0004 separation), a monolithic tracking module would be the consistent shape — but the DAG fixes D2 and D4 as distinct decisions D7 depends on, so the monolith would contradict the architecture above it.

### Validation Approach

**Confirmation criteria:**
- A panel recommended by the plan but not yet drawn renders as "pending" and never as a result — verified by recommending a panel, generating an artifact before any result is entered, and inspecting the matrix/lab view (expected: panel shown pending, 0 fabricated result) ([PRD-v1, FR-9 AC L194](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- A biomarker with ≥2 stored timepoints shows its values side by side in the matrix — verified by storing 2 timepoints for one biomarker and inspecting the matrix (expected: both timepoints cross-referenced, not latest-only) ([PRD-v1, FR-9 AC L193, US-4 AC L76](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- A projection renders only when an item has ≥3 stored timepoints and carries the "naive projection from recent trend — not a clinical forecast" label with its method, datapoint count, a widening uncertainty band, and key dates/milestones on the time axis — verified by storing 3 timepoints and inspecting the projection (expected: label + method + count + band + milestones all present); and an item with exactly 2 timepoints renders trend-only with no projection ([PRD-v1, FR-11 AC L210-212](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- An unanswered check-in renders as "not yet answered" and an answered watch-out is available to the next generation — verified by leaving a check-in unanswered (expected: not-yet-answered, not a result) and by answering one and confirming it is read on the next generation ([PRD-v1, US-5 AC L83, L85, FR-10 AC L201](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- A recorded post-visit physician input from a visit appears as an input available to the next plan/report generation — verified by recording physician feedback in the store after a visit and confirming it is read on the next generation (expected: the recorded input is carried forward, not dropped) ([PRD-v1, FR-12 L214-219](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).

**Falsification criteria:**
- If a recommended-but-undrawn panel renders as a result (a value or in-range/alert state) rather than pending, the pending-not-result contract has failed — block the render and fix the store-state-to-view mapping before release ([PRD-v1, FR-9 AC L194](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- If a projection renders for an item with fewer than 3 stored timepoints, the guardrail has been breached — halt and restore the ≥3-timepoint gate before any artifact ships, since a <3-point projection is the fabricated forecast the guardrail forbids ([PRD-v1, FR-11 AC L212](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- If a watch-out answer signaling a contraindication is dropped from the next generation (recorded in the store but absent from the next plan/report), the answers-feed-next-generation contract has failed — block release and fix the store-read path ([PRD-v1, FR-10 AC L202, US-5 AC L84](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- If a recorded physician input is dropped between generation cycles (stored after a visit but 0 carried forward into the next plan/report generation), the FR-12 capture-and-carry contract has failed — block release and fix the store-read path that feeds the next generation ([PRD-v1, FR-12 L214-219](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- If any lab value or symptom answer reaches the model (appears in a model-bound dispatch) or leaves the local machine during matrix/projection render, the ADR-0001 PII boundary has been violated — halt and reroute onto the local-store/no-egress path ([ADR-0001, Decision](ADR-0001-pii-trust-boundary-no-train-routing.md) [VERIFIED]; [PRD-v1, NFR-1 AC L227](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- Time horizon: run all checks at the first lab-loop/matrix/projection render (before the July-2026 visit, when the first such artifact ships per LM-01) and at every release thereafter ([landmarks.md, LM-01 trigger windows L43-45](../../vault/meta/landmarks.md) [VERIFIED]).

**Review triggers:**
- The first real biomarker-matrix or multi-timepoint projection render is measured against the <500KB ceiling (the D4↔D7 tension, OQ-1) — re-evaluate the placement if a guardrail-passing render cannot fit the budget.
- The projection method changes from simple trend extrapolation to a modeled/clinical forecast — re-open this placement, since a modeled forecast may warrant precomputation (Alternative B) and its own validation.
- The watch-out question-generation source is fixed (see Open Questions) — re-validate that the questionnaire surfaces the watch-outs the operator's active protocols imply ([PRD-v1, FR-10 AC L200](../prd/PRD-v1-local-first-health-tracking-planning.md) [VERIFIED]).
- The store substrate (ADR-0002) or the generation model (ADR-0004) changes — re-validate that the store-schema and render-view halves still map cleanly across the changed boundary.
