## ADR-0046: Scale Specialist Dispatch to the Full Roster with a Progressive-Activation Gate

> **Y-Statement:** In the context of the live plan-generation runtime, where specialist dispatch iterates a CLOSED four-domain tuple — `plan_schema.PLAN_DOMAINS = ("workout", "nutrition", "supplements", "peptides")` hard-wired at every entry point (the `/generate-plan` front door and the evolution loop both iterate it), each domain mapped 1:1 to a role by `plan_driver._ROLE_OF_DOMAIN` and to a translator by `generate_plan._PLAN_TRANSLATORS`, so exactly four of the design roster's specialists are dispatched regardless of operator ([plan_schema.py:49](../../scripts/store/plan_schema.py); [plan_driver.py:117-122](../../scripts/plan/plan_driver.py); [generate_plan.py:286-291](../../scripts/plan/generate_plan.py); [server.py:784](../../scripts/serve/server.py) [VERIFIED]) — while the design roster is 15 domain specialists · 2 safety/escalation · 1 orchestrator whose plan is meant to be PROGRESSIVE, not a fixed N-card template ([../../design/specialist-plan-contracts.md:12,293](../../design/specialist-plan-contracts.md) [VERIFIED]) — facing the tension that a closed four-tuple both UNDER-serves an operator whose goals or data span more domains AND would, if simply widened to all 15+, issue a metered model call and render a card for every domain including the empty-state ones (a dermatology, gut, or lymphatic domain for an operator who has surfaced nothing there), we decided to SCALE the dispatch runtime to the 15+-specialist roster behind a PROGRESSIVE-ACTIVATION gate — a domain is dispatched and rendered ONLY when the operator has a stated goal or data in it, so the active-domain set is computed from the operator's surface at plan time rather than read from the closed `PLAN_DOMAINS` 4-tuple — to achieve a plan that matches each operator's actual surface area while paying dispatch cost only for active domains, accepting that dispatch fan-out cost, latency, and spend now scale with the active-domain count (a MODERATE, reversible dispatch-runtime change), that the activation gate adds a new goal/data-presence decision surface that can mis-fire in either direction, and that the scale-up couples HARD to ADR-0041 (every one of the now-15+ dispatched specialists must emit the uniform DOMAIN PROGRAM shape).

### Context

The live plan-generation runtime dispatches a CLOSED, hard-wired set of four plan domains. `plan_schema.PLAN_DOMAINS = ("workout", "nutrition", "supplements", "peptides")` is the closed plan-domain set — its own comment attributes it to ADR-0010 D1 — with a three-member tracked subset ([plan_schema.py:48-50](../../scripts/store/plan_schema.py) [VERIFIED]). Each of the four domains is mapped 1:1 to a dispatch role by `plan_driver._ROLE_OF_DOMAIN` (`workout→personal-trainer`, `nutrition→nutritionist`, `supplements→supplement-specialist`, `peptides→peptide-specialist`) ([plan_driver.py:117-122](../../scripts/plan/plan_driver.py) [VERIFIED]) and to a plan translator by `generate_plan._PLAN_TRANSLATORS` on the same four keys ([generate_plan.py:286-291](../../scripts/plan/generate_plan.py) [VERIFIED]). The dispatch runtime is domain-count-driven: `plan_orchestrator._dispatch_domains` iterates `for domain in domains` and issues one specialist call per domain via `_dispatch_prompt(_ROLE_OF_DOMAIN[domain], …)` ([plan_orchestrator.py:358-383](../../scripts/plan/plan_orchestrator.py), the loop at :379 and the role lookup at :381 [VERIFIED]) — so the count of specialists dispatched equals the size of the domain set it is handed.

That set is the closed four-tuple at every production entry point. The in-app `/generate-plan` front door iterates `for domain in plan_schema.PLAN_DOMAINS` to issue an author call per domain ([server.py:784,804](../../scripts/serve/server.py) [VERIFIED]); the automated evolution loop's module likewise takes `PLAN_DOMAINS` as its default specialist set (in its name-space disjointness check) and iterates the same tuple in its plan-date resolution ([plan_loop.py:77,407](../../scripts/serve/plan_loop.py) [VERIFIED]), while the loop's re-gen dispatch itself rides the shared `_dispatch_domains` seam over that set ([plan_orchestrator.py:358-383](../../scripts/plan/plan_orchestrator.py) [VERIFIED]). Today's plan is therefore a fixed four-domain artifact regardless of who the operator is — four dispatched specialists, four rendered domains.

The design substrate specifies a far larger roster: 15 domain specialists · 2 safety/escalation (medical-liaison, medical-safety-reviewer) · the care assistant (orchestrator) — 18 agents in all, of which the medical-safety-reviewer is a pre-deployment gate rather than a runtime plan contributor and the care assistant is the orchestrator, and two of the domain specialists (genetics, labs) are cross-cutting INPUT layers that feed every domain rather than emit their own card ([../../design/specialist-plan-contracts.md:12,365,389,437,456](../../design/specialist-plan-contracts.md) [VERIFIED]). Today's wiring covers four of these plan-authoring domain specialists — a four-of-roster subset.

Two forces pull against simply widening the tuple, and they pull on different stakeholders. The operator surface is uneven: for any given operator, some domains carry a stated goal or tracked data and others are empty-state — the design's own note marks a dermatology, gut, or lymphatic domain as "largely empty-state" for an operator who has surfaced no goal or data there, states that "the domain card renders only when the operator surfaces a goal or data," and that "the comprehensive plan is progressive: domains activate as needed, they don't all emit a rich card for everyone" ([../../design/specialist-plan-contracts.md:293,303,325,346](../../design/specialist-plan-contracts.md) [VERIFIED]). Against that operator-facing force, dispatch is not free: each specialist call is a metered model dispatch over the de-identified summary, charged before the call is issued ([plan_orchestrator.py:363-382](../../scripts/plan/plan_orchestrator.py) [VERIFIED]) — so widening the fixed set to all 15+ domains would issue a model call and render a card for every domain including the empty-state ones (an operational cost and a low-signal-noise concern), while keeping the fixed four under-serves an operator whose goals or data span more than four domains (a plan gap for the data subject). The maintainer's cost is a third force: the four-domain set is hard-wired across three registries (`PLAN_DOMAINS`, `_ROLE_OF_DOMAIN`, `_PLAN_TRANSLATORS`) and iterated as a constant at each entry point, so both widening it and making the active set depend on operator data touch every one of those sites.

Because this changes the dispatch-runtime topology — how many specialists are dispatched, and what determines the active set — and it constrains the orchestrator and the plan model that consume that set, it is an architecture decision, not an implementation detail.

### Decision

**Scale the specialist-dispatch runtime from the four hard-wired domains to the full 15+-specialist roster, gated by PROGRESSIVE ACTIVATION: a domain is dispatched and rendered ONLY when the operator has a stated goal or data in it. The active-domain set is computed from the operator's surface at plan time, not read from the closed `PLAN_DOMAINS` 4-tuple — the plan is not a fixed N-card template.**

The decision fixes three things and leaves their realization to spec/build:

1. **The roster scales through the existing dispatch seam.** The dispatch registries (`PLAN_DOMAINS` / `_ROLE_OF_DOMAIN` / `_PLAN_TRANSLATORS`, [plan_schema.py:49](../../scripts/store/plan_schema.py); [plan_driver.py:117-122](../../scripts/plan/plan_driver.py); [generate_plan.py:286-291](../../scripts/plan/generate_plan.py) [VERIFIED]) grow from the four wired domains to the design roster's plan-authoring domain specialists, and each added specialist is dispatched by the SAME `_dispatch_domains` seam that dispatches the four today ([plan_orchestrator.py:358-383](../../scripts/plan/plan_orchestrator.py) [VERIFIED]). The per-domain dispatch mechanism is unchanged; only the roster size and the source of the active set change.

2. **Activation is data-driven, not a constant.** The active-domain set is computed at plan time from the operator's surface — a stated goal or data present in the domain — replacing the constant iteration over `PLAN_DOMAINS` at each entry point ([server.py:784](../../scripts/serve/server.py); [plan_loop.py:77,407](../../scripts/serve/plan_loop.py) [VERIFIED]). A domain with neither a goal nor data is not dispatched and renders no personalized card — it is empty-state, per the design's progressive-activation rule ([../../design/specialist-plan-contracts.md:293](../../design/specialist-plan-contracts.md) [VERIFIED]).

3. **Each dispatched specialist emits the uniform DOMAIN PROGRAM (ADR-0041).** The scale-up dispatches the 15+ specialists into ADR-0041's uniform seven-field output schema. The activation gate decides WHICH specialists are dispatched; ADR-0041 decides WHAT each emits ([ADR-0041, Decision](ADR-0041-uniform-specialist-domain-program-schema.md) [VERIFIED]).

**Reversibility: MODERATE.** This is a dispatch-runtime and activation-gate change — the three registries grow and the active-set source moves from a constant tuple to a computed set — not a stored-record migration; no plan-record shape changes. It couples to the HARD ADR-0041 (each dispatched specialist must emit the DOMAIN PROGRAM). The decision does NOT fix the activation signal's exact definition, whether the gate sits at dispatch or at render, or the precise card-emitting-vs-input roster partition — those are spec/build questions (Open Questions), bounded by the data-driven-activation rule.

### Rationale

The three options were weighed across four criteria the Context makes load-bearing — **operator-surface fit** (does the plan match the operator's actual domains, neither capped nor padded?), **dispatch cost control** (what does an empty-state domain cost per plan?), **roster scalability** (what does adding the Nth specialist cost?), and **coupling to the uniform schema** (do the dispatched outputs land in one reconcilable shape?) — against dispatching all 15+ every time (Alternative A) and keeping the fixed four with manually-added domains (Alternative B).

On **operator-surface fit**, only the data-driven gate matches the plan to the operator. The fixed four (Alternative B's starting point) caps every operator at four domains even when goals or data exist elsewhere — a plan gap the design's larger roster exists to close. Dispatch-all (Alternative A) reaches every domain but pads the plan with empty-state cards for domains the operator never surfaced; the design explicitly rejects that shape, requiring a card to render "only when the operator surfaces a goal or data" ([../../design/specialist-plan-contracts.md:293](../../design/specialist-plan-contracts.md) [VERIFIED]). Progressive activation is the only option that both reaches the full roster AND renders exactly the operator's active domains.

On **dispatch cost control**, the difference is measurable per plan. Each dispatched specialist is a metered model call charged before issue ([plan_orchestrator.py:363-382](../../scripts/plan/plan_orchestrator.py) [VERIFIED]). Dispatch-all issues a model call for every roster domain on every plan — up to the full 15+ per plan, independent of how many the operator actually uses. The gate issues calls only for the active set, so a narrow-surface operator pays for a handful, not the whole roster; progressive activation is precisely the cost control that makes a 15+-domain roster affordable. The fixed four pays for four but buys the plan gap above.

On **roster scalability**, the gate turns adding a specialist into a roster-registry entry rather than a new hard-coded edit at every entry point. Today `PLAN_DOMAINS` is iterated as a constant at the front door and the loop ([server.py:784](../../scripts/serve/server.py); [plan_loop.py:407](../../scripts/serve/plan_loop.py) [VERIFIED]); once the active set is computed data-driven, a new specialist is one registry row and it activates for operators who have data in it — no new per-domain call-site edit. Alternative B (manual add) keeps the constant-iteration pattern, so each new domain is a hard-coded edit at N sites and the curated set cannot track a given operator's real surface.

On **coupling to the uniform schema**, all three options dispatch specialists whose outputs the orchestrator must reconcile, and ADR-0041 makes that shape uniform; the gate does not change what a dispatched specialist emits, only which are dispatched — so the scale-up is clean precisely because it rides ADR-0041's single output contract rather than multiplying per-domain output shapes ([ADR-0041, Decision](ADR-0041-uniform-specialist-domain-program-schema.md) [VERIFIED]). The cost the decision accepts is real and named (Consequences-Negative): dispatch fan-out now scales with the active-domain count, the activation gate is a new decision surface that can mis-fire, and the scale-up is not usable until ADR-0041's schema and the specialist profiles exist. That cost is accepted because matching the plan to each operator's surface while paying only for active domains is exactly the property the fixed four cannot provide and dispatch-all provides only at full-roster cost with empty-state noise.

### Consequences

**Positive:**
- The plan matches the operator's actual surface area: an operator with goals or data across many domains gets a genuinely multi-domain plan (today capped at four), and an operator with a narrow surface is not shown empty cards for domains they never surfaced — the progressive-plan property the design requires ([../../design/specialist-plan-contracts.md:293](../../design/specialist-plan-contracts.md) [VERIFIED]).
- Dispatch spend is bounded to active domains: no metered model call is issued for an empty-state domain, so a 15+-domain roster costs, per plan, only the operator's active subset rather than the full roster ([plan_orchestrator.py:363-382](../../scripts/plan/plan_orchestrator.py) [VERIFIED]).
- Empty-state is honest: an inactive domain either does not render or emits the design's "nothing operator-specific" goal-agnostic reference — never a fabricated personalized card ([../../design/specialist-plan-contracts.md:303,325,346](../../design/specialist-plan-contracts.md) [VERIFIED]).
- Adding a specialist becomes a roster-registry entry that activates on operator data, not a new hard-coded 4-tuple edit iterated at each entry point.

**Negative:**
- **Dispatch fan-out cost, latency, and spend scale with the active-domain count (the MODERATE cost).** Today each plan issues four metered specialist calls; a broad-surface operator can now activate many more, each a charged model dispatch ([plan_orchestrator.py:363-382](../../scripts/plan/plan_orchestrator.py) [VERIFIED]). Progressive activation caps this at the active set rather than the full roster, but both the per-plan ceiling and the expected per-plan cost rise above four, and plan latency grows with the number of concurrent dispatches.
- **The activation gate is a new decision surface that can mis-fire in either direction.** "Is this domain active?" becomes a runtime judgment over goal/data presence that did not exist when the set was a fixed tuple. A false negative silently drops a domain the operator cares about (a plan gap); a false positive dispatches and renders an empty-state domain (wasted spend plus low-signal noise). The correctness of the plan's domain coverage now depends on that judgment being right.
- **Couples HARD to ADR-0041.** Each of the now-15+ dispatched specialists MUST emit the uniform DOMAIN PROGRAM; the scale-up is not usably shipped until ADR-0041's schema and the specialist profiles exist, and scaling the dispatch runtime multiplies the blast radius of any DOMAIN PROGRAM contract change from four consumers to the full active roster ([ADR-0041, Decision](ADR-0041-uniform-specialist-domain-program-schema.md) [VERIFIED]).
- **Roster growth trips an existing threshold (a 6+-month, cross-ADR constraint).** Growing `PLAN_DOMAINS` beyond four is an ADR-0010 review trigger, and it turns ADR-0040's `LARGE_CHANGE_THRESHOLD_DOMAINS = 3` majority-of-four into a minority on the wider universe — ADR-0040 OQ-2 must re-decide that threshold as a fraction before the loop runs against the scaled set ([ADR-0040, Decision §6 / OQ-2](ADR-0040-large-change-hold-until-confirm.md) [VERIFIED]).

**Neutral:**
- The per-domain dispatch mechanism is unchanged: `_dispatch_domains` already iterates whatever `domains` set it is handed and looks up `_ROLE_OF_DOMAIN[domain]` ([plan_orchestrator.py:358-383](../../scripts/plan/plan_orchestrator.py) [VERIFIED]); the change is the SIZE and the SOURCE of that set (a computed active set vs the closed 4-tuple), not the dispatch shape.
- The three registries keep their shape — maps and a tuple — just larger, and, for the active set, filtered by activation. The tracked subset (`TRACKED_DOMAINS`, [plan_schema.py:50](../../scripts/store/plan_schema.py) [VERIFIED]) reshapes analogously if a scaled domain is tracked.

### Alternatives Considered

#### Alternative A: Dispatch all 15+ specialists on every plan (no activation gate)
Widen the four-tuple to the full roster and dispatch every domain specialist for every operator, every plan — the plan is a fixed N-card template of the whole roster.
- **Supporting evidence:** Simplest control flow — no activation judgment, no false-negative risk, and it reaches every domain, so nothing the operator cares about is ever missed. It is the smallest change to the existing constant-iteration pattern (swap a bigger tuple into the same `for domain in …` loops, [server.py:784](../../scripts/serve/server.py) [VERIFIED]).
- **Trade-offs:** REJECTED — it issues a metered model call for every roster domain on every plan (up to 15+ charged dispatches, [plan_orchestrator.py:363-382](../../scripts/plan/plan_orchestrator.py) [VERIFIED]) regardless of how many the operator uses, and it renders a card for every domain including the empty-state ones, which the design explicitly forbids ("the domain card renders only when the operator surfaces a goal or data," [../../design/specialist-plan-contracts.md:293](../../design/specialist-plan-contracts.md) [VERIFIED]). The result is high per-plan cost and low-signal noise (empty-state cards) for every operator.
- **When this becomes the right choice:** If every operator had goals or data in every domain (so no domain is ever empty-state), or if dispatch were free and empty cards were harmless — neither holds here.

#### Alternative B: Keep the fixed four and manually add domains as demand appears
Leave the closed set as a curated tuple; when a new domain is wanted, a maintainer adds it to the three registries by hand, for all operators.
- **Supporting evidence:** Zero new activation machinery; the active set stays a small, reviewed constant, so cost and behavior are predictable and there is no goal/data-presence judgment to get wrong. It is the current pattern extended incrementally.
- **Trade-offs:** REJECTED — it does not scale and is not data-driven. Each new domain is a hard-coded edit to `PLAN_DOMAINS` / `_ROLE_OF_DOMAIN` / `_PLAN_TRANSLATORS` iterated as a constant at every entry point ([plan_schema.py:49](../../scripts/store/plan_schema.py); [plan_driver.py:117-122](../../scripts/plan/plan_driver.py); [generate_plan.py:286-291](../../scripts/plan/generate_plan.py) [VERIFIED]), and a manually-curated set cannot track a given operator's real surface — it either under-serves (misses a domain the operator has data in) or bloats (carries domains no operator uses). The whole point is that the active set follows the operator's data, not a maintainer's edit.
- **When this becomes the right choice:** If the domain set were genuinely static and small forever with no roster growth — the design's 15+-domain roster is the direct counter-evidence.

#### Dissent: Gate activation on an explicit per-domain operator opt-in, not on inferred goal/data presence
**Source:** The activation-signal design space (this ADR's OQ-1) — a purist holds that inferring "the operator has a goal or data here" is error-prone (the false-negative/false-positive surface in Consequences-Negative), and that a domain should activate only when the operator explicitly opts in via a settings toggle, making activation precise and operator-controlled rather than inferred.
**Conditions under which this becomes the right choice:** If goal/data-presence inference proves too noisy in practice — measurably high false-negative (dropped active domains) or false-positive (empty-state dispatches) rates at the OQ-1 signal definition — an explicit per-domain opt-in trades operator burden for precision and would dominate. It loses when the inference is reliable, because an explicit toggle per domain imposes setup burden and defeats the "the plan follows your data automatically" property; the two are also combinable (infer by default, allow an explicit override), which is the likely spec resolution.

### Validation Approach

**Confirmation criteria:**
- **A domain with an operator goal or data is dispatched AND rendered (executable).** Seed an operator surface carrying a goal or data in a domain D beyond the original four; run the plan front door; assert D's specialist was dispatched (exactly one author call issued for D) AND D's domain card is present in the resulting plan. Threshold: active D → dispatch-count-for-D == 1 AND card-for-D present == True. If D is active but not dispatched, the gate under-activates — halt.
- **The active-domain set is data-driven, not the fixed 4-tuple (executable, the load-bearing probe).** Seed two distinct operator surfaces — one whose active domains are {A, B}, one whose active domains are {A, C, E, G, I} — and assert the dispatched set equals the computed active set for EACH surface, and that the dispatched set is NOT invariant across the two. Threshold: dispatched-set == computed-active-set for each surface AND the two dispatched sets differ. If the dispatched set is the same closed four (or the same constant) regardless of operator surface, the activation gate is unwired and the runtime still reads `PLAN_DOMAINS` — halt.

**Falsification criteria:**
- **An empty-state domain emits a personalized card → fail (deterministic).** Seed an operator with NO goal and NO data in domain D (a dermatology, gut, or lymphatic domain is the design's canonical empty-state example); run the plan; assert D is NOT dispatched and renders no personalized card — at most the design's honest "nothing operator-specific" goal-agnostic reference, never a fabricated personalized card ([../../design/specialist-plan-contracts.md:293,303](../../design/specialist-plan-contracts.md) [VERIFIED]). Threshold: empty-state D → dispatch-for-D == 0 AND personalized-card-for-D == 0. If an empty-state domain emits a personalized card, progressive activation is broken — halt.
- **A domain with data is NOT dispatched → fail (deterministic).** Seed an operator with a goal or data present in domain D; assert D is in the computed active set and IS dispatched. Threshold: data-present D → dispatch-for-D == 1. A missed active domain (a false negative) is a plan gap — halt and repair the activation signal before release.
- **Fan-out is bounded to the active set, never the full roster on a narrow surface (deterministic).** For a narrow-surface operator whose active set is smaller than the roster, assert dispatch-count == |active set| and dispatch-count < |roster|. Threshold: dispatch-count == |active set| ≤ |roster|; if dispatch-count == |roster| for a narrow-surface operator, the gate is bypassed and the cost-control property is unmet ([plan_orchestrator.py:363-382](../../scripts/plan/plan_orchestrator.py) [VERIFIED]) — halt.
- **Time horizon:** run the empty-state-no-card probe, the data-present-dispatch probe, and the fan-out-bound probe at the first roster/activation build, at the operator-present LIVE run (real per-domain spend, OQ-4), at every release thereafter, and before the July-2026 physician-visit deliverable.

**Review triggers:**
- A new specialist domain is added to the roster — verify it is activation-gated (not dispatched for an empty-state operator) and emits the uniform DOMAIN PROGRAM (ADR-0041).
- `PLAN_DOMAINS` grows beyond four — an ADR-0010 review trigger; it also turns ADR-0040's `LARGE_CHANGE_THRESHOLD_DOMAINS = 3` majority-of-four into a minority, so re-decide that threshold as a fraction (ADR-0040 OQ-2) before the loop runs against the scaled set ([ADR-0040, Decision §6 / OQ-2](ADR-0040-large-change-hold-until-confirm.md) [VERIFIED]).
- ADR-0043 (Orchestrator) lands — re-confirm the orchestrator's brief-selection (WHO to brief) and this decision's activation gate (WHICH domains are active) compose without a double-gate or conflict.
- The activation-signal definition changes (what counts as "a goal or data" in a domain, OQ-1) — re-run the false-negative / false-positive probes at the new signal.
- The operator-present LIVE run is scheduled — a real multi-domain dispatch spends model budget per active domain (OQ-4).
