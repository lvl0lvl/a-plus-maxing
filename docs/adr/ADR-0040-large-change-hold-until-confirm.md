## ADR-0040: Large-Change Hold-Until-Confirm via a Bounded Confirmation-Pointer the Resolver Honors

> **Y-Statement:** In the context of the automated plan-evolution loop (ADR-0036), whose front-door re-gen ALREADY records + resolves-as-standing a materially-large swap before any operator sight — the promote inside `run_orchestrated` writes the plan through the ADR-0032-frozen record path and `resolve_plan` resolves that latest-dated reading as standing ([plan_loop.py:194-199](../../scripts/serve/plan_loop.py); [plan_schema.py:462-498](../../scripts/store/plan_schema.py) [VERIFIED]), while T4 shipped only a large-change ADVISORY that its own docstring calls "NOT a hold ... the true hold-until-confirm is the deferred follow-on ADR-0036-T4b" ([confirm.py:96-107](../../scripts/serve/confirm.py) [VERIFIED]) — and where the same promoted set is ALSO tailored + egressed to the raw ADR-0037 maintained artifact by `_post_promote_tailoring` on every promoted re-gen ([plan_loop.py:207-213](../../scripts/serve/plan_loop.py) [VERIFIED]), so a majority-of-domains automated swap silently STANDS then RENDERS with raw personalization before the operator confirms — facing the tension that a pre-record hold would EDIT the byte-frozen record spine the project has held across its EXTEND-NOT-REBUILD era (~15 sessions — the posture ADR-0032 restates, [ADR-0032:26,43](ADR-0032-dna-aware-planning.md) [VERIFIED]) for ZERO safety gain (and would still need durable state to park the unconfirmed plan across the confirm latency), we decided to hold WITHOUT touching the record write: leave `record_plan` byte-frozen, persist a BOUNDED confirmation-pointer that marks a `≥ LARGE_CHANGE_THRESHOLD_DOMAINS` re-gen's `(domain, plan_date)` pending (a new bounded store stream that RELAXES ADR-0038's no-new-store-stream rule, not the open `plan-arc::`-class stream it forbade), teach EVERY direct standing-plan reader (the shared `resolve_plan`/`read_plan` read AND the ADR-0038 horizon `window_block` direct scan) to SKIP an unconfirmed reading so the held re-gen does NOT become standing — today resolves `NO_PLAN_TODAY` (the held domain resolves exactly as a non-re-gen day would; the prior confirmed plan stays in append-only history but is not re-surfaced as "today") until confirm, NOT a walk-back to the earlier-dated prior plan — and GATE `_post_promote_tailoring` so a held domain is neither tailored nor egressed until confirm — an explicit operator act on the `land_confirmed` precedent ([confirm.py:35-93](../../scripts/serve/confirm.py) [VERIFIED]) that flips the pointer and fires the deferred tailoring exactly once — to achieve a fail-closed hold that is safety-EQUIVALENT to a pre-record gate (the safety boundary lives at the resolver + the tailoring seam, not the record write) while the ADR-0032 record path stays byte-unchanged, accepting one bounded new store stream and a recorded-yet-not-standing reading class the resolver must skip on every read.

### Context

The automated plan-evolution loop (ADR-0036) re-enters the front door and produces a NEW dated plan for all domains on every debounced trigger. Its T4 large-change treatment is an ADVISORY, not a hold — and the hold-half was left explicitly open as ADR-0036 OQ-4 ("How does a large re-generation ... surface for operator confirmation vs swap silently", [ADR-0036, OQ-4](ADR-0036-automated-plan-evolution-loop.md) [VERIFIED]). Three live-tree facts make the current behavior a silent-swap-then-render leak, each verified against the source:

- **The large swap is ALREADY the standing plan before the advisory runs.** In `regenerate`, the front-door promote inside `run_orchestrated` records the plan through the ADR-0032-frozen record path FIRST; only then does the change-magnitude check run. The code says so in its own comment: "The new plan is ALREADY the standing plan — the front-door promote inside `run_orchestrated` recorded it before this check runs" ([plan_loop.py:194-199](../../scripts/serve/plan_loop.py) [VERIFIED]). `resolve_plan` then resolves the latest-dated reading as standing by date equality / latest-on-file ([plan_schema.py:462-498](../../scripts/store/plan_schema.py), the reversed-scan + latest-dated resolution at [plan_schema.py:485-498](../../scripts/store/plan_schema.py) [VERIFIED]). So a `≥ LARGE_CHANGE_THRESHOLD_DOMAINS` (=3-of-4, [plan_loop.py:50](../../scripts/serve/plan_loop.py); `PLAN_DOMAINS` is the closed 4-set, [plan_schema.py:49](../../scripts/store/plan_schema.py) [VERIFIED]) swap STANDS the moment it records, with no operator gate.

- **The T4 mechanism is a notice, not a hold — by its own contract.** `confirm.confirm_large_change` "names the changed domains + the rationale so the operator sees that a majority-of-domains swap landed. Nothing here holds, reverts, or persists — the true hold-until-confirm is the deferred follow-on ADR-0036-T4b" ([confirm.py:96-107](../../scripts/serve/confirm.py) [VERIFIED]). THIS ADR is that ADR-0036-T4b (discovery bead `a-plus-maxing-yvrs`).

- **The same swap is ALSO tailored + egressed before any confirm.** After the advisory, `regenerate` calls `_post_promote_tailoring` over the full promoted set ([plan_loop.py:207-213](../../scripts/serve/plan_loop.py) [VERIFIED]); when a `tailor_client` is threaded, that runs the ADR-0037 care-lane tailoring pass, which reads the operator's RAW `_care_profile` detail and renders raw-personalized sections into the gitignored maintained artifact — a named raw-egress carve-out ([ADR-0037, Decision](ADR-0037-care-agent-plan-tailoring.md) [VERIFIED]; [plan_loop.py:295-330](../../scripts/serve/plan_loop.py) [VERIFIED]). So an unconfirmed large swap does not merely stand — it is personalized and egressed to the raw artifact before the operator has seen it.

Three forces constrain the fix:

- **The fail-closed health-plan posture.** A materially-large automated re-gen (a majority of the operator's plan changing on a data trend the operator did not initiate) must NOT silently become the followed plan, and must NOT be raw-tailored/egressed, until the operator confirms. On decline, the PRIOR standing plan must be retained — never the unconfirmed swap left standing.

- **The ADR-0032 frozen record spine (a one-way door).** ADR-0032's EXTEND-NOT-REBUILD posture byte-froze the store (`scripts/store/*`) and the inner plan engine, naming the record path among the surfaces that "stay byte-frozen" ([ADR-0032:26,43](ADR-0032-dna-aware-planning.md) [VERIFIED]); `record_plan` is that path ([plan_schema.py:371-396](../../scripts/store/plan_schema.py) [VERIFIED]). This surface has been held byte-frozen across the project's EXTEND-NOT-REBUILD era (~15 sessions — a freeze predating ADR-0032, which restates the posture). Editing the record write to become conditional is a heavy, hard-to-reverse door.

- **ADR-0038's no-new-store-stream rule.** ADR-0038 decided horizons compose over existing owners with "Zero new store schema" and rejected a new `plan-arc::` stream ([ADR-0038:48,67-70](ADR-0038-plan-time-horizons.md) [VERIFIED]); ADR-0036's OQ-5 reconciled the loop's debounce state to introduce zero new stream by DERIVING it from existing history ([ADR-0036, OQ-5](ADR-0036-automated-plan-evolution-loop.md) [VERIFIED]). Any new persisted state this decision adds must answer to that rule.

The decision the Context forces: prevent an unconfirmed large re-gen from standing AND from being tailored, fail-closed to the prior plan, WITHOUT damaging the byte-frozen record spine and WITHOUT casually multiplying store streams. Because it changes what becomes the standing plan and when raw egress fires — a data-model + safety-boundary change touching the ADR-0032 spine and/or the ADR-0038 store-schema rule (both one-way doors) — it is a decision, not a code comment.

### Decision

**A large automated re-gen (`change_magnitude ≥ LARGE_CHANGE_THRESHOLD_DOMAINS`) is HELD: it is recorded but does NOT resolve as the standing plan and is NOT tailored/egressed until the operator confirms. The hold is a bounded confirmation-POINTER the resolver honors — the ADR-0032 record write stays byte-frozen.**

1. **The record WRITE path is byte-unchanged; the read-path gains an ADDITIVE skip (frozen-spine scope reconciled).** `run_orchestrated`'s front-door promote records the re-gen through `record_plan` → `store.append` exactly as today ([plan_schema.py:371-396](../../scripts/store/plan_schema.py) [VERIFIED]); ADR-0040 edits neither `record_plan`, `store.append`/`keying.py`, nor the inner plan engine — the exact WRITE-path surface ADR-0032's OWN Validation names byte-frozen (`git diff --numstat` = 0 on `scripts/store/keying.py`/`store.append` and `scripts/plan/{orchestrate,pipeline,assemble,generate_plan,adjudicate,adjust,track}.py`, [ADR-0032 Validation](ADR-0032-dna-aware-planning.md) [VERIFIED]). The held plan lives in its normal `plan::<domain>` home, fully in the append-only audit trail. **Honest scope caveat (AR-007):** the read-side functions this decision edits — `resolve_plan`/`read_plan` (§3) — live in `scripts/store/plan_schema.py`, i.e. WITHIN ADR-0032's broad `scripts/store/*` glob but OUTSIDE its Validation-named WRITE surface. The edit is a PROSPECTIVE-ADDITIVE read-path guard (a pointer-aware pre-filter of the readings resolution runs over; the date-equality resolution body itself is byte-unchanged — §3), not a rewrite of a write-path/engine line. So the safety-critical spine (the record write + the inner engine) is genuinely byte-frozen; the read-path skip is the one additive change to a store-module read function, justified as a guard rather than an engine edit — NOT an overclaimed "whole `scripts/store/*` byte-unchanged."

2. **A bounded confirmation-pointer marks the held re-gen (the ADR-0038 relaxation).** On a `≥ threshold` re-gen the loop persists a SMALL bounded confirmation entry keyed by `(domain, plan_date)` carrying a decision token (`pending` → `confirmed` | `declined`) — a pointer/marker, NOT a duplicate of any plan content, progress, or cadence. This is realized PRESUMPTIVELY as a new bounded store stream (OQ-1 may instead site it on the ADR-0010 D2 open-on-extras seam ADR-0038 blesses, [ADR-0038:35](ADR-0038-plan-time-horizons.md) [VERIFIED] — the mechanism is identical either way); on the new-stream realization it RELAXES ADR-0038's no-new-store-stream rule, and it is precisely the opposite of the open, drift-prone `plan-arc::` stream ADR-0038 rejected (which reinvented `goal_schema`/`calendar_schema` ownership, [ADR-0038:67-70](ADR-0038-plan-time-horizons.md) [VERIFIED]): it owns exactly one fact — the confirm decision for a held re-gen — that no existing stream carries and that cannot be DERIVED (unlike the debounce date, ADR-0036 OQ-5).

3. **EVERY direct standing-plan reader SKIPS an unconfirmed reading; the skip yields `NO_PLAN_TODAY`, NOT a resolver walk-back.** The pointer-aware standing-plan read drops any `plan::<domain>` reading whose `(domain, plan_date)` carries a confirmation-pointer entry that is not `confirmed`. On the held re-gen's OWN date, dropping the held reading leaves no reading dated today, so the standing-plan resolution returns **`NO_PLAN_TODAY` (plan `None`)** — the held domain resolves EXACTLY as a non-re-gen day would; the held re-gen does NOT become standing, and the prior confirmed plan stays in append-only history but is NOT re-surfaced as "today." This is deliberately NOT a `resolve_plan` walk-back to the earlier-dated prior plan: the skip is a pointer-aware PRE-FILTER of the readings the resolution runs over — applied CALLER-SIDE (to the readings BEFORE the pure `resolve_plan` call), NOT inside `resolve_plan`'s body, which stays PURE over the readings it receives ([plan_schema.py:462](../../scripts/store/plan_schema.py) [VERIFIED]). So `resolve_plan`'s date-equality body is left byte-unchanged, and `track.resolve_plan_progress`'s `has_plan`/`plan_date` contract (CONTRACTS-TRACK-1: `has_plan` ⇔ a plan dated `on_date`, [track.py:81-122](../../scripts/plan/track.py) [VERIFIED]) and the ADR-0037 tailoring emit-gate (`if resolved["state"] is not None: continue`, [tailoring.py:187-192](../../scripts/plan/tailoring.py) [VERIFIED]) keep their exact meaning. The held reading is ALSO excluded from the `NO_PLAN_TODAY` `plan_date = max(timepoint)` value ([plan_schema.py:493-498](../../scripts/store/plan_schema.py) [VERIFIED]), so the reported "latest on-file date" never leaks the held date.
   **The skip binds the COMPLETE set of DIRECT `plan::<domain>` standing-plan readers, not `resolve_plan` alone** — grep for `plan::` readers pins the bounded set:
   - (a) the shared `resolve_plan` / `read_plan` standing-plan read ([plan_schema.py:462-517](../../scripts/store/plan_schema.py) [VERIFIED]) — the caller-side pre-filter is applied at each standing-plan CALL SITE (which then calls the pure `resolve_plan`), so it transitively covers the dashboard "today", `track.resolve_plan_progress` ([track.py:81](../../scripts/plan/track.py) [VERIFIED]), the ADR-0037 tailoring emit-gate ([tailoring.py:187](../../scripts/plan/tailoring.py) [VERIFIED]), and the loop's `_prior_standing_plan` ([plan_loop.py:240-245](../../scripts/serve/plan_loop.py) [VERIFIED]); the debounce `_last_regen_date` ALSO calls `resolve_plan` ([plan_loop.py:373-385](../../scripts/serve/plan_loop.py) [VERIFIED]) but is the ONE call site that does NOT pre-filter (§5 / Negative-3), so "transitively covered" means the standing-plan call sites that pre-filter, NOT every `resolve_plan` caller; AND
   - (b) `horizons.window_block` — the ADR-0038 range-query, a DIRECT `store.read(f"plan::{domain}")` max-timepoint scan that NEVER calls `resolve_plan` ([horizons.py:132-162](../../scripts/plan/horizons.py) [VERIFIED]). A held (unconfirmed) re-gen dated today is the max-timepoint reading in both the 7- and 30-day windows, so teaching `resolve_plan` alone leaves the held plan surfacing as the standing week/month block — `window_block` MUST honor the pointer independently (drop held → the next-latest CONFIRMED in-window block).

   The debounce `_last_regen_date` is the ONE `plan::` reader deliberately EXCLUDED from the skip — it must COUNT the held re-gen, not skip it (Negative-3 / §5). A reading with NO pointer entry (every historical plan, every manual plan, every sub-threshold re-gen — no marker is ever written for them) resolves EXACTLY as today, so the change is additive and backward-compatible by construction. **The safety-equivalence-to-a-pre-record-gate claim (Rationale) holds ONLY because this COMPLETE direct-reader set — `{resolve_plan/read_plan, horizons.window_block}` plus their transitive consumers — honors the pointer:** a pre-record gate never records, so no reader can see the held plan; the resolver-hold matches that guarantee only when every direct `plan::` standing-plan reader skips the unconfirmed reading.

4. **The hold GATES the tailoring seam (HARD constraint).** `_post_promote_tailoring` is gated to run ONLY for confirmed-standing promoted domains; a held (unconfirmed) domain is EXCLUDED from the tailoring call until it is confirmed ([plan_loop.py:207-213,295-330](../../scripts/serve/plan_loop.py) [VERIFIED]). This is first-class, not incidental: without it, a held plan that the resolver correctly refuses to stand would STILL be raw-tailored and egressed to the maintained artifact — re-introducing the silent-swap-THEN-render leak on the raw-egress surface. A held domain produces ZERO tailored artifact until confirm.

5. **Fail-closed; confirm is an explicit operator act.** The ONLY transition that promotes a held reading is an explicit operator CONFIRM. `pending`, `declined`, and (for a marked reading) an absent decision all resolve to `NO_PLAN_TODAY` for the held domain (today carries no confirmed plan; the prior confirmed plan stays in append-only history, not re-surfaced as today) — never the unconfirmed swap left standing. This is still fail-closed: no unconfirmed plan ever stands, and no held domain is tailored/egressed (§4). The confirm act follows the `land_confirmed` explicit-operator-confirm precedent (the operator-confirm IS the gate; the act adds no second sink, [confirm.py:35-93](../../scripts/serve/confirm.py) [VERIFIED]): it flips the `(domain, plan_date)` pointer to `confirmed` — after which the standing-plan read no longer skips the reading, so it resolves at `plan_date` — and fires the DEFERRED `_post_promote_tailoring` for the now-confirmed domains exactly once. (Confirm is meaningful only within the held plan's standing window: under date-equality a confirm arriving after `plan_date` has passed does not make the past-dated plan "today" — the confirm-window semantics are pinned at spec, OQ-7.) To fail closed across the confirm latency, the pending marker is written before the held reading is exposed to any standing-plan read (the loop is a single synchronous headless process, so exposure occurs only after `regenerate` returns; the marker is written inside that call — see Validation and OQ-4).
   **Debounce COUNTS the held re-gen (it does NOT skip).** The `_last_regen_date` debounce marker ([plan_loop.py:373-385](../../scripts/serve/plan_loop.py) [VERIFIED]) is NOT a standing-plan surface — it answers "did a re-gen happen (so the min-interval gate should hold)," a question ORTHOGONAL to "is this the standing plan." It MUST treat the held re-gen as a re-gen that occurred (advancing the debounce date), so it is the ONE `plan::` reader that does NOT honor the confirmation-pointer skip. If the debounce instead skipped the held reading, its date would revert to the prior confirmed date and the next cadence tick (≥ `MIN_REGEN_INTERVAL_DAYS`, on a sustained signal) would RE-FIRE a second large re-gen while the first is still pending — each a metered ADR-0027 de-id-IN call — a pending-over-pending re-gen storm. **Pending-over-pending:** because the debounce counts the held re-gen, a further large re-gen for a still-pending domain is naturally SUPPRESSED for the min-interval; whether a re-gen that DOES clear the interval over a still-pending pointer supersedes the prior pending pointer or is itself held-and-suppressed is pinned at spec (OQ-6), fail-closed default preserved (no unconfirmed plan stands either way).

6. **Threshold reused; revisit as a FRACTION beyond 4 domains.** The hold fires on the existing pinned `LARGE_CHANGE_THRESHOLD_DOMAINS = 3` over the closed 4-domain universe — a majority-of-domains swap ([plan_loop.py:48-50](../../scripts/serve/plan_loop.py) [VERIFIED]). If `PLAN_DOMAINS` grows beyond 4 (a fifth plan/tracked domain is an ADR-0010 review trigger), the absolute `3` becomes a minority and MUST be revisited as a fraction (OQ-2).

7. **Synthetic/mock only; activation operator-gated.** This is built + mock/fixture-tested at 0 live spend. The loop's live activation stays operator-gated (ADR-0039's disabled-by-default scheduled runner); ADR-0040 changes what the loop does when it fires, not whether it fires.

### Rationale

The two hold mechanisms were weighed on the three forces the Context makes load-bearing — **frozen-spine preservation**, **fail-closed safety-equivalence**, and **buildability under EXTEND-NOT-REBUILD** — against a pre-record hold (Alternative B) and keeping the advisory-only (Alternative C).

The decisive observation is that the safety property — "an unconfirmed large re-gen is neither the standing plan nor tailored/egressed" — is enforced at the STANDING-PLAN RESOLVER and the TAILORING SEAM, not at the record write. The record write only puts de-identified plan content into the append-only store (ADR-0021/0001 keep the persisted store de-identified); a recorded-yet-not-standing reading leaks nothing, because the only raw-egress surface is tailoring, which clause §4 gates. Therefore holding at the resolver + tailoring seam (A, chosen) is safety-EQUIVALENT to holding at the record write (Alternative B, the pre-record gate) — both yield "not standing + not tailored until confirm" — while the chosen path leaves `record_plan` byte-frozen.

On **frozen-spine preservation** the chosen path wins outright: it edits READ-side resolution (`resolve_plan`/`_prior_standing_plan`, additive + pointer-gated) and the loop's post-promote seam (`plan_loop.py`, ADR-0036-era code, never frozen), while `record_plan` / `store.append` / the inner engine stay byte-identical ([plan_schema.py:371-396](../../scripts/store/plan_schema.py) [VERIFIED]). The pre-record gate instead makes the frozen record write CONDITIONAL — the exact one-way door held byte-frozen across the project's EXTEND-NOT-REBUILD era (~15 sessions — the posture ADR-0032 restates, [ADR-0032:26,43](ADR-0032-dna-aware-planning.md) [VERIFIED]) — and buys no safety the resolver hold does not already provide. On **buildability**, the pre-record gate is strictly MORE surface, not less: a held plan withheld from the record must be parked somewhere durable across a possibly-multi-day confirm latency — either a NEW pending-plan stream (which relaxes ADR-0038 MORE than the chosen bounded pointer, since it parks a full plan value, not a pointer) or in process memory (lost on restart, not durable, not auditable). So the pre-record gate incurs BOTH frozen-spine damage AND equal-or-worse new state. The chosen path's cost is the single bounded pointer stream (Consequences-Negative-1) — the minimal new state that answers a fact no existing stream carries.

The cost the decision accepts is that the ADR-0038 no-new-store-stream rule is relaxed for a bounded pointer, and that the store now holds a class of readings that are recorded-yet-not-standing which every standing-plan read must correctly skip (Consequences-Negative). Keeping the advisory-only (Alternative C) is rejected because it does not satisfy the safety property at all — it is the silent-swap-then-render leak this ADR exists to close.

### Consequences

**Positive:**
- The ADR-0032 record spine stays byte-unchanged: `record_plan` / `store.append` / the inner engine are untouched, so the EXTEND-NOT-REBUILD-era frozen-record invariant (~15 sessions) and its downstream byte-for-byte guarantees hold. The hold is additive read-side + loop-layer code.
- The safety property is met and is fail-closed: an unconfirmed `≥ threshold` re-gen is neither resolved as standing (skip across the complete direct-reader set, §3) nor tailored/egressed (tailoring gate, §4); a decline or no-action leaves the held re-gen not standing — the held domain resolves `NO_PLAN_TODAY` until confirm (§5), never the unconfirmed swap left standing. Only an explicit operator confirm promotes.
- The audit trail is preserved and richer than a pre-record hold: the held plan IS recorded (in its normal `plan::<domain>` home) with the T4 `rationale` already composed ([plan_loop.py:187-188](../../scripts/serve/plan_loop.py) [VERIFIED]), so "what changed and why" is inspectable during the hold — the operator confirms against a real, stored, de-identified plan, not a transient.

**Negative:**
- **A bounded new store stream relaxes ADR-0038's zero-new-stream rule — a one-way door on the store schema.** ADR-0038 and ADR-0036 OQ-5 established the loop adds no new stored stream; this decision amends that to admit a `(domain, plan_date) → decision` pointer. It is bounded (a pointer, not a duplicate content/progress/cadence surface, so NOT the ownership-matrix violation ADR-0038 rejected), but it is nonetheless a new persisted schema the store must carry, gate through the wiki/PII disciplines where applicable, and never let grow into a second plan surface. Once shipped, removing it is itself a migration.
- **The store now holds recorded-yet-not-standing readings that every standing-plan read must skip correctly.** Before this decision, "latest recorded == standing." After it, a held reading is recorded but not standing, so EVERY DIRECT `plan::<domain>` standing-plan reader must honor the pointer or it will surface an unconfirmed plan as standing: the shared `resolve_plan`/`read_plan` read (covering the dashboard "today", `track.resolve_plan_progress`, and the ADR-0037 tailoring emit-gate transitively) AND the ADR-0038 horizon range-query `horizons.window_block` (a DIRECT `store.read(f"plan::{domain}")` max-timepoint scan that never calls `resolve_plan`, so it is NOT auto-covered — [horizons.py:132-162](../../scripts/plan/horizons.py) [VERIFIED]) AND the loop's `_prior_standing_plan`. A consumer that reads `plan::<domain>` without consulting the pointer is a latent leak of the exact behavior this ADR forbids — the correctness burden is now spread across every standing-plan reader, an invariant to enforce in review rather than a single stored gate. **The debounce `_last_regen_date` is the explicit EXCEPTION (Negative-3): it must NOT skip.**
- **The debounce must COUNT the held re-gen (Negative-3 — the one reader that does NOT skip).** `_last_regen_date` reads `plan::` history to answer "did a re-gen happen (min-interval gate)," NOT "is this the standing plan." It MUST advance on a held re-gen or the debounce reverts and the next cadence tick re-fires a second large re-gen while the first is still pending — a pending-over-pending re-gen storm, each firing a metered ADR-0027 de-id-IN call and accumulating pointers. The debounce (a re-gen DID happen → do not re-fire) and the standing-plan resolver (the held plan is NOT standing) are OPPOSITE for this reader; conflating them is the failure. The min-interval naturally suppresses pending-over-pending within the interval; the supersede-vs-hold behavior once the interval clears is pinned at OQ-6.
- **A held domain's TAILORED presentation VANISHES from the maintained artifact during the hold (AR-004).** Tailored sections are re-rendered fresh from the non-held promoted set on every re-emit (the `tailored_sections` mapping the tailoring pass builds, [tailoring.py:145-209](../../scripts/plan/tailoring.py); [maintained.py:228-268](../../scripts/generate/maintained.py) [VERIFIED]); the maintained artifact's `_preserve_prior_content` preserves only the annotations/tracking-history container, NOT tailored sections ([maintained.py:180-207](../../scripts/generate/maintained.py) [VERIFIED]). A held domain is excluded from the tailoring call (§4) and its tailored section is neither re-rendered (held) nor preserved — so the operator's personalized view shows NO current tailored plan for that domain until confirm (combined with §3's `NO_PLAN_TODAY`, the plan-vs-actual view reads blank for the held domain). The prior confirmed plan remains in append-only history but is NOT re-tailored/re-rendered. This is acceptable fail-closed behavior (nothing unconfirmed is personalized), but it is a real operator-visible effect — "no tailored plan shown for the held domain," not "the prior tailored plan persists" — and must be surfaced in the confirm UX (OQ-5).
- A transient window exists between the frozen promote (inside `run_orchestrated`) and the pointer write (after it returns, in `regenerate`); it is bounded to a single synchronous headless call with no intervening read (the loop is not concurrent), but it is real and must be closed by writing the marker before `regenerate` returns (OQ-4).

**Neutral:**
- The T4 advisory becomes the confirm PROMPT surface: `confirm.confirm_large_change`'s changed-domains + rationale receipt ([confirm.py:96-125](../../scripts/serve/confirm.py) [VERIFIED]) is repurposed from a fire-and-forget notice into the payload the operator confirms against — the same shape, a different disposition. No second advisory path is added.
- The loop's debounce, cadence, and de-id boundary are unchanged; ADR-0040 acts only on the promoted-then-large branch, after the debounce already decided a re-gen fires.

### Alternatives Considered

#### Alternative A: Bounded confirmation-pointer the resolver honors (Chosen)
Record unchanged (frozen spine preserved); a bounded `(domain, plan_date) → decision` pointer marks a `≥ threshold` re-gen pending; EVERY direct standing-plan reader (`resolve_plan`/`read_plan` AND the horizon `window_block` direct scan) skips an unconfirmed reading so the held domain resolves `NO_PLAN_TODAY` (the held plan does not stand; NOT a walk-back to the prior-dated plan), while the debounce counts it; `_post_promote_tailoring` is gated to confirmed-standing domains; an explicit operator confirm flips the pointer and fires the deferred tailoring.
- **Supporting evidence:** The only option that meets the safety property (not standing + not tailored, fail-closed to prior) while leaving `record_plan` / the inner engine byte-frozen ([plan_schema.py:371-396](../../scripts/store/plan_schema.py) [VERIFIED]) — because the safety boundary lives at the resolver + tailoring seam, not the record write. Backward-compatible by construction (no pointer entry → resolves as today). Reuses the T4 rationale/advisory and the `land_confirmed` explicit-confirm precedent ([confirm.py:35-93,96-125](../../scripts/serve/confirm.py) [VERIFIED]).
- **Trade-offs:** One bounded new store stream relaxing ADR-0038 (Negative-1) and a recorded-yet-not-standing reading class every resolver must skip (Negative-2). Accepted because the frozen-spine preservation and safety-equivalence dominate, and the pointer is minimal, bounded state.
- **When this becomes the right choice:** When a large automated re-gen must be held for operator confirmation, the ADR-0032 record spine must stay byte-frozen, and the confirmation fact has no existing stored home to derive from.

#### Alternative B: Pre-record hold in the ADR-0032-frozen record spine
Hold the promote itself so a `≥ threshold` re-gen is NOT recorded until the operator confirms; on confirm, record it as standing.
- **Supporting evidence:** The most literal reading of "hold-until-confirm" — if it is never recorded, it can never resolve as standing, and the resolver needs no change. Superficially the simplest mental model.
- **Trade-offs:** REJECTED. (1) It EDITS the byte-frozen ADR-0032 record path (`record_plan` / the promote inside the inner engine) to become conditional — the one-way door held byte-frozen across the project's EXTEND-NOT-REBUILD era (~15 sessions — the posture ADR-0032 restates, [ADR-0032:26,43](ADR-0032-dna-aware-planning.md) [VERIFIED]) — for ZERO safety gain over the chosen resolver hold (both yield not-standing + not-tailored, because the safety boundary is the resolver + tailoring seam, not the write). (2) It does NOT even avoid new state: a plan withheld from the record must be parked durably across the confirm latency — a new pending-plan stream (relaxes ADR-0038 MORE than the chosen bounded pointer: it parks a full plan, not a pointer) or in-memory (lost on restart, not auditable). So it incurs both frozen-spine damage AND equal-or-worse new state. (3) It loses the audit property the chosen path keeps — the operator would confirm against a transient, not a stored, inspectable plan.
- **When this becomes the right choice:** Only if the record path were NOT frozen and there were no bounded resolver-side hold available — neither holds here.

#### Alternative C: Keep the T4 advisory-only; no hold
Leave the current behavior: the large swap records + stands + is tailored, and `confirm.confirm_large_change` fires a visibility NOTICE after the fact ([confirm.py:96-107](../../scripts/serve/confirm.py) [VERIFIED]).
- **Supporting evidence:** Zero new code, zero new store stream, zero frozen-spine risk; the operator is still NOTIFIED that a majority-of-domains swap landed, and for a loop where every automated re-gen is trustworthy an advisory is arguably enough. (This is the honest dissent: if large re-gens were rare, additive, and always benign, the notice-after-the-fact would suffice and the hold would be over-engineering.)
- **Trade-offs:** REJECTED. It does not satisfy the safety property AT ALL — the swap becomes the followed plan AND is raw-tailored/egressed to the maintained artifact ([plan_loop.py:207-213](../../scripts/serve/plan_loop.py) [VERIFIED]) BEFORE the operator confirms. That is the silent-swap-then-render leak, and it is exactly the hold-half ADR-0036 OQ-4 left open ([ADR-0036, OQ-4](ADR-0036-automated-plan-evolution-loop.md) [VERIFIED]). For a health plan, a majority-of-domains change driven by automated data the operator did not initiate is precisely where silent standing is unacceptable.
- **When this becomes the right choice:** Only if a future decision scopes the loop to purely additive, individually-trustworthy re-gens where no swap is materially large — not the current design.

### Validation Approach

**Confirmation criteria:**
- **Held re-gen does NOT stand (executable):** seed a store so a loop re-gen replaces `≥ LARGE_CHANGE_THRESHOLD_DOMAINS` standing plans; fire `regenerate`; assert (a) the new plan IS recorded in `plan::<domain>` (the frozen write ran) AND (b) the standing-plan resolution returns **`NO_PLAN_TODAY` (state `NO_PLAN_TODAY`, plan `None`)** for each held domain — NOT the new held plan, and NOT a walk-back to the prior-dated confirmed plan ([plan_schema.py:462-498](../../scripts/store/plan_schema.py) [VERIFIED]). Threshold: recorded == True AND resolve == `NO_PLAN_TODAY` (plan is None) for every held domain, with the reported `plan_date` NOT equal to the held date (the held reading is excluded from `max(timepoint)`). If resolve == the new plan pre-confirm, the resolver skip is not wired — halt; if resolve walks back to the prior-dated plan, the date-equality shape was altered (CONTRACTS-TRACK-1 / the ADR-0037 emit-gate regressed) — halt.
- **Held re-gen does NOT surface in the horizon window block (executable, the AR-002 probe — LOAD-BEARING):** thread the same held large re-gen and call `horizons.window_block` for BOTH the 7-day (week) and 30-day (month) windows; assert each returns the prior CONFIRMED in-window block, NOT the held (max-timepoint) reading ([horizons.py:132-162](../../scripts/plan/horizons.py) [VERIFIED]). Threshold: 0 held-plan surfacing in either window block. If `window_block` returns the held plan, the direct-`plan::`-scan skip is unwired and the safety-equivalence claim is broken on the horizon surface — halt. (This is distinct from the `resolve_plan` probe: `window_block` never calls `resolve_plan`, so a `resolve_plan`-only skip passes the first probe while failing this one.)
- **Held re-gen is NOT tailored (executable, the HARD-AC probe):** thread a `tailor_client` and fire the same large re-gen; assert `_post_promote_tailoring` emits ZERO tailored artifact for the held domains (the maintained artifact carries no tailored section for them) ([plan_loop.py:207-213,295-330](../../scripts/serve/plan_loop.py) [VERIFIED]). Threshold: 0 tailored output for any held domain before confirm. If a held domain is tailored, the silent-swap-then-render leak is open — halt.
- **Confirm promotes + tailors once (executable):** confirm one held `(domain, plan_date)`; assert (a) the resolver now stands the confirmed reading, and (b) the deferred `_post_promote_tailoring` fires exactly once for that domain (idempotent per `(plan, date)`, ADR-0037 §1). Threshold: standing == confirmed plan AND tailoring-fire-count == 1. A second confirm of the same `(domain, date)` produces 0 additional tailored artifact.
- **Record WRITE spine byte-frozen; only the read-path skip touches `plan_schema.py` (grep + diff, AR-007):** assert the diff for this build touches NEITHER `scripts/store/plan_schema.py::record_plan` / `store.append` / `keying.py` NOR the inner engine (`scripts/plan/{orchestrate,pipeline,assemble,generate_plan,adjudicate,adjust,track}.py`) — the exact ADR-0032 Validation-named freeze surface — and that the ONLY `scripts/store/plan_schema.py` edit is the read-side resolution skip (no write-path line touched), plus `scripts/plan/horizons.py::window_block` + `scripts/serve/plan_loop.py` + the confirm/pointer surface. Threshold: 0 edits to the ADR-0032-frozen record WRITE path + engine; `plan_schema.py` edits confined to the read-side resolution.

**Falsification criteria:**
- **Fail-closed on decline (deterministic):** hold a large re-gen, then DECLINE it (or leave it `pending`); assert the held domain resolves `NO_PLAN_TODAY` (plan `None`) indefinitely — the held re-gen never stands — and 0 tailored artifact is emitted for the declined domains, and the unconfirmed reading STAYS in the append-only history (auditable, never standing). Threshold: declined/pending → resolve == `NO_PLAN_TODAY`, tailored == 0. If a declined or unactioned large re-gen ever stands (resolves to the held plan), the fail-closed default is broken — halt.
- **Debounce counts the held re-gen — no pending-over-pending storm (deterministic, AR-003):** hold a large re-gen, then advance the clock past `MIN_REGEN_INTERVAL_DAYS` with a SUSTAINED signal still present; assert `_last_regen_date` reflects the HELD re-gen's date (the debounce advanced) and that exactly the intended number of re-gens fires — NOT one-large-re-gen-per-week-forever. Threshold: debounce date == held re-gen date; re-gen count over N intervals == the pinned expectation (not N). If the debounce reverted to the prior confirmed date and a second large re-gen fired within the interval, `_last_regen_date` wrongly honored the skip (Negative-3) — halt.
- **Late confirm has defined semantics (deterministic, AR-008):** hold a large re-gen dated `plan_date`; advance the clock so today > `plan_date`; confirm the `(domain, plan_date)` pointer; assert the spec-pinned confirm-window behavior (OQ-7) holds — either the confirm re-stamps the plan to the confirm date so it becomes today's plan, OR a confirm past the staleness bound is refused and the domain re-enters the normal re-gen path — and that the deferred `_post_promote_tailoring` keys on the pinned date (not a stale past date). Threshold: a late confirm never silently renders a past-dated tailored section as "today." (Behavior fixed at spec; the probe pins whichever OQ-7 resolves to.)
- **Backward-compat (paired control):** a SUB-threshold re-gen (`change_magnitude < LARGE_CHANGE_THRESHOLD_DOMAINS`) and every pre-existing/manual plan (no pointer entry) resolve as standing IMMEDIATELY with NO confirm required, and ARE tailored on promote as today. Threshold: no-pointer readings → standing + tailored unchanged from pre-ADR behavior; a paired large re-gen → held. If a no-pointer reading is skipped, the resolver over-holds — halt.
- **Transient-window / marker-before-exposure (deterministic):** simulate a process interruption between the frozen promote and the pointer write; assert the resolver fails CLOSED — a `≥ threshold` reading with no resolved confirm decision resolves to `NO_PLAN_TODAY`, never as standing. Threshold: an interrupted large re-gen never stands. If the pointer write can trail the reading's exposure to a standing-plan read such that it stands unmarked, re-order the marker write before `regenerate` returns — halt.
- **Bounded pointer, not a content stream (grep):** assert the confirmation-pointer persists ONLY `(domain, plan_date, decision)` — no plan content, progress, or cadence — so it is not a `plan-arc::`-class duplicate surface (the ADR-0038 rejection). Threshold: the pointer stream carries 0 plan-content / progress / cadence fields.

**Review triggers:**
- A new standing-plan consumer is added (a report, an export, a new dashboard read) — verify it consults the confirmation-pointer, or it will surface a held plan as standing (Negative-2).
- `PLAN_DOMAINS` gains a fifth domain (an ADR-0010 review trigger) — the absolute `LARGE_CHANGE_THRESHOLD_DOMAINS = 3` is now a minority; re-decide it as a fraction (OQ-2) before the loop runs against the wider domain set.
- The ADR-0037 tailoring seam's call shape or hook point changes — re-verify the held-domain exclusion (§4) still gates the seam.
- ADR-0038's store-schema rule is revisited — re-confirm the bounded-pointer relaxation is still the narrowest admissible new state (or migrate to the D2-extras realization, OQ-1).
