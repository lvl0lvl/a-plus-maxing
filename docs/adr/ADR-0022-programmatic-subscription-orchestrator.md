## ADR-0022: Adopt a Programmatic Subscription Orchestrator for Plan Generation (Runtime Supersession of S68)

> **Y-Statement:** In the context of the operator-confirmed S91 full-target plan engine, whose inner reconciliation+adjudication pipeline is fully built and wired (`generate_plans` / `run_generation` / `adjudicate` / the already-wired `ModelClient` author seam) but is driven today only by the S68 interactive Claude-Code dispatch session (`/generate-plan`, "agent-in-the-loop by design, not a scripted pipeline"), facing the tension that the S91 target wraps every plan in a post-assembly quality judge plus a multi-agent whole-plan safety review plus a bounded revise loop — a generate→judge→safety-review→revise cycle a human-driven interactive session cannot run repeatedly or unattended — we decided to adopt a programmatic subscription orchestrator that runs the plan-domain specialists as agents (mirroring the autonomous build pipeline), superseding the design doc's §"Runtime model" while WRAPPING the existing inner engine unchanged and riding ADR-0015's swap seam so all-API / local-model / combo execution is not foreclosed, to achieve repeatable unattended end-to-end generation, accepting that the mandatory human-in-the-loop checkpoint S68 valued on every safety-relevant dispatch is lost — making the multi-agent safety-review tier load-bearing — and that the orchestrator must never bypass the inner safety gate.

### Context

The plan engine's inner pipeline is built and wired. `orchestrate.generate_plans(authors, store_read, root, *, plan_date, gates, reauthor, adjudicator)` runs the reconciled multi-domain pass — compute every domain's candidate, reconcile across domains, adjudicate any held finding, record the survivors — and `run_generation` adds `collate_doctor_visit_queue` ([orchestrate.py:482](../../scripts/plan/orchestrate.py), [pipeline.py:28-65](../../scripts/plan/pipeline.py) [VERIFIED]). The plan-author envelope is authored through the one model client: `compute_plan(domain, …, client=None)` calls `_author_callable(client)(domain, summary)`, fail-closed on a `ModelCallError` to the honest no-plan state (`reason == AUTHOR_CALL_FAILED`) ([generate_plan.py:90-108, 303, 355-371](../../scripts/plan/generate_plan.py) [VERIFIED]). That `ModelClient.author` seam is the ADR-0015 swap point — an injectable backend, swappable without a caller edit ([client.py:32-74, 102-130](../../scripts/model/client.py); [ADR-0015, Decision](ADR-0015-swappable-no-train-model-client.md) [VERIFIED]). What is NOT yet decided is the runtime that DRIVES this engine.

Two forces pull against each other. The S68 runtime decision fixed it as an interactive session: "Plan generation runs as an interactive Claude-Code / agent-dispatch session, not a standalone API client … A standalone `scripts/` API client is a later North-Star option the seam must not foreclose," and the orchestrator-vs-liaison split (decision 4) keeps the step-4 reconciliation as the orchestrator's job ([plan-generation-pipeline-v1.md, §Runtime model L18-20, §The five decisions item 4 L27](../../vault/design/plan-generation-pipeline-v1.md) [VERIFIED]). The `/generate-plan` skill reaffirms this: under runtime A the orchestrator (a human-driven session) inlines each specialist's full profile, captures its output, and feeds the seam, with "A non-interactive auto-dispatch CLI … the skill is agent-in-the-loop by design, not a scripted pipeline" listed as deliberately NOT present ([generate-plan/SKILL.md L17-21, L137-142](../../.claude/skills/generate-plan/SKILL.md) [VERIFIED]). That interactivity is a real merit — a human is in the loop on every safety-relevant dispatch (each specialist, each `adjudicator` re-dispatch).

Against that merit, the S91 target adds three layers an interactive session does not scale to running repeatedly: a post-assembly plan-quality judge, a multi-agent whole-plan safety review, and a post-review revise loop (the review/output tiers, authored separately) ([.pipeline/engine/discovery.md, §"What the operator's full target ADDS" decisions 3-5 L68-72](.pipeline/engine/discovery.md) [VERIFIED]). A generate→judge→safety-review→revise cycle run for every plan and re-run as wearables/labs arrive is an autonomous control loop, not a thing a human walks through by hand each time. The operator now wants the autonomous-orchestrator model — "a subscription orchestrator … like the autonomous build pipeline" ([.pipeline/engine/discovery.md, §decision 2 L66-67, §"Genuine viable approaches" L174-179](.pipeline/engine/discovery.md) [VERIFIED]). Because this changes the engine's runtime/control surface rather than implementing the settled inner engine, and reverses a recorded operator decision, it is a decision, not a code change.

### Decision

Adopt a programmatic subscription orchestrator that runs the plan-domain specialists as agents — driving the generate→judge→safety-review→revise loop unattended, mirroring the autonomous build pipeline's orchestrator-runs-specialists pattern — as the plan engine's V1 runtime. This supersedes the S68 §"Runtime model" interactive-session decision in `plan-generation-pipeline-v1.md`. The orchestrator WRAPS the existing inner engine unchanged (`orchestrate.generate_plans` / `pipeline.run_generation` / `adjudicate` / `assemble`), runs through the already-wired `ModelClient` seam, and attaches the new quality-judge and whole-plan safety-review tiers (authored as the review-tier decisions) without re-authoring the reconciler. The runtime rides ADR-0015's swap seam: it picks subscription execution for V1 without foreclosing all-API, local-model, or combo substitution.

### Rationale

The runtime was evaluated against the S68 interactive session (status quo) and a standalone no-train API client across five criteria the target makes load-bearing: **autonomy/repeatability**, **ability to run judge+safety-review+revise unattended**, **reproducibility**, **PII-surface**, and **cost**.

On **autonomy/repeatability** and **unattended review tiers**, only a programmatic orchestrator delivers them. The interactive session puts a human in the loop on every dispatch ([generate-plan/SKILL.md L17-21](../../.claude/skills/generate-plan/SKILL.md) [VERIFIED]) — workable for a single hand-walked plan but not for a generate→judge→safety-review→revise cycle re-run as data arrives. The build pipeline already demonstrates the orchestrator-runs-specialists pattern at scale (execute-plan dispatches role agents through wave gates autonomously); the plan engine mirrors it. On **reproducibility**, a programmatic driver runs the same sequence each time, where an interactive session's exact dispatch order and prompts vary per operator run. On **PII-surface**, the choice is net-neutral: both the interactive session and the orchestrator dispatch over the SAME de-identified summary the de-id-IN boundary emits (ADR-0020) — the orchestrator changes WHO drives the dispatches, not WHAT crosses the boundary, so the crown-jewel boundary is unchanged by this decision (it is ADR-0020/0021's concern). On **cost**, subscription execution carries no marginal per-call API charge for the agent dispatches, where a standalone no-train API client would meter every specialist and judge/review dispatch per-token — a recurring cost the per-plan-plus-revise loop multiplies; this is the concrete reason to pick subscription-now over API-now even though the seam keeps API reachable.

Long-term, the orchestrator does NOT lock the engine to subscription: it dispatches through the ADR-0015 `ModelClient` seam ([client.py:32-74](../../scripts/model/client.py) [VERIFIED]), so the same runtime can later run all-API or against a local model (ADR-0001's North-Star Alternative C) or a combo by swapping the backend — the substitution seam ADR-0015 fixed for the client, extended here to the engine runtime so it does not ossify.

### Consequences

**Positive:**
- The engine can run the full generate→judge→safety-review→revise loop unattended and repeatably, where the interactive session ran it only by a human walking each dispatch by hand ([generate-plan/SKILL.md L17-21, L137-142](../../.claude/skills/generate-plan/SKILL.md) [VERIFIED]) — the capability the S91 review/output tiers require.
- Zero engine rebuild: the orchestrator REUSES the built inner pipeline verbatim. `run_generation` already forwards the `reauthor`/`adjudicator` hooks unchanged to `generate_plans` and records nothing the reconciler + safety gates did not pass ([pipeline.py:20-23, 60-65](../../scripts/plan/pipeline.py) [VERIFIED]); the orchestrator supplies those hooks programmatically instead of a human supplying them interactively.
- The North-Star path stays reachable: dispatching through the ADR-0015 `ModelClient` seam means all-API / local-model / combo is a backend swap, not a runtime rewrite ([client.py:42-43](../../scripts/model/client.py) [VERIFIED]; [ADR-0015, Decision](ADR-0015-swappable-no-train-model-client.md) [VERIFIED]).

**Negative:**
- The mandatory human-in-the-loop checkpoint S68 valued is lost. Under the interactive session a human reviewed every safety-relevant dispatch (each specialist author, each `adjudicator` medical-liaison re-dispatch) before the orchestrator proceeded ([generate-plan/SKILL.md L70-110](../../.claude/skills/generate-plan/SKILL.md) [VERIFIED]); the orchestrator now drives those safety-relevant dispatches autonomously. This shifts the safety burden ONTO the multi-agent whole-plan safety-review tier (the review-tier decision) — that tier becomes load-bearing, not optional: it is now the standing safety lens a human formerly provided per-dispatch, a 1+ year structural dependency.
- The orchestrator now drives `adjudicator` (medical-liaison) dispatches with no human gate between the held finding and the re-dispatch. The inner gate's fail-closed default still holds — a held finding with no content-valid override records nothing ([orchestrate.py:36-39](../../scripts/plan/orchestrate.py) [VERIFIED]) — but the correctness of the autonomous adjudicator dispatch (does it dispatch the right liaison over the right finding) is now the orchestrator's responsibility, where a human formerly supplied it.
- Subscription-runtime coupling for V1: picking subscription execution couples the V1 runtime to the subscription session model. The ADR-0015 seam keeps the backend swappable, but the orchestrator's DRIVE layer (how it spawns agents) is built against subscription-session semantics first; an all-API or local-model cutover requires re-validating that drive layer against the new execution model, not only swapping the backend — a deferred but real migration cost the seam narrows but does not erase.

**Neutral:**
- The orchestrator's role mirrors the build pipeline's execute-plan orchestrator (runs specialists, gates wave/loop transitions) — a second instance of the same orchestration pattern in the project, not a novel control shape.
- `/generate-plan` (the interactive skill) is not deleted; it becomes the hand-driven entry the orchestrator's programmatic drive supersedes for the autonomous loop, retained for single-plan manual runs.

### Alternatives Considered

#### Alternative A: Programmatic subscription orchestrator (Chosen)
A programmatic orchestrator runs the plan-domain specialists as agents and drives the generate→judge→safety-review→revise loop unattended, mirroring the autonomous build pipeline, wrapping the built inner engine.
- **Supporting evidence:** Only this option runs the S91 review/output tiers (judge + whole-plan safety review + revise) repeatably and unattended ([.pipeline/engine/discovery.md, §decisions 3-5 L68-72](.pipeline/engine/discovery.md) [VERIFIED]); it reuses `generate_plans`/`run_generation`/`adjudicate` verbatim ([pipeline.py:20-23](../../scripts/plan/pipeline.py) [VERIFIED]) and rides the ADR-0015 swap seam so the North-Star path is preserved ([client.py:42-43](../../scripts/model/client.py) [VERIFIED]). Subscription execution carries no marginal per-call API charge for agent dispatches.
- **Trade-offs:** Loses the per-dispatch human checkpoint (Negative-1) — the whole-plan safety-review tier must carry that burden — and couples the V1 drive layer to subscription-session semantics (Negative-3).
- **When this becomes the right choice:** It is, for V1, when the engine must run the judge+safety-review+revise loop repeatably and re-run on new data without a human walking each dispatch.

#### Alternative B: Keep the S68 interactive Claude-Code dispatch session (status quo)
Retain the `/generate-plan` interactive session — a human orchestrator inlines each specialist profile, captures the output, and feeds the seam, with a human reviewing every safety-relevant dispatch ([generate-plan/SKILL.md L70-110, L137-142](../../.claude/skills/generate-plan/SKILL.md) [VERIFIED]).
- **Supporting evidence:** Its real merit is the operator-in-the-loop checkpoint on EVERY safety-relevant dispatch — the human sees each specialist's output and each medical-liaison adjudication before the orchestrator proceeds, the strongest safety posture for a health plan. It introduces no standalone API surface (the S68 privacy stance) and is the current, tested, shipped runtime ([plan-generation-pipeline-v1.md, §Runtime model L18-20](../../vault/design/plan-generation-pipeline-v1.md) [VERIFIED]).
- **Trade-offs:** A human-driven session does not scale to running the judge+safety-review+revise loop repeatedly or unattended — each plan, and each re-run as wearables/labs arrive, would require a human to walk every dispatch by hand. The S91 target's autonomous review/output tiers are exactly the thing it cannot run at the needed cadence.
- **When this becomes the right choice:** If the operator decides the per-dispatch human checkpoint must be preserved over autonomy — i.e. no plan should ever be assembled without a human reviewing each safety-relevant dispatch in real time — then the interactive session remains correct and the review-tier automation is rejected.

#### Alternative C: Standalone no-train API client orchestrator
Build the orchestrator as a standalone `scripts/` no-train API client that meters every specialist and judge/review dispatch through the API directly (S68's explicitly-deferred North-Star option).
- **Supporting evidence:** This is the same autonomous, unattended driver as Alternative A and would also run the full loop repeatably; S68 named it the North-Star runtime whose seam must not be foreclosed ([plan-generation-pipeline-v1.md, §Runtime model L20](../../vault/design/plan-generation-pipeline-v1.md) [VERIFIED]). It is the most provider-portable form (no subscription-session coupling).
- **Trade-offs:** It meters every agent dispatch per-token — for a generate→judge→safety-review→revise loop run per plan and re-run on new data, the recurring API cost is the multiplier the subscription model avoids. There is no capability the subscription orchestrator lacks that the API client adds TODAY; the only gain is provider-portability, which the ADR-0015 swap seam already preserves as a later cutover. Building API-now pays the recurring cost before the portability is needed.
- **When this becomes the right choice:** When the subscription model's limits (rate, concurrency, or the loop's dispatch volume) make subscription execution insufficient, OR when the North-Star local-model/combo runtime is adopted — at which point the ADR-0015 seam carries the cutover and the standalone API/local client becomes the runtime ([client.py:42-43](../../scripts/model/client.py) [VERIFIED]).

### Validation Approach

**Confirmation criteria:**
- The orchestrator runs the full generate→judge→safety-review→revise loop unattended over a synthetic PII-free fixture and produces a recorded plan plus the collated doctor-visit queue — verified by invoking the orchestrator end-to-end (no human dispatch in the loop) and asserting `run_generation` returns `results` with ≥1 recorded `plan::<domain>` and `dvq_entries` populated ([pipeline.py:54-65](../../scripts/plan/pipeline.py) [VERIFIED]).
- The orchestrator dispatches over ONLY the de-identified summary (the ADR-0020 boundary output): inspect every specialist dispatch the orchestrator issues during a run and assert each receives the de-identified summary, count of raw-PII fields in any dispatch payload = 0 — the same boundary the interactive session honored ([generate-plan/SKILL.md L59-68](../../.claude/skills/generate-plan/SKILL.md) [VERIFIED]).
- The orchestrator reuses the inner engine unchanged: assert it calls `orchestrate.generate_plans`/`collate_doctor_visit_queue` with no new store stream and no plan recorded outside `record_plan` ([pipeline.py:20-23](../../scripts/plan/pipeline.py) [VERIFIED]).

**Falsification criteria:**
- **Inner-safety-gate-bypass test (the load-bearing threshold):** seed a held safety finding (an additive-AE / Rx-BPMH / conflict hold) and run the autonomous orchestrator with NO content-valid override produced for it. Threshold: **0 plans recorded past an unadjudicated hold** — the held domain must record nothing and reach the honest no-plan state, exactly as the inner gate enforces ([orchestrate.py:36-39, 67-69](../../scripts/plan/orchestrate.py) [VERIFIED]). If ≥1 plan records past an unadjudicated hold (i.e. the autonomous orchestrator bypassed the inner safety gate the human-in-the-loop formerly backstopped), the runtime has broken the safety floor — halt and restore the held-records-nothing default before release.
- If the orchestrator's autonomous `adjudicator` dispatch produces a plan over a held CRITICAL / H1-H2 finding (≥1 such record), INV-CRITICAL-NON-OVERRIDABLE is breached by the autonomous path — halt and re-verify the gate is reused unbypassed.
- If a backend swap (subscription → all-API or local-model, ADR-0015) requires editing the orchestrator's drive layer in more than the backend injection point — i.e. >1 file outside the `ModelClient` seam — the substitution seam has ossified at the engine runtime; re-open the seam before adopting the new backend ([ADR-0015, Falsification](ADR-0015-swappable-no-train-model-client.md) [VERIFIED]).
- Time horizon: run the inner-safety-gate-bypass test and the unbypassed-adjudicator test at the first build of the orchestrator and at every release thereafter, and before the July-2026 physician-visit deliverable ships.

**Review triggers:**
- The Tier-3 review/output ADRs (the plan-quality judge, the whole-plan safety review, the revise loop) reach build — re-verify the orchestrator drives each tier unattended and the held-records-nothing floor still holds through the revise loop.
- A subscription rate/concurrency limit blocks the loop's dispatch volume — re-open Alternative C (standalone API client) against the cost trade-off.
- The North-Star transition to all-API / local-model / combo is initiated — the runtime swaps the backend through the ADR-0015 seam; re-validate the drive layer against the new execution model (the subscription-coupling negative).
