# Adversarial Review — Design Doc Template Proposal

## 1. Summary

**Finding counts by severity:** Critical = 2, Major = 9, Minor = 8, Nitpick = 3 (total 22).

The most consequential defects, ordered by downstream blast radius:

1. **F-001 (Critical, Broken References / Contradictions).** The proposal repeatedly asserts that `AGENT_TEMPLATE.md` has **11 sections** (§1 line 44; §2 line 65; §6 line 258; §9 line 370; §12 line 416). The actual file (`/Users/waltermcgivney/Documents/Projects/skills_library/roles/AGENT_TEMPLATE.md`) has **10 `##`-level sections**. Every section-coverage claim in the proposal is keyed to a wrong count; if the proposal becomes canonical, every Pass-2 design doc inherits the wrong section roll-call. This propagates into 18 downstream artifacts.
2. **F-002 (Critical, Downstream Breakage).** Phase 2 (Rubric Construction) and Phase 4 (Validation Loop) of `/upgrade-agent` have **no upstream design-doc section** named in the proposal's `/upgrade-agent phase` mapping column. Phase 2 builds the agent-specific rubric and Phase 4 runs the fact-check+judge validation loop; both must consume *something* from the design doc, but the proposal's section-by-section phase tags only cite Phases 1, 3, 5, 6, 7, 8 — never 2 or 4. A design doc that does not feed the rubric phase forces `/upgrade-agent` to re-derive scoring criteria per role, which is the exact "re-discover per role" failure mode the proposal claims to prevent (line 44).
3. **F-005 (Major, Edge Cases / Contradictions).** §3 (Pass-1 Deliverable Digest) is REQUIRED for foundation roles and CONDITIONAL for specialist roles. But §4 (Inherited Cross-Role References) is REQUIRED for all roles — including foundation roles. The first foundation role authored (Role 1, architect) has no sibling design docs to reference yet (it is authored first per CONTINUATION_BRIEF §7 ordering). The proposal does not specify what §4 looks like for the FIRST role authored under the template; it cannot reference docs that do not exist. Either §4 must be CONDITIONAL or the "first-role" case needs an explicit clause.
4. **F-009 (Major, Operational Completeness).** "Writer produces" specs use undefined or under-specified verbs in multiple sections (§5 "the rule text in imperative or first-person-experiential voice per Role 2 Finding 4" — no acceptance test for which voice when; §9 "format spec" appears without any worked format example; §11 "recognition cue" with no definition; §14 "test stimulus" with no example). Pass-2 writers can produce content that nominally satisfies the spec but is operationally divergent across the 4 foundation roles.
5. **F-012 (Major, Scope Violations / Contradictions).** §15 (Acceptance Criteria) item (a) and (b) cite "line count ≤200 per `/upgrade-agent` Identity Core constraint" and "token count ≤2,000 per same." These are agent.md acceptance criteria, not design-doc acceptance criteria. §15 is supposed to gate whether the resulting agent.md is fit-for-purpose, but the proposal's `/upgrade-agent phase` tag says §15 feeds Phase 5 + Phase 7, which means the design doc carries acceptance criteria for an artifact it does not itself produce. The owning consumer (`/upgrade-agent` Phase 7 final consistency check, lines 291–301 of `upgrade-agent.md`) already enforces these — duplication risk per CLAUDE.md Cross-Document Ownership Matrix.
